## Branch J2 — mixture control can happen before/during training or after training in parameter space

### New candidate: OptiMer — post-hoc distribution-vector optimization

Primary source: Haiyue Song and Masao Utiyama, `OptiMer: Optimal Distribution Vector Merging Is Better than Data Mixing for Continual Pre-Training`, arXiv:2603.28858v2 (`https://arxiv.org/html/2603.28858v2`). Public official code was released after the preprint at `https://github.com/nict-astrec-att/optimer`; public main observed in this invocation at SHA `582cf63d3dfef8fa6d7e35068afa412288147c5b`.

Mechanism: for each data distribution `D_i`, independently continue-pretrain the same base model and define a distribution vector `tau_i = theta_CPT_i - theta_pt`. Then optimize scalar composition weights post-hoc with TPE/Bayesian optimization:

`theta_merge = theta_pt + alpha_it * tau_it + sum_i alpha_i * tau_i`.

This moves one version of the mixture decision out of the expensive CPT trajectory and into a reusable parameter-space composition problem. It is distinct from Data Mixing Agent: Data Mixing Agent chooses changing data distributions during target CPT; OptiMer first creates independently trained distribution vectors and then chooses how to combine them after CPT.

### Quantitative evidence and exact scope

Experimental setting is Gemma 3 27B. Japanese, Chinese, Math and Code CPT datasets each contain `1B` tokens. OptiMer trains one independent 1B-token CPT model per distribution; uniform DataMix trains one model on the same aggregate `nB` token budget. Search uses 100 TPE trials, 20 random startup trials, 8 GPUs, and objective-matched proxy tasks.

Main table averages:
- Ja + Math: uniform DataMix `67.86`; DataMix retrained with OptiMer-derived ratio `68.70`; OptiMer `69.98`.
- Ja + Code: uniform DataMix `67.23`; derived-ratio DataMix `67.44`; OptiMer `69.68`.
- Ja + Zh + Math: uniform DataMix `63.71`; derived-ratio DataMix `68.66`; OptiMer `70.37`.

The paper therefore reports `2.1–6.7` points over its uniform DataMix baseline across tested combinations. The derived-ratio retraining result is especially useful because it shows the post-hoc weights contain information that transfers back into a conventional data-mixture recipe, while OptiMer still performs best in those tests.

Search cost is sharply lower in the paper's ratio-search comparison: a 100-trial OptiMer search takes `8.6 h`, versus `128.9 h` for one DataMix run; the paper summarizes `15–35x` lower ratio-search cost. It explicitly excludes the underlying CPT training cost because total training tokens are matched: `n` independent 1B-token models versus one `nB`-token DataMix model. Within an OptiMer trial, merge consumes `10.2%` and evaluation `89.8%` of trial time, making evaluator cost the dominant optimization bottleneck.

The same vector pool `{En, Math, Ja, Zh}` is re-optimized in four separate 100-trial searches for different objectives without re-CPT. This provides a real amortization advantage when objective weights change after expensive CPT has already happened.

Distribution-vector geometry is only mechanistic support, not a universal theorem: in the tested models, CPT-vs-IT cosine similarity is about `0.03` and CPT-pair similarity `0.29–0.31`; the paper links this low overlap to feasible linear composition. It also extends the search range to `[-1,1]` and reports gains for Japanese/Chinese objectives with negative weights, often subtracting the English vector. Treat this as tested evidence that parameter-space subtraction can remove interference in these settings, not as a general rule.

### Strong scope guard: OptiMer has not beaten optimized data mixing head-to-head

The paper's DataMix baseline uses uniform ratios. Its Limitations section explicitly states that DoReMi/RegMix could narrow the gap and that a direct 27B comparison remains future work. Therefore do **not** infer that OptiMer dominates RegMix, Data Mixing Agent, or other learned/dynamic mixture controllers. This is the highest-value matched comparison now missing.

Other limitations retained exactly:
- tested CPT length is 1B tokens per distribution; the authors warn that longer CPT may diverge too far from the common base and propose iterative train/merge as future work;
- architecture evidence is Gemma 3 27B and Gemma-SEA-LION-v4-27B, not Llama/Qwen;
- benchmark reporting uses a uniform 1-shot setting, so absolute scores are not directly leaderboard-comparable.

### Public artifact audit

The original author repository now points to the official NICT release. Current official README pins an unusually concrete environment: Python 3.11, torch 2.6.0/CUDA 12.4, transformers 4.51.3, Optuna 4.7.0, mergekit commit `d4b4b6c08f9e7014c0acf1c4402b9409d778a79e`, lm-eval 0.4.9.1, vLLM 0.8.4, accelerate 1.6.0, datasets 4.0.0 and PyYAML 6.0.2.

However, the current `optuna_merge_search.py` does not seed `TPESampler`, `CmaEsSampler`, or `RandomSampler`; it also uses unseeded Python `random.randint` for trial-start staggering. The public search therefore does not define a deterministic winning-weight trajectory by default. This is a reproducibility defect in the search contract, not evidence against the method. A clean reproduction should explicitly seed the sampler, Python RNG, evaluation subset/order, and persist study/version hashes.

The current code defaults differ from the paper in another important way: README/script default to `50` trials and proxy limit `300`, while the paper reports `100` trials with first `100` proxy samples and top-3 re-evaluation on first `300`; these are configurable, so reproduction must override defaults rather than assume README defaults recreate Table 1. Default CPT weight range is `[0,1]`; negative-weight experiments require explicitly setting a negative range.

## Branch J1 refinement — Data Mixing Agent acquisition cost and 52/54 ambiguity are now pinned

Primary source: Yang et al., ACL 2026 / arXiv:2507.15640v2 (`https://arxiv.org/html/2507.15640v2`).

Fresh primary-source verification resolves the previous frontier as far as public text permits:
- source trajectory corpus: 100B random DCLM source tokens plus about 10B Dolmino-Math target tokens;
- max reweighting steps `M=80`, `R=8K` samples per step;
- four trajectory-sampling runs with `P=96` and `K={1,100,1000,10000}`, giving `384` trajectories;
- each trajectory trains a LLaMA-structure `50M` proxy from scratch and evaluates checkpoints at every reweighting step;
- feedback environment uses 500 MMLU validation Q/A plus 500 random MATH-train samples, yielding `27,266` feedback records;
- proxy trajectory training + evaluation costs `1996.08 GPU h`; the 2.1M-parameter agent's SFT+CQL training is reported under 10 minutes.

The domain-dimensionality inconsistency is genuinely internal to the paper: one method sentence says source and target are each classified into 26 domains, “leading to a 54-dimensional” space, while the introduction/experiments repeatedly use `52-dimensional`; arithmetic and the two 26-domain halves support 52, but this remains a paper typo/ambiguity rather than something to silently rewrite.

Reported main-run savings versus RegMix average `106.33 GPU h` in math and `264.29 GPU h` in code. A simple acquisition-only amortization calculation gives roughly `18.8` math adaptations or `7.6` code adaptations before `1996.08 GPU h` is recouped by those reported main-run savings alone. This is an inference, not a paper claim, and ignores performance value, evaluator costs, storage, and variation across deployments.

No official Data Mixing Agent implementation was located in fresh exact-title/arXiv-ID GitHub searches; the first author's public publication page links the paper but not code. Keep this as “public implementation not located,” not an absolute absence claim.

## Updated control lattice

The data/replay-mixture axis should now be split by **when** the expensive decision is optimized:
1. pre-CPT/static: fixed/uniform ratio or proxy-derived fixed ratio;
2. during-CPT/online: Data Mixing Agent-style feedback-driven trajectory control;
3. post-CPT/parameter-space: OptiMer-style distribution-vector composition;
4. hybrid: post-hoc OptiMer weights converted back into a retrained data-mixture ratio, or iterative train/merge.

The reusable expensive object differs:
- Data Mixing Agent amortizes a learned controller/trajectory corpus across future adaptations, but pays a large up-front proxy/evaluation acquisition cost;
- OptiMer amortizes independently trained per-distribution CPT checkpoints/vectors across future objectives, but pays persistent checkpoint/vector storage and per-objective merge/evaluation search.

Neither should be credited for gains from the other axis. Parameter-write control (shared LoRA / selective de-correlation / routing) remains orthogonal and should only be crossed after data-controller comparisons are budget-matched.
