## Why major 4B parameters are CPU-offloaded on this public path

Public `scripts/zero3_offload.json` sets:

- ZeRO stage 3;
- `offload_param.device = "cpu"` with pinned memory;
- `stage3_param_persistence_threshold = "auto"`.

DeepSpeed 0.16.4 propagates the configured offload device into `DeepSpeedZeRoOffload.offload_device`, passes that as `Init(remote_device=...)`, and creates non-persistent parameter partitions on `remote_device`. Its `local_device` is the accelerator device.

Transformers 4.57.3 resolves `stage3_param_persistence_threshold="auto"` to `10 * hidden_size`. Qwen3-VL-4B has hidden size 2,560, so the threshold is **25,600 scalars**. Large weight matrices therefore exceed the persistence threshold and are non-persistent; small norms/biases can remain persistent. This means the main matrix partitions live on CPU under the public offload config, while CPO's `.to(param.device)` targets the accelerator path.

This establishes a source-level transfer mechanism; it does not establish measured PCIe/NVLink traffic.

## Stronger repair hypothesis from the offload semantics

The current code moves **global** support to every rank, then discards `(W-1)/W` of it; it also moves an entire CPU-offloaded BF16 parameter partition to GPU just to evaluate masked drift.

A more natural public-offload implementation is:

1. precompute rank-local protected indices and rank-local refs once from the global mask;
2. because the ZeRO partition itself already resides on CPU, compute masked `diff/sign` against `param.ds_tensor` locally on CPU;
3. send only the rank-local regularizer contribution needed by the gradient hook to the accelerator.

If both rank-local int64 indices and fp32 gradient values are transferred in the hook, payload becomes approximately `12*ceil(s/W)` H2D per call. In the same 4B/10%/W=8 scenario that is **0.620 GiB/rank**, versus the source-modeled **7.233 GiB/rank** current path — a conditional **~91.4% payload reduction**.

If rank-local indices can be cached safely on the accelerator, only fp32 regularizer values need recurring transfer: approximately `4*ceil(s/W)` = **0.207 GiB/rank** in that scenario, a conditional **~97.1% reduction** from the current source-modeled total.

These are repair hypotheses, not validated performance results. CPU-side masked math cost, pinning, overlap, GPU index-cache cost, gradient-hook semantics and the already-known `1/world_size` correctness issue must all be profiled together.
