### Persistent trainer state

`compute_importance_mask.py` stores, for every tensor with protected coordinates:

1. a **dense bool mask** with the tensor's full shape;
2. float32 `ref_weights` only for the accumulated protected coordinates.

`CLGRPOTrainer.__init__` then additionally materializes and retains `_mask_flat_idx`, an int64 flat index for **every protected coordinate**, while retaining the dense bool masks and float32 references on CPU.

Define:

- `N` = scalar count across tensors that have at least one protected coordinate and therefore keep a dense mask;
- `u` = fraction of those `N` scalars in the accumulated protected union.

Ignoring Python/container/serialization overhead and transient buffers, the source-structural logical tensor payload is therefore:

- current saved mask payload: `N + 4uN` bytes;
- persistent trainer auxiliary state: `N + 4uN + 8uN = N + 12uN` bytes.

The important consequence is that even at nominal `p=10%`, the runtime auxiliary payload is **not** roughly ten percent of a model. Under a full-mask-domain scenario, after the first 10% mask it is `2.2N` bytes: dense bool for all covered scalars plus float32 references and int64 indices for the protected tenth.

This is a source-structure statement, not a measured RSS/file-size result. Tensors whose movement is exactly zero can be absent, small tensors can have `floor(0.1*n)=0`, and actual task-to-task support overlap is not yet measured.

## New construction-path concern: two full model states coexist during mask building

The public mask builder says it loads state dicts "one at a time to minimise peak memory", but its actual lifetime is:

1. load current task model and retain `cur_sd`;
2. while `cur_sd` is still live, load the previous model and retain `prev_sd`;
3. only then compute per-tensor differences and eventually free `prev_sd`.

Thus the source structure permits at least two full BF16 model-state tensor payloads to coexist during mask construction. Using the public 4B/8B weight-byte anchors, that is about **16.53 GiB (4B)** or **32.66 GiB (8B)** just for the two weight payloads, before model/Python metadata, dense masks, reference tensors and transient float32 diff/top-k buffers. This is not a measured process RSS.

## Per-step transfer/runtime hypothesis that now needs profiling

Inside every `_compute_loss`, for each masked tensor the release does:

- `flat_idx = ... .to(param.device)` for the full accumulated protected index set;
- `ref = ... .to(param.device, dtype=float32)` for the full accumulated reference set;
- only **after that**, in ZeRO-3, filters those globals to this rank's partition.

Therefore the implementation can redundantly materialize full protected index/reference data on each rank before partition filtering. Whether that becomes host-to-GPU traffic, CPU-local copies, or another placement under the exact offload runtime depends on DeepSpeed placement and must be profiled rather than inferred. The 8B launcher uses ZeRO-3 with both parameter and optimizer CPU offload and does not freeze vision, LLM or merger, so a whole-model mask domain is operationally plausible but still must be measured rather than assumed.
