## New executed result: exact-storage dedup is not a generally safe CPO repair

The predecessor checkpoint measured that the public CPO mask builder can save a dead tied `lm_head.weight` alias because `state_dict()` exposes both tied names while the trainer later iterates `named_parameters()` and consumes only the canonical duplicate-free parameter name. I had proposed exact-storage/view deduplication as a repair candidate. This run falsified that repair as a general rule.

Public CPO anchor remains `MaolinLuo/CPO@9429452cb536a9e713b73b91c0011b96df44962c`:
- `src/compute_importance_mask.py` builds candidate keys from every floating `state_dict()` entry present in both checkpoints, then stores dense bool masks and float32 references.
- `src/trainer/grpo_trainer_cl.py` precomputes indices for every saved key, but actual hooks/loss contributions are driven by `model.named_parameters()` names.

PyTorch 2.8 documents `named_parameters(..., remove_duplicate=True)` as the default and `state_dict()` as containing parameters plus persistent buffers. Its `Module._named_members` source memoizes member objects, not raw storage signatures.

### Synthetic safety harness

Harness: `tools/cpo_trainer_namespace_filter_harness_20260828.py`

Three cases were compared at 50% per-tensor TopP under:
1. the public release-style `state_dict()` key set;
2. the predecessor's proposed exact-storage/view dedup;
3. a new **trainer-namespace filter** that keeps only canonical names from `named_parameters(remove_duplicate=True)` in both current and previous models.

#### Case A — ordinary tied Parameter alias

- Release mask keys: `a.weight`, `b.weight`.
- Trainer keys: only `a.weight`.
- Storage dedup: only `a.weight`.
- Trainer-namespace filter: only `a.weight`.

Both candidate repairs remove the dead alias here.

#### Case B — two distinct Parameter objects sharing the exact same storage/view

Constructed with `p = nn.Parameter(x)` and `q = nn.Parameter(p.data)`.

- Release mask keys: `p`, `q`.
- Trainer canonical keys: `p`, `q`.
- Exact-storage/view signatures are identical.
- Storage dedup keeps only `p` and therefore **changes trainer semantics** by dropping `q`.
- Trainer-namespace filtering keeps both `p` and `q`, exactly matching the trainer's canonical namespace.

This is the decisive counterexample: **storage identity is not the same thing as Parameter identity**. A repair that deduplicates solely by storage/view can silently remove a distinct trainable Parameter that the public trainer would regularize.

#### Case C — persistent floating buffer

- Release mask keys after a synthetic buffer change: `p`, `buf`.
- Trainer canonical keys: only `p`.
- Storage dedup still keeps `buf` because it has distinct storage.
- Trainer-namespace filtering removes `buf`.

Therefore the public builder can also create dead bookkeeping for changed persistent floating buffers, because the trainer has no `named_parameters()` path that can consume them. This is a generic builder/trainer namespace mismatch; it is not evidence that Qwen3-VL currently has a materially changing persistent float buffer in the target run.

## Safer repair contract

For a repair that preserves the current public trainer semantics:

1. Load the current and previous model objects, not only their state dicts.
2. Record the ordered canonical floating parameter names from `model.named_parameters(remove_duplicate=True)` for each model.
3. Require current/previous canonical parameter namespaces, shapes and dtypes to match, or **fail closed** with an explicit mismatch report.
4. Compute and save masks only for those canonical parameter names that also exist in both state dicts.
5. Do **not** deduplicate by storage pointer/view signature alone.

This removes same-Parameter tied aliases and persistent buffers that are dead to the trainer, while preserving distinct Parameter objects even when they share identical storage. It also aligns mask coverage accounting with the namespace the trainer can actually regularize.

The predecessor's `exact-storage-dedup` control should therefore be treated as a useful tied-alias diagnostic, **not** as the general production repair.
