## New high-impact source-level discrepancy: ZeRO-3 attenuates the sparse CPO regularizer by data-parallel world size

The public paper/release environment makes a stronger static conclusion possible than the predecessor had established.

### Exact public path

The CPO README pins training to PyTorch `2.8.0` and DeepSpeed `0.16.4`, and states RL launchers are configured for eight H100 GPUs. The public 2B CPO launcher uses `scripts/zero2.json`; the public 4B and 8B CPO launchers use `scripts/zero3_offload.json` with eight-GPU RL execution.

In CPO's ZeRO-3 branch, `_compute_loss` determines the current rank's DeepSpeed parameter-partition interval and creates a pending regularizer gradient only for protected coordinates that fall in **that rank's** partition. Its `Tensor.register_hook` then adds those coordinates into the full parameter gradient on that rank.

DeepSpeed `v0.16.4` is tag commit `e2dc3eeb1923073e32739596a4fd051417d4ff92`. Its `deepspeed.utils.torch.register_grad_hook` uses `param.register_post_accumulate_grad_hook(...)` on torch >= 2.1 for the ZeRO-3 reduction hook. PyTorch 2.8's documented backward-hook ordering is explicit: Tensor `register_hook()` executes first; post-accumulate-grad hooks execute only after the leaf's `.grad` has been accumulated. Therefore the CPO-added coordinate reaches DeepSpeed's reduction hook before reduction.

DeepSpeed 0.16.4 `reduce_scatter_coalesced`, blob `2fadce52222cda680600253ae840f84b89bda7ed`, explicitly performs `tensor_partition_flat_buffer.div_(world_sz)` before reduce-scatter. Its ZeRO-3 stage calls this function from `__avg_scatter_grads`, whose own docstring says it averages gradients and scatters partitions.

### Consequence

For a protected coordinate owned by rank `r`, the public CPO ZeRO-3 path contributes its regularizer gradient `g` only on rank `r`; the other `W-1` data-parallel ranks contribute zero regularizer gradient at that coordinate. DeepSpeed then averages the full gradients across `W` ranks. The surviving regularizer contribution is therefore `g/W`.

This differs from the non-ZeRO-3 CPO path, where each replica computes the same protected-coordinate regularizer from the full parameter/reference state, so ordinary data-parallel averaging preserves the regularizer magnitude.

At the public eight-GPU launcher setting, the paper/release `mask_lambda=100` therefore has source-level lambda-equivalent regularizer magnitude:

- 2B / ZeRO-2 path: approximately `100`;
- 4B / ZeRO-3 path: `12.5`;
- 8B / ZeRO-3 path: `12.5`.

Durable static diagnostic:

- `tools/cpo_zero3_worldsize_scaling_20260828.py`;
- `CPO_ZERO3_WORLDSIZE_SCALING_20260828.json`.

This is not a numerical training reproduction. It is an algebraic consequence of the current public CPO hook placement, PyTorch 2.8 hook order, and DeepSpeed 0.16.4 averaging behavior. A live eight-GPU test remains valuable to falsify any unobserved runtime assumption, but the current source contract itself is internally sufficient to predict the `1/W` scaling.

### Logging is attenuated too

The release's ZeRO-3 `mask_loss_value` is rank-local because each rank sums only its own protected partition; the logger gathers those partials and calls `nanmean`. Absent unusual empty/uneven-partition effects, the logged `mask_loss` is therefore also about `1/W` of the sum of the release's per-tensor masked means. This can make the underweighting look internally self-consistent rather than obvious in TensorBoard.

## Implication for interpreting the published scale result

The CPO paper reports strong 2B/4B/8B scaling and uses the same nominal `lambda=100`, `p=10%` setup. The current public launchers do **not** implement the same effective regularization strength across those scales because they switch from ZeRO-2 at 2B to owner-only ZeRO-3 injection at 4B/8B.

Therefore the published cross-size comparison cannot presently be interpreted as a clean test that the same CPO regularizer scales unchanged with model size. It may still be a strong empirical result, and the paper tables may have been generated with unreleased or different code/config. No current public artifact binds the paper tables to the release path, so this finding must not be used to retroactively rewrite the paper numbers or claim they are wrong.

A corrected ZeRO-3 implementation has at least two obvious candidate semantics to test, not silently assume:

1. replicate the deterministic protected-coordinate regularizer contribution on every DP rank before averaging; or
2. keep owner-only injection but multiply it by DP world size before DeepSpeed's averaging.

Either should be checked against a single-GPU/non-ZeRO reference on identical parameters, masks, refs and base RL gradients before any expensive model run.
