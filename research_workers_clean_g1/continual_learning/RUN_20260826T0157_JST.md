## 2. DriftLens supplies a runnable same-label visual-drift benchmark, but not a sequential alarm trace
Primary paper: Salvatore Greco, Bartolomeo Vacchetti, Daniele Apiletti, Tania Cerquitelli, *Unsupervised Concept Drift Detection From Deep Learning Representations in Real-Time*, IEEE TKDE 37(10), 2025, DOI `10.1109/TKDE.2025.3593123`.
Public code/artifacts inspected at `grecosalvatore/drift-lens`, observed source commit `0b7b943b128f8e23b56e5cd56fa40bc3dd35119e`.

Useful same-label source-controlled cases exist:
- use case 8: STL-10, all 10 original labels retained; drift is Gaussian blur applied to images from all classes;
- use case 9 in the experiment README: FairFace gender classification, same Male/Female labels, with a race/domain shift to East/Southeast Asian images.

The released use-case-8 wrapper fixes a concrete comparable condition: ViT, window size 250, 100 windows per severity, five runs, drift proportions 0/5/10/15/20%, and 10,000 threshold-estimation samples. The Python implementation explicitly sets `training_label_list=[0..9]` and `drift_label_list=training_label_list`.

However, this evaluation is **window classification, not sequential change-point detection**. For each severity it independently samples 100 balanced windows; all windows are labeled drift if severity>0 and no-drift if severity=0. Thus it measures type-I/window-detection behavior under same-label blur but does not directly produce an event stream from which Episode Recall, false alarms per stable episode, alarm duplication, or detection delay/NDT can be measured. It is therefore a good representation/threshold comparator but not yet the required alarm trace.

## 3. Reproducibility defect in the released DriftLens use-case-8 wrapper
The public shell wrapper `experiments/scripts/1_drift_detection_performance_evaluation_scripts/use_case_8_vit_drift_detection_accuracy.sh` invokes the use-case-8 Python module without `--run_driftlens`.

The Python parser defines `--run_driftlens` as a boolean `store_true`, so its default is false. In the main path, baseline/threshold construction and DriftLens scoring occur only when that flag is true; otherwise the script prints `DriftLens skipped`.

The experiment README says the scripts under this directory reproduce the paper's drift-detection tables, so the provided use-case-8 wrapper is not self-sufficient for reproducing the DriftLens row unless the user manually adds `--run_driftlens` (or invokes the Python module differently). This is a **wrapper-level reproducibility defect**, not evidence against the underlying method.

A second useful implementation detail: when DriftLens is enabled in this use-case script, the threshold is estimated from sampled reference windows, then values below the 1st percentile and above the 99th percentile are removed and the maximum remaining distance is used as the per-batch threshold. The script also parses `threshold_sensitivity`, but the inspected use-case-8 main path computes the threshold via this explicit 1%/99% trim. Treat the exact executable threshold path as stronger than the shell argument name when reconstructing this benchmark.

## 4. New matched-comparison opportunity
DriftLens is a better immediate substrate than LargeMonitor for constructing the requested **same-label alarm trace**, because it has runnable code and exact same-label visual drift generation. The missing piece is temporalization: instead of independently sampled windows, freeze one reference embedding/model and create a chronological stable->blurred->stable or stable->domain-shift stream using the exact released embeddings/generation logic. Then hold the representation score fixed and compare alarm controllers on the identical score sequence:
1. empirical-threshold/window detector as released by DriftLens;
2. LargeMonitor-style robust CUSUM reconstruction (clearly labeled adaptation until `kappa_h` etc. are recovered);
3. quantile+persistence+post-alarm-freeze controller inspired by TFIDD;
4. standard ADWIN/Page-Hinkley/CUSUM controls.

Evaluation contract remains: threshold/hyperparameter selection on held-out stream(s), then Episode Recall + False Alarm Rate + Normalized Detection Time on untouched same-label streams, plus raw score separability and compute. This directly separates **representation quality** from **alarm-control quality**.

## 5. Literature-wide warning strengthened
A 2025 Artificial Intelligence Review survey on image-stream concept drift reports that image drift-detection evaluation remains fragmented: false alarms are variously raw counts/rates/MTFA, detection delay definitions vary, threshold tuning often uses the evaluation stream, and many image benchmarks inject non-standardized blur/domain/class changes. This supports keeping the stricter 2026 event-level evaluation contract rather than accepting downstream accuracy or window F1 as proof of reliable online alarms.
