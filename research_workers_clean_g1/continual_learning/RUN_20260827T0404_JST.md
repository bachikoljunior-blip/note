### Sampling seed defect

`sample.py` calls `np.random.seed(42)` but also uses Python's separate `random.choice(...)` and `random.sample(...)` without any `random.seed(...)`. Therefore the public candidate-mixture generator is **not exactly reproducible from the stated NumPy seed alone**. This affects which Dirichlet draw is selected across concentration strengths and which deduplicated candidates are finally selected. This is a public-code reproducibility defect, not evidence that the paper's reported results are wrong.

`train_predictor.py` is better seeded: LightGBM receives `seed=42` and NumPy is seeded to 42; its `main` also sets `np.random.seed(42)`. However, evaluation-file discovery uses unsorted `glob.glob(...)` results and chooses `matched_dirs[0]` / `csv_files[-1]`. If more than one match exists, the chosen evaluation artifact can depend on filesystem enumeration order. The repository also has no `requirements.txt`, `pyproject.toml`, lockfile, or container recipe; `merge_models.sh` only says `pip install mergekit`. Thus Python/LightGBM/mergekit/OpenCompass versions are not pinned by the public repo.

### Optuna search is still unseeded

The official `optuna_merge_search.py` creates `TPESampler(...)`, `CmaEsSampler(...)`, or `RandomSampler()` **without an explicit sampler seed**. The script persists a study to `optuna.db`, so a particular run becomes replayable once its database exists, but no winning paper study DB is published in the repository. Therefore the initial search trajectory cannot be exactly reconstructed from the public code alone. Python `random` is also unseeded; it is used for evaluation-start staggering, which should not change the mathematical merge weights but can alter execution ordering/timing in parallel runs.

### Current public code can accidentally couple CPT weights by path naming

The script derives Optuna parameter names with `cpt_names = [Path(p).parent.name or Path(p).name for p in args.cpt_models]`, then samples `trial.suggest_float(f"w_{cpt_name}", ...)`. The README example passes sibling paths `/path/to/japanese_ckpt /path/to/math_ckpt`; both have parent directory name `to`. Under that exact usage, both CPTs request the same Optuna parameter name `w_to`, so their search weights are coupled rather than independently optimized. This defect is conditional: it does not trigger if each checkpoint lives under a uniquely named parent directory. It is a current-public-code issue only; do not infer that the authors' internal paper runs used colliding paths.

The public NICT repository still contains no paper-winning `optuna.db`, `search_summary.json`, Table-1 weight files, Gemma CPT checkpoints, distribution-vector files, or checkpoint hashes, and no GitHub release. Fresh public search also did not locate an author-published OptiMer model bundle on Hugging Face. Therefore the paper's reported optimum remains **deterministic reconstruction / re-search**, not exact replay, even though the software environment is now much better pinned.
