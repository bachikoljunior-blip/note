## Branch E — Fast-Slow Training (FST) is a strong fast-context continual-learning control, but not yet a public reproducible baseline

Primary source: Tiwari et al., `Learning, Fast and Slow: Towards LLMs That Adapt Continually`, arXiv:2605.12484 (May 2026), plus the authors' official GEPA blog. Public paper: https://arxiv.org/abs/2605.12484 ; official blog: https://gepa-ai.github.io/gepa/blog/2026/05/11/learning-fast-and-slow/ ; advertised code page: https://rishabhtiwari.ai/projects/fst/code/ . As observed this invocation, the code page still says `Code coming soon`, so the full training implementation is not independently inspectable/reproducible from public code yet.

Mechanism: maintain slow model parameters `theta` and a Pareto-frontier population of textual fast weights/prompts `Phi`. Every `T=6` slow-weight RL steps, GEPA uses the next lookahead batches, current policy rollouts, rich textual failure traces and a frozen reflection LM to mutate/select prompts; RL then trains the same model under the evolved prompt population. The headline implementation uses Qwen3-family 8B models, CISPO/GRPO-style RL, and OpenAI `gpt-5.2` as the reflection/proposer model. This is not simply prompt tuning after RL: the text context and model weights co-evolve.

Quantitative evidence from the primary paper:
- Matched-reward sample efficiency: FST reaches RL's running peak in `3.0x` fewer steps on CodeIO, `1.4x` fewer on Math/Polaris, and `3.0x` fewer on HoVer-hard.
- Fitted validation asymptotes: CodeIO `47.4%` FST vs `43.0%` RL; Math `49.2%` vs `46.4%`; HoVer-hard `25.0%` vs `17.3%`.
- At matched reward, the paper reports up to `70%` lower token-level KL from the base policy than RL-only, supporting the mechanism that task-specific information can be offloaded to fast context instead of forcing all adaptation into persistent weights.
- Plasticity probe after prior training: on Math→HoVer-hard, the RL-initialized model collapses to approximately `0%` within ~40 steps and stays near zero while the FST-initialized checkpoint remains close to the base-init learning trajectory. On Physics→HoVer-hard at step 400, FST-init reaches `24.2%` versus RL-init `19.9%` and is still improving.
- Three-stage continual run: HoVer→CodeIO→Physics, one uninterrupted 600-step trajectory with the data/task changed every 200 steps. In the CodeIO stage, RL starts at `18.3%` and peaks at `20.7%` (`+2.5pp`), while FST reaches `37.7%` (`+19.6pp`) by the end of the stage and is near-peak after ~80 steps; the paper describes this as roughly `8x` the within-stage acquisition gain of RL.

Important boundary/task-supervision scope: the official authors' blog states that in this continual run the FST seed prompts are `100% task-agnostic` and that the prompt optimizer autonomously decides how and when to change the system prompt in response to the changing data. This is materially stronger than a task-specific prompt bank. However, the experimental stream is still an externally scheduled, abrupt three-stage sequence whose dataset/reward/verifier changes every 200 steps. It is not evidence for a smoothly drifting mixture with no externally defined task stages. Because code is not yet public, the exact prompt-population persistence/reset lifecycle across those stage switches cannot be independently verified from implementation.

Compute/storage caveat: the paper explicitly warns that equal RL-step count is not equal compute. On HoVer, RL-only is ~60 s/RL step and FST without rollout reuse ~100 s/RL step; rollout reuse can reduce the FST RL-phase step to ~47 s, but periodic GEPA evaluation/reflection remains additional work. A headline run is reported at roughly `25–40 H100-GPU-hours`, with GEPA/reflection a sizable fraction; external `gpt-5.2` reflection calls are billed separately. Therefore `3x fewer optimizer steps` is a sample-efficiency result, not proof of 3x lower end-to-end compute. Fast textual state is cheap in parameters but consumes context tokens, external optimizer calls, and durable prompt-state storage. Restart/persistence should be scored explicitly: if the optimized context is not carried forward, the fast channel is lost even though slow weights remain.

Status: **high-value provisional continual-learning control**. It provides direct LLM-scale evidence that separating fast task-specific adaptation from slow persistent weights can preserve plasticity, but current public reproducibility and fully boundary-free continuous-stream evidence are missing.

## Branch F — TFGN public disclosure now supports a capability-level surrogate contract, not reproduction

Primary source: Ganguli, `TFGN: Task-Free, Replay-Free Continual Pre-Training Without Catastrophic Forgetting at LLM Scale`, arXiv:2605.15053v2, plus the author's official explainer. Public paper: https://arxiv.org/abs/2605.15053 ; explainer: https://www.anurupganguli.com/tfgn .

The public paper itself states that the architecture mechanism, source code, weights and reproducible training recipe are gated behind a signed mutual NDA pending patent prosecution/commercial licensing. It also states that reported BWT/HellaSwag numbers are **single-seed point estimates without confidence intervals** and places multi-seed validation on future work. This materially limits evidential weight: the headline numbers are inspectable claims, not publicly reproducible evidence.

Extension A does expose a useful capability-level decomposition even though wiring/lever specifications are withheld. The five public roles are:
1. **Sensing** — read the architecture's internal routing/state distribution.
2. **Prediction** — maintain an internal model of the next routing/network state.
3. **Gating** — scale gradient updates by prediction-error/surprise.
4. **Consolidation** — trigger a state-freeze when the trajectory stabilizes.
5. **Cross-layer coupling** — propagate the regulation decision consistently across depth.

At the ~398M, 1B-token/phase Prose→Python→Math Extension-A ladder, the paper reports BWT `-0.06010` for the historical anchor, `-0.03880` after enhanced routing, `-0.01900` after sensing+prediction with diagnostic-only consolidation, and `-0.01140` for the full active-consolidation headline. The paper interprets the sequential reductions as ~35%, ~51%, then ~40% contributions, yielding the advertised ~81% reduction from anchor to headline. Because these are single-seed and the implementation is not public, they should be treated as a **mechanism hypothesis with matched internal ablations**, not as reproduced evidence.

The main TFGN result remains unusually interesting: dense shared read path, content-conditioned write separation, no replay/task IDs/Fisher penalty, and reported LLaMA-3.1-8B Retrofit BWT about `-0.007`. But the exact lever that creates the near-orthogonal write subspaces is intentionally undisclosed. A web search this invocation did not find a publicly published machine-learning patent/application revealing those lever details; absence from this search is not proof that no application exists or will become public later.

Status: **high-priority unverified mechanism family**. The correct public surrogate target is not "reproduce TFGN" but test the disclosed principle using fully public components: dense shared read path + input-conditioned write partition/projector + internal surprise-based update gating + stability-triggered consolidation. Any such implementation must be labeled a new surrogate/hypothesis, not TFGN.

## Updated cross-mechanism comparison contract

The high-value LLM comparison is now at least four-way, under the same data order, total examples/tokens, wall-clock/compute budget, no replay, and no model-visible task ID:
1. **Single shared slow state** — parameter-only RL/SFT or one shared adapter.
2. **Fast-context offloading** — FST-like optimized external context + slow weights.
3. **Dense shared read / protected write** — public TFGN-surrogate style input-conditioned write separation + surprise/consolidation.
4. **Expert/routed state** — supervised or unsupervised routing with matched persistent storage.

Score independently: old-domain retention/BWT; current-domain acquisition speed; future-task plasticity; KL/base drift; gradient interference/orthogonality; active parameters; archive state; external prompt/context bytes and token overhead; restart persistence; reflection/router compute; replay/old-data access; training-time boundary/task-label availability; inference router/task ID; total GPU-hours/wall-clock. A method does not win merely because it uses fewer optimizer steps or fewer trainable parameters.

A particularly important falsification is to remove hard task stages. Convert a fixed total-token language corpus into a continuously changing mixture without exposing transition timestamps. If FST only works because GEPA sees a clean stage change, or if a write-partition method requires sharply clustered domains, the matched continuous-mixture evaluation should reveal it.
