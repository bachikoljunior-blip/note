## 1. Important correction: the observed CLDD 5→10-stream table delta is not a clean causal isolation of calibration-population size
The previous checkpoint treated the regenerated tables in public commit `tachyonicClock/cldd@f186455e3f39a8b3ac2e37b941cdbb8a7e8ecedb` as direct evidence that expanding detector-tuning streams from five to ten can materially alter held-out results. The source still supports a weaker observational statement, but not that causal attribution.

At the immediate parent `72d12ff2d1a6fca711fbbf46a1d1f85a189fdc7b` and at `f186455...`, detector tuning uses the same `config/hp/detector.yml`: 30 trials, objective `my_f1`, maximize=true, mode=`w`. In `src/hpsearch_config.py`, mode `w` deletes the existing study and then calls `optuna.create_study(...)` without supplying a sampler or a sampler seed. Public Optuna documentation states that an omitted sampler defaults to `TPESampler`, and its reproducibility guidance requires explicitly supplying a fixed sampler seed; otherwise the suggestion sequence is not guaranteed reproducible.

Therefore the before/after tables around `f186455...` compare two fresh HPO runs whose trial proposals can differ stochastically even if the search space and objective are unchanged. The code change to experiment generation is indeed the five→ten stream expansion, but the regenerated numerical delta is jointly consistent with:
- calibration-population expansion;
- a different unseeded TPE proposal path / selected hyperparameters;
- downstream consequences of whichever hyperparameters won that fresh run.

Scope correction: the table deltas are evidence that the released pipeline is sensitive across the two regenerated protocol executions, but they do **not** isolate the marginal causal effect of five versus ten tuning streams.

The Makefile's archival target stores the whole `logs/` tree into a local scratch `.7z` archive, but targeted public/archive searches again found no public copy of the referenced experiment archive or tuned-HP files.

Because the sampler itself is not seeded in source, fixed CLDD source + fixed error streams alone is insufficient to replay the exact winning HPO trajectory. An original `optuna.journal.log`, `best_trial.yml`, or equivalent receipt would recover the realized trial path; absent that, a rerun is a reconstruction, not an exact replay.

Optuna's own documentation additionally warns that deterministic HPO requires a fixed sampler seed and is harder under parallel/distributed execution. CLDD detector HPO uses one sequential `study.optimize` call per study, so the main identified nondeterminism here is the unspecified sampler RNG, not within-study `n_jobs>1`.
