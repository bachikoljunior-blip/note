## New result 2 — sparse runtime state must not be conflated with sparse persistence
A quantitative persistence crossover analysis changes the preferred storage repair.

For support fraction `u` within a tensor, ignoring small serializer metadata:
- current release dense bool + fp32 refs: `(1 + 4u)N` bytes;
- global int64 sparse idx + fp32 refs: `12uN` bytes;
- global int32 sparse idx + fp32 refs: `8uN` bytes;
- bit-packed mask + fp32 refs: `(0.125 + 4u)N` bytes.

Therefore:
- int64 sparse beats the current release persistence only for `u < 12.5%`;
- int32 sparse beats it only for `u < 25%`;
- against a bit-packed mask, int64 sparse wins only below `1.5625%` and int32 sparse below `3.125%`.

A real `torch.save` size test with `N=5,000,000` confirmed the crossover:

| support | release bool+ref | int64 sparse+ref | int32 sparse+ref | bitpacked+ref |
|---:|---:|---:|---:|---:|
| 10.0% | 7,001,925 B | 6,001,925 B | 4,001,925 B | 2,626,885 B |
| 19.0% | 8,801,925 B | 11,401,925 B | 7,601,925 B | 4,426,885 B |
| 27.1% | 10,421,893 B | 16,261,893 B | 10,841,861 B | 6,046,853 B |
| 34.39% | 11,879,877 B | 20,635,845 B | 13,757,829 B | 7,504,837 B |

So the runtime repair and persistence repair should diverge: **rank-local sparse idx/ref is still the preferred steady-state runtime form, but global int64 sparse persistence becomes worse after modest union growth.** A stronger candidate is global bit-packed mask + fp32 refs on disk, converted once at load to canonical sorted rank-local sparse state. Int32 sparse persistence remains a possible low-support fast-load format when a tensor has `<2^31` elements, but support must be measured rather than assumed.
