## New primary-source finding — Hydra: a near-direct rollback-node selector ablation on a fixed recovery substrate
Primary: Alexander Du, Jianjun Ou, Danyang Zhuo, Matthew Lentz, `Hydra: Efficient, Correct Code Generation via Checkpoint-and-Rollback Support`, arXiv:2605.15238v1, submitted 2026-05-14.
- Abstract: https://arxiv.org/abs/2605.15238
- HTML primary rendering: https://arxiv.org/html/2605.15238v1
- PDF: https://arxiv.org/pdf/2605.15238

### Why this source is unusually relevant to the open selector gap
Appendix E states that **all baseline policies use the same checker implementation, checkpoint interval, prompts, and sampling configuration as TokPol/TokPolK and differ in how they select rollback nodes after an error event**. This is much closer to the desired selector-only comparison than systems where detector, restore boundary, memory injection, and retry logic all change together.

The common candidate set is the ancestor `progress` nodes on the current search-tree path before a detected compiler error. Checkpoints reuse accepted prefix + incremental checker state. A policy receives the same runtime/search-tree state after an error and chooses where generation should resume.

### The compared rollback-node policies
1. **Random Repair**
   - On each error, uniformly samples one ancestor progress node.
   - Memoryless across attempts.

2. **Statement-Level / Backwards Repair**
   - Orders candidates from the most recent accepted progress node backward toward the root.
   - Uses positional recency only, not a root-cause model.
   - In the reported implementation, each candidate is attempted once (`a=1`) before moving earlier.

3. **Entropy-Based Repair**
   - First tries the most recent candidate, then ranks remaining candidate regions by maximum model token entropy.
   - Uses top-128 token log probabilities as an uncertainty signal.
   - In the reported implementation, `a=2` local attempts are used to match ROCODE's local-attempt setting.

4. **TokPol**
   - Maintains a probability distribution over latent root-cause position relative to the detected error.
   - A rollback can succeed only if it begins before the latent root cause in the policy model.
   - Scores each candidate by estimated token cost of the attempt plus expected cost of fallback attempts if it fails.
   - After a failed attempt on the same target, conditions the root-cause belief on that failed start and shifts probability mass toward earlier/deeper rollback positions.
   - Selects the candidate minimizing expected continuation token cost.

### Primary empirical selector result
Figure 7 evaluates **100 C++ tasks generated by Qwen2.5-Coder-32B that exhibit an initial static error**. The paper reports that TokPol has **substantially lower latency and token consumption than Random, Backwards, and Entropy**. The published CDF figure visually confirms TokPol's distribution is shifted toward lower latency/token use; the paper does not print exact per-policy medians in the nearby text, so no numeric median is inferred here.

The authors interpret the entropy result as evidence that model-side uncertainty is only weakly coupled to checker-reported failure, whereas a prior over root-cause distance can choose useful restart points while preserving more validated work.

### Root-cause distance is genuinely nonlocal in this domain
Hydra estimates a proxy for the root-cause location by asking a stronger 120B model for minimal compiling repairs and taking the first divergence position. This is not ground-truth localization, but the resulting distribution is broad:
- roughly 20–40% of failing cases can be repaired locally;
- roughly 30–40% require backtracking at least halfway from the reported compiler-error position.

This directly rejects a universal `latest checkpoint / purely local repair is enough` heuristic for the tested static-error population. It also rejects universal full restart: many errors do not require throwing away the whole valid prefix.

### Separate checkpoint-placement evidence inside Hydra
Hydra treats materialized checker-checkpoint interval separately from logical rollback-node selection. Dense checkpoints reduce checker replay distance but add checkpoint overhead; sparse checkpoints reduce overhead but make the checker replay farther after rollback. The implementation chooses the largest interval whose simulated checker catch-up probability has a Wilson-CI lower bound at least `Q=0.99`.

The main paper reports that checkpoint materialization itself gives little latency benefit for Qwen2.5-Coder-32B C++ when generation is slow relative to the checker, while benefit becomes clearer when generation is faster / checking comparatively expensive. This is useful negative evidence: **checkpointing and rollback-target quality are separate control variables; a good selector does not imply dense checkpointing is always valuable**.

### Strong matched-substrate claim — but not a perfect fixed-budget causal isolation
Hydra is a strong near-direct selector-policy ablation because checker, checkpoint interval, prompt, sampling, candidate state, and error event substrate are held fixed. However, the experiment does **not** satisfy the strictest version of the frontier requirement:
- Random is memoryless.
- Backwards uses `a=1` attempt per candidate.
- Entropy uses `a=2`.
- TokPol adaptively updates a root-cause posterior after failed attempts and optimizes expected continuation cost.

Therefore the compared objects are **rollback-selection policies**, not a pure one-shot target-ranking function with literally identical retry budget/state across every method. Differences in attempt scheduling/memory are part of the selector policy. Treat the evidence as showing that an informed adaptive target-selection policy is more efficient on this substrate, not as proving that root-cause-distance ranking alone causally dominates every alternative under equal retry budget.

### Metric and domain scope
- Selector ablation: 100 C++ tasks with an initial compiler/static error, Qwen2.5-Coder-32B.
- Primary selector claim is lower **latency and token consumption**, not a printed significant delta in final task success.
- Overall Hydra experiments report near-100% static correctness and functional correctness comparable to repair baselines, while the abstract reports up to 71% latency and 70% token reduction versus post-hoc repair on C/C++ tasks that encounter static errors. Those overall Hydra deltas change more than target selection and must not be attributed to TokPol alone.
- Candidate rollback points are accepted code-prefix progress nodes, not arbitrary semantic agent states.
- Detector is a compiler/static checker, substantially more deterministic than learned failure critics in open-ended agents.
- The root-cause prior uses a stronger-model repair proxy, not annotated true root causes; transfer to other models/domains is unproven.

## Design hypothesis strengthened by Hydra — scope-bounded
For a detected failure at time/error position `e`, historical target selection can be formulated as an expected-cost problem over candidate checkpoints `c` and an uncertain causal/root-cause location `r`:
- going too shallow/local risks preserving the cause and failing again;
- going too deep/early discards validated work and costs more replay/regeneration;
- a failed local repair is evidence that should update the target posterior toward earlier checkpoints;
- the best next target trades probability of actually preceding the cause against rollback/replay cost.

This is well-supported for Hydra's compiler-error setting. It is **not yet established** that the same posterior/cost model transfers to long-horizon web/GUI/tool agents, where failures may be distributed, semantic, partially compensable, or externally irreversible.

## Tempered / rejected hypotheses added this run
- `Always roll back to the latest accepted checkpoint`: rejected as a universal strategy in the tested static-error population; many root causes are substantially earlier than the reported error.
- `Always restart from the root`: also unsupported; a large fraction can be repaired without discarding the full valid prefix.
- `Model token entropy is a sufficient rollback-target signal`: not supported in Hydra's policy ablation; entropy-based repair is less efficient than TokPol and is described as weakly coupled to checker failure.
- `Any informed rollback policy comparison in Hydra proves a pure target-selector causal effect`: rejected. Retry attempts and policy memory differ, so the correct unit of comparison is the full rollback-selection policy.
- `Dense/frequent checkpoints are always the right companion to a better rollback selector`: rejected as a universal systems rule; benefit depends on generation/checker speed ratio and checkpoint overhead.
