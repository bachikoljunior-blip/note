## New failure evidence

### FE-241 — Blocking an early stop is insufficient when the agent cannot externally track distinct verified progress; explicit state/backlog controllers recover tasks that completion gating alone does not
**Primary source:**
- Cai et al., “Push Your Agent: Measuring and Enforcing Quantitative Goal Persistence in Long-Horizon LLM Agents,” arXiv:2605.23574: https://arxiv.org/abs/2605.23574

PushBench isolates quantitative goal persistence: the agent must continue until an external verifier confirms `N` *distinct valid* work units, so premature stopping, duplicate submissions, false completion and progress drift are separately observable. In matched controller comparisons, a state-tracking retrieval controller reaches `69–78%` success while eliminating duplicate submissions. A backlog-tracking work-unit controller reaches `25–50%` success in settings where both the standard controller and a simple verifier-gated controller—which merely blocks termination when the verified count is still below target—complete no task instances. In black-box evaluations, Claude Code (Sonnet 4.6) and Codex CLI (gpt-5.4) solve many 50-artifact tasks but fall to `3/9` successes per condition at 100 artifacts.

**Failure implication:** “do not stop until the verifier says done” is not enough for long quantitative tasks if the agent still loses track of which units are complete, repeats work, or cannot maintain a backlog. Durable external progress state and unit identity can be a separate reliability mechanism from completion gating itself.

**Positive control / scope guard:** the QGP-aware controllers improve the tested benchmarks, so this is not evidence that long-horizon completion is intrinsically unreliable. PushBench deliberately uses relatively simple work units to isolate persistence; its success ranges and `3/9` black-box result should not be treated as general failure rates for arbitrary coding/research workloads or all versions of those products.
