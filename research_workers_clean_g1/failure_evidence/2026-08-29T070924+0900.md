## New failure evidence

### FE-435 — Atomic replacement prevents torn files, not stale read-modify-write lost updates; Hermes resolved a cron-state race by putting every mutation path under one cross-process transaction lock
**Primary sources:** NousResearch/hermes-agent issue #18003 and its maintainer/sweeper resolution comment, https://github.com/NousResearch/hermes-agent/issues/18003

Issue #18003 identifies a `jobs.json` coordination race: `create_job`, `update_job`, and `remove_job` could each load a snapshot, mutate it, and atomically replace the file without holding the same lock across the whole read-modify-write transaction. Scheduler-maintained fields used locking on separate paths. Two writers could therefore each produce a perfectly intact JSON file while the later atomic replace silently overwrote the earlier writer's durable change. Reported impact included lost creates/removes, reverted pause/resume edits, and stale scheduler timestamps that could in turn yield missed or duplicate runs.

The July 12 maintainer/sweeper resolution says current main has implemented a common `_jobs_lock()` combining a process-local `RLock` with a cross-process `.jobs.lock` advisory lock, and that create/update/remove plus `mark_job_run` now hold this lock across their read-modify-write work. A cross-process test verifies that a separate process cannot enter `_jobs_lock()` while another owns it; the resolution says the implementation ships in `v2026.7.1`.

**Phase-1 failure mapping:** trigger = two mutation paths read the same old cron-state snapshot and later each atomically replace the file; detectable signal = per-file write integrity is valid but writer version/predecessor differs from current durable state; fail-closed response = serialize the complete read-modify-write transaction under one cross-process ownership mechanism (or use a transactional/CAS store), not merely atomic file replacement; recovery witness = a second process cannot enter the mutation critical section while the first owns it and all mutation paths share the same lock discipline.

**Scope guard:** exact to Hermes `jobs.json` cron CRUD/scheduler mutation paths described in #18003 and the stated v2026.7.1 implementation. This does not establish that advisory file locks are universally sufficient across distributed hosts/filesystems, nor does it convert atomic rename itself into a concurrency primitive.
