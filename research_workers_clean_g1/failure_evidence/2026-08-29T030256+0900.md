## New failure evidence

### FE-393 — Lock ownership alone does not protect an external resource from a stale holder after pause/lease loss
**Primary source:** Hazelcast FencedLock documentation, https://docs.hazelcast.com/hazelcast/5.2/data-structures/fencedlock

Hazelcast documents a concrete stale-holder scenario: client 1 acquires a distributed lock, suffers a long GC pause, misses session heartbeats, and loses the lock; client 2 acquires it, while client 1 can later wake without immediately knowing it lost ownership. Both may then act on the shared resource. Hazelcast's prescribed mitigation is a monotonically increasing fencing token that the external resource itself validates, rejecting the older holder's write.

**Phase-1 failure mapping:** trigger = holder pause outlives lease/session and a newer holder acquires; detectable signal = monotonic fencing generation attached to the protected mutation; fail-closed response = external resource rejects any mutation with a token older than the highest accepted token; recovery witness = newer holder's side effect remains authoritative and delayed stale side effect is rejected.

**Scope guard:** this is Hazelcast's documented asynchronous-network/GC-pause failure model and FencedLock mitigation. It does not prove that every lock implementation behaves identically, nor that a fencing token is sufficient unless the protected external resource actually enforces it.

### FE-394 — A producer request can be acknowledged as complete before the record is durably replicated
**Primary source:** Apache Kafka producer configuration, https://kafka.apache.org/40/configuration/producer-configs/

Kafka documents that with `acks=1`, the leader writes the record to its local log and responds without waiting for follower replication. If the leader fails immediately after the acknowledgment but before followers replicate, the record is lost. The same documentation states `acks=all` waits for the in-sync replicas and is the strongest available guarantee under the stated conditions.

**Phase-1 failure mapping:** trigger = caller treats a transport/API acknowledgment as durable completion while durability policy is weaker than the desired post-condition; detectable signal = acknowledgment policy plus independent durable-state/replica witness; fail-closed response = do not equate request completion with durable business completion unless the required durability contract is satisfied; recovery witness = independent readback/replica-backed state proves the committed record, or the operation remains non-final/retry-safe.

**Scope guard:** exact to Kafka producer durability semantics for the documented `acks` modes. It is not a claim that all HTTP/API 2xx responses have this property.

### FE-395 — A successful webhook response can precede the application's own durable business-state update
**Primary source:** Stripe webhook documentation, https://docs.stripe.com/webhooks

Stripe explicitly recommends returning a successful `2xx` response quickly and gives an example in which the endpoint returns `200` before updating a customer's invoice as paid in the accounting system. Therefore transport delivery success and the downstream durable business post-condition are intentionally separable.

**Phase-1 failure mapping:** trigger = upstream observes `2xx` and treats it as proof that downstream business effects are committed; detectable signal = separate delivery receipt versus downstream business-state readback/transaction receipt; fail-closed response = completion of the end-to-end action requires the business post-condition, not merely webhook transport success; recovery witness = accounting/business object independently reflects the intended state or a durable queued-work receipt guarantees later processing under an explicit contract.

**Scope guard:** this is an integration-level separation illustrated by Stripe's webhook guidance. It does not assert that Stripe itself loses events after `2xx`, and it does not establish exactly-once processing for the downstream application.

### FE-396 — Event-ID-only dedup can miss duplicate logical webhook effects when duplicates have different Event objects
**Primary source:** Stripe webhook documentation, https://docs.stripe.com/webhooks

Stripe says webhook endpoints can receive duplicate events and that, in some cases, two separate Event objects are generated and sent. Its guidance is to identify this second class of duplicate using the `data.object` ID together with `event.type`, rather than relying only on Event IDs.

**Phase-1 failure mapping:** trigger = same logical source transition is represented by two transport/event objects with different event IDs; detectable signal = logical object identity + event type (or another domain-level effect key), not transport ID alone; fail-closed response = suppress a second irreversible commit for the same logical effect; recovery witness = duplicate transport objects produce one committed business effect while each delivery remains auditable.

**Scope guard:** exact to Stripe's documented duplicate-event behavior and recommended identity fields; it is not a universal idempotency key for every event system.

### FE-397 — Async completion identity can become stale across retries, so execution-scoped identity matters
**Primary source:** Temporal Activity Execution documentation, https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/activities/activity-execution.mdx

Temporal documents that a Task Token uniquely identifies an Activity Task Execution and that retries can leave an external service holding an invalid token from an earlier attempt. The same documentation distinguishes Activity Execution from Activity Task Execution and notes that an Activity ID is unique among open Activity Executions of a Workflow Run and can be reused after an earlier execution closes.

**Phase-1 failure mapping:** trigger = delayed external result returns after retry/replacement; detectable signal = execution/attempt-scoped token or generation rather than only reusable logical activity identity; fail-closed response = reject result bound to a superseded execution; recovery witness = only the current execution's result can close/advance the current parent state.

**Scope guard:** Temporal is used here as a concrete identity-lifetime example. Its stale Task Token is rejected by Temporal; this item does not claim Temporal misattributes stale completions.

### FE-398 — Own multi-process matched probe: a stale claimant overwrites the newer claimant without fencing, but resource-side generation fencing rejects it
**Own probe:** `research_workers_clean_g1/failure_evidence/probes/2026-08-29T030256+0900-concurrency_resume.py` and `.json`

Two independent OS processes operate on the same SQLite database with fixed event order: generation 2 (`B_current`) commits first, then delayed generation 1 (`A_stale`) resumes. The no-fence table ends as `A_stale`, generation 1. The matched fenced table accepts generation 2 (`rowcount=1`) and rejects delayed generation 1 (`rowcount=0`), ending as `B_current`, generation 2.

**Phase-1 failure mapping:** trigger = delayed stale process resumes after newer generation committed; detectable signal = monotonic generation carried to the protected resource; fail-closed response = conditional resource mutation rejects older generation; recovery witness = newer state remains exact and stale update affects zero rows.

**Scope guard:** stronger than the prior single-process simulation because competing writers are separate processes, but still one host + SQLite. It does not reproduce network partitions, distributed database replication, lease expiry, clock skew, or arbitrary production storage semantics.

### FE-399 — Own matched probe: a late child from superseded parent attempt N can overwrite N+1 if aggregation is keyed only by logical child ID
**Own probe:** same `2026-08-29T030256+0900-concurrency_resume.py` and `.json`

Parent attempt 2 is current. Its child result arrives first, then the delayed result from parent attempt 1 arrives. An unbound aggregator keyed only by `logical_child=child-1` ends with `result_from_1`, overwriting the current result. The matched generation-bound aggregator accepts only `parent_attempt=2`, preserves `result_from_2`, and records the attempt-1 result as rejected.

**Phase-1 failure mapping:** trigger = superseded parent has a late child still in flight while replacement attempt is active; detectable signal = parent-attempt/generation identity on each child result; fail-closed response = result cannot mutate current parent state unless its parent generation matches; recovery witness = current attempt's result remains authoritative and stale result is separately auditable/rejected.

**Scope guard:** deterministic two-process protocol simulation only. It demonstrates the misattribution mechanism, not a bug in any named workflow engine.

### FE-400 — Own matched probe: distinct transport IDs can still represent one logical effect, so transport-ID dedup alone commits twice
**Own probe:** same probe artifacts.

Two records have different transport IDs (`evt_A`, `evt_B`) but the same logical object (`invoice_42`) and event type (`invoice.paid`). A message-ID-only deduper commits the effect twice; a logical `(object_id,event_type)` deduper commits it once.

**Phase-1 failure mapping:** trigger = publisher emits/re-emits the same logical effect as a distinct transport record; detectable signal = stable domain-level effect identity; fail-closed response = second logically equivalent irreversible commit is suppressed; recovery witness = one business effect with both transport deliveries retained for audit.

**Scope guard:** synthetic identity test shaped to the documented Stripe duplicate class; the chosen `(object_id,event_type)` key is not asserted to be sufficient for unrelated domains.

### FE-401 — Own continuation probe: process exit plus a durable checkpoint does not itself imply hidden background progress
**Own probe:** same probe artifacts.

A subprocess writes `{stage: paused, seq: 1, resume_token: ...}` and exits. After an idle wait with no resumer, exact readback remains byte-equivalent in semantic fields (`stage=paused`, `seq=1`). Only an explicit second process presenting the same resume token advances the state to `{stage: completed, seq: 2}`.

**Phase-1 failure mapping:** trigger = orchestrator assumes checkpoint persistence implies work continues somewhere after the execution process exits; detectable signal = no current execution/resume receipt and unchanged checkpoint sequence; fail-closed response = do not infer liveness/progress from a durable checkpoint alone; recovery witness = explicit generation-bound resume invocation advances the sequence and durable state.

**Scope guard:** local synthetic process/checkpoint test only. It does not characterize platforms that intentionally run durable background workers.

### FE-402 — A paused LangGraph can expose an empty `state.next`, creating a false-completion signal for callers that equate empty-next with done
**Primary source:** LangGraph issue #6956, https://github.com/langchain-ai/langgraph/issues/6956

The issue supplies a self-contained minimal reproduction where a node calls `interrupt()` twice. After resuming the first interrupt and reaching the second, the graph is still paused waiting for input but `graph.get_state(config).next` returns `()`. The reporter identifies the consequence directly: code relying on `state.next` to determine waiting/completion can mistake the run for complete.

**Phase-1 failure mapping:** trigger = repeated interrupt/resume causes snapshot scheduling metadata to omit the still-paused node; detectable signal = pending interrupt/wait obligation disagrees with empty `next`; fail-closed response = terminal completion requires an explicit terminal invariant, not empty ready/next alone; recovery witness = pending interrupt is resolved or terminal state independently proves no remaining obligations.

**Scope guard:** open reporter-supplied minimal reproduction for the stated package versions; no maintainer-confirmed root cause or merged fix is claimed here.

### FE-403 — Recovery bookkeeping can permanently over-count pending work and create false liveness after execution actually drains
**Primary source:** Ray issue #65313, https://github.com/ray-project/ray/issues/65313

The issue describes `MarkGeneratorFailedAndResubmit` for a still-running streaming generator: the task is already counted pending, recovery setup increments the pending count again, and later completion decrements only once. The reported consequence is a permanently positive `num_pending_tasks_`, causing `CoreWorker::IsIdle()` to remain false, blocking drain/shutdown and surfacing a job as if tasks were still running. The issue includes a proposed fix/test relationship but remains open at observation time.

**Phase-1 failure mapping:** trigger = recovery/resubmission path increments liveness accounting for work already counted; detectable signal = pending counter diverges from concrete in-flight attempt set; fail-closed response = do not infer liveness solely from an unvalidated aggregate counter; recovery witness = counter is derivable/reconciled from exact attempt identities and returns to zero when all attempts finish.

**Scope guard:** current open Ray issue, not a merged-project guarantee and not generalized beyond the named streaming-generator recovery path.
