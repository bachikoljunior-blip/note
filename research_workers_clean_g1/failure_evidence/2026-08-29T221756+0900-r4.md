## FE-464 — A stream/action can return terminal success while the authoritative durable message row is still pending
**Sources:** Convex Agent issue #274 and merged PR #296.
- https://github.com/get-convex/agent/issues/274
- https://github.com/get-convex/agent/pull/296

In `@convex-dev/agent@0.6.1`, `thread.streamText(..., { saveStreamDeltas: true })` could receive a final `finishReason: "stop"` with zero response content. The stream was marked finished, `result.text` and `result.finishReason` resolved, and the caller returned success, but serialization produced zero replacement messages, so the trailing durable assistant row remained `status: "pending"` indefinitely. A watchdog scoped only to the action therefore exited even though authoritative persistence still contained an unresolved obligation.

Merged PR #296 on 2026-07-22 synthesizes an empty assistant message for that boundary case, replaces the pending row, then atomically finishes the stream. Its awaited and `returnImmediately` regressions both leave one pending row when the patch is reverted and pass with the fix.

**Trigger:** transport/stream terminal signal precedes or bypasses durable finalization when a boundary payload is empty.

**Detectable signal:** action/stream success plus a durable `pending` row for the same logical response.

**Fail-closed response:** do not use transport completion as the sole completion witness; independently verify that the authoritative pending obligation has been discharged.

**Recovery witness:** merged PR #296 with red/green pending-row regressions.

**Scope:** Convex Agent `streamText` with saved deltas and an empty final response step. This does not prove that every successful stream can leave durable work pending.

## FE-465 — An asynchronous input batch can be omitted or cross-contaminate the successor session if completion is bound to the currently selected UI rather than its origin
**Sources:** OpenClaw issue #114563 and merged PR #114568.
- https://github.com/openclaw/openclaw/issues/114563
- https://github.com/openclaw/openclaw/pull/114568

OpenClaw Control UI could submit an existing-chat message before an asynchronous `FileReader` finished, silently omitting the selected attachment. If the user switched from session A to B before the read completed, the late attachment could instead be inserted into B. The maintainer-authored reproduction used real Chromium with a deterministic mock Gateway; it therefore tests browser/UI ownership and full `chat.send` payload formation, not live-Gateway delivery.

Merged PR #114568 on 2026-07-27 uses one abortable, session-owned attachment-read lifecycle, blocks send until the batch is committed, and aborts pending reads on session adoption, pane replacement, and disconnect. It reports 270 focused tests and 62 real-Chromium scenarios.

**Trigger:** async preparation outlives a mutable current-session pointer.

**Detectable signal:** message payload lacks the selected attachment, or completion of A's read mutates B after a fast switch.

**Fail-closed response:** bind pending async work to immutable origin ownership and gate send on the whole batch reaching a terminal committed state; abort on ownership change.

**Recovery witness:** merged PR #114568 with deferred-FileReader cross-session regressions.

**Scope:** OpenClaw Control UI attachment preparation before Gateway dispatch. It is not live-Gateway or arbitrary child-result evidence.

## FE-466 — Correctly detecting a stale lock is insufficient if the caller classifies the transient cleanup boundary as permanently fatal
**Sources:** Hermes Agent issue #54167 and merged PR #54176.
- https://github.com/NousResearch/hermes-agent/issues/54167
- https://github.com/NousResearch/hermes-agent/pull/54176

Hermes' scoped Telegram bot-token lock code could identify a dead owning PID and delete the stale lock, yet still return acquisition failure for that attempt. `_acquire_platform_lock()` then classified the condition as `retryable=False`, so the reconnect watcher never tried again. The issue reports production incidents on 2026-06-23 and 2026-06-28 where Telegram stayed permanently disconnected until manual lock deletion/restart despite the owner PID being dead.

Merged PR #54176 on 2026-06-28 changes this lock-acquisition failure to retryable and adds a regression asserting the retryable classification.

**Trigger:** stale-owner cleanup and reacquisition are split across attempts, but the intermediate failure is converted into a permanent terminal state.

**Detectable signal:** owner proven dead / stale lock removed while platform remains fatal and reconnect watcher is disabled.

**Fail-closed response:** distinguish confirmed live ownership conflict from transient stale-lock cleanup; keep reconnection eligible when ownership is not durably held by another live actor.

**Recovery witness:** merged PR #54176 plus two reported production incidents for the failure side.

**Scope:** Hermes Telegram scoped-lock startup/reconnect path. It does not imply all lock failures are retryable.

## FE-467 — A lease-renewal exception can let a stale worker continue past its last confirmed authority and overwrite a successor's terminal result
**Source:** Deer Flow merged PR #4431 (fixes #4414).
- https://github.com/bytedance/deer-flow/pull/4431

Before the fix, Deer Flow aborted a worker when lease renewal explicitly returned `False`, but merely logged database/network exceptions and kept executing. If those exceptions lasted past the last durably confirmed lease expiry, another worker could reconcile the run to `error` while the stale worker continued model execution, tool calls, checkpoint work, hooks, and finalization. A second race let the stale worker's local `success` overwrite the peer-owned durable `error`.

Merged PR #4431 on 2026-07-26 treats the stored lease expiry as the last confirmed ownership deadline, retries only while that authority remains valid, then fail-stops on expiry/unconfirmed ownership. It adds an `ownership_lost` fence that blocks later state/progress/completion persistence and makes terminal completion writes monotonic. Regressions go red on main and green with the fix; the peer-takeover test uses two `RunManager` instances sharing one store, while a transient-renewal-recovery control remains green.

**Trigger:** ambiguous renewal failure is treated as permission to keep executing after confirmed authority expires.

**Detectable signal:** peer has already committed a terminal outcome while the old owner continues and can still write completion.

**Fail-closed response:** bound execution by last durably confirmed authority, cancel/fence local continuation after loss, and make terminal writes reject stale replacement.

**Recovery witness:** merged #4431 with shared-store peer takeover and late-finalization red/green tests.

**Scope:** Deer Flow heartbeat-enabled multi-worker run ownership in the tested shared-store/two-manager setup. This is not an actual multi-host/network-partition incident, and the PR explicitly notes already-committed remote tool effects may be uncancellable.

## FE-468 — A freshness fix can itself destroy useful caching if its witness cannot distinguish another process's write from the current process's own write
**Source:** Hermes Agent merged PR #46237 (fixes #45966).
- https://github.com/NousResearch/hermes-agent/pull/46237

When two processes shared a `SessionDB`, a gateway-cached `AIAgent` could replay a stale in-memory transcript after another process appended turns. The initial repair compared durable `message_count` with a count captured when the agent was built. But because the process's own turn also increments the count and the snapshot was not refreshed, the very next local turn always looked externally stale. The PR measured five consecutive same-process turns as five rebuilds and zero cache reuses before the follow-up correction.

The merged repair refreshes the cached count after the current turn flushes, so same-process writes re-baseline the witness while a genuine cross-process append still invalidates. Tests drive the real `SessionDB`: five same-process turns all reuse, external append rebuilds, and failure/legacy/pending cases no-op safely.

**Trigger:** freshness witness tracks a shared monotonic counter but does not record which accepted local transition it already incorporates.

**Detectable signal:** stale-state repair prevents stale reuse but turns every normal local turn into a cache miss/rebuild.

**Fail-closed response:** reconcile the witness after own committed writes and invalidate only when authoritative state advances outside the accepted local transition.

**Recovery witness:** merged #46237 with real-SessionDB matched same-process/cross-process tests.

**Scope:** Hermes per-conversation agent cache coherence over shared `SessionDB`. This does not establish a generic cache-coherence protocol.

## FE-469 — Useful work can finish while the orchestrator remains running, then be falsely reaped as failed; a child terminal failure can also fail to wake the parent at all
**Source:** Multica issue #3548 and maintainer/collaborator diagnosis.
- https://github.com/multica-ai/multica/issues/3548

A self-hosted Multica report measured 25 `idle_watchdog` failures in one workspace; 22 already had completion-style final assistant messages, and durations clustered at the apparent finish time plus the 30-minute idle window. The finished work survived in task messages and durable side effects, but the daemon later wrote `failed` with empty `result.output`. A collaborator confirmed the Claude stream-json backend parsed an explicit end-of-turn `result` marker but waited for process exit/EOF to finalize; inherited foreground subprocess descriptors could keep the process alive and let the watchdog misclassify the completed turn.

The same maintainer diagnosis confirmed a separate liveness hole: delegated terminal runtime failure produced neither the comment nor child-`done` event that redispatched the squad leader, so the parent's failover logic never ran. The reporter observed an issue idle about 14 minutes until a manual rerun woke the leader.

**Trigger:** terminal authority is attached to process exit rather than protocol/business completion, or failure delivery bypasses the parent wake path.

**Detectable signal:** final message/durable side effect exists while task remains `running` until watchdog failure; or a child reaches terminal failure while parent queue remains idle.

**Fail-closed response:** use protocol/business terminal markers for task completion and explicitly route terminal child failure through the parent continuation contract after retry budget exhaustion.

**Recovery witness:** maintainer-confirmed code-path diagnosis; issue is closed, but this slice did not establish a linked merged fix, so no shipped-resolution claim is made.

**Scope:** the reported Multica daemon/task lifecycle and diagnosed Claude/delegation paths. A later Codex report in the same thread may have a different cause and is not folded into this root cause.

## FE-470 — An unattended background workflow that can enter an interactive permission state has a hidden manual-user dependency and no liveness bound
**Source:** Claude Code issue #78487.
- https://github.com/anthropics/claude-code/issues/78487

Claude Code 2.1.212 on Windows was reported to let Workflow-spawned background agents wait indefinitely on permission-gated tool calls when no approver answered. One observed run sat about 55 minutes (`idle 51m15s`, total `55m26s`) with zero output until `TaskStop`; another parallel-agent run showed a roughly 58-minute silent stall. Since the described behavior change routes background permission requests to the main session rather than auto-denying them, an unattended workflow can require a human response without an auto-deny timeout or idle watchdog.

**Trigger:** background execution reaches an interactive approval gate while the approval surface is unattended or invisible.

**Detectable signal:** started agent has no matching terminal result and no output for tens of minutes, with progress possible only after a human answer or kill.

**Fail-closed response:** a zero-residual-user-dependency route must ensure every unattended permission state has a deterministic non-human terminal policy; otherwise the workflow remains an unresolved child under control26 rather than a parity mechanism.

**Recovery witness:** none yet; issue remains open as of the public source observed on 2026-08-29.

**Scope:** reported Claude Code Workflow/background-agent behavior on version 2.1.212 / Windows. The reporter's second occurrence may be scheduler-side and is not assumed to share the permission root cause; Linux/macOS exposure is not claimed from this evidence.

## FE-471 — Loss of a local wrapper process can be a false failure signal for an already accepted remote run that keeps streaming and completes successfully
**Source:** Paperclip issue #1804.
- https://github.com/paperclipai/paperclip/issues/1804

In a live local Paperclip + live OpenClaw gateway reproduction, the gateway accepted a run, continued streaming assistant output for minutes, and the issue ultimately reached `done`, while Paperclip surfaced a `process_lost` condition because its orphan reaper inferred remote liveness from the local child/wrapper process. The reported run therefore had contradictory observations: local wrapper considered lost, remote execution demonstrably still alive and later successful.

**Trigger:** a local transport/process handle is treated as the authoritative liveness witness for externally owned work.

**Detectable signal:** `process_lost` is emitted after gateway acceptance while remote events continue and a later remote terminal success arrives.

**Fail-closed response:** after external acceptance, distinguish local attachment loss from remote run failure and require an external terminal/heartbeat/reconciliation witness before declaring the work failed.

**Recovery witness:** none established here; issue remained open in the observed public source.

**Scope:** Paperclip `openclaw_gateway` adapter behavior in the reported live local setup. It does not prove the same liveness split for local-process adapters.
