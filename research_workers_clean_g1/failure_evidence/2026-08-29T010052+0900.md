## New failure evidence

### FE-373 — A lease/lock holder can become stale while still alive; downstream fencing is required to reject late writes
**Primary source:** Redis, “Distributed Locks with Redis,” https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/

Redis’s own Redlock documentation explicitly warns not to assume a lock remains held for as long as the process that acquired it is alive. The lock is TTL-bounded, and the current documentation recommends fencing tokens, especially for processes that can take significant time. It also notes that Redis TTL expiration uses wall-clock time, so sufficiently bad clock shifts can create a condition in which more than one process acquires what each believes is the lock.

**Phase-1 failure mapping:** trigger = claimant continues working after its lease validity ended, or time behavior causes a second claimant to acquire the lock; detectable signal = a monotonically ordered fencing/claim generation carried with every mutation, not merely “I once acquired the lock”; fail-closed response = the protected resource rejects a write whose fencing generation is older than the resource’s latest accepted generation; recovery evidence = a newer claimant can commit while a deliberately delayed old claimant’s write is refused.

**Scope guard:** this is an official lock-contract warning/design requirement, not an empirical incidence rate and not a proof about all Redis deployment configurations.

### FE-374 — Repository writes need compare-and-swap identity; blind concurrency is a documented conflict surface
**Primary source:** GitHub REST API docs, “Repository contents,” https://docs.github.com/en/rest/repos/contents

GitHub’s create/update contents endpoint requires the current blob `sha` when replacing an existing file and exposes `409 Conflict`. The same docs state that create/update and delete requests against repository contents conflict when used in parallel and must be serialized. A stale claimant therefore cannot safely treat “same path” or “same intended value” as sufficient authority to overwrite the latest state.

**Phase-1 failure mapping:** trigger = writer acts on a stale blob version or concurrent writers mutate/delete the same logical object; detectable signal = predecessor blob SHA mismatch / `409 Conflict`; fail-closed response = do not transform a conflict into an unconditional overwrite or blind refreshed-SHA retry; recovery evidence = read the current predecessor, re-derive the intended patch against that exact state, then commit with the new CAS identity and read back the resulting content.

**Scope guard:** this item is a documented GitHub Contents API contract. It does not prove atomicity across multiple files or every GitHub write surface.

### FE-375 — Temporal Local Activity results can be externally effective before they become durable, causing re-execution after a crash
**Primary source:** Temporal, “Local Activity,” https://docs.temporal.io/local-activity

Temporal documents a matched durability difference. A regular Activity is durably tracked by the Temporal Service; after the Activity completes, a Worker crash does not cause that completed Activity to execute again. By contrast, a Local Activity’s result is durable only when the enclosing Workflow Task completes and records a `MarkerRecorded` event. If the Worker crashes after the Local Activity runs but before that marker is recorded, the Workflow Task is retried and the Local Activity runs again. Temporal therefore describes Local Activities as at-least-once and says they should be idempotent.

**Phase-1 failure mapping:** trigger = crash after a Local Activity side effect but before its completion marker is durable; detectable signal = effect occurred while the corresponding durable marker is absent; fail-closed response = keep non-idempotent/external writes out of this boundary or bind them to an idempotency key; recovery evidence = replay after the crash produces exactly one logical downstream effect, with the marker/history and external effect identity agreeing.

**Scope guard:** this is Temporal-specific documented runtime behavior. The regular-vs-local comparison is a useful positive control inside Temporal, not a claim that all workflow runtimes have identical semantics.

### FE-376 — Registering compensation only after an Activity returns can miss a partial external effect
**Primary source:** Temporal, “Saga Pattern,” https://docs.temporal.io/design-patterns/saga-pattern

Temporal’s Saga guidance gives the concrete example of a credit-card charge occurring before an Activity fails to return success. If compensation is registered only after the forward Activity reports success, that partial side effect can be left without a compensation. Temporal recommends registering compensation before Activity execution for side-effecting operations and making compensation idempotent and capable of no-op when the forward action never happened.

**Phase-1 failure mapping:** trigger = external mutation commits but the forward call fails before durable success/result registration; detectable signal = externally visible effect with no corresponding forward-success record; fail-closed response = pre-register an idempotent compensator or otherwise bind forward-effect identity before execution; recovery evidence = after injected mid-call failure, external readback is either the intended final state or a verified compensation state, never an untracked partial mutation.

**Scope guard:** this is a documented failure mode/design pattern, not a frequency estimate. Whether pre-registration is sufficient depends on the compensator and external system.

### FE-377 — Queue receive semantics expose a hard loss-vs-duplicate trade-off; a successful-but-unacknowledged settle can still replay
**Primary source:** Microsoft, “Prevent message loss and duplicate processing in Azure Service Bus,” https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-message-loss-and-duplicates

Azure Service Bus documents a direct matched trade-off. In Peek Lock mode, if a consumer fails before completing or loses the lock/link, the message can be delivered again, so duplicate processing is possible. In Receive and Delete mode, the service removes the message as soon as it is delivered, so a consumer crash before processing can lose work permanently. The same guide also states that a transient failure can cause a send or settle to be retried even when the service already applied it, yielding successful-but-unacknowledged duplication.

**Phase-1 failure mapping:** trigger = crash/network fault between message delivery, business effect, and settlement acknowledgement; detectable signal = durable message/effect identity plus settlement status and downstream readback, not delivery count alone; fail-closed response = never equate “received” or “settled call returned ambiguously” with exactly-once business completion; recovery evidence = dedup/idempotency receipt or downstream state proving one logical effect, while loss-sensitive paths retain the message until the effect is durably established.

**Scope guard:** this is Azure Service Bus behavior under the documented receive modes. It does not estimate duplicate/loss frequency in arbitrary deployments.

### FE-378 — Late child/callback results need attempt-specific identity; Step Functions invalidates superseded task tokens
**Primary sources:** AWS Step Functions, “Discover service integration patterns,” https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html ; “SendTaskSuccess,” https://docs.aws.amazon.com/step-functions/latest/apireference/API_SendTaskSuccess.html

For callback tasks, Step Functions issues a task token that identifies the specific task instance. If the task times out, the documentation says a new random token is generated. A later `SendTaskSuccess` for an expired or already-closed token returns `TaskTimedOut`; invalid tokens return `InvalidToken`. Thus a result from a superseded attempt is not accepted merely because it refers to the same business task.

**Phase-1 failure mapping:** trigger = child/worker from attempt N returns after parent/dispatcher has already timed out and started attempt N+1; detectable signal = attempt-scoped capability/token mismatch; fail-closed response = reject late result from the superseded token rather than attaching it to the current parent by business key alone; recovery evidence = only the currently issued token can advance the workflow, while a delayed old token is deterministically rejected.

**Scope guard:** this entry uses Step Functions as a positive control for attempt-bound callback identity. It does not claim a measured bug in Step Functions; the counterexample target is any handoff design that lacks the equivalent attempt binding.

### FE-379 — Webhook delivery can be duplicated and reordered; transport success does not create an exactly-once event stream
**Primary source:** Stripe, “Receive Stripe events in your webhook endpoint,” https://docs.stripe.com/webhooks

Stripe documents that webhook endpoints may receive the same event more than once and that event delivery order is not guaranteed. Manual resend does not cancel the platform’s automatic retry behavior. Stripe therefore recommends logging processed event IDs and skipping repeats; in cases where distinct Event objects represent the same logical event, it recommends combining the object ID with event type for deduplication.

**Phase-1 failure mapping:** trigger = automatic/manual retry overlap, network ambiguity, or out-of-order delivery; detectable signal = stable event/logical-object identity plus event type and current object readback when order matters; fail-closed response = deduplicate before committing side effects and refuse order-dependent transitions without reconstructing missing/current state; recovery evidence = replay/reorder test yields one logical effect and final state consistent with the authoritative object, independent of delivery order.

**Scope guard:** these are Stripe webhook delivery guarantees and best practices, not a measured duplicate rate and not a claim about every webhook provider.

### FE-380 — A cached “latest” pointer may be stale by design; reconstructing continuation from cache alone is unsound
**Primary source:** Redis, “Cache-aside with Go,” https://redis.io/docs/latest/develop/use-cases/cache-aside/go/

Redis’s cache-aside production guidance says the cache TTL is the upper bound on how long a stale value can be served. It recommends invalidation on writes and explicitly says cache-aside is robust because it never assumes the cache holds the latest value; after invalidation, the next miss re-fetches from the primary. This directly applies to any checkpoint system that caches a `LATEST` pointer separately from the durable checkpoint objects.

**Phase-1 failure mapping:** trigger = durable state advances while a cached latest/current pointer remains valid under its TTL; detectable signal = cached pointer version/hash disagrees with a primary read or target checkpoint provenance; fail-closed response = treat cache as a hint only for continuation-critical identity and revalidate against the authoritative store before resuming; recovery evidence = primary pointer and target checkpoint hash/provenance agree, and a stale cached pointer is rejected rather than resumed.

**Scope guard:** this is Redis cache-aside guidance; it establishes the stale-cache hazard, not a claim that GitHub or this repository uses Redis.
