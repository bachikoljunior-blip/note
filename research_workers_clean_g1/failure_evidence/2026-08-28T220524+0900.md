## New failure evidence

### FE-364 — Error-rate breakers can be structurally blind to successful non-converging agent loops
**Primary source:** Shaikh, Bombarde, Pathak, “Agent Mesh: Reliability Primitives for Non-Idempotent Agent Delegation — Identity Adequacy and Evidence Adequacy,” arXiv:2608.26225v1, 26 Aug 2026, https://arxiv.org/html/2608.26225v1

In one production incident an independent-verifier agent issued 54 consecutive successful tool calls over about 11 minutes and stopped only when a human killed the run. Every call returned success, so an error-rate breaker had no signal on which it could fire. The paper’s platform-level diagnosis is that some delegations fail by ceasing to converge while continuing to emit individually successful actions.

**Phase-1 failure mapping:** trigger = repeated effect/action pattern with no outcome change while calls remain successful; detectable signal = content/effect progress rather than RPC/tool error status; fail-closed response = refuse further same-scope work once a discriminating no-progress witness is established, while preserving a distinct “stalled” verdict rather than calling the task complete; recovery evidence = require a later retry/resume to show a changed grounding/mutation signature before restoring budget.

**Scope guard:** single production platform, retrospective incident corpus, no randomized baseline. The measured incident characterizes a failure class; it does not estimate a general incidence rate or effect size for progress breakers.

### FE-365 — A no-progress signal keyed to an identifier constant by construction can deterministically kill a converging repair
**Primary source:** same Agent Mesh paper.

The platform fingerprinted failed attempts by identifiers that, for one recovery family, were the failing check name — a property of the strategy that stayed constant whether four defects had been fixed or none. The stall detector therefore tripped on the third round regardless of actual progress, while the graded budget refund saw the same constant evidence and could never activate. One run peaked at 6/6 components and ended at 3/6 even though the leading repair had moved from a collection crash to five failing tests and then to two failing tests with three newly passing. Two other recovery paths were found by replay to fingerprint constants and would have failed the same way. The paper reports a two-direction reversion check: with the constant-vocabulary filter reverted, a converging replay again dies on round three; with the diagnostics fallback reverted, a genuinely stuck replay never stops.

**Phase-1 failure mapping:** trigger = stop/continue decision computed over a field incapable of changing under legitimate progress; detectable signal = pre-test whether the fingerprint has discriminating power on matched improving vs stuck traces; fail-closed response = if evidence is non-discriminating, abstain from terminal/stall judgment rather than declaring completion or failure; recovery evidence = matched replay must preserve the converging trace while still stopping the stuck trace.

**Scope guard:** this is strong within the tested platform/replay pair, but it does not establish that the specific constant-vocabulary filter is optimal in other workloads.

### FE-366 — Transactional workspace cleanup can coexist with duplicate external effects across retries, making a correct component unwinnable
**Primary source:** same Agent Mesh paper.

A service event log deliberately lived outside the transactional workspace and therefore outside cleanup. It accumulated 21 events across six invocations over four hours; a test expecting one publish failed after observing effects from earlier invocations. The producer itself was demonstrably idempotent in the narrower sense that each invocation published exactly three events; the duplication was in the persistent external ledger across invocations. The paper identifies additional effect classes outside containment, including package installation/resolution, per-service database writes, post-write hooks, and model-provider calls. Recovery actions are a useful positive control: that enumerated effect class uses a durable lease and deduplicates, while the measured duplicate-effect failure occurred in an effect class nobody had enumerated. The proposed content-addressed general effect ledger is explicitly **not built**, so no efficacy claim is made for it.

**Phase-1 failure mapping:** trigger = retry/resume after an effect commits outside the rollback boundary; detectable signal = durable effect identity and pre/post external-state witness, not workspace cleanliness alone; fail-closed response = suppress or quarantine a retry when the same logical effect may already be committed and its external state cannot be proven; recovery evidence = either a durable dedup receipt/lease for the exact effect or a verified compensation/readback showing one logical effect after replay.

**Scope guard:** observed harm is one platform and one measured external-log incident; the proposed general effect ledger remains unvalidated in that study.

### FE-367 — Durable replay defaults can re-run side effects; “at-most-once per retry” is not end-to-end exactly-once
**Primary source:** AWS Durable Execution SDK Developer Guide, “Idempotency and retries,” current 2026 docs, https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/

AWS documents that replay and retry can each run an operation more than once. The default at-least-once step starts work without waiting for the START checkpoint to commit, so an interruption can cause the step to run again on replay; AWS says this is safe only for idempotent operations. At-most-once per retry waits for START to commit and turns an interrupted attempt into `StepInterrupted`, but the docs explicitly warn that this is still per retry attempt: a retry strategy can run the step again, and end-to-end single execution requires combining at-most-once with no retry. The same guide warns that generating an idempotency key outside a durable step changes it on replay and defeats deduplication, potentially doubling the external effect.

**Phase-1 failure mapping:** trigger = interruption after a non-idempotent external side effect but before durable completion evidence; detectable signal = step semantics + retry policy + stable idempotency identity; fail-closed response = choose at-most-once/no-retry for one-shot effects or require a stable dedup key generated inside durable state; recovery evidence = duplicate-request response must resolve to the original successful effect, or external readback must show a single effect keyed by the stable identity.

**Scope guard:** this entry is a documented execution contract and hazard, not an empirical frequency estimate.

### FE-368 — Resume identity errors can silently fork state, and a paused workflow does not imply hidden background progress
**Primary source:** LangChain/LangGraph Interrupts documentation, current 2026 docs, https://docs.langchain.com/oss/python/langgraph/interrupts

LangGraph documents that `thread_id` is the persistent cursor: reusing it resumes the same checkpoint, while using a new value starts a brand-new thread with empty state. An interrupt saves state and then waits indefinitely until the graph is explicitly re-invoked with a resume command. On resume, the entire node restarts from its beginning rather than continuing at the exact source line. The docs therefore warn that non-idempotent side effects before the interrupt can execute again and create duplicate records or duplicate history entries.

**Phase-1 failure mapping:** trigger = resume with the wrong continuation identity, or assume a paused run progresses in the background, or place irreversible effects before a replay boundary; detectable signal = durable continuation ID bound to the expected checkpoint plus explicit paused/interrupted status; fail-closed response = reject a resume whose continuation identity does not match the intended checkpoint, and never treat elapsed time as progress evidence; recovery evidence = same-ID replay reconstructs the expected state, wrong-ID replay is detected as a new execution, and pre-interrupt effects are either idempotent or separated after the interrupt.

**Scope guard:** this is LangGraph’s documented runtime semantics, not a claim about every agent framework.

### FE-369 — Scenario coverage is not causal ownership; unsafe handoff can awaken correct bystanders and regress them
**Primary source:** same Agent Mesh paper.

One failing cross-service scenario was caused by two components, but the original routing rule reopened every dependency declaring the scenario: five components woke and three correct bystanders regressed working code. In another incident, a stale-state failure was routed to two components that merely declared the scenario while the service owning the stale state was never nominated. A repair window with bad attribution spent 943 tool turns over 71 minutes, including 451 read/search turns, re-deriving causality the platform had already computed and discarded. The revised routing design treats effect-transition checkpoints as evidence and makes abstention a first-class outcome when evidence is ambiguous; the paper reports blast radius 5→2 on the arrangement case, while also stating that the motivating routing success criterion has not yet been observed live.

**Phase-1 failure mapping:** trigger = handoff/repair ownership inferred from broad membership or coverage instead of the first unproven state transition; detectable signal = correlation-bound checkpoint ladder and scoped topology identity; fail-closed response = abstain/fallback on ambiguous ownership rather than confidently excluding the true owner or editing bystanders; recovery evidence = bounded blast radius plus proof that the true owner is included before any bystander mutation is accepted.

**Scope guard:** the before/after deployment observation is not randomized and the paper explicitly marks routing success criteria as not fully validated.

### FE-370 — The enforcement layer itself can create false failure or false completion states
**Primary source:** same Agent Mesh paper.

The study records 12 distinct incidents where enforcement blocked correct work. The costliest clamp restricted both reads and writes to a misdiagnosed target set, consuming 107 agent turns with zero accepted writes because the defect-bearing file was outside the allowed set. The study also reports the opposite polarity: a wrongly permissive appeal accepted a correct diagnosis against the wrong file and thereby foreclosed remaining repair routes. The running response mechanisms include boot-time exoneration against independently verified correct artifacts, clamp yielding after repeated owned-file refusal, and deletion of guards that no mutation can make fail. Clamp yielding fired five times in one run, but all deployment outcomes are observational before/after measurements and the paper explicitly rejects reading them as effect sizes.

**Phase-1 failure mapping:** trigger = checker/guard encodes an invalid mode assumption or accepts/rejects evidence against the wrong object; detectable signal = independently verified correct corpus plus mutation proof that the guard is armed and attributable; fail-closed response = refuse to start a gate that blocks known-correct traffic, or yield/abstain when the evidence object is mismatched; recovery evidence = correct artifact passes after exoneration while a targeted mutant still fails, with no terminal verdict issued from the wrong evidence object.

**Scope guard:** twelve incidents are from one strict platform and are not a population frequency; the response mechanisms’ causal benefit is unmeasured.

### FE-371 — Replaying a generative agent from a checkpoint can recover position without reproducing behavior; conflicting oracle results should be quarantined, not retried as if informative
**Primary source:** same Agent Mesh paper.

The paper contrasts deterministic dataflow replay with agent delegation: the latter composes actions afresh at inference time and may rely on a test suite authored by the delegation itself. Its conclusion is that replay can recover position without guaranteeing the same behavior or oracle result. The platform keys check observations by workspace digest × resolved execution-environment digest × check-contract digest; when two observations under the same key disagree, evidence is quarantined rather than treated as a meaningful retry outcome.

**Phase-1 failure mapping:** trigger = identical reconstructed state yields conflicting verification outcomes; detectable signal = same state/environment/contract identity with divergent result; fail-closed response = quarantine the contradictory evidence and block terminal completion/failure attribution until the oracle is made deterministic or independently corroborated; recovery evidence = repeated observation under the same identity converges to a stable result or is explicitly marked unresolved.

**Scope guard:** the quarantine rule is a deployed response in the studied platform, not a general proof that all agent replay is nondeterministic.

### FE-372 — “Rewind” is only as strong as its environment boundary; external effects can remain stale after local context/filesystem restoration
**Primary source:** Zhuang et al., “AgentRewind: Recoverable Execution for Long-Horizon LLM Agents,” arXiv:2608.14380v1, 14 Aug 2026, https://arxiv.org/abs/2608.14380

AgentRewind deliberately records aligned checkpoints of agent context and controlled environment state. Its actual recovery boundary is the workspace directory tree: file modifications can be reverted, deleted files restored and new files removed. The paper explicitly states that effects outside the workspace filesystem — network requests, external-service calls and external runtime state — cannot be undone. The retained prefix is restored from the log rather than re-executed, which avoids re-triggering those prefix effects, but it does not erase external effects already committed before rewind.

**Phase-1 failure mapping:** trigger = restore a local checkpoint after an irreversible/external mutation; detectable signal = effect inventory showing a mutation outside the checkpointed environment; fail-closed response = do not claim global rollback or safe retry unless every externally committed effect has an idempotent identity, compensator or verified current-state witness; recovery evidence = joint context+local-environment readback plus separate external-system reconciliation.

**Scope guard:** AgentRewind’s empirical improvements concern its controlled engineering environments; this entry uses the paper’s explicit rollback-boundary limitation and does not claim failure of the framework inside that boundary.
