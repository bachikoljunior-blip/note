## FE-451 — Divergent state-resolution predicates can produce both a silent-success validator and an unsafe completion/archive action; merged repair converges all consumers on one canonical resolver
**Source:** Fission-AI/OpenSpec merged PR #1280 (merged 2026-07-03), covering issues #1182/#1202/#1156.
- https://github.com/Fission-AI/OpenSpec/pull/1280

The pre-fix OpenSpec CLI had sibling commands resolving the same logical change through different predicates. `status`/`instructions` accepted a change directory, while `validate` gated membership on `proposal.md`; with a proposal-less but resolvable change, `validate --all` printed `No items found to validate` and exited 0. In a second path, `status` resolved tracked task files through the schema's `generates` glob while `view/list/archive` hardcoded top-level `tasks.md`; a 3/5 incomplete change split across nested task files could therefore be archived because the incomplete-task gate saw no tasks.

The merged repair points the divergent consumers at canonical resolution helpers and adds parity regressions for exit code, nested delta discovery, task-file resolution, and the archive incomplete-task gate. The PR reports an empirical pre-fix archive of a 3/5 unfinished change and a pre-fix `validate --all` silent exit-0, followed by passing parity tests after the change.

**Trigger:** one logical state has multiple local membership/completion resolvers -> an edge layout is visible to one consumer but absent to another -> the absent consumer interprets “not found” as “nothing to do” or bypasses a completion guard.

**Detectable signal:** sibling commands disagree on the resolved object set for the same change; validator returns success with zero candidates while another canonical command resolves active work; archive/completion path observes fewer obligation files than status.

**Fail-closed response:** define one canonical resolution function for the obligation set and assert consumer parity, including empty-set exit semantics. “No resolved items” must not become success when authoritative state still proves an active object.

**Recovery witness:** merged PR #1280; empirical pre-fix reproductions plus post-fix command/resolver parity tests.

**Scope:** exact to the OpenSpec resolution paths covered by #1280. This is not a proof that arbitrary empty-ready queues are false completion, and it is distinct from artifact-content completeness (#1084/#1098).

## FE-452 — A queued effect can be rebound to whichever session becomes current; merged repair restricts migration to the original conversation lineage
**Source:** NousResearch/hermes-agent merged PR #74581 (merged 2026-07-30), related to #74133 and closing #74580.
- https://github.com/NousResearch/hermes-agent/pull/74581

Hermes Desktop queued follow-up prompts were migrated whenever the selected session ID differed from the queue key. During an A→B session switch, route state could change before store selection, causing `migrateQueuedPrompts(A, B)` to move A's pending prompt into B; B's idle composer then auto-drained that prompt into the wrong conversation.

The merged repair permits queue/draft re-keying only when the two IDs share the same conversation lineage (for example compression tip→root), and blocks cross-conversation A→B migration. Regression tests cover the unsafe migration primitive, the A→B guard, and lineage-aware queue-drain gates.

**Trigger:** pending effect ownership is inferred from mutable “currently selected/current route” state -> UI/session switch races queue migration -> old-session work becomes successor-session input.

**Detectable signal:** queue entry origin and destination do not share lineage; selected/busy IDs disagree transiently with the queue owner; a prompt created under A appears in B without an explicit transfer.

**Fail-closed response:** bind pending effects to immutable origin/session lineage; permit only explicitly validated same-lineage rekeys; never substitute current-active session for origin ownership.

**Recovery witness:** merged PR #74581 with focused migration/drain tests.

**Scope:** exact to Hermes Desktop composer queue/follow-up routing. It supports the broader owner-binding failure class but does not prove that all asynchronous child results use the same lineage field.

## FE-453 — A client-side deadline can report failure while the backend contract still permits the operation to continue; timeout mismatch creates an indeterminate outcome, not a retry-safe failure
**Sources:** NousResearch/hermes-agent issue #93911 and open PR #93965.
- https://github.com/NousResearch/hermes-agent/issues/93911
- https://github.com/NousResearch/hermes-agent/pull/93965

Issue #93911 reports Desktop `bot_relay.deliver` going through a generic 30-second `requestProfile` deadline even though the backend delivery contract permits a much longer turn. Long legitimate target turns can therefore be surfaced as failed by Desktop while backend work may still be running/settling. The open repair #93965 threads a per-call timeout through the SDK and sets the relay delivery call to the backend's documented ~1320-second bound; its focused tests prove the timeout reaches the routed gateway layer and other callers retain the default.

This is the same dangerous decision boundary as other “response lost after effect may have started” failures: a local timeout says the caller stopped waiting, not that the remote effect did not happen.

**Trigger:** caller deadline < authoritative remote operation envelope -> caller aborts/returns failure before remote terminal state -> retry logic may treat an unknown outcome as a clean negative.

**Detectable signal:** timeout occurs before the backend's own documented maximum and no independent terminal/result readback proves non-execution.

**Fail-closed response:** classify the outcome as indeterminate unless authoritative cancellation/settlement is observed; align client deadline with the remote contract or add reconciliation/idempotency before retry.

**Recovery witness:** contributor repair #93965 has focused SDK tests, but it is still open/unmerged as of this scan; do not upgrade to shipped guarantee.

**Scope:** exact to Hermes Desktop routed `bot_relay.deliver` timeout plumbing. It does not establish that the backend necessarily commits a message after every 30-second client timeout.

## FE-454 — Human approval is not a freshness token: an approved pending mutation can overwrite state that changed after staging unless approval revalidates a bound precondition
**Sources:** NousResearch/hermes-agent issue #75130, open PR #76294, and newer open PR #96059.
- https://github.com/NousResearch/hermes-agent/issues/75130
- https://github.com/NousResearch/hermes-agent/pull/76294
- https://github.com/NousResearch/hermes-agent/pull/96059

The stale-proposal family shows two related gaps. #76294 documents pending skill patches whose textual anchor disappeared after staging; without pre-approval stale inspection they still looked actionable until replay failed. The newer #96059 targets the stronger case: an approval may remain syntactically applicable yet still be stale relative to the exact state reviewed. It proposes versioned optimistic-concurrency preconditions for single and batched mutations, revalidates after admission, executes zero operations on mismatch, retains the pending record, and makes legacy records without preconditions fail closed.

Its adversarial matrix includes: any touched skill changing before approval invalidates the entire batch; a competing create occupying the same logical name blocks approval; reversed two-skill batches serialize across independent processes; and rollback preserves a newer external publication instead of restoring stale snapshots. The focused exact-head matrix reports 105 passing tests, but the PR is open and its hosted workflows were still awaiting fork-workflow authorization, so this remains contributor-level recovery evidence.

**Trigger:** proposal is reviewed at snapshot S -> target changes to S+1 before approval replay -> approval is treated as unconditional authority rather than authority conditional on reviewed state.

**Detectable signal:** no persisted precondition/version/state vector ties the approved request to the exact reviewed target; replay cannot distinguish fresh approval from approval of an obsolete snapshot.

**Fail-closed response:** persist exact optimistic preconditions with the proposal, revalidate atomically after acquiring mutation authority, perform zero effects on mismatch, and keep the proposal for explicit re-review/re-stage. Approval identity and target-version identity must both match.

**Recovery witness:** #96059 supplies multi-process/adversarial local tests but remains open/unmerged; #76294 is also open. No shipped guarantee claimed.

**Scope:** exact to Hermes pending skill mutation approval/replay paths described by those PRs. It does not imply every approval system requires the same filesystem state vector; the invariant is only that approval alone is insufficient when the reviewed object can change before execution.
