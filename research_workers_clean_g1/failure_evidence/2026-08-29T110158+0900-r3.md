## FE-460 — A resource-side fencing predicate can be correct and well tested while production remains completely unfenced because no production path ever advances the token
**Sources:** Ptah issue #2474 and merged PR #2480.
- https://github.com/stokaro/ptah/issues/2474
- https://github.com/stokaro/ptah/pull/2480

Ptah already enforced a fencing token in the store's write predicate (`WHERE ... fencing_token <= ...`) and had `Run.Claim`, whose contract was to take a run and issue a token that fences prior workers. Yet production `prepare` initialized the token to 1 and no working verb called `Claim`; the token therefore never advanced outside tests. The issue explicitly states that two workers on one run were not fenced apart because the second worker never claimed.

Merged PR #2480 on 2026-08-28 wires `prepare`, `backfill`, and `catchup` through a saved claim before work begins. Its live test has worker A claim, worker B claim afterward, then verifies A's next commit is rejected with `ErrConflict`; a CLI-level sequence also reads the token after each verb because testing only one verb had left the other production paths unmeasured.

**Trigger:** fencing is implemented at the resource and directly unit-tested, but the lifecycle event that advances fencing authority is absent from one or more real entry points.

**Detectable signal:** token remains constant across successive worker ownership transitions; removing a production-path claim does not redden existing tests; stale worker can still pass a resource predicate because no newer token was issued.

**Fail-closed response:** claim in every work-producing entry point, durably save the claim before work, and test each real entry point plus the stale-holder negative control.

**Recovery witness:** merged PR #2480 with live stale-holder rejection and CLI-level token progression.

**Scope:** Ptah inference `prepare`/`backfill`/`catchup` run claiming. This is a real shared-store/live-path fencing repair, but it is not evidence of a multi-host/network-partition incident and does not close that broader frontier.

## FE-461 — Thirteen green tests covered the stale-write decision function while production issued unconditional updates; concurrent/late writes could overwrite newer state until the decision was wired into the committing transaction
**Sources:** Ptah issue #2391 and merged PR #2419.
- https://github.com/stokaro/ptah/issues/2391
- https://github.com/stokaro/ptah/pull/2419

`embedrun.ResolveWrite` encoded three safety rules: a write must not cross generations, an older source version must not overwrite a newer one, and a tombstone must survive a late update. Thirteen unit tests exercised that function. Production did not call it. The actual target path rendered an unconditional `UPDATE ... WHERE id=...` with no generation or version predicate, so every arriving write won over the row it found.

The issue's measured failure showed a second generation backfill overwriting the first generation's rows. Merged PR #2419 moves resolution into `Target.Commit`: it reads current rows `FOR UPDATE` inside the committing transaction, resolves each candidate against the locked row, and also refuses a cross-generation target early at `prepare` to avoid paying provider cost before the same hard write-side guarantee. The repair adds repeated concurrent same-key commits where the newer version must always win, plus discriminating tombstone/version cases and mutation tests that fail when the row lock, resolver, or individual rule is removed.

**Trigger:** a safety decision is tested in isolation but the actual write path bypasses it; sequential fixtures do not exercise the race the rule exists to order.

**Detectable signal:** non-test call graph has no call to the decision function; production SQL lacks equivalent predicates; two concurrent commits can both read the same prior state and last-committer wins rather than newer-version wins.

**Fail-closed response:** enforce the decision within the committing transaction/resource predicate, include concurrency tests that fail without the lock/predicate, and add an early refusal only as a cost-saving duplicate of—not a replacement for—the write-side guarantee.

**Recovery witness:** merged PR #2419, measured before/after two-generation behavior, repeated concurrent write test, and mutants for unconditional writes/lock removal/rule removal.

**Scope:** Ptah's PostgreSQL inference target commit path. It does not establish generic exactly-once execution or safety across other stores.

## FE-462 — The implementation that was tested did not run, while the implementation that ran was untested and disagreed, producing false staleness and needless recomputation
**Sources:** Ptah issue #2474 comment and merged PR #2484.
- https://github.com/stokaro/ptah/issues/2474
- https://github.com/stokaro/ptah/pull/2484

Ptah had two answers to freshness. The unused `TargetRow.Stale` implementation guarded a version mismatch with both old and current version being present; the live `internal/embedverify` layer treated `row.Version != found.Version` as stale whenever the source had a version, even when the target row had never recorded one. On a strategy switch this made every existing row appear stale and could recompute an unchanged corpus at provider cost.

The only staleness tests exercised the unused implementation; the live layer had zero `LayerFreshness` tests. Merged PR #2484 moves the careful guard into the live layer, deletes the redundant unused answer, and adds the previously missing table case such that the test fails without the fix. The same cleanup removes other redundant decision wrappers so one semantic question has one authoritative implementation.

**Trigger:** duplicate semantic predicates drift; test coverage attaches to the dead/non-authoritative copy instead of the production path.

**Detectable signal:** direct tests are green while the production implementation has no matching tests; two implementations return different answers on a boundary case; freshness jumps after a strategy/config transition despite unchanged content.

**Fail-closed response:** collapse to one authoritative predicate in the path that actually executes and test the production-facing boundary case rather than only the helper.

**Recovery witness:** merged PR #2484 with the live-layer regression test and deletion of the redundant answer.

**Scope:** Ptah inference freshness across the described source-version transition. It is not evidence that every duplicate helper is dangerous or that all recomputation is erroneous.

## FE-463 — Progress counters can move while durable phase/liveness state never advances when the phase machine is tested but not called by real verbs
**Sources:** Ptah issue #2441 and merged PR #2463.
- https://github.com/stokaro/ptah/issues/2441
- https://github.com/stokaro/ptah/pull/2463

Ptah could complete `prepare → backfill → catchup`, embed 50 rows and commit three batches, yet `status` still reported `prepared, running`. `Run.Advance` was the sole phase-transition function; it carried the allowed-transition table and a fencing check, had tests, but had no production caller. Thus status was stale, ordering constraints were out of effect, and a resume could not rely on the phase to distinguish lifecycle position.

Merged PR #2463 replaces the unusable one-step `Advance` behavior with a high-water-mark `Reach` contract that tolerates repeated idempotent calls behind the current phase while refusing forward skips. Each real verb records its owned phase, and the e2e test reads the phase back through `status` after every verb instead of trusting the verb's own response. The patch also includes a control against dragging the phase backward and tests that fail if any production verb stops reaching/saving its phase.

**Trigger:** execution progress and durable lifecycle state are maintained by separate paths, with the lifecycle transition function absent from actual entry points.

**Detectable signal:** counters/effects advance while stored phase remains frozen; direct transition tests pass but real e2e status never changes; removing a verb's phase write previously changed no test.

**Fail-closed response:** persist lifecycle advancement in the same real operation path as the effects it describes, make repeated/replayed verbs monotonic/idempotent rather than backward-moving, and validate by independent state readback.

**Recovery witness:** merged PR #2463 with live per-verb status readback and mutation controls.

**Scope:** Ptah inference run phase tracking. It does not imply that a single scalar phase is sufficient for arbitrary DAG/pending-obligation completion semantics.
