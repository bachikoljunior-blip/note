## New failure evidence

### FE-254 — Completion gating alone does not solve quantitative long-horizon persistence; verifier-aligned progress state does
**Primary source:**
- Cai et al., “Push Your Agent: Measuring and Enforcing Quantitative Goal Persistence in Long-Horizon LLM Agents,” arXiv:2605.23574: https://arxiv.org/abs/2605.23574

PushBench holds tasks, target-dependent budgets, hidden valid sets and verifiers fixed while changing the controller’s progress-state exposure, duplicate filtering and stopping logic. On 36 fixed RepoScan tasks per row, gpt-5.4 + LangGraph reaches only `16.7%` success under the standard controller and `22.2%` with completion/verifier gating, versus `77.8%` with StateQGP; duplicate-submit rate is `0.663` under standard and `0.000` under StateQGP. For gpt-4.1 + LangGraph, StateQGP improves matched-task success over standard by `+41.7 pp` with a paired-bootstrap `95%` interval `[+27.8,+58.3]`, while verifier gating alone improves by only `+8.3 pp` with interval `[-2.8,+22.2]`.

The focused stateful ablation further separates generic memory features from verifier-aligned progress. Page memory alone reaches `44.4%`, while the full controller reaches `72.2%`; full StateQGP exceeds a dedupe+page variant without buffered progress state by `+27.8 pp` with `95%` interval `[+13.9,+41.7]`. On verifier-backed DataOps-lite, standard and verifier-gated controllers finish `0` task instances across all three models and both controlled backends, while UnitQGP reaches `25–50%` depending on model. Black-box Claude Code Sonnet 4.6 and Codex CLI gpt-5.4 each solve `7/9` tasks at target `N=50` but only `3/9` at `N=100`; an explicit checklist prompt changes duplicate/tool-use behavior but has zero paired success gain in those high-target tests.

**Failure implication:** blocking unsupported “done” claims is not equivalent to maintaining verified forward progress. Long-horizon controllers need externalized, verifier-aligned state over what is complete, duplicated, pending and eligible for termination. Generic reminders or completion gating can leave the agent trapped in repeated/no-progress work.

**Scope guard:** PushBench uses repository-artifact retrieval and synthetic verifier-backed work units with fixed budgets. StateQGP reduces these failure modes but does not make arbitrary long-horizon tasks reliable; high targets can still exhaust budget, and external-memory baselines become competitive for stronger policies in some RepoScan rows.

### FE-255 — Runtime-fault diagnosis from a single agent trace remains weak even when the fault is injected under matched inputs; a clean reference helps only some fault classes
**Primary source:**
- Zhang et al., “When Agentic Executions Fail: Detecting and Localizing Runtime Faults from Telemetry,” arXiv:2608.14680: https://arxiv.org/abs/2608.14680

AgentChaosBench fixes the task input and local Qwen3.5-9B execution model, then pairs a clean run with executions containing one of ten injected operational faults across tool, model, guardrail and A2A boundaries. The released design contains `250` faulty traces plus `25` no-fault controls. On structured single-trace diagnosis, local zero-shot detectors up to 14B reach only `13.6–19.2%` top-1 fault-type accuracy; DeepSeek-v4-pro reaches `24.8%`. Jointly getting fault type and location correct reaches only `8–22%` depending on detector.

The matched clean reference is not a universal fix. The paper reports up to `+55 pp` recall improvement for Context Overflow and gains for selected latency/routing faults, but Guardrail Bypass remains unresolved because the abnormality depends on a policy counterfactual rather than a conspicuous local error signal. The raw traces also have a median serialized size around `108K` tokens and reach about `638K`, so observability itself can exceed practical detector context budgets; a compact structured view reduces size substantially but does not make diagnosis close to solved.

**Failure implication:** “we log every tool call” does not imply operational faults are diagnosable from that trace. Reference-dependent failures need explicit baselines/policy invariants, and telemetry compression can become part of the diagnostic system rather than a neutral transport detail.

**Scope guard:** this is a controlled fault-injection benchmark over five agentic applications and a fixed local execution model. Low zero-shot diagnosis accuracy is not proof that trained or rule-based detectors cannot do better, and injected faults are not a frequency estimate for production incidents.

### FE-256 — Frozen-model agents can degrade sharply over their operational lifetime; memory policy and maintenance events can dominate model upgrades
**Primary source / author project:**
- Zhu et al., “Your Agents Are Aging Too: Agent Lifespan Engineering for Deployed Systems,” arXiv:2605.26302: https://arxiv.org/abs/2605.26302
- Author project/results page: https://agingbench.github.io/

AgingBench evaluates frozen-weight agents across `8–200` sequential sessions over seven scenarios and multiple memory policies. The author results page reports a maximum recall drop of `85%` across ten sessions in S7 for GPT-4o-mini + OpenHands under frozen weights and scaffolding. In S1, changing only the compaction/memory policy yields a `4.5×` spread in measured half-life, larger than any model swap in the reported comparison. In S6, a single flush-history maintenance event causes a `67%` post-shock cliff with no recovery in the displayed naturalistic setting.

A newer/stronger model is not guaranteed to erase the lifetime effect: on S7, the page reports mean recall `0.82` for Claude Code Sonnet 4.6 versus `0.79` for Opus 4.7. On S2, behavioral constraint violation can stay at zero while factual constraint precision and lagged recall decay, so a “policy-compliant” behavioral monitor can remain green while the underlying state becomes wrong.

**Failure implication:** day-one benchmarks and model-version upgrades do not certify persistent-agent reliability. Compression policy, interference, revision semantics and lifecycle maintenance should be evaluated as independent intervention axes, with longitudinal curves and stage-level write/retrieve/utilize diagnostics.

**Scope guard:** the headline figures are benchmark/project results over roughly 400 controlled runs, not production failure rates. Exact decay magnitudes are scenario- and policy-specific, and the project is a 2026 preprint/benchmark rather than evidence that all deployed memories age at the same rate.

### FE-257 — A causal-looking rescue intervention can reverse across model generations because the dominant long-horizon bottleneck moves upstream or downstream
**Primary source:**
- Shao et al., “Beyond End-to-End Success: Diagnosing Failures in Long-Horizon Security LLM Agents,” arXiv:2608.20563: https://arxiv.org/abs/2608.20563

The paper instruments long-horizon security tasks with capability-exposure checkpoints so a failure before the relevant state is observed is not mislabeled as failure to reuse that state. In a pre-specified `92`-seed Gemini 2.5 Flash study, protocol-disambiguation guidance raises state observation from `65.5%` under a matched non-guidance control to `95.4%`. The authors report that repeating the same frozen intervention design with Gemini 3.7 Flash produces the opposite effect, and state observation no longer reliably predicts final task completion.

**Failure implication:** a repair validated on one model generation can become harmful or irrelevant on the next because the bottleneck migrates. End-to-end success alone cannot reveal whether the tested capability was ever exposed, whether an upstream discovery step failed, or whether failure moved downstream after exposure.

**Scope guard:** the exact cross-generation reversal is reported in the primary abstract, but the current HTML-accessible primary record does not expose the full cell table. Do not generalize the direction or magnitude beyond the paper’s observed-state-reuse protocol until the exact primary table is independently extracted/reproduced.

### FE-258 — World-state completion and correct self-termination are separable capabilities; execution feedback can improve doing without fixing knowing when to stop
**Primary source:**
- Chen et al., “Done, But Not Sure: Disentangling World Completion from Self-Termination in Embodied Agents,” arXiv:2605.08747v4: https://arxiv.org/abs/2605.08747

VIGIL scores hidden world-state completion (`W`) separately from benchmark success (`B`), where `B` additionally requires a correct semantic terminal report. Across `20` models on `1,000` frozen embodied episodes, systems with comparable `W` differ by as much as `19.7 pp` in `B`. This exposes distinct outcomes that ordinary success metrics collapse together: missed execution, post-attainment drift, unsupported commitment and verified success.

A matched action-feedback intervention improves execution/world completion broadly, but commitment failures persist for models that do not already ground their terminal report in achieved state. Better motor/tool feedback therefore need not repair premature “done” claims or failure to stop after the world state is already correct.

**Failure implication:** a stop action should be treated as a separately verified decision over external state, not inferred from local execution competence or from the agent’s final message. Systems need both a world-state completion check and a terminal-commitment check when false completion or post-attainment drift matters.

**Scope guard:** VIGIL is an embodied, egocentric-RGB benchmark with deterministic hidden-state checks. The measured `19.7 pp` closure gap is not automatically a text-agent or coding-agent effect size, though the measurement distinction transfers conceptually.

### FE-259 — Task completion can coexist with unsafe runtime side effects at very high rates; safety depends on the complete harness–model–carrier configuration
**Primary source:**
- Zhou et al., “AgentS4D: Benchmarking Runtime Risks across the Execution Lifecycle of LLM-Based Workspace Agents,” arXiv:2607.27294: https://arxiv.org/abs/2607.27294

AgentS4D crosses `328` controlled risk-injected cases with all `20` combinations of four workspace-agent harnesses and five LLM backends, producing `6,560` runs. `4,461` runs (`68.0%`) trigger a prespecified unsafe signal, and `4,344` runs (`66.22%` of all runs) are both unsafe and complete. From those primary counts, `4,344/4,461 = 97.38%` of unsafe runs still satisfy the benchmark’s completion predicate.

The paper reports that safety varies with the harness–LLM pairing and with the carrier/induction route: the same target harm or induction strategy can produce different behavior when delivered through files, skills, tools, memory or other runtime surfaces. Thus a correct final artifact can coexist with unauthorized reads/writes/disclosures or other unsafe side effects during execution.

**Failure implication:** final task success is not a safety metric for stateful workspace agents. Safety evaluation should independently verify lifecycle side effects and run the actual integrated harness/model configuration across multiple risk carriers rather than transfer a model-only safety score.

**Scope guard:** these are deliberately risk-injected sandbox cases, not production incident frequencies or universal rankings of the tested harnesses/models. The result supports the evaluation decomposition, not the claim that 68% of ordinary deployments are unsafe.
