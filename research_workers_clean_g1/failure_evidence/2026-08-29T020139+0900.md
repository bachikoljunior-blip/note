## New failure evidence

### FE-382 — A failed/incomplete streaming terminal event can be misclassified as a successful final agent response
**Primary sources:** OpenAI Agents Python issue #3106, https://github.com/openai/openai-agents-python/issues/3106 ; merged fix PR #3107, https://github.com/openai/openai-agents-python/pull/3107

Issue #3106 supplied a minimal failed-stream reproducer in which `response.failed` (and analogous `response.incomplete` paths) was stored/finalized as a usable response. The streamed run could expose partial output even though the API-level response status was `failed`. PR #3107 changed streamed and websocket handling to reject failed/incomplete terminal payloads rather than turn them into `ModelResponse`/`final_output`, with regression tests.

**Phase-1 failure mapping:** trigger = terminal transport/model event is `failed` or `incomplete` but carries output payload; detectable signal = terminal event type/status, not merely presence of text/output; fail-closed response = do not emit successful final result from a failed/incomplete terminal; recovery witness = raw terminal may remain inspectable, but only an accepted success terminal can create final output and the failed/incomplete path raises a typed error.

**Scope guard:** directly covers the OpenAI Agents Python streaming/websocket paths described at issue time and the merged fix. It is not evidence that current releases still exhibit the bug and not a claim about every agent SDK.

### FE-383 — Resume dedup can drop a tool result that executed successfully but was never sent to the server
**Primary sources:** OpenAI Agents Python issue #3004, https://github.com/openai/openai-agents-python/issues/3004 ; merged fix PR #3006, https://github.com/openai/openai-agents-python/pull/3006

Issue #3004 provided a deterministic no-API reproducer for a mixed parallel turn containing approval-gated tools and one non-approval tool. The non-approval tool executed successfully and its `function_call_output` existed locally, but state hydration marked its `call_id` as already acknowledged by the server. Resume input construction then omitted that output, causing the server-managed conversation to fail with “No tool output found”. PR #3006 changed hydration so locally generated-but-unsent outputs are treated as unsent and preserved on resume, with regression coverage.

**Phase-1 failure mapping:** trigger = interrupt/resume after a turn in which some tool outputs are local while other calls are approval-gated; detectable signal = per-output provenance distinguishing “generated locally” from “sent/acknowledged by server”; fail-closed response = never deduplicate an output solely because its call ID is present in reconstructed local state; recovery witness = resumed payload includes the successful unsent output together with approval/rejection outputs and the conversation continues without the missing-output error.

**Scope guard:** exact to server-managed conversation resume behavior covered by issue #3004/PR #3006. It does not imply all HITL resume systems use this dedup mechanism.

### FE-384 — A model retry can rewind away a committed user turn and leave an answer without its question
**Primary sources:** OpenAI Agents Python issue #3852, https://github.com/openai/openai-agents-python/issues/3852 ; merged fix PR #3857, https://github.com/openai/openai-agents-python/pull/3857

Issue #3852 supplied a self-contained SQLiteSession reproducer for v0.18.1: without a retry the persisted roles were `['user', 'assistant']`; with one retryable failure followed by success the session became `['assistant']`. The retry rewind removed input that had already been committed once, while the successful retry did not re-persist it. PR #3857 changed streamed retry handling so committed local-session input is not rewound and added regression coverage preserving prior history, the current user input, and the assistant response.

**Phase-1 failure mapping:** trigger = retry after current-turn input has already crossed the durable-session boundary; detectable signal = input item is committed and owned by the run rather than the individual model attempt; fail-closed response = do not delete committed input unless the retry path also proves it will re-persist exactly one replacement; recovery witness = after injected one-retry path the session contains exactly one current user turn and one corresponding assistant turn.

**Scope guard:** reproduced for the local Session streamed path described in 0.18.1 and fixed by PR #3857; server-managed conversations use a different rewind path and are outside this item.

### FE-385 — Retry can inherit stale continuation instructions and skip the normal entry point
**Primary sources:** Apache Airflow issue #56704, https://github.com/apache/airflow/issues/56704 ; fix/backport commit `53c05a0e80c581c24ecbfb7f9c3a4dc35d70fd2d`, https://github.com/apache/airflow/commit/53c05a0e80c581c24ecbfb7f9c3a4dc35d70fd2d

Airflow issue #56704 documents a deferrable task whose `next_method` and `next_kwargs` persisted into retry. Instead of restarting through `execute()`, the retry immediately reused the prior deferred continuation and could fail again on stale state. The fix clears `next_method` and `next_kwargs` on retry/terminal state transitions and adds parametrized tests for `UP_FOR_RETRY`, `FAILED`, and `SUCCESS` asserting both fields become null.

**Phase-1 failure mapping:** trigger = retry begins after prior attempt stored continuation-local method/arguments; detectable signal = retry boundary plus attempt-local continuation fields still populated; fail-closed response = reset attempt-local continuation metadata before the next attempt unless it is explicitly generation-bound and valid; recovery witness = retry enters the normal start path and tests/readback show stale continuation fields cleared.

**Scope guard:** direct to the Airflow task-instance fields and affected versions represented by issue/fix. It does not establish the same field-level bug in other workflow engines.

### FE-386 — Broker redelivery can turn a duplicate start attempt into a false authoritative failure for work that is still running
**Primary sources:** Apache Airflow issue #58441, https://github.com/apache/airflow/issues/58441 ; merged PR #60855, https://github.com/apache/airflow/pull/60855 ; merged companion PR #64052, https://github.com/apache/airflow/pull/64052

Issue #58441 reports Airflow 3.1.x behavior where a Celery broker redelivery delivers the same task while the original worker is still running it. The duplicate worker receives a 409 because the task instance is already running; the generic failure propagated through Celery and the scheduler could mark the still-running task failed. PR #60855 introduced a typed `TaskAlreadyRunningError` and reports manual end-to-end Breeze validation in which redelivery no longer marked the task failed and the original worker continued. PR #64052 makes the Celery side raise `Ignore()` for this case so the duplicate delivery is not recorded as task failure.

**Phase-1 failure mapping:** trigger = at-least-once broker redelivers an already-running logical task; detectable signal = stable task identity plus authoritative state `running`, and a typed duplicate-start conflict distinct from execution failure; fail-closed response = suppress/ignore the duplicate dispatch rather than convert it into an authoritative task failure; recovery witness = original execution remains running/able to finish while the redelivery produces no conflicting failure state.

**Scope guard:** covers the Airflow/Celery redelivery path described by #58441 and its merged fixes. It is not a statement that every duplicate delivery should be silently ignored; the identity/current-state match is essential.

### FE-387 — Workflow retry can duplicate aggregate outputs even when the logical child set is unchanged
**Primary sources:** Argo Workflows issue #7617, https://github.com/argoproj/argo-workflows/issues/7617 ; merged fix PR #7652, https://github.com/argoproj/argo-workflows/pull/7652

The Argo Workflows 3.2.4 issue provides a reproducible DAG/`withParam` example and reports that retry handling could duplicate the output collected by the final step: three expected outputs became six after two retries, with each output repeated twice. The maintainer merged PR #7652 as “fix: Retry with DAG. Fixes #7617”, updating retry handling for task-group nodes and adding retry tests.

**Phase-1 failure mapping:** trigger = retry of a DAG/task-group containing looped children; detectable signal = output identity/cardinality exceeds the logical child set and repeats prior-attempt outputs; fail-closed response = aggregate by logical child/attempt semantics rather than append every retry artifact as a new logical result; recovery witness = retry reopens the required failed group without duplicating already-accounted logical outputs.

**Scope guard:** reporter-observed duplication is exact to the supplied Argo 3.2.4 reproduction; PR #7652 is the merged project fix. This item does not prove duplicated external side effects, only duplicated collected outputs.

### FE-388 — Long in-flight tool work can be re-dispatched from checkpoint while the original execution is still running
**Primary source:** LangGraph issue #7417, https://github.com/langchain-ai/langgraph/issues/7417

An open LangGraph Cloud report describes long tool/subagent calls that, around a repeated time boundary, were re-dispatched from the last checkpoint while the original was still running. The reporter states the duplicate traces had identical tool arguments, separate tool nodes with no preceding model node, and both original and duplicate completed, producing 2–3x redundant work/cost across tested LangGraph 1.1.3–1.1.6 on EU Cloud. Several attempted configuration/workaround changes did not remove the reported pattern.

**Phase-1 failure mapping:** trigger = long in-flight operation outlives the runtime’s liveness/recovery assumptions; detectable signal = same logical tool-call identity concurrently in flight, especially a dispatch lacking a fresh causal model decision; fail-closed response = re-dispatch requires a durable in-flight generation/claim check or idempotent action receipt; recovery witness = delayed original and any recovery attempt cannot both commit the same logical action.

**Scope guard:** this is an open external issue and the stated mechanism/cause has not been treated here as maintainer-verified. Evidence is limited to the reporter’s traces/configuration range; do not generalize to all LangGraph Cloud deployments or current versions.

### FE-389 — Resuming only part of a multi-interrupt node can prematurely re-execute that node
**Primary sources:** LangGraph privileged maintainer issue #6208, https://github.com/langchain-ai/langgraph/issues/6208 ; merged PR #6158, https://github.com/langchain-ai/langgraph/pull/6158

The maintainer-authored issue states that a node with two interrupts could rerun after only one resume because the runtime lacked metadata for how many resumes/interrupt IDs remained pending. Merged PR #6158 implements selective interrupt task scheduling and includes tests for sequential resume and a node with multiple interrupts requiring full resume.

**Phase-1 failure mapping:** trigger = node has multiple outstanding interruption obligations and receives only a subset of resume values; detectable signal = explicit pending interrupt IDs/count per task; fail-closed response = keep the task suspended until every required interrupt for that execution generation is resolved; recovery witness = partial resume returns remaining interrupts without re-executing the node, and full resume schedules it exactly once.

**Scope guard:** exact to the LangGraph interrupt scheduling semantics covered by the maintainer issue and merged tests, not a claim about unrelated handoff protocols.

### FE-390 — Matched own probe: without fencing, a stale claimant overwrites the newer claimant; with resource-side fencing, the same stale write is rejected

A deterministic local comparison holds event order fixed: claimant B with generation 2 commits, then delayed claimant A with generation 1 resumes. In the no-fence arm, A overwrites B and final value is `A_stale`. In the SQLite resource-side fencing arm, B’s update affects one row, A’s stale generation update affects zero rows, and final state remains `B_current` with fence 2.

**Scope guard:** this directly tests the enforcement logic in one deterministic single-process SQLite simulation. It does not reproduce Redis lease expiry, network partitions, clock skew, GC pauses, or distributed database behavior.

### FE-392 — Interruption during handoff can leave “work remains” and “nothing ready” simultaneously, then falsely report workflow completion
**Primary source:** Microsoft AutoGen issue #7043, https://github.com/microsoft/autogen/issues/7043

An open AutoGen GraphFlow report describes interruption around agent transition followed by saved-state resume. The supplied state example has remaining work for the next agent, `enqueued_any=false`, and an empty `ready` queue; resume immediately reports “Digraph execution is complete” while no agent executes. This is a direct consistency-counterexample shape: a terminal/completion label is incompatible with the persisted work/ready invariants.

**Phase-1 failure mapping:** trigger = interruption between recording completed work and enqueueing successor work; detectable signal = invariant conflict `remaining_work > 0` with empty ready/enqueued set; fail-closed response = do not declare completion from empty ready queue alone; classify state as inconsistent/recovery-required and reconstruct from an atomic transition boundary or explicit successor receipt; recovery witness = either remaining work is durably zero, or the intended successor is generation-bound/enqueued and resumes.

**Scope guard:** issue #7043 remains open and needs triage; treat this as a source-qualified reporter reproduction/state snapshot, not a maintainer-confirmed root cause and not a claim about all AutoGen GraphFlow versions.
