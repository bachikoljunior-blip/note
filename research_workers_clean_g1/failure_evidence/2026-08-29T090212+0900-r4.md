## FE-449 — A late background subagent result from the old conversation can mutate the fresh conversation after `/new`; merged repair pins the durable spawning session and fails closed if that owner is dead
**Sources:** NousResearch/hermes-agent issue #57498 and merged PR #60871.
- https://github.com/NousResearch/hermes-agent/issues/57498
- https://github.com/NousResearch/hermes-agent/pull/60871

Issue #57498 reports that background `delegate_task` subagent completions were written to the most recently active session rather than the session that spawned them. The observed class includes wrong-session contamination and cross-channel mixing when multiple sessions remain open or share routing keys.

Merged PR #60871 supplies the matched repair and a direct N→N+1 regression: before the patch, if a delegation completes after the user `/new`s the chat, the result is injected into the fresh session's context; after the patch it is bound to the spawning session. The implementation stamps the durable parent `state.db` session ID at dispatch and carries it on the completion event instead of recovering “latest open session for the peer.” The follow-up hardens the same contract: an ended/unknown spawning session is not resurrected; its completion is dropped from injection (while retained in delegation records), and `/new` interrupts delegations owned by the expiring durable session. The PR merged on 2026-07-08 and reports full gateway plus delegation tests and a dedicated pin/live/drop/reset matrix.

**Trigger:** parent conversation A dispatches asynchronous subagent work -> routing/lifecycle advances to fresh conversation B -> A's child completes after B is current -> completion chooses “latest/current active session” instead of its durable origin.

**Detectable signal:** a completion whose dispatch parent ID is A appears in B's context, or routing resolves by current peer/open-session state rather than the immutable dispatch owner.

**Fail-closed response:** stamp the return address at dispatch; on completion require that exact durable parent owner (or an explicitly permitted lineage continuation). Never substitute “currently active.” If the origin is terminal/unknown, preserve the result out of band but do not inject it into another live conversation.

**Recovery witness:** matched A → `/new` → B regression shows A's late completion is not injected into B; ended/unknown owner tests fail closed; reset severs owned delegations. PR #60871 is merged.

**Scope:** exact to Hermes messaging-gateway async `delegate_task` completion routing covered by #60871. It is a real late **child work result** contaminating a successor conversation and closes the prior frontier for that class. It does not establish that every background-process path shares the same owner identity or is fixed by the same field.

## FE-450 — A stable chat/session key may still be too coarse across `/new`; terminal-process completion needs physical UI-session/lineage ownership, not key pinning alone
**Sources:** NousResearch/hermes-agent issue #83213, contributor RCA/comments, and open PR #84174.
- https://github.com/NousResearch/hermes-agent/issues/83213
- https://github.com/NousResearch/hermes-agent/pull/84174

Issue #83213 reports a distinct late-result contamination path for `terminal(background=True, notify_on_complete=True)`: process starts in session A, user `/new`s to B, then A's completion is injected into B as a synthetic `role="user"` message and B's agent acts on it. The completion event already carries a `session_key`, which initially suggested that honoring this key would fix routing.

A contributor then traced current main and found that fix too weak for chat-keyed platforms: `/new` can retain the same `session_key` while rotating the physical session ID. Therefore the old process and fresh session B legitimately share the key; key equality cannot distinguish them. The finer owner is the spawning UI session identity/lineage. The contributor explicitly withdrew the partial key-only plan rather than ship a surface-limited repair.

Open PR #84174 implements the stronger candidate: capture `origin_ui_session_id` at process spawn, carry it through checkpoints/restart recovery/watcher requeue/completion injection, and resolve the live lineage; if the origin is terminally reset, fail closed instead of leaking into B. Its integrated current-main A → `/new` → B reproduction reportedly selected B before the patch and no longer delivers to B after the patch; a harmless real background-process smoke retained the same owner. It reports 726 broad tests and 46 focused tests passing. The PR remains open/unmerged, so this is contributor-level recovery evidence, not an accepted guarantee.

**Trigger:** design treats a routing/session key as an immutable execution owner -> `/new` rotates the physical conversation while preserving the key -> old process completion arrives and passes the coarse-key test into B.

**Detectable signal:** origin and current conversation have different physical session IDs/lineage but the same `session_key`; a late completion can only identify the key and therefore cannot prove which conversation owns it.

**Fail-closed response:** do not equate stable routing key with execution generation. Capture the finest durable owner available at spawn, carry it through persistence/recovery, and resolve only explicitly allowed continuation lineage; terminal reset means no injection.

**Recovery witness:** integrated A→B reset reproduction plus checkpoint/restart/watcher paths preserve origin UI owner and prevent delivery into B; real-process smoke preserves owner. Because #84174 is open, require merge/maintainer acceptance or equivalent current-main implementation before upgrading to a shipped guarantee.

**Scope:** exact to Hermes background terminal completion routing described in #83213/#84174. It does not contradict FE-449: async delegation uses a durable `parent_session_id`, while terminal process completion requires a different owner/lineage contract. The pair is evidence against generalizing one identity field across sibling asynchronous subsystems.
