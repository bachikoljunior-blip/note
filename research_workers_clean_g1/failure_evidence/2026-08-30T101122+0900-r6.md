## FE-473 — parent-level success can coexist with an inspectable unmet subagent obligation

Public source: Google Gemini CLI issue #22323, opened 2026-03-13 and still open at observation time: https://github.com/google-gemini/gemini-cli/issues/22323

Observed trace in the reporter-supplied saved session for Gemini CLI 0.32.1 on Windows:

1. The parent tool result for `codebase_investigator` is recorded with `status: "success"` and `Termination Reason: GOAL`.
2. The embedded subagent result simultaneously states that a system-mandated maximum-turn termination occurred before any specific task was identified or initiated.
3. `RelevantLocations` is empty and the embedded summary states that no codebase analysis was performed.
4. The requested obligation was concrete repository architecture/integration analysis, so the same saved session contains both the parent success marker and direct evidence that the requested analytical post-condition was not achieved.
5. The main agent later continued with manual exploration, so this evidence is about the specialized subagent result/status mapping, not total conversation failure.

Falsifying relation within the reported scope:

`parent transport/tool success + GOAL termination` != `requested subagent business/post-condition satisfied`.

The independently inspectable witness is the result payload itself: it records max-turn interruption, no analysis, and an empty relevant-location set. Therefore a consumer that treats only the parent `success`/`GOAL` marker as authoritative can falsely discharge an obligation that the result body shows is still unmet.

### Exact scope / uncertainty

This is reporter-provided issue evidence for Gemini CLI 0.32.1, Windows, the `codebase_investigator` subagent, and the reproduced session shown in issue #22323. The issue is currently open, tagged P1 / need-retesting, with no linked pull request in the issue metadata observed here. It is not evidence that every Gemini CLI subagent or current release misclassifies terminal state, and it is not a merged-fix guarantee. The source also notes the overall conversation recovered by doing manual file exploration, so this finding must not be generalized to overall task failure.

### Phase-1 relevance

For scheduled-Chat parity, a terminal marker must not by itself clear an authoritative obligation when an independent post-condition witness says the required work is absent. A safe acceptance path needs an inspectable obligation/post-condition predicate separate from process/message/tool-level success. FE-473 supplies a narrow counterexample; it does not by itself prove a complete parity mechanism.
