### FE-444 — A delayed cancel from execution N can abort a restarted execution N+1 when authority is keyed only by session identity
**Sources:** anomalyco/opencode issue #20095 and merged commit `c5442d418dd94fdd0d719962e4e3cd9e029e79f5`.
- https://github.com/anomalyco/opencode/issues/20095
- https://github.com/anomalyco/opencode/commit/c5442d418dd94fdd0d719962e4e3cd9e029e79f5

The issue reproduces three cancel races in OpenCode 1.3.3/dev: cancel-before-start can be lost, a delayed cancel from the old run can abort a newly restarted run using the same session ID, and permission/question waits can remain dangling after cancel. The issue was closed as resolved after the Effect/Stream/Runner migration. The cited merged commit adds a Runner state machine using `SynchronizedRef`, per-run monotonically increasing IDs, fibers, `Deferred`, and finish logic that changes state only when the finishing run ID still matches the current run.

**Trigger:** run N is cancelled/restarted under the same logical session ID -> stale completion/cancel callback from N arrives after N+1 is current.

**Detectable signal:** N+1 aborts or state flips even though the callback belongs to the older run; companion signals are lost pre-start cancel or dangling waits.

**Fail-closed response:** do not authorize cancel/finalization solely from reusable session identity; bind authority to current run/generation identity and atomically verify it before mutating lifecycle state.

**Recovery witness:** implementation state changes only when the callback/run ID equals the current Runner generation; cancellation is propagated via current fiber/deferred state. The public issue closer attributes all listed paths to the upstream migration, and the referenced commit is merged into the public repository.

**Scope:** OpenCode SessionPrompt/Runner lifecycle in the cited versions and fix. This is a direct stale-control-event N→N+1 contamination case, not proof about arbitrary child-result channels.

### FE-445 — “Background dispatch succeeded” is false completion in finite one-turn parents whose completion channel dies with the turn
**Sources:** NousResearch/hermes-agent issues #53027 and #63142, current `gateway/session_context.py`, and `hermes_cli/oneshot.py`.
- https://github.com/NousResearch/hermes-agent/issues/53027
- https://github.com/NousResearch/hermes-agent/issues/63142
- https://github.com/NousResearch/hermes-agent/blob/main/gateway/session_context.py
- https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/oneshot.py

#53027 contains a real cron reproduction: parent dispatches `delegate_task`, saves/delivers a final response saying it is waiting, then exits; the subagent completes but its `ASYNC DELEGATION BATCH COMPLETE` never reaches the closed cron session. #63142 reports the same regression after 0.18.2 with before/after logs. Current Hermes source now defines finite runtimes that cannot receive late completions as async-delivery unsupported and routes `delegate_task` to synchronous/inline execution; `hermes -z` explicitly calls `declare_stateless_channel()` before its one turn.

**Trigger:** one-turn parent advertises async-delivery support -> top-level delegate is detached -> parent emits its only final response and exits before child completion can re-enter.

**Detectable signal:** dispatch confirmation exists but parent output lacks child result; child result is orphaned, never routed, or arrives after parent lifetime.

**Fail-closed response:** capability-test the *return channel*, not merely dispatcher availability. If the parent cannot receive a late completion, refuse the async promise and execute/join inline or surface an explicit unsupported result.

**Recovery witness:** finite runtime declares `async_delivery_supported()==False`; existing synchronous aggregation returns the child work product within the sole turn.

**Scope:** finite Hermes surfaces documented in the cited issues/current source. It does not say async delegation is unsafe in persistent interactive/gateway contexts that actually retain a completion channel.
