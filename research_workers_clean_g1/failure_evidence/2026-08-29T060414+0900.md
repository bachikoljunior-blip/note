### FE-422 — Detached review results can arrive after the source has advanced and still look current; a merged Gajae Code fix binds review authority to a canonical source snapshot
**Primary sources:** Yeachan-Heo/gajae-code issue #3469 and merged PR #3631.

Issue #3469 reports a concrete Ultragoal run in `gjc 0.12.0`: Architect A started reviewing source revision R1, the parent advanced through R2/R3 and obtained a newer Architect B approval, then A finished 4–11 minutes later with a contradictory BLOCK for R1. The late review carried no stale marker because task metadata identified the reviewer/assignment but not an immutable reviewed worktree/diff/workflow generation. The repository owner later confirmed that an intermediate fix requiring equal submitted hashes was insufficient: mutually consistent stale claims could remain gate-eligible if runtime never derived and froze the canonical reviewed source.

Merged PR #3631 derives a canonical content-addressed review-source identity before dispatch, persists cohort/dispatch/delivery provenance, marks late deliveries stale, excludes stale/invalid lanes from completion gates, and includes the exact `R1-late-after-R2/R3` race plus same-snapshot join coverage. The PR reports 236 targeted tests passing; the repository owner closed #3469 as resolved by that merged PR.

**Phase-1 failure mapping:** trigger = detached reviewer dispatched on R1 while mutable parent source advances to R2/R3; detectable signal = delivered review's canonical source identity differs from the gate's frozen current source identity; fail-closed response = retain the result only as stale/advisory and exclude it from current completion authority; recovery witness = the R1-late-after-R2/R3 regression is rejected while same-snapshot parallel reviews still join.

**Scope guard:** exact to the reported Gajae Code Ultragoal review/gate path and merged #3631 behavior. It is evidence for stale review authority, not a general proof that every superseded child-result channel is now safe.

### FE-423 — File existence can create false completion after an interrupted partial write; OpenSpec currently reports incomplete artifacts as `done`
**Primary sources:** Fission-AI/OpenSpec issue #1084 and open PR #1098.

OpenSpec issue #1084 reports that interrupting `/opsx:propose` after `proposal.md` is created but before it is fully written leaves a partial artifact on disk. On `/opsx:continue`, `detectCompleted()` reaches `artifactOutputExists()` and treats existence/glob match as completion, so `openspec status --json` reports the proposal `done` and skips regeneration. The result is silent: an empty or half-written file and a complete file receive the same completion verdict.

Open PR #1098 proposes composing existence with a content check and reports 7 new empty/whitespace/comment/glob cases with 145 artifact-graph tests passing. It remains open with a design-review label, so this run does not treat the proposed check as a merged guarantee. Moreover, non-empty content is only the proposed tested predicate; it does not prove semantic completeness of arbitrary partially written files.

**Phase-1 failure mapping:** trigger = interruption between file creation and completed artifact commit; detectable signal = an artifact path exists without an independent completion/content witness; fail-closed response = do not promote existence alone to terminal `done`; require a completion contract that is stronger than presence; recovery witness = interrupted/invalid artifact is regenerated or explicitly rejected rather than skipped.

**Scope guard:** reporter-scoped OpenSpec artifact-graph failure. The open PR's validation only covers its stated syntactic content cases; this evidence does not generalize that predicate into a universal semantic-completeness test.

### FE-424 — One logical internal send can be persisted twice under local and Remote Control routes with different message IDs
**Primary source:** openai/codex issue #36529.

The Windows Codex Desktop report provides an A/B matrix with bundled CLI `0.146.0-alpha.9.2`, one enrolled Remote Control host, and iPhone/iPad clients. With no remote client actively viewing the destination task, one internal send produces one delivery. If iPhone or iPad actively views the destination and the caller omits an explicit recipient host, the same payload is persisted twice: first locally, then through the Remote Control route with a different message ID. Returning the mobile client to the task list removes the duplicate; explicitly targeting `hostId=local` also removes it in the tested environment. In one isolation trial the second copy arrived about 16.7 seconds later.

**Phase-1 failure mapping:** trigger = a destination task is simultaneously reachable by local and active Remote Control routing while caller uses the default/omitted host route; detectable signal = identical logical payload appears through two route authorities under distinct transport/message IDs; fail-closed response = bind one logical send to one authoritative destination route or dedupe above route-specific message identity; recovery witness = the same logical send yields one persisted user-message record under the matched A/B condition.

**Scope guard:** open reporter evidence on the stated Windows/Desktop/Remote Control versions and devices. The report proves duplicate message persistence in that setup; it does not prove a particular downstream external side effect was duplicated.

### FE-425 — Freshness keyed to a generic mutable timestamp can keep a stale `resume_pending` session alive forever; Hermes merged a causal-event timestamp fix
**Primary sources:** NousResearch/hermes-agent issue #46934 and merged PR #56264.

Hermes' earlier resume path used generic `updated_at` to decide whether `resume_pending` remained fresh. The failure is self-reinforcing: every new message updates `updated_at`, so a stale zombie session can keep looking fresh and resume old context indefinitely. Merged PR #56264 changes the freshness gate to `last_resume_marked_at`, which is set once when resume is marked and is not bumped by ordinary per-message touches. Its matched table records: fresh `resume_pending` remains resumable; a stale resume mark with fresh generic `updated_at` changes from stale-context resume to a new session; freshness window `<=0` retains the explicit opt-out behavior. The PR reports 86 targeted tests green and an E2E import/temp-home check.

**Phase-1 failure mapping:** trigger = stale recovery state plus later unrelated mutations that refresh a generic object timestamp; detectable signal = `updated_at` is fresh while the causal resume-mark timestamp is stale; fail-closed response = evaluate recovery freshness from the causal event identity/time, not generic record touches; recovery witness = fresh mark resumes, stale mark resets even when generic metadata was just touched.

**Scope guard:** exact to the merged Hermes gateway/session freshness path and configured freshness semantics. It does not imply all recovery systems should use wall-clock age rather than generation or durable causal identity.

### FE-426 — Prompt-level “reference only” framing did not stop stale work when orchestration promoted the synthetic summary to the active user turn
**Primary sources:** NousResearch/hermes-agent merged PR #44454, issue #80622, and merged PR #81070.

PR #44454 had already merged a stale-task mitigation: compaction headings were reframed as historical/DO NOT EXECUTE and a topic-consistency carveout was removed. Issue #80622 then reproduced a stricter regression on a checkout containing that fix. An assistant response had completed with `finish_reason=stop`; Hermes inserted a 32,052-character `[CONTEXT COMPACTION — REFERENCE ONLY]` message as `role=user`; no new human request followed; the synthetic handoff became active and immediately drove new tool calls that resumed already-completed historical work. The text itself explicitly said not to execute the summary, so textual framing was insufficient once orchestration granted active-turn authority.

Merged PR #81070 closes #80622 by introducing user-origin predicates and guards across post-compaction continuation/retry/undo/resume paths, refusing a sole reference handoff as the active anchor, restoring a pending real user ask before continuation, and returning a non-duplicated skip status when no user-originated turn exists. It reports 448 targeted tests, an E2E sole-handoff/restore/mid-tool-loop probe, and mutation checks where reverting the fix makes guard tests fail.

**Phase-1 failure mapping:** trigger = synthetic reference handoff is stored in a user-role slot after a completed turn with no later human request; detectable signal = role says `user` but origin/provenance says synthetic compaction; fail-closed response = active-turn selection and retry/resume authority require user-origin provenance rather than textual labels or role alone; recovery witness = sole handoff drives no model/tool continuation, pending genuine user content is restored and does drive continuation, mid-tool-loop exception remains covered.

**Scope guard:** exact to Hermes' compaction/turn-selection surfaces covered by merged #81070. It is not evidence that prompt framing never matters; it shows that framing alone did not control authority in this tested orchestration path.

### FE-427 — A session can be successfully marked and scheduled for resume yet still abandon the unfinished task when recovery policy assumes an interactive human
**Primary sources:** NousResearch/hermes-agent issue #57056 and open PR #57323.

Issue #57056 reports a webhook-only EKS deployment. Mid-turn SIGTERM correctly marks the session `resume_pending`, restart correctly schedules the session, but the empty-message resume branch tells the model to report restoration, ask the user what to do next, and skip unfinished history. On a webhook surface there is no live responder; the observed resumed turn makes one API call, returns a short `finish_reason=stop` acknowledgement with no tool calls, and produces no downstream output. Thus scheduler-level recovery succeeded while useful task continuation failed.

Open PR #57323 proposes platform-aware guidance for webhook/API-server/MSGraph webhook paths and reports five isolated tests, but the PR author explicitly notes the load-bearing webhook-only manual reproduction had not yet been run on their machine. The PR remains open, so no merged recovery guarantee is claimed.

**Phase-1 failure mapping:** trigger = interrupted task on a non-interactive platform resumes through a policy written for interactive sessions; detectable signal = `resume_pending`/scheduled-resume witnesses exist but the resumed turn terminates without remaining-work completion and no human responder exists; fail-closed response = bind continuation policy to interaction-surface capability and preserve ambiguity around already-landed destructive effects; recovery witness = a non-interactive restart completes or explicitly re-establishes the unfinished task without requiring a nonexistent user reply.

**Scope guard:** reporter-scoped Hermes webhook behavior plus an unmerged candidate fix. It does not establish that all webhook retries are safe to re-execute; issue/PR themselves retain the separate idempotency problem for already-landed effects.
