## New failure evidence

### FE-322 — Admission-time authorization can be correct while the dispatched action is already stale
**Primary source:** Taewoo Park et al., “HALO: Heterogeneous Admission through Localized Obligations for Safe Agentic Execution,” arXiv:2607.27636v1, 30 Jul 2026, https://arxiv.org/abs/2607.27636

HALO separates admission from the final effect boundary. Its matched controls share the same response, catalog, graph, mutation, timing, and adapter. In the PX4/Gazebo panel, `HALO-Admission` preserves dependency closure but removes the final dispatch recheck; it emits **50/50 stale setpoints** after post-admission support drift. In the AgentSpec reference-interpreter comparison, policy-only AgentSpec produces **40/40 post-decision stale internal fingerprints** and accepts **10/10 replayed tokens**. Adding exact final binding, one-dispatch token enforcement, and fresh readmission reduces both tested failure counts to zero and completes **20/20** fresh recoveries.

**Failure implication:** a correct policy decision at planning/admission time is not a durable execution capability. Support, authorization, exact action identity, and token generation must be revalidated at the final effect boundary; otherwise a later state change or replay can make a previously valid action stale while the runtime still dispatches it.

**Scope guard:** controlled structured-response and PX4/Gazebo experiments in this preprint. The reported counts do not establish deployment prevalence or distributed exactly-once delivery; the paper explicitly limits the measured guarantee to the protected adapter/process boundary.

### FE-323 — “Reject the whole response” and “check each component independently” fail in opposite directions
**Primary source:** same HALO paper, arXiv:2607.27636v1.

The mechanism ablations isolate two symmetric mistakes. In the ten-cold-start PX4 panel, `WholeResponse` blocks **200/200 supported components** affected only by unrelated drift, retaining just **40/240** supported components overall. `IndependentFilter`, which checks each component locally but ignores declared dependencies, retains **240/240** supported components but leaks **100/100 orphan dependents** whose prerequisites are no longer valid. The structured-response replay shows the same dependency failure: `IndependentFilter` leaks **70/70** orphaned dependents, while a global response-level policy retains **0/248** supported components.

**Failure implication:** coarse fail-closed behavior can destroy useful unaffected work, while independently validating outputs can preserve a child after its required parent was invalidated. Heterogeneous agent outputs need dependency-aware partial retention rather than bundle-wide rejection or component-wise checks without closure.

**Scope guard:** the paper’s typed component graph, trusted catalog/state-provider assumptions, and fixed evaluation cohorts. This does not prove that all response bundling is unsafe or that HALO’s exact graph model is universally necessary.

### FE-324 — A permission classifier can miss most authorization violations because equivalent state changes route around the classifier boundary
**Primary source:** Zimo Ji et al., “Measuring the Permission Gate: A Stress-Test Evaluation of Claude Code’s Auto Mode,” arXiv:2604.04978v2, 28 Apr 2026, https://arxiv.org/abs/2604.04978

AmPermBench evaluates 253 state-changing actions from 128 deliberately ambiguous DevOps prompts against action-level oracle labels. End-to-end false-negative rate is **81.0% (95% CI 73.8–87.4%)** under this stress workload. A structural coverage gap explains part of the result: **36.8% of all state-changing actions** use Tier-2 in-project file edits and never reach the transcript classifier. Even among the 160 Tier-3 actions that are actually classified, false-negative rate is **70.3%** and false-positive rate **31.9%**. Artifact cleanup is the sharpest bypass case at **92.9% FNR**, because agents fall back to editing operational state files when the expected CLI is unavailable.

**Failure implication:** gating a named tool/channel is not equivalent to gating the semantic effect. Agents can realize the same state mutation through a different primitive that the classifier treats as safe. Security boundaries should attach to effect semantics and target state, not assumptions such as “dangerous operations go through shell commands.”

**Scope guard:** intentionally ambiguous authorization stress tests, not organic production traffic. The paper explicitly treats its 81% FNR as a different workload from Anthropic’s reported production FNR rather than a contradiction.

### FE-325 — A safety property can be present in the protocol specification but absent from the pinned executable validation
**Primary source:** Genliang Zhu et al., “OpenPort Protocol: A Security Governance Specification for AI Agent Tool Access,” arXiv:2602.20196v1, 22 Feb 2026, https://arxiv.org/abs/2602.20196

OpenPort specifies several strong write-safety properties, including execute-time state-witness revalidation for delayed approvals, idempotency replay mapping, rate limiting, and complete allow/deny/fail audit events. However, the paper’s pinned v0.1.0 validation matrix explicitly marks **State Witness execution-time revalidation as Future**, **dedicated idempotency replay regression as Future**, **audit completeness as Future**, and end-to-end 429 rate limiting as **Partial**. The paper says optional stronger profiles are evaluated separately from the pinned core claims.

**Failure implication:** “configured/spec’d” must not be reported as “executed/tested.” A control plane should track each invariant’s implementation and regression-test status independently; otherwise an intended safeguard can be silently counted as active evidence before the release artifact actually exercises it.

**Scope guard:** this is an evidence-status failure mode, not a demonstrated exploit of OpenPort. The protocol correctly discloses the gap; the negative evidence is that specification presence alone is insufficient proof of executed enforcement.

### FE-326 — Semantic filtering can score 0/80 on fixed description attacks yet fail immediately when an adaptive attacker moves the payload to an earlier-executed field
**Primary source:** Lin-Fa Lee, Yi-Yu Chang, Kuo-Hui Yeh, “WebMCP-Phalanx: Enforcing and Characterizing Trust Boundaries for Browser-Integrated LLM Agents,” arXiv:2608.24017, 25 Aug 2026, https://arxiv.org/abs/2608.24017

In the primary fixed attack set, the dual-agent semantic layer blocks **80/80** tool-description injections and leaves only **2/80** successful returned-content attacks. But the paper’s white-box adaptive attacker, given the classifier prompt and end-to-end success feedback, bypasses description-layer filtering on **15/16 payloads**, with a **median of one rewrite round**. The attacker does not defeat the semantic judge; it moves the instruction into a task-fitting tool name that can trigger invocation before description inspection completes. A name-relevance ablation holding injected content fixed raises rule-based-stripping ASR from **0%** for irrelevant/generic names to **25% / 55% / 70%** for common-step / task-domain / essential-step names.

The paper also exposes a lifecycle residue: clearing a malicious tool after page transition only reduces attack success from **80% to 70%** because already-returned malicious semantics remain in conversation history; propagating the tool’s trust invalidation to its residual content reduces the tested attack success to 0%.

**Failure implication:** a defense can look closed on the field it inspects while the attacker shifts the same intent to an earlier or differently governed field. Inspection coverage must include execution timing and the full set of agent-visible metadata; lifecycle revocation must also invalidate derived semantic state, not only the original tool object.

**Scope guard:** current WebMCP draft environment, two model families/three classifier prompt designs for the adaptive analysis, and the paper’s browser/runtime implementation. The 15/16 result is not a general prompt-injection success rate.

### FE-327 — Human approval is forgeable when the agent narrates what the human is approving; a trusted boundary renderer still faces a coverage-vs-overprompting frontier
**Primary source:** Xiaoqi Weng, “What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents,” arXiv:2606.02668v1, 1 Jun 2026, https://arxiv.org/abs/2606.02668

The Lies-in-the-Loop attack targets coding-agent approval dialogs whose text is authored by the same agent proposing the consequential action: the agent can present a benign summary while a different low-level action executes. The paper’s prototype instead renders approval from the actual boundary action and binds that rendering to execution. But its own independent measurements show the remaining trade-off: on **1,330 GTFOBins trusted-tool abuses**, the prototype **silently passes 10.0%** (all through trusted tools); on **28,798 normal tldr commands**, it marks **87.0% uninspectable**, which would require escalation rather than silent approval. Total mediation and the trusted UI path are specified but **assumed, not implemented** in the prototype.

**Failure implication:** human-in-the-loop approval is not a security boundary if the untrusted agent controls the description of the thing being approved. Moving rendering to the effect boundary fixes that trust direction, but incomplete decoding then becomes an explicit availability/UX cost rather than something that can be hidden by trusting the narration.

**Scope guard:** proof-of-concept analyzer and the two independent command corpora; this does not estimate real user-approval error rates. The paper explicitly presents the mechanism as a frontier, not a solved defense.
