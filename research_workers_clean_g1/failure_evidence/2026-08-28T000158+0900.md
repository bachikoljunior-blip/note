## New failure evidence

### FE-277 — One-time memory admission verification can improve inputs yet still underperform lifecycle-persistent verification in every tested backbone×benchmark cell
**Primary source:** Wang et al., “MemGuard: Persisting Verifier Signals for LLM-Agent Memory Governance,” arXiv:2608.21867v1, 22 Aug 2026, https://arxiv.org/abs/2608.21867

MemGuard evaluates four backbones across Terminal-Bench 2.0, SWE-Bench Verified, WebArena, and Mind2Web under matched task order, step budget, retrieval budget, and decoding settings. The paper includes a verifier-only control that uses the same verification signal at admission time but discards it afterward. That verifier-only control improves over ReasoningBank in most cells by accepting better candidates, yet it underperforms full MemGuard in all 16 backbone–benchmark settings. Full MemGuard persists reward/confidence/label/verification-time metadata and reuses it during retrieval, conflict resolution, summarization, and archival; across five seeds it reports the best success metric and lowest average steps in all 16 cells, with gains over the strongest prior memory baseline up to 7.9 success-rate points on WebArena and 5.6 step-success-rate points on Mind2Web.

**Failure implication:** filtering a memory once at write time is not equivalent to governing it throughout its lifetime. A record that was acceptable when written can later become stale, conflicting, over-generalized, or low-confidence relative to newer evidence; if the original verifier signal is discarded, retrieval has no durable quality/provenance handle to attenuate or retire it.

**Scope guard:** this is an arXiv v1 over the four named benchmarks/backbones and the authors’ verifier/governance design. It does not establish that persistent verifier metadata is sufficient against forged verifier outputs, malicious memory writers, or environment compromise, nor that the reported gains generalize to all memory architectures.

### FE-278 — Transport-layer TLS does not preserve agent-command integrity across a terminating API router; semantic client-side checks can be bypassed before the client sees the provider response
**Primary source:** Xie et al., “The Proxy Knows Too Much: Sealing LLM API Routers with Attested TEEs,” arXiv:2606.16358v1, 15 Jun 2026, https://arxiv.org/abs/2606.16358

A conventional LLM API router terminates the client TLS session and opens a separate upstream session, so the router sees and can rewrite plaintext prompts, tool schemas, tool calls, and responses. The paper models four malicious-router classes including tool-call rewriting/dependency substitution, trigger-gated adaptive attacks, and passive exfiltration. All four attack classes succeed against the plaintext-access baseline; the authors report existing client-side defenses as evadable because the malicious intermediary can condition its manipulation on audit-evading states before the client receives the payload. Their positive control, AEGIS, confines plaintext relay to a client-attested enclave whose measured code is pinned as a faithful passthrough; all four tested attack classes, including adaptive tests against the same boundary, are blocked. The trusted path is 851 lines and the reported local relay overhead is about 6 ms/request.

**Failure implication:** HTTPS to “a router” proves only the channel to that router, not end-to-end command integrity from the actual model provider to the agent executor. If a downstream automation trusts tool calls after a terminating intermediary, post-hoc semantic anomaly detection is not an integrity primitive; cryptographic/attested end-to-end provenance or an equivalent faithful-passthrough guarantee is a distinct control.

**Scope guard:** AEGIS is a prototype relying on TEE attestation, reproducible/pinned code measurements, and the paper’s tested providers/workloads. It does not eliminate metadata side channels or prove the enclave/platform itself invulnerable.

### FE-279 — Effect authorization and secret confinement are separate boundaries; protecting only one leaves a distinct agent security failure surface
**Primary source:** Ma & Schmid, “SecureClaw: Clawing Back Control of LLM Agents,” arXiv:2606.09549v1, 8 Jun 2026, https://arxiv.org/abs/2606.09549

SecureClaw separates two failures that are often conflated: unauthorized external actions and sensitive plaintext exposure inside the agent runtime before any final-output check can intervene. The design therefore puts authorization at the effect sink while moving sensitive reads through a trusted gateway that replaces plaintext with opaque handles/bounded summaries; state-changing writes use a PREVIEW→COMMIT protocol in which only a trusted executor may commit the exact canonical request authorized by policy. In the authors’ common harness over AgentDojo, AgentLeak, and Agent Security Bench, SecureClaw is the only evaluated defense that simultaneously retains usable task utility and reports 0% ASR on ASB, 0.64% ASR on AgentDojo, and 3.23% overall leak on AgentLeak’s attacked parity lane.

**Failure implication:** an action gate cannot undo a secret already exposed to an untrusted planner/runtime, while read-side redaction alone cannot stop an authorized-looking but unsafe effect. Long-running agents handling secrets and side effects need separately verifiable read/declassification and write/commit boundaries rather than treating “the safety layer” as a single check.

**Scope guard:** these are results under the paper’s benchmark harness and trusted-gateway/trusted-executor assumptions. The remaining 3.23% leak on AgentLeak also shows the architecture is not a universal confidentiality proof.
