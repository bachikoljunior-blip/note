## New failure evidence

### FE-404 — Recovery can create phantom liveness by double-counting one in-flight attempt; Ray has an open fix with a reversion-sensitive test
**Primary sources:** Ray issue #65313 and PR #65314, https://github.com/ray-project/ray/issues/65313 and https://github.com/ray-project/ray/pull/65314

The reported Ray path `MarkGeneratorFailedAndResubmit` starts with a streaming generator already counted as pending, then `SetupTaskEntryForResubmit` increments the pending count again. When the resubmitted attempt later completes, only one decrement occurs, leaving `num_pending_tasks_` permanently high. The proposed PR releases the finished attempt's pending count before re-adding the new attempt. Its regression test runs two recovery cycles: without the fix the count becomes 2 after the first cycle and 3 after the second; reverting only the decrement makes the test fail with 2 and also trips the existing leak check.

**Phase-1 failure mapping:** trigger = recovery/resubmission of an already-counted in-flight attempt; detectable signal = aggregate pending counter disagrees with the exact attempt set; fail-closed response = liveness/idle decisions must not trust unreconciled aggregate bookkeeping; recovery witness = each recovery cycle preserves exactly one pending count while the replacement attempt is live and returns to zero after completion.

**Scope guard:** issue and PR are open as of 2026-08-29. The test/reversion evidence is author-supplied in the PR and is stronger than issue-only description, but no merged Ray guarantee is claimed.

### FE-405 — An HTTP `500` can be an indeterminate mutation outcome; treating it as proof of no side effect makes a new-key retry unsafe
**Primary source:** Stripe advanced error handling, https://docs.stripe.com/error-low-level

Stripe documents that POST mutations returning `500` are cached by the idempotency layer and that a client should treat the result as indeterminate. Stripe explicitly advises against retrying with a new idempotency key because the original request may have produced side effects. Thus an error response is not equivalent to a no-effect receipt.

**Phase-1 failure mapping:** trigger = mutating request returns `500` after an unknown server-side point of execution; detectable signal = error class plus stable logical idempotency identity and later authoritative object/webhook/readback; fail-closed response = do not declare “not executed” and do not rotate the key merely because the response was an error; recovery witness = same-key replay/authoritative reconciliation establishes whether the logical effect exists without creating a second effect.

**Scope guard:** exact to Stripe's documented mutation/idempotency behavior. It is not a claim that every HTTP 500 may hide a committed side effect.

### FE-406 — Timeout/server error can occur after resource mutation, so blind retry can stack effects; AWS documents client-token idempotency as the countermeasure
**Primary source:** Amazon ECS idempotency guidance, https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_Idempotency.html

AWS states that a mutating operation may time out or return a server error after resources were already mutated, making it hard to know whether the mutation occurred. Repeating such requests can stack changes or create more resources than intended. ECS `RunTask` and related APIs use a client token so a retry with the same token and parameters returns the original result rather than performing another mutation; changing parameters under the same successful token produces a conflict.

**Phase-1 failure mapping:** trigger = ambiguous transport failure after mutation; detectable signal = stable client token + parameter fingerprint; fail-closed response = retry only under the same logical operation identity, and reject same-token/different-parameter reuse; recovery witness = retry returns the prior operation result with no extra mutation.

**Scope guard:** exact to the documented ECS idempotency contract and its named APIs; not a universal guarantee for AWS or arbitrary APIs.

### FE-407 — Own matched probe: response loss after commit duplicates a mutation without stable idempotency, while stable identity replays one result; rotating the key defeats protection
**Own probe:** `research_workers_clean_g1/failure_evidence/probes/2026-08-29T040631+0900-ambiguous_retry.py` and `.json`

A deterministic SQLite application-layer probe commits an `invoice_42=paid` effect and then simulates response loss. Four arms use the same logical request:
- no idempotency: first commit succeeds but response is lost; retry commits again -> `effect_count=2`;
- stable idempotency key: first commit succeeds but response is lost; retry with the same key replays `effect_id=1` -> `effect_count=1`;
- rotated idempotency key: retry with a new key creates a second commit -> `effect_count=2`;
- same key with changed parameters: request is rejected as `IdempotencyMismatch` and effect count remains 1.

**Phase-1 failure mapping:** trigger = caller cannot distinguish “request never executed” from “commit happened, response was lost”; detectable signal = stable logical operation key + request fingerprint; fail-closed response = same-key replay for identical request, hard conflict for changed request; recovery witness = one durable effect and replay of the original receipt.

**Scope guard:** single-process SQLite deterministic simulation. It demonstrates the retry/identity mechanism, not network, distributed database, or Stripe/AWS production behavior.

### FE-408 — Immediate streaming cancellation can discard the current turn; OpenAI Agents Python added a merged after-turn mode whose checkpoints occur after session persistence
**Primary sources:** openai-agents-python issue #1895 and merged PR #1896, https://github.com/openai/openai-agents-python/issues/1895 and https://github.com/openai/openai-agents-python/pull/1896

The issue reports that `result.cancel()` stops a streaming run immediately, discarding the incomplete turn so it is not saved to the session and cannot be resumed cleanly. The merged fix adds `cancel(mode="after_turn")`, allowing the current turn to finish. The PR states that its cancellation checkpoints are placed after session saves; it also adds a streaming handoff session-state test.

**Phase-1 failure mapping:** trigger = cancellation arrives while current turn has user-visible/in-progress work but no durable session boundary; detectable signal = cancellation mode + durable session/turn checkpoint status; fail-closed response = if continuity is required, do not claim the in-progress turn is durably resumable until the persistence boundary is crossed; recovery witness = session contains the completed turn before cancellation takes effect.

**Scope guard:** exact to OpenAI Agents Python's streaming cancellation behavior and the merged after-turn option. Immediate cancel intentionally remains available and is not claimed to preserve partial-turn state.

### FE-409 — User-visible streamed state can outrun the durable checkpoint, then disappear after cancel/resync

### FE-410 — A durability layer can promise replay but still re-execute a non-idempotent tool when its cache key is unstable; Pydantic AI merged a regression-tested fix
**Primary sources:** pydantic-ai issue #6907 and merged PR #6944, https://github.com/pydantic/pydantic-ai/issues/6907 and https://github.com/pydantic/pydantic-ai/pull/6944

Under Pydantic AI's Prefect durability integration, a tool-call task hashed a live `ToolsetTool`. Because one field was not JSON-serializable, hashing fell back to cloudpickle; the composite digest then depended on object-sharing/memo layout. On flow retry, the model request replayed from cache but deserialization changed object identity layout, causing the tool cache key to change and the tool body to run again. The issue reports reproducible 5/5 behavior: two flow attempts, tool body runs twice, no tool-result replay. The merged PR changes the cache projection to a JSON-native value-addressed form and adds `test_flow_retry_replays_tool_result`; the PR states 110 Prefect tests passed.

**Phase-1 failure mapping:** trigger = retry reconstructs semantically identical inputs with different object identity/serialization graph; detectable signal = cache key changes while canonical logical inputs are value-equal; fail-closed response = do not rely on object-identity-sensitive serialization for side-effect replay identity; recovery witness = flow retry replays the prior tool result and tool body run count remains 1.

**Scope guard:** exact to Pydantic AI's Prefect durability integration and the fixed cache-key path. It does not imply cloudpickle is always unsafe or that Prefect itself necessarily duplicates arbitrary tasks.

### FE-411 — Omitting context fields from a cache key can make one agent run replay another run's answer inside the same flow; merged fix binds those fields into the key
**Primary sources:** pydantic-ai issue #6903 and merged PR #6944, https://github.com/pydantic/pydantic-ai/issues/6903 and https://github.com/pydantic/pydantic-ai/pull/6944

The issue demonstrates two `agent.run()` calls in one Prefect flow with the same prompt but different `metadata` (`tenant=a` vs `tenant=b`). Because the cache-key projection omitted `metadata`, the second run's model request and tool call became `Cached(type=COMPLETED)` and returned the first run's `tenant=a` answer. The issue scopes the blast radius to one flow under the default policy. PR #6944 adds the omitted tool-readable context fields to the projection and a regression test requiring the two metadata-distinct runs to produce separate results.

**Phase-1 failure mapping:** trigger = two executions differ in semantically relevant context omitted from replay identity; detectable signal = cached result provenance does not match the current context fingerprint; fail-closed response = cache/replay key must bind every execution input that can affect the tool/model result; recovery witness = metadata-distinct runs no longer share the recorded result.

**Scope guard:** exact to the documented Pydantic AI Prefect cache projection and one-flow default cache scope. It is not evidence of cross-flow leakage under that default policy.

### FE-412 — Declaring a durability capability does not guarantee every tool is durably wrapped; late/decorator toolset registration can silently bypass activities/tasks/steps
**Primary sources:** pydantic-ai issue #6902 and open PR #6954, https://github.com/pydantic/pydantic-ai/issues/6902 and https://github.com/pydantic/pydantic-ai/pull/6954

The issue shows that a `DynamicToolset` registered via `@agent.toolset` after agent construction is not seen when durability capabilities bind. In measured Temporal configuration it receives no dynamic-toolset activities; in Prefect it produces no `Call Tool` task, so the tool executes inline in flow code. The issue states this means uncheckpointed execution/re-execution on retry for Prefect/DBOS and workflow-sandbox execution for Temporal. The open PR changes the runtime guard to reject executing toolsets that arrived after the durable construction boundary, with tests across Temporal, DBOS, and Prefect.

**Phase-1 failure mapping:** trigger = capability binding happens before late tool registration; detectable signal = executing tool lacks an engine activity/task/step or is absent from the construction-time registered set; fail-closed response = reject the run instead of silently executing an unwrapped tool under a "durable" configuration; recovery witness = every executing toolset is either durably wrapped from construction time or deterministically rejected.

**Scope guard:** issue and PR are open as of 2026-08-29. The reproduction is source-level and engine-specific; no merged fix is claimed yet.
