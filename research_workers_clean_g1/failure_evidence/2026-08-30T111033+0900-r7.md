## FE-474 — lease expiry/reclaim is not itself a stale-writer fence

Public source inspected: `kritibehl/faultline` README, current public GitHub content fetched during this invocation.

Observed source-qualified trace: the repository models a worker that owns token 7, stalls or is partitioned long enough for its lease to expire, a second worker reclaims with token 8, and the first worker later attempts a stale commit. The protected job store rejects the token-7 commit at commit time. The repository also lists a network-partition fault profile and reports zero duplicate commits across its recovery runs. Its stated correctness path is lease issuance plus monotonically increasing fencing token plus commit-time token validation.

Negative mechanism: expiry and reassignment only establish that a successor may legitimately run; they do not, by themselves, stop the predecessor from later issuing a mutation when it resumes. The safety boundary in this tested design is the mutation-time resource check on the monotonic token. A lock/lease holder's local belief is therefore insufficient authority after an unobserved partition/stall.

Matched-comparison limitation: the published README describes what would corrupt state if the stale commit were accepted, but the reported test suite keeps fencing enabled. I did not observe a published unfenced red arm in this bounded slice. Therefore FE-474 is evidence for the stale-owner failure mechanism plus a fenced positive control, **not** an empirical lock-only-vs-fenced A/B claim.

Exact tested scope: deterministic in-repository fault injection using a single job store, including a network-partition profile and stale-worker race. The source explicitly says multi-region replication is not modeled and describes concurrency scaling as an in-repo simulation rather than a production benchmark. Do not generalize this to real multi-host/network-partition production behavior, globally ordered fencing across shards, or arbitrary downstream resources.

Phase-1 acceptance assessment: this evidence-gathering route used public read-only source access plus lightweight role-local repository persistence. It required no richer-mode/Work/protected-primary/manual-user execution, no hosted runner/Codespaces/artifact/LFS/package/cloud/external model credit, and no incremental monetary cost. The mechanism itself is not accepted as a complete parity route from this evidence alone; a resource that cannot atomically enforce the token/CAS remains an unresolved child.
