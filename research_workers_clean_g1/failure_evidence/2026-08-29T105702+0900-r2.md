## FE-455 — Retry idempotency can exist yet be completely defeated by a caller that rotates identity; unbounded retry then converts a duplicate into a feedback storm
**Sources:** OpenClaw issue #52149, maintainer closure comment, and current `main` `src/agents/announce-idempotency.ts`.
- https://github.com/openclaw/openclaw/issues/52149
- https://github.com/openclaw/openclaw/blob/main/src/agents/announce-idempotency.ts

The reported OpenClaw sub-agent completion path already had a gateway idempotency cache, but `sendAnnounce` generated a fresh `crypto.randomUUID()` for every re-delivery. When the parent session was busy, cleanup reset `cleanupHandled=false` and retried again without a terminal cap. The reporter observed one completion being re-announced about 4,450 times over 6.7 hours, with roughly 436M cache-read tokens and about $161 of cost.

On 2026-04-25 the maintainer closed the issue as implemented after review, stating that current `main` and `v2026.4.22` use deterministic announce identity plus persisted retry bookkeeping and bounded retry/expiry termination. Current public `main` directly shows `buildAnnounceIdFromChildRun()` binding the announce to `(childSessionKey, childRunId)` and `buildAnnounceIdempotencyKey()` deriving the delivery key from that stable identity. The maintainer comment cites a main snapshot, not necessarily the exact fix commit, so that SHA is not treated as the implementation commit.

**Trigger:** retry path mints a fresh transport/idempotency identity for the same logical completion + retry lifecycle can reopen indefinitely.

**Detectable signal:** one logical child-run completion appears under many distinct delivery keys; retry count survives no logical terminal state; repeated failures do not converge.

**Fail-closed response:** persist a stable logical completion identity across attempts, persist retry bookkeeping across restart, and bound/terminalize retries; do not let a caller invalidate the dedupe domain on each attempt.

**Recovery witness:** maintainer-confirmed implementation plus current-main deterministic announce identity.

**Scope:** exact to OpenClaw's tested sub-agent announce/cleanup path. It does not establish that every retry loop needs the same key schema or retry cap.

## FE-456 — A durable session key can become stale after compression and allow a late async result to be consumed by the wrong live session; merged repair adds a distinct origin UI identity plus continuation resolution
**Sources:** Hermes issue #57576 comments and upstream commit `aab351bfa6c66381bda6c3a7b61dcd4e65f5c5e5` (`fix(delegation): route async results to origin session`).
- https://github.com/NousResearch/hermes-agent/issues/57576
- https://github.com/NousResearch/hermes-agent/commit/aab351bfa6c66381bda6c3a7b61dcd4e65f5c5e5

Hermes' TUI async-delegation queue could compare a completion only against the current `session_key`. Compression rewrites that key, so a completion dispatched before compression could later look orphaned or could match a different session whose lineage historically passed through the same identifier. The merged upstream commit on 2026-07-08 adds `origin_ui_session_id` as a return address distinct from the durable conversation ID, resolves pre-compression keys to the live continuation, and requires positive ownership before an unrelated poller consumes the event.

The merged tests explicitly cover a stale/rotated key preferring the origin UI session, a compressed parent routing to its live continuation, and a third unrelated session leaving the event alone. A finalized origin can route to the verified continuation rather than whichever session is merely current.

**Trigger:** ownership is reconstructed from a mutable/rotatable session key after async work was dispatched.

**Detectable signal:** dispatch-time key no longer names the live continuation, or multiple live sessions can plausibly claim the same historical key.

**Fail-closed response:** persist an origin identity at dispatch, maintain lineage/continuation resolution separately, and require positive ownership before injection.

**Recovery witness:** merged upstream commit plus focused regression tests in the patch.

**Scope:** exact to Hermes TUI async-delegation routing across compression/session rotation. It does not prove that terminal-process completions (#84174) are fixed by the same merged path.

## FE-457 — A background completion can be durable and correctly routed yet still cross the user-authorization boundary by synthesizing a new user turn after the real client request ended
**Source:** Hermes open PR #86011, fixing #85957.
- https://github.com/NousResearch/hermes-agent/pull/86011

The reported API-server path lets a `/v1/chat/completions` or `/v1/runs` request dispatch background delegation and finish. A later child completion can then self-POST to the API server as `role=user`, creating a new authenticated model turn that the client never sent. The PR describes this as capable of driving additional tool actions after the client-owned turn has ended.

The proposed repair distinguishes non-push API sessions from push-capable messaging adapters: API-server delegation completions become durable `deferred` rows, no self-POST occurs, and the next real client request atomically consumes same-session results exactly once as explicitly non-actionable background context. The PR reports focused tests and real-environment verification, but it remains open/unmerged.

**Trigger:** completion delivery mechanism equates “background result is ready” with “a new user turn is authorized.”

**Detectable signal:** session history gains a new user/assistant turn with no corresponding client request; idle completion causes model/tool execution.

**Fail-closed response:** on pull/client-owned surfaces, park completion durably and require the next real client request to supply the authorization boundary; completion context itself must not synthesize user authority.

**Recovery witness:** contributor PR #86011 with focused tests, still unmerged.

**Scope:** exact to Hermes non-push API-server async-delegation completion delivery. Push-capable adapters are explicitly a different contract.

## FE-458 — Duplicate wakeups can produce overlapping runs and duplicate external effects even when both runs are individually valid
**Source:** Paperclip issue #4393 (open; Paperclip 0.3.1, `local_trusted`, `gemini_local`).
- https://github.com/paperclipai/paperclip/issues/4393

A reporter created one issue with `assigneeAgentId` and observed two `issue_assigned` wakeups about 15 seconds apart. The first run (`6d7b749d`) ran 10:36:35–10:37:04 while the second (`af6978e5`) ran 10:36:50–10:37:21, so they overlapped. Both independently created a follow-up issue in another company, yielding two distinct downstream issues (`EWI-11`, `EWI-12`) because neither saw the other's work.

**Trigger:** duplicate dispatch for the same assignment is admitted while the first run is still active; no single-flight/logical-effect claim prevents both from progressing.

**Detectable signal:** same wake reason/assignment produces overlapping run intervals and two distinct downstream records.

**Fail-closed response:** dedupe/claim at the logical wake or effect boundary, not only inside each run; second wake must reconcile against an active/committed logical operation before side effects.

**Recovery witness:** none accepted yet; issue remains open. The reporter's sentinel workaround is application-level and not treated as a framework repair.

**Scope:** reporter-scoped to the stated Paperclip 0.3.1 assignment path and configuration.

## FE-459 — Recovery can be idempotent at the “recovery issue” layer while still duplicating the non-idempotent business effect contained in the recovered task body
**Source:** Paperclip issue #5267 (open; observed v2026.428.0).
- https://github.com/paperclipai/paperclip/issues/5267

Paperclip's recovery path already had a mechanism intended to prevent duplicate active recovery issues, yet the reporter observed `stranded_issue_recovery` re-running a task body containing `POST /agents`. The original stalled task plus recovery created `Designer`, `Designer 2`, and `Designer 3`, each a distinct pending-approval agent. A separate heartbeat case produced `Engineer 1` through `Engineer 5` before the issue could be marked done.

This is a useful layer-separation counterexample: deduping the recovery orchestration record does not make the recovered business mutation idempotent. The logical effect needs its own stable identity or authoritative readback.

**Trigger:** recovery replays a non-idempotent create command/body without an effect-level idempotency key or existence reconciliation.

**Detectable signal:** one source issue/recovery lineage yields multiple distinct records differing only by generated/suffixed identity.

**Fail-closed response:** bind retries to a stable logical-effect key at the mutation endpoint, or reconcile the intended business object before replay. Recovery-job uniqueness alone is insufficient.

**Recovery witness:** none accepted yet; issue remains open.

**Scope:** reporter-scoped to the Paperclip recovery/create-agent examples. It does not prove all stranded-task recovery paths duplicate effects.
