## New failure evidence

### FE-428 — Concurrent resume can violate consume-once even when sequential resume looks correct; a pinned-framework conformance study observed the gated effect firing once per racing process
**Primary source:** Sajjad Khan, *Resume Means Resume: A Machine-Checked Conformance Contract for Checkpoint, Interrupt, and Resume Semantics in Workflow Persistence Layers*, arXiv:2608.03836 (2026-08-04), https://arxiv.org/abs/2608.03836

The paper defines machine-checkable persistence properties and exercises pinned releases with a deterministic, LLM-free fault harness. Its strongest coordination counterexample is that consume-once can hold under sequential delivery yet fail under concurrent delivery: when `k` processes resume one parked interrupt, the gated effect can fire `k` times. Across its reported cross-process matrix, failure saturation is 1.0 in 36 of 40 cells and the failure crosses hosts. The same study reports that LangGraph 1.2.9 is exactly-once across ordinary interrupt/resume in the tested path but can re-execute durably recorded work after a real SIGKILL, so crash recovery and explicit resume do not share one effect guarantee merely because they use one persistence API.

The paper's repaired cross-process cell moves consumption to a shared-store read-path claim before any node executes, serving one racer and refusing the rest. This supplies a useful matched shape: sequential tests alone are insufficient to establish consume-once; the race must be tested at the authority-consumption point.

**Phase-1 failure mapping:** trigger = two or more processes concurrently resume the same parked interrupt; detectable signal = the same interrupt authority is accepted by more than one process / gated effect count exceeds one; fail-closed response = atomically claim consumption in shared durable state before executing any gated node; recovery witness = exactly one racer receives authority and all others are rejected without effect execution.

**Scope guard:** exact to the pinned framework releases and deterministic fault matrix reported by arXiv:2608.03836. It is not evidence that every current release of those frameworks has the same profile or that all workflow systems violate consume-once.

### FE-429 — A late background result can mutate the *successor* session/branch because completion writes through mutable current ownership; oh-my-pi merged a start-time ownership binding
**Primary sources:** can1357/oh-my-pi issue #5743 and merged PR #5747, https://github.com/can1357/oh-my-pi/issues/5743 and https://github.com/can1357/oh-my-pi/pull/5747

Issue #5743 deterministically reproduces a background `bash` started in one session, followed by `new_session`, `switch_session`, `branch`, or another transcript-leaf rewrite before the command completes. On the affected main revision, `recordBashResult()` writes through the mutable live `sessionManager`; pending bash messages and minimized-output artifacts lack the originating session/branch identity. The late `old-output` is therefore written into the replacement session or new branch, and a later model prompt can consume stale output from the predecessor. An intentionally dropped original session can even be recreated by the straggling result.

Merged PR #5747 captures a ref-counted `BashSessionTarget` when execution starts and resolves each later transition against that captured owner: same file/leaf stays current, moved leaf appends off-leaf, changed file uses a detached clone, and an intentional drop discards the result. Its focused real-`AgentSession` suite is reported as 1 pass / 8 fail on main and 9 pass after the fix, with broader related session/RPC suites also passing.

**Phase-1 failure mapping:** trigger = effect-bearing/background child starts under session/branch N and finishes after active ownership changes to N+1; detectable signal = result's captured origin identity differs from mutable active session/leaf at completion; fail-closed response = route by captured origin ownership (or discard when origin was intentionally dropped), never by current mutable pointer alone; recovery witness = late N result does not appear in N+1 transcript while valid off-leaf/original placement still succeeds.

**Scope guard:** exact to oh-my-pi's user-initiated background bash/session transition path covered by #5743/#5747. It directly demonstrates a late result mutating successor state, but it does not prove every generic child-tool/result channel shares the same bug.

### FE-430 — Cross-process turn serialization needs durable ownership *and* post-wait state reload; otherwise a completed reply can be lost against a long-lived stale owner
**Primary sources:** NousResearch/hermes-agent issue #84234 and merged PR #86383, https://github.com/NousResearch/hermes-agent/issues/84234 and https://github.com/NousResearch/hermes-agent/pull/86383

Issue #84234 reports Desktop and an independent CLI process running turns on the same session while one process holds a long compression lease. During the 2026-08-11 incident, the external CLI compression windows lasted 106.8s and 195.8s; Desktop completed turns but their durable flushes were rejected after only a short wait, yielding user-visible `session_persistence_failed` behavior. The report distinguishes this from ordinary SQLite lock contention: 20 `being compressed by another writer` occurrences and zero `database is locked` occurrences were recorded in the same window.

Merged PR #86383 adds a cross-process SQLite `session_turn_leases` table with acquire/refresh/release, expired/dead-holder reclamation, and `SessionTurnLeaseLostError` fencing. Importantly, it also performs a **post-admission transcript reload when acquisition was contended** before running the turn, rather than treating acquisition alone as sufficient. The PR reports 49 targeted tests before versus 84 after, including 35 new tests.

**Phase-1 failure mapping:** trigger = two processes attempt the same session while one holds long-lived persistence/compression ownership; detectable signal = second process waited/contended and its pre-wait transcript snapshot may be stale, or it loses lease authority before flush; fail-closed response = durable cross-process claim, fenced writes, and reload latest transcript after waiting before execution; recovery witness = contending processes serialize without silently dropping a completed reply and the admitted process acts on post-wait state.

**Scope guard:** exact to Hermes session-turn/compression paths covered by #84234/#86383. It does not establish that all Hermes message-delivery duplicate paths are solved, nor that SQLite leases alone guarantee exactly-once external effects.

### FE-431 — A liveness timeout can manufacture a disconnect when the protocol's legitimate idle wait is longer than the local abort guard
**Primary source:** merged maintainer PR openclaw/openclaw #83320 (closes #83264), https://github.com/openclaw/openclaw/pull/83320

OpenClaw's isolated Telegram ingress could pass a high `channels.telegram.timeoutSeconds` value directly as the Bot API `getUpdates` long-poll timeout while retaining a fixed 45s hard request abort. With a configured 90s poll, the local guard aborted at 45s before Telegram could return the legitimate empty success, so health remained disconnected and idle accounts could enter restart loops. The maintainer-authored merged fix caps isolated long polling below the hard guard; its documented example maps 90s to 40s.

The PR reports 57 focused tests across timeout/polling/fetch-abort files plus changed-lane checks. It explicitly says no live Telegram account was exercised and a proof-override label was used, so this run treats the fix as contract/seam-tested rather than live end-to-end evidence.

**Phase-1 failure mapping:** trigger = valid idle operation whose protocol wait budget exceeds a local liveness/abort budget; detectable signal = abort fires before a legitimate empty-success heartbeat can occur; fail-closed response = make the observation window compatible with the protocol timeout (or use an independent liveness witness) rather than declaring deadness from self-induced abort; recovery witness = high configured poll duration is bounded below the hard guard and empty poll success remains observable in tests.

**Scope guard:** exact to OpenClaw isolated Telegram long polling covered by merged #83320. No claim is made that the live Telegram restart loop was directly re-run in that PR.

### FE-432 — Non-atomic `read → delete → dispatch` can produce either duplicate resume application or permanent loss; a session lock cannot repair a snapshot loaded before the lock
**Primary sources:** agentscope-ai/agentscope issue #2227 and open PR #2235, https://github.com/agentscope-ai/agentscope/issues/2227 and https://github.com/agentscope-ai/agentscope/pull/2235

AgentScope issue #2227 describes a shared Redis resume queue consumed by `XRANGE` followed by `XDEL`. In the reported deterministic interleaving, process A and B can both read the same resume event before either deletes it; A deletes and dispatches, B's delete is a no-op but B still dispatches the same event. The issue also identifies the opposite loss window: A deletes the only event and dies before durable dispatch, permanently losing the HITL/external-tool resume. A third path stores retry only as an in-process `asyncio.Task`, which disappears with process death.

The report further notes that the distributed session lock does not close the duplicate window because session state is loaded and the stateful agent constructed **before** the lock. Two processes can therefore load the same parked state, acquire the lock sequentially, and each apply the same resume against stale pre-lock snapshots.

Open PR #2235 proposes a dedicated Redis consumer-group stream with explicit ACK, reclaim, heartbeat, bounded concurrency, durable idempotency, and post-lock reload. It remains open, so this run records the failure/repro and proposed acceptance contract but not a merged guarantee.

**Phase-1 failure mapping:** trigger = multiple consumers race a two-step queue consume or a consumer dies after destructive dequeue; detectable signal = one stream entry observed by multiple consumers, or deleted entry lacks durable handoff/ACK evidence; fail-closed response = claim/ACK protocol plus stable resume identity and reload latest state inside the session lock; recovery witness = forced crashes at read/claim/commit-before-ACK boundaries eventually yield one state application, with redelivery rejected idempotently.

**Scope guard:** issue-author/member reporter evidence for AgentScope's specified multi-instance Redis resume path; PR #2235 is open. External tool side effects still require their own idempotency beyond resume-level dedupe, as the issue itself states.

### FE-433 — Spending single-use approval authority before terminal outcome can make a successful side effect look like a never-existing approval; Microsoft merged an occurrence-aware lifecycle repair
**Primary sources:** microsoft/agent-framework issue #7458 and merged PR #7594, https://github.com/microsoft/agent-framework/issues/7458 and https://github.com/microsoft/agent-framework/pull/7594

Issue #7458 shows AG-UI approval resume being consumed and the approved tool executed at request ingress before the subsequent model run. A provider/transport/replica failure after that point leaves no outcome record. In the standalone repro, POST #1 consumes the approval and executes `deploy_change('prod')`, then the simulated provider call fails; POST #2 with the identical resume receives `APPROVAL_RESUME_NOT_FOUND`, the same result as an interrupt ID that was never pending. The reporter also reproduced the shape in a deployed Azure Container Apps incident on 2026-07-30. After an initial automated non-repro comment, the reporter re-ran against the then-current release/main and reproduced again; a maintainer later closed the issue as fixed in #7594.

Merged PR #7594 introduces an occurrence-aware approval lifecycle for registration, claims, execution ownership, recovery, terminal outcomes, replay deduplication and bounded retention. Its stated effect is that approval retries/reconnects are deterministic and fail closed when execution outcome is uncertain, with replay protection and multi-call duplicate-ID handling retained.

**Phase-1 failure mapping:** trigger = single-use approval is consumed and its effect executes before the enclosing run reaches a durable terminal outcome; detectable signal = resume authority is absent on retry while an executed-effect/result record exists or outcome is uncertain; fail-closed response = lifecycle claim with explicit execution/outcome ownership rather than collapsing consumed/applied/never-pending into one `NOT_FOUND`; recovery witness = retry/reconnect can distinguish terminal replay, uncertain execution, and never-pending without re-executing an effect.

**Scope guard:** exact to Microsoft Agent Framework Python AG-UI approval lifecycle covered by #7458/#7594. The merged PR's broader lifecycle claims are not generalized to unrelated approval protocols.

### FE-434 — Idempotency can itself create a retry dead-end if the cache records a hard failure before the final response is classified
**Primary source:** open NousResearch/hermes-agent PR #77800 (closes #77797 if merged), https://github.com/NousResearch/hermes-agent/pull/77800

PR #77800 documents two coupled API-server wake retry failures. First, outcome-unknown timeout/connection/429 retries without a producer-stable key can overlap multiple agent runs for one logical delivery. Second, an initial idempotency implementation cached the producer result **before** the chat handler mapped an empty failed/partial result to HTTP 502; a durable replay using the correct stable key could then receive the same cached 502 repeatedly without re-running the agent, exhausting the producer retry budget.

The proposed fix keeps a stable opaque key across one logical delivery, coalesces equal in-flight requests, but admits only successful/soft outcomes to durable replay; a hard 502 is returned to current joiners without becoming the replay terminal, so a later durable replay with the same key can recompute. The PR reports 118 affected-surface tests and a full-suite candidate-only failure delta of zero, but it remains open and explicitly notes that one exact old-waiter/new-replacement overlap is not directly covered by the new regression.

**Phase-1 failure mapping:** trigger = idempotency record is committed at an internal intermediate outcome that later maps to a retryable hard failure; detectable signal = stable-key retry repeatedly replays the same hard error without a completed logical effect; fail-closed response = bind durable dedupe admission to the logical terminal success/acceptable outcome, while still coalescing the in-flight attempt; recovery witness = first same-key attempt can return 502, later durable same-key replay re-runs and succeeds exactly once at the logical outcome layer.

**Scope guard:** open PR evidence for Hermes' non-streaming API-server wake path only. It is not a merged guarantee and does not cover streaming requests or arbitrary idempotency caches.
