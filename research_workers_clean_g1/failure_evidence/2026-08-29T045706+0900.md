## New failure evidence

### FE-413 — Retrying one logical send under a fresh transport/client identity can bypass an existing command journal and multiply steering effects
**Primary source:** PrimeIntellect prime-agent issue #821, https://github.com/PrimeIntellect-ai/prime-agent/issues/821

The reported daemon path already has a durable command recovery journal keyed by `(clientId, commandId)`, and reconnect replay within one `DaemonClient` reuses the same identity. The separate `sendRemoteAgentSessionMessage` retry loop instead creates a new `DaemonClient` on each attempt; each client has a fresh random protocol client ID and a request counter starting at zero. The same logical `send_message` retry therefore arrives under a new journal key. The receiver also mints a fresh server-side `agentmsg_<uuid>` for each accepted attempt and has no message-level dedupe on that path. The reporter measured five timeout-reported attempts producing five identical deliveries under five distinct `agentmsg_` IDs.

**Phase-1 failure mapping:** trigger = local timeout/transport failure after the supervisor may already have accepted a send; detectable signal = retry's logical instruction is the same but command/client/message identities change; fail-closed response = preserve one logical idempotency identity across retry or reconcile the prior command before issuing another; recovery witness = N retries of one logical instruction yield one journaled/delivered effect.

**Scope guard:** reporter-supplied prime-agent 0.7.0/main-path evidence. The issue was closed administratively when maintainers moved the backlog to discussion-first triage; the closure comment does not confirm a technical fix. No maintainer-confirmed resolution is claimed.

### FE-414 — A tool can report “failed to start” after its message has already been queued, claimed and delivered; retrying the reported failure can duplicate a real effect
**Primary source:** NousResearch/hermes-agent issue #97051 and discussion comments, https://github.com/NousResearch/hermes-agent/issues/97051

On the reported cross-connection relay path, `message_agent` writes a relay envelope before starting a separately gated waiter command. The Desktop drain loop can claim and dispatch that envelope immediately. If the waiter command is then blocked by the approval gate, the tool returns a delivery failure even though the recipient already received the message; only the sender-side reply waiter failed. The reporter states this was confirmed twice on a live local+remote-gateway setup and cites an envelope that moved through queued/claimed/dispatched state while the sending turn reported the block. A contributor explicitly scoped the intended fix around making that reporting truthful with a race-focused regression test.

**Phase-1 failure mapping:** trigger = external/durable effect becomes deliverable before a later local start/approval step fails; detectable signal = caller status says failure while authoritative queue/claim/delivery state proves the effect exists; fail-closed response = do not instruct retry from the local error alone; order the gate before enqueue or reconcile/unwind the durable effect; recovery witness = a reported failure implies no deliverable envelope, or authoritative readback changes the outcome to accepted/already-delivered.

**Scope guard:** open reporter-confirmed issue as of 2026-08-29, with a contributor taking the task but no merged fix observed. This is exact to the reported Hermes relay path and configuration; it is not a generic guarantee about `message_agent`.

### FE-415 — Own matched probe: false failure after effect creation produces two deliveries; gate-before-effect or authoritative readback holds the logical effect to one
**Own probe:** `research_workers_clean_g1/failure_evidence/probes/2026-08-29T045706+0900-false_failure_retry.py` and `.json`

A deterministic three-arm simulation fixes one logical effect `effect-42` and a caller that retries a `failed_to_start` outcome:
- enqueue-before-gate: first effect `msg-1` is delivered, then the caller is told failure; retry creates `msg-2` -> delivered count **2**;
- gate-before-enqueue: first failure creates no transport effect; the later successful retry creates `msg-1` -> delivered count **1**;
- enqueue plus authoritative logical-effect readback: the effect is already delivered when the later local path would otherwise look failed; readback changes the receipt to `accepted_via_readback` and caller skips retry -> delivered count **1**.

**Phase-1 failure mapping:** trigger = ambiguous/false local failure after durable effect; detectable signal = authoritative logical-effect state conflicts with local status; fail-closed response = gate before effect or reconcile by logical-effect identity before retry; recovery witness = exactly one durable effect after the retry decision.

**Scope guard:** single-process deterministic simulation only. It tests ordering/readback mechanics; it is not production relay/network evidence and does not validate Hermes implementation details.

### FE-416 — Dropping every transport retry to avoid duplicates can permanently lose the only delivery; Vercel Chat merged a fix that processes retries and dedupes by stable event identity
**Primary sources:** vercel/chat issue #666 and merged PR #667, https://github.com/vercel/chat/pull/667

Both Slack Socket Mode handlers had acked and discarded all envelopes with `retry_num > 0`. Slack can send a retry because the original delivery occurred while no socket was open during restart/deploy/connection refresh; in that case the retry is the only delivery the app sees, so unconditional retry dropping loses the event. PR #667 merged on 2026-07-02 and routes retry envelopes through normal processing while retaining `Chat.processMessage` dedupe on stable Slack message/event identity. It also raises the default dedupe TTL from 5 to 10 minutes because Slack's final retry arrives around the old 5-minute boundary, where expiration could turn a true retry into a double-process. The PR reports end-to-end validation and dedicated retry/dedupe tests.

**Phase-1 failure mapping:** trigger = at-least-once transport retries after an unseen original delivery; detectable signal = retry metadata plus stable event/message identity; fail-closed response = do not classify all retries as duplicates; process them through a dedupe layer whose identity and retention cover the retry horizon; recovery witness = unseen retry is processed, previously processed retry is suppressed.

**Scope guard:** exact to the merged Vercel Chat Slack Socket Mode behavior and its documented retry timings/dedupe implementation.

### FE-417 — The opposite failure also occurs: a callback adapter that has a dedupe cache but never consults it queues the same platform retry multiple times
**Primary source:** NousResearch/hermes-agent merged PR #10588, https://github.com/NousResearch/hermes-agent/pull/10588

The WeCom callback adapter declared `_seen_messages` and a TTL constant but did not check them in `_handle_callback()`. WeCom retries callback delivery on timeout, so each retry was treated as a fresh message and queued again. PR #10588 merged on 2026-04-16, adds the TTL-aware message-ID check before queueing, returns success for a duplicate, prunes the cache, and reports 40 WeCom tests passing.

**Phase-1 failure mapping:** trigger = platform redelivery with the same callback message ID; detectable signal = repeated stable message ID within the dedupe interval; fail-closed response = suppress a retry only after determining it represents an already-admitted logical message; recovery witness = duplicate callback receives an acknowledgement without a second queue insertion.

**Scope guard:** exact to the merged Hermes WeCom callback adapter change. It does not establish the correct claim lifecycle for failures after admission; FE-418 covers that distinct boundary.

### FE-418 — Marking a message “seen” before processing succeeds can turn at-least-once recovery into silent loss; an open WeCom fix treats dedupe as a claim lifecycle
**Primary sources:** NousResearch/hermes-agent issue #62860 and open PR #62861, https://github.com/NousResearch/hermes-agent/issues/62860 and https://github.com/NousResearch/hermes-agent/pull/62861

The reported `MessageDeduplicator.is_duplicate()` writes the message ID into the seen set at check time. On WeCom, acknowledgement happens after processing; if processing raises after this early mark, WeCom redelivers the same `msgid`, but the surviving adapter sees the stale mark and suppresses every retry for the 300-second TTL. The issue includes a deterministic fault-injection reproduction where the first handler call raises and the same-ID redelivery never reaches the handler a second time. PR #62861 remains open; it changes the conceptual model to a claim: release when processing did not complete, retain after a completed turn even if reply delivery later failed, and cover batching/background paths. The PR reports 157 relevant tests passing plus one pre-existing environmental failure.

**Phase-1 failure mapping:** trigger = dedupe claim recorded before success, followed by processing failure and same-ID redelivery; detectable signal = claim exists but no completed-handler witness exists; fail-closed response = release the claim exactly when processing did not complete, while retaining it for completed work to prevent replaying tool side effects; recovery witness = pre-completion failure permits redelivery, completed processing suppresses it.

**Scope guard:** confirmed reporter path is WeCom because its ack/redelivery semantics create this recovery window. The issue itself notes DingTalk's immediate-ack path is not affected in practice. The PR is open; no merged Hermes guarantee is claimed.

### FE-419 — Durable resume can still reconstruct from stale adjacency state instead of the exact suspended-step payload; Mastra merged a regression-tested correction
**Primary source:** mastra-ai/mastra merged PR #16066, https://github.com/mastra-ai/mastra/pull/16066

Before the fix, direct workflow resume could validate a resumed step against `prevOutput`, even when the suspended step had already persisted its own payload in `stepResults[step.id].payload`. If the previous-step output was stale, resume could fail despite the correct suspended payload being available. PR #16066 merged on 2026-05-08 and changes direct resume to prefer the persisted suspended payload, matching the conditional-branch resume path; it adds a regression test specifically for resuming with stale previous output.

**Phase-1 failure mapping:** trigger = resume after suspension when adjacent/previous output no longer matches the suspended step's saved input; detectable signal = resumed-step checkpoint payload and reconstructed `prevOutput` disagree; fail-closed response = bind resume to the suspended step's own persisted payload before falling back to adjacency-derived state; recovery witness = the stale-previous-output regression resumes using the saved payload.

**Scope guard:** exact to Mastra's workflow resume path and merged test. It is not a claim that adjacency-derived state is always stale.

### FE-420 — Labeling a mid-tool-call partial stream as terminal `stop` can create false completion and an unrecoverable user-driven retry loop
**Primary source:** NousResearch/hermes-agent merged PR #32012, https://github.com/NousResearch/hermes-agent/pull/32012

A prior safety change represented a mid-tool-call partial-stream stub with `finish_reason="stop"` to avoid auto-retrying a potentially side-effectful tool. That terminal label bypassed all continuation machinery: the turn ended with warning text, and a user's later “continue” caused the model to retry the same oversized tool call, hitting the same stale condition repeatedly. PR #32012 merged on 2026-05-25 changes the stub to `finish_reason="length"`, attaches dropped-tool names, and routes recovery through a smaller-chunk continuation prompt. It explicitly preserves `tool_calls=None`, so continuation does not auto-execute the partial tool; retries are bounded to three. The PR reports 50 targeted tests passing.

**Phase-1 failure mapping:** trigger = stream truncation inside an unfinished tool call; detectable signal = partial tool-call state exists despite a terminal-looking finish classification; fail-closed response = distinguish “incomplete but safe to continue as text” from true terminal completion without auto-executing a partial tool; recovery witness = continuation path is entered with no tool auto-execution and bounded retry behavior.

**Scope guard:** exact to the merged Hermes partial-stream continuation path and its tests. It does not prove all `finish_reason="stop"` uses are false completion.

### FE-421 — A run configured as durable can silently become entirely non-durable when an override replaces the root capability
**Primary source:** pydantic/pydantic-ai issue #6911, https://github.com/pydantic/pydantic-ai/issues/6911

The issue reports that `agent.override(spec=...)` with a capabilities list replaces the agent's root capability, which removes the attached durability capability for the duration of the override. A real Prefect 3.7.7 probe records baseline execution as `['model:task', 'task', 'model:task']`, but under the spec override as `['model:FLOW-CODE (not durable)', 'FLOW-CODE (not durable)', 'model:FLOW-CODE (not durable)']`: every model and tool unit escaped durable tasks with no error or warning. The durability capability also cannot simply be re-listed in the spec because its serialization name is `None`. The issue is still open; a contributor proposed a fail-loud `UserError` approach but no merged fix was observed.

**Phase-1 failure mapping:** trigger = spec override replaces the capability root inside a durable container; detectable signal = expected durability capability/task wrappers disappear from the executing capability tree; fail-closed response = reject an override that would silently drop durability, or explicitly preserve a capability that is required to survive override; recovery witness = every model/tool unit remains in durable tasks or the run fails before executing side effects.

**Scope guard:** empirical probe is Prefect 3.7.7 only. The issue discusses DBOS/Temporal consequences from the shared source mechanism, but those engines were not probed; this checkpoint does not promote those consequences to empirical evidence.
