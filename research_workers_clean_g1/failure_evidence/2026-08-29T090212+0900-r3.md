## FE-448 — Provider request IDs can be validly reused across Turns, so request-ID-only response routing can mutate historical state and strand the live Turn
**Sources:** current `tutti-os/tutti` troubleshooting documentation and Host conformance test.
- https://github.com/tutti-os/tutti/blob/main/docs/conventions/troubleshooting/agent-session-lifecycle.md
- https://github.com/tutti-os/tutti/blob/main/packages/agent/host/conformance/interactive_response.go

Tutti's lifecycle troubleshooting guide documents a concrete interaction failure class: an approval/question can remain waiting after the user responded because a provider request ID is transport-local rather than a session-wide durable identity. The same provider request ID may validly appear in two different Turns. Selecting an Interaction or deduplicating a runtime operation by request ID alone can therefore bind the response to historical Turn state and leave the current Turn pending.

The documented repair is exact identity binding: carry `(workspaceId, agentSessionId, turnId, requestId)` into Host, select the Interaction atomically by that tuple, and scope runtime-operation idempotency to the same tuple rather than scanning/guessing historical rows.

Current conformance source supplies the matched control. `runInteractiveResponseReusedRequestID` seeds `turn-previous` and `turn-current` with the **same** `provider-request` ID. It responds to the previous tuple first and explicitly asserts that the current tuple is still `pending`; then it responds to the current tuple and requires both interactions to be answered under distinct operation IDs. A companion race control permits two identical concurrent answers to replay as answered, while conflicting answers resolve as one answered and one superseded.

**Trigger:** transport request ID is reused in a later Turn -> response path treats that request ID as globally durable or session-unique -> it selects/deduplicates against the wrong historical Interaction.

**Detectable signal:** command tuple `(workspace, session, turn, request)` disagrees with the selected/stored operation tuple, or responding to an older tuple changes the status of the current Turn sharing the same provider request ID.

**Fail-closed response:** never route or deduplicate an interactive response by provider request ID alone; require the exact durable tuple and atomically reject/supersede mismatched competing operations.

**Recovery witness:** with the same provider request ID deliberately reused across two Turns, answering the previous tuple leaves the current tuple pending, then the current tuple is answered separately with a distinct operation ID; conflicting concurrent answers do not both become authoritative.

**Scope:** exact to Tutti's interactive-response/runtime-operation path and its current conformance contract. This is a stale-response/historical-binding counterexample, not a claim that all provider request IDs are reused or that every framework needs this exact four-field tuple.
