## New findings

### C113 — a provenance-complete candidate serializer already exists; current `choice_set` throws most of it away

`ActionFrontierNode.to_dict()` already serializes every currently available candidate field needed for Stage-A provenance without inventing hidden state:

- `node_id`, `branch_id`;
- `obligation_id`, `obligation_version`;
- complete typed `proposal` = action + payload + proposal score + metadata;
- `proposal_source`, `proposal_batch_id`, `proposal_model_tier`;
- `cached_at_workspace_version`;
- full execution-cost estimate including source/sample count/estimator version;
- the complete `priority_explanation` used by the deterministic scheduler.

`StructuredActionProposal.to_dict()` in turn preserves the full typed action/payload plus score and metadata. By contrast, `select_admissible_action()` currently reduces each candidate to only node/branch/action kind, estimated cost and budget admission.

Therefore the canonical Stage-A candidate row should be exactly the immutable `ActionFrontierNode.to_dict()` payload plus decision-local fields that do not belong to the node itself: rank index, frozen `BudgetAdmission`, experiment effect class, experiment-allowed boolean and exclusion reason. A separate lossy feature vector can be derived for learning, but the causal log should retain the complete source object.

### C114 — define two hashes, not one: candidate identity and scheduler ordering

The deterministic baseline depends on `frontier.ranked()` ordering, not merely on the unordered candidate set. A single set hash can therefore fail to bind the exact baseline decision context.

Recommended canonicalization:

1. `candidate_set_sha256`: SHA-256 over canonical JSON of full candidate rows sorted by stable `node_id` and excluding rank-dependent fields;
2. `ranked_choice_sha256`: SHA-256 over canonical JSON of the same full rows in the exact `frontier.ranked()` order including `rank_index` and frozen budget admission.

Canonical JSON should use UTF-8, sorted object keys, compact separators, and no nonsemantic timestamps. Logging both hashes detects either provenance drift or ranking-policy drift while still allowing the underlying set to be compared across policies.

### C115 — exact `ExecutionDecisionEvent` hook and schema can be specified without changing proving semantics

The correct hook is after `select_admissible_action(frontier, snapshot, ...)` has frozen the ranked choice/budget view and immediately before `frontier.consume(...)` mutates frontier state. At that point proposal generation, validation, cache insertion and cost estimation have already happened, while the selected action has not yet executed.

Minimum durable event:

```json
{
  "event": "execution_decision",
  "schema_version": 1,
  "run_id": "<state.sample_id>",
  "task_id": "<task.task_id>",
  "decision_index": 0,
  "decision_id": "<run_id>:exec:0",
  "workspace": {
    "workspace_id": "...",
    "version": 1,
    "parent_version": null,
    "sha256": "<sha256(canonical workspace.to_dict())>"
  },
  "frontier_policy": "action_cost_aware_v1",
  "candidate_set_sha256": "...",
  "ranked_choice_sha256": "...",
  "candidates": ["<canonical full candidate rows>"],
  "legal_node_ids": ["..."],
  "deterministic_baseline_node_id": "...",
  "behavior_policy": {
    "policy_id": "...",
    "policy_version": "...",
    "type": "epsilon_mixture",
    "epsilon": 0.25,
    "probability_by_node_id": {"node": 1.0}
  },
  "chosen_node_id": "...",
  "chosen_propensity": 1.0,
  "budget_snapshot": {},
  "cost_estimator": {
    "source": "...",
    "snapshot_id": "...",
    "snapshot_sha256": "...",
    "estimator_version": "..."
  },
  "ledger_boundary": {
    "event_count_before": 0,
    "tail_event_id_before": null
  }
}
```

The workspace fingerprint can be computed directly from `ProofWorkspace.to_dict()`, which already serializes workspace id/version/parent, specification, obligation graph, accepted facts, branches, roots and status. No extra model-visible state is needed.

The decision event must be durably appended before `frontier.consume`. If a later branch-validity check unexpectedly invalidates the consumed node, that is an outcome (`not_executed_after_decision`) rather than a reason to delete the decision record.

### C116 — `ExecutionOutcomeEvent` should carry verified progress and execution cost, not pseudo-reward for structural edits

A separate outcome event should be keyed by `decision_id` and emitted on every post-decision path, including no-op/pre-execution invalidation, normal continuation and terminal return. Minimum fields:

- chosen `node_id` and execution status/reason;
- pre/post workspace version and post-workspace SHA-256;
- exact `ledger_event_ids` already produced by `action_cost_observed` plus event count/tail after execution;
- actual execution-cost vector;
- terminal `ControllerResult.accepted` when assembly was reached;
- compact verifier-grounded progress labels: newly accepted fact IDs/count and obligation IDs that newly became checker+safety accepted.

For initial policy learning, immediate positive labels should be limited to kernel/checker-grounded facts and final accepted proof. `DECOMPOSE`, `PROPOSE_ARGUMENT`, `REFINE_ARGUMENT` and `CHANGE_REPRESENTATION` should not receive hand-written positive pseudo-reward merely for changing workspace shape. Their credit should arrive through sequential return/value if they enable later verified facts or terminal success. This avoids teaching the controller to manufacture structure.

### C117 — immutable proposal-batch provenance needs a third append-only event type

Because one model request can generate multiple cached `ActionFrontierNode`s with the same `proposal_batch_id`, provider-generation cost is a shared batch fact. Current `attribute_proposal_batch()` rewrites the provider ledger metadata to the latest consuming action, destroying many-to-many provenance.

Recommended event:

```json
{
  "event": "proposal_batch_consumption",
  "schema_version": 1,
  "run_id": "...",
  "decision_id": "...",
  "decision_index": 0,
  "proposal_batch_id": "proposal:<run_id>:<n>",
  "node_id": "...",
  "proposal_source": "model",
  "proposal_model_tier": "cheap|strong|...",
  "workspace_version_before": 1,
  "provider_ledger_event_ids": ["..."]
}
```

Provider request/usage/charge/tool events remain immutable with stable request/batch identity and no action-specific reassignment. Consumption events are pure joins and must not contribute any additional cost themselves.

Regression invariant for a two-proposal batch `B` consumed as `N1` then `N2`:

1. snapshot serialized provider ledger events for `B` before either consumption;
2. consume/execute `N1`, append join `(B,N1,D1)`;
3. later consume/execute `N2`, append join `(B,N2,D2)`;
4. assert provider ledger events byte/canonical-JSON equal the pre-consumption snapshot and retain no latest-consumer overwrite;
5. assert both consumption joins exist and are distinct;
6. assert reconciled run token/API totals are identical before vs after adding consumption joins, preventing double counting.

### C118 — existing trace-store durability primitive is sufficient; the missing piece is per-decision invocation of it

`JsonlTraceStore` already has `_atomic_append_text`: it reconstructs the file into a same-directory temporary file, fsyncs it, then installs via `os.replace`, preventing partial JSON-line writes. The current problem is not lack of an atomic persistence primitive; it is that `append_result()` is only called after a complete `ControllerResult` exists.

A minimal instrumentation path is therefore to expose an `append_event` / `append_events` method using the existing atomic primitive and inject an optional decision-event sink into the structured runtime. The sink should append `execution_decision` before mutation, then `proposal_batch_consumption` and `execution_outcome` as they occur. Final `append_result()` remains a summary projection and must tolerate already-present per-decision events rather than duplicating them.

### C119 — safe epsilon logging has a stricter fallback condition than merely `L < 2`

For initial randomized collection, define the experiment pool as candidates satisfying all three conditions:

1. present and valid in the frozen current frontier;
2. budget-admitted under the frozen snapshot;
3. in the explicitly allowed low-effect structural action set.

Randomize only when the deterministic baseline action itself belongs to that pool and the pool has at least two members. Then, for pool size `L`, assign baseline probability `(1-epsilon)+epsilon/L` and each other pool action `epsilon/L`; actions outside the pool have probability zero and an explicit exclusion reason.

If the deterministic baseline is outside the experiment-safe pool, or `L < 2`, do **not** force a safe-subset action merely to collect data. Fall back to the deterministic baseline with propensity 1 and log `randomization_skipped_reason`. This keeps collection behavior a controlled perturbation of the production baseline rather than silently changing the scheduler's admissible semantics.

## Updated synthesis

The next implementation target is now precise enough to be regression-tested before any policy learning:

1. preserve the full `ActionFrontierNode.to_dict()` candidate rows;
2. bind candidate identity and scheduler order with two canonical hashes;
3. append a decision event before `frontier.consume`;
4. replace mutable proposal-batch action attribution with append-only consumption joins;
5. append an outcome event on every post-decision path;
6. use only verifier-grounded immediate progress labels;
7. randomize only a safe low-effect subset when the deterministic baseline is itself inside that subset;
8. keep run-level total cost primary and separate generation/shared-batch spend from selected execution spend.

This instrumentation isolates causal ExecutionSelection without yet touching upstream GenerationControl. It also makes interrupted runs useful rather than preferentially dropping expensive/failed trajectories, reducing survivorship bias before OPE/RL.
