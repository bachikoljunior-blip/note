## C83 — “Reversible proof-state edit” is not enough: outer-controller Fork/Restore/Merge safety must include external-call identity, authorization/progress, required results, and atomic rule epochs

Primary source: Yusheng Zheng et al., *When Can Agents Safely Checkpoint, Fork, Restore, and Merge? Exact Checking for Execution Edits*, arXiv:2608.22928 (submitted 2026-08-24), https://arxiv.org/abs/2608.22928
Public implementation/proof base: https://github.com/eunomia-bpf/agent-check-restore-safety

The paper studies a general agent runtime rather than Lean theorem-solving quality, but its safety result applies directly to the proposed outer-controller actions `BACKTRACK_OR_PRUNE`, checkpoint/fork/restore, and any future branch merge once proof search has external or persistent effects.

Core constraint:
- an execution edit cannot undo an earlier authorization or a tool request already sent;
- unsafe edits can therefore duplicate a tool action, discard a result the task still needs, or race/conflict with an in-flight call;
- the Agent is treated as untrusted, so the trusted runtime derives what must be preserved from the durable execution record rather than from Agent/planner prose.

The record needs more than a proof-state snapshot. The source explicitly tracks:
1. task/workflow structure and which results remain required;
2. which workflow calls refer to the same underlying action;
3. earlier authorizations and call progress/return links/queued requests;
4. the runtime rules currently in force and edit-rule lineage.

A still-required result cannot simply disappear after an edit: it must remain safely completable, already be satisfied, or have an authorized removal. The paper proves that losing even the links between copied calls and their underlying action can change the correct safety verdict: tool/call text alone is insufficient to decide whether a restored call reuses an earlier authorization or needs a new one.

The runtime also does not trust a previously computed edit verdict indefinitely. Before installation it re-derives/rechecks against the current execution record; if a relevant tool call progressed, the old candidate is stale. Accepted rules switch atomically: overlapping calls are governed wholly by the old or new rule version, rather than partly by both. The Lean mechanization covers registration, six edit forms, atomic rule update, concurrent calls and finite-execution preservation; the artifact repository contains the executable runtime/proof base and describes durable execution records, stable Operation identities, state replay and history-bound Rule changes.

### Consequence for the proposed Lean controller

A pure local Lean proof-state fork/restore can often be treated as cheap/reversible **only if all affected computation is local/immutable and there are no unresolved effects tied to the discarded branch**. Once the outer controller can spawn workers, launch model/tool/search calls, mutate verified/shared memory, or issue any external operation, restoring only the Lean state is not a semantically complete rollback.

Therefore D1/D3 should refine Stage-A eligibility:

- local immutable proof-state snapshot/fork/backtrack with no in-flight or persistent effects: potentially Stage A;
- restore/fork/backtrack after worker/model/search/tool launch: Stage A only if the trusted executor preserves stable action identities, outstanding-result obligations, and deduplicated/reusable return links;
- merge of branches with effects: not Stage A until an exact merge/edit checker or a much narrower proof-specific equivalent establishes compatibility;
- persistent writes and external side-effecting calls remain Stage B or deterministic-baseline-only unless versioned/isolated and governed by an exact edit rule.

### D2 event-schema extension

Add an **execution-edit safety record** beside the proof/controller state:

- stable `action_id` / operation identity for each external or persistent action;
- `call_id`, source branch/snapshot and copied-call lineage;
- authorization identity/version and whether the current call is `new` or `reuse`;
- call phase: proposed/authorized/sent/committed/result-recorded/failed/cancelled-if-truly-cancellable;
- durable return/result link and queued-request identity;
- explicit still-required-result obligations plus authorized-removal records;
- active edit/rule epoch, old/new rule version and atomic-switch status;
- in-flight calls at edit request time;
- edit candidate input-record digest and final recheck digest;
- edit verdict plus a checkable reason/proof/certificate where available.

The controller-state hash alone is therefore insufficient for edit safety. Replay for `BACKTRACK/FORK/RESTORE/MERGE` must reconstruct both the proof/search state and this execution/effect record. A stale edit verdict must cause recomputation, not silent application.

### Scope guard

This paper proves/checks **runtime execution safety**, not theorem-proving accuracy or compute efficiency. It does not show that Fork/Restore/Merge improves pass@budget. Its contribution here is to sharpen the trusted substrate and logging requirements for safely experimenting with those controller actions.

## Updated synthesis

The proposed learned Lean outer controller now needs two separable correctness layers:

1. **Decision quality / OPE layer:** typed action, exact support/propensity, verifier-grounded objective, calibrated value/cost, conservative deployment.
2. **Trusted execution-edit layer:** proof/search snapshot plus durable external-effect identities, authorizations/progress, required-result obligations, and atomic edit-rule epochs.

This separation prevents a dangerous equivalence: `proof state restored` does **not** imply `execution safely restored`.
