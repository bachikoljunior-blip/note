## Synthetic journal benchmark

### Purpose and scope

C136 identified that CSSC's current `_atomic_append_text` copies the entire prior JSONL file for every append, which is safe but potentially expensive for high-frequency per-decision logging. A local synthetic benchmark compared three durability mechanisms using canonical JSON decision-like events with roughly 2 KiB filler payload per event:

1. **whole-file copy+replace** — behaviorally mirrors the current `_atomic_append_text`: copy existing file to a temp file, append one event, fsync the temp, atomically replace;
2. **segmented immutable JSON** — one canonical JSON file per stable event id, temp write + file fsync + atomic rename + containing-directory fsync;
3. **SQLite WAL/FULL** — stdlib `sqlite3`, `journal_mode=WAL`, `synchronous=FULL`, one transaction/commit per event, `event_id` primary key, final WAL checkpoint.

The benchmark is local-filesystem evidence only. It is useful for mechanism selection but is not a prediction of CSSC production latency on another filesystem/container/OS. SQLite's physical write traffic was not directly measured, so only elapsed time and final on-disk footprint are compared for it.

### Observed results

Median of three runs where repeated measurements were taken:

| Events | Whole-file copy+replace | Segmented JSON | SQLite WAL/FULL |
|---:|---:|---:|---:|
| 100 | 0.2125 s | 0.2116 s | 0.1135 s |
| 1000 | 7.5206 s | 2.0359 s | 0.6710 s |

Single 10-event pass was 0.0296 s / 0.0160 s / 0.0195 s respectively.

For 1000 events, the final logical JSON stream was about 2.19 MB. Whole-file copy+replace physically wrote about **1.097 GB** through the benchmark's counted user-space writes, approximately **500.5×** the final logical stream size, exactly matching the triangular rewrite prediction. Segmented JSON wrote about **2.19 MB** of event payload, approximately 1× logical payload, at the price of 1000 separate event files and two explicit fsync operations per event (file + directory). SQLite's post-checkpoint database footprint was about 4.15 MB in this run, roughly 1.89× the logical JSON payload; its true device-level write amplification was not instrumented.

At 100 events, copy+replace wrote about 11.06 MB for a final ~219 KB stream, approximately 50.5×. This confirms C136 quantitatively in the local environment rather than merely by asymptotic reasoning.

### Idempotence / rollback prototype checks

A minimal segmented-journal prototype and a minimal SQLite journal were both tested with stable event ids:

- first append succeeds;
- replaying the exact same canonical payload returns an idempotent `identical` result;
- reusing the same event id with a different canonical payload raises a duplicate-conflict error;
- a SQLite event inserted in an uncommitted transaction and then rolled back is absent afterward.

These are mechanism checks, not production-quality crash-injection tests. Segmented power-loss durability still requires filesystem-specific validation of directory fsync semantics, and SQLite should be tested under process-kill/power-loss style fault injection before relying on it for experiments.

## New findings

### C145 — whole-file copy+replace is unsuitable as the default high-frequency decision journal

The synthetic measurements confirm the write-amplification concern is material by 1000 events: about 7.52 s median versus 2.04 s segmented and 0.67 s SQLite in this environment, with ~1.097 GB counted rewrite traffic for a ~2.19 MB logical stream.

This does not invalidate CSSC's current completed-run trace store; its append frequency is low and its atomicity tests are valuable. It means only that **the same primitive should not be promoted unchanged into the per-decision causal logger**.

### C146 — SQLite WAL/FULL is the leading journal candidate for Stage-A experiments, with segmented JSON as the audit-friendly fallback

Under this local benchmark SQLite was roughly 3.0× faster than segmented JSON and 11.2× faster than whole-file copy+replace at 1000 events. It also avoids a directory with thousands of event files and provides primary-key idempotence naturally.

Recommended next prototype:

- `decision_events(event_id TEXT PRIMARY KEY, run_id TEXT, decision_index INTEGER, event_type TEXT, payload_sha256 TEXT, canonical_json TEXT)`;
- WAL + `synchronous=FULL` for experimental collection;
- explicit transaction per pre-action decision write;
- optional small transaction containing batch-consumption + outcome only where ordering semantics permit;
- export/compact to canonical JSONL after run completion;
- reject conflicting duplicate primary keys by comparing stored payload hash/canonical bytes.

Segmented JSON remains useful as a simpler independent reference implementation for crash/idempotence tests and environments where SQLite filesystem semantics are unsuitable.

### C147 — journal overhead must be reported per decision and compared to action/check latency

The SQLite result is fast enough locally (~0.67 ms/event at 1000 events by simple elapsed/event division), but this is not automatically negligible. Some structural CSSC actions may be cheaper than a durable database commit, and a controller optimizing small local actions could still be biased by journal latency.

The instrumentation-equivalence study should therefore report:

- median/p95 journal append latency by event type;
- journal time as fraction of total run wall-clock and as fraction of selected-action execution time;
- event count/run;
- database/WAL/checkpoint bytes;
- comparison under representative local structural action and Lean-check action latencies.

If journal time is non-negligible, batch only **post-action** outcome/export writes where causal ordering remains valid; the pre-action decision must remain durable before action execution.

### C148 — causal durability and accounting durability should remain separate stores

The benchmark reinforces the architectural split already suggested by C135/C137:

- monetary/resource `CostLedger` remains append-only immutable accounting events and reconciliation;
- `DecisionEventJournal` stores causal policy decisions, exact propensities, batch-consumption relationships and outcomes;
- final trace export joins both by stable run/decision/batch/event ids.

Trying to make the cost ledger itself carry every causal join would complicate reconciliation and blur whether a zero-cost relational event represents resource consumption.

### C149 — journal selection should be frozen before randomized collection because the logger is part of the treatment substrate

Switching logging backend midway through an experiment can alter wall-clock and failure/censoring behavior. Before collecting epsilon data, freeze:

- journal backend/version;
- SQLite pragmas or segmented-durability contract;
- canonical JSON version;
- event schema version;
- checkpoint/export policy.

A backend change after collection starts defines a new substrate version and should be analyzed separately or re-baselined.

## Updated synthesis

The measurement substrate choice is no longer hypothetical. The local benchmark strongly disfavors per-decision whole-file replacement and makes SQLite WAL/FULL the best first implementation candidate, while retaining segmented JSON as a simple audit reference.

This improves the causal experiment design in two ways: interrupted expensive trajectories can be persisted without quadratic write amplification, and logging overhead can be measured explicitly instead of disappearing inside the wall-clock target that the learned controller is supposed to optimize.
