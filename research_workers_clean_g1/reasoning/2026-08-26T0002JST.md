## C33 — Lean formal signals need coverage-aware selective risk control; a verified formal artifact is not by itself a calibrated decision signal

Primary/public source:
- `Risk-Controlled Lean-as-Judge for Natural-Language Mathematical Reasoning` (CovCal), arXiv:2605.28365, public code `paulinebourigault/covcal-lean`.

Mechanism:
- Treats Lean as a **partial-observation** judge rather than an omniscient verifier of the original natural-language claim.
- Aggregates answer classes and Lean statuses into typed coverage, proved coverage, unresolved-rival mass, and a formal margin.
- Accepts only when fixed coverage/margin thresholds are satisfied; otherwise abstains.
- Calibrates the selective rule with finite-sample Clopper–Pearson upper bounds under either a conservative Bonferroni grid search or a dev-then-cal regime.

Evidence:
- On MATH-500, the paper reports a sharp coverage cliff: the proof-winning answer is correct about 96% of the time at high proved coverage but only 20% at low coverage.
- A generic 7B autoformalizer proves a class for only about 28% of problems; manual audit finds only ~43% of those proofs faithful to the original problem.
- With that sparse formalizer, the conservative Bonferroni certificate is infeasible on all 20 bootstrap partitions.
- A prover-specialized formalizer reaches ~79% coverage and makes the certificate feasible on 17/20 partitions, accepting roughly 48% of problems at ~0.98 accepted accuracy.

Why this matters for proof-search routing:
- This is not a theorem-proving router paper, so direct transfer is unproven.
- But it supplies a stronger statistical control pattern than raw confidence: **coverage + abstention + finite-sample selective-risk certification**.
- A Lean proof-search controller should therefore consider not only `P(next attempt succeeds)` but also whether the observed trajectory is sufficiently informative for that probability to be trusted. Missing/ill-typed/unresolved feedback should reduce decision coverage rather than being silently folded into a point estimate.
- It also reinforces a scope guard: kernel verification proves the formal statement, not necessarily faithfulness of an upstream autoformalization or retrieved context.

Sources:
- https://arxiv.org/abs/2605.28365
- https://github.com/paulinebourigault/covcal-lean

## C34 — The current cost-quality Lean router uses success probabilities operationally but reports no probability-calibration diagnostics

Primary source:
- `Optimizing the Cost-Quality Tradeoff of Agentic Theorem Provers in Lean`, arXiv:2606.04883v3 (23 Jun 2026), public code `eth-sri/optimizing-lean-agents`.

Mechanism:
- Router utility is `tau(s) = q_hat(s) - lambda * c_hat(s)` and chooses `Attempt` iff `tau(s) > 0`.
- `q_hat` is a scikit-learn logistic regression trained with default hyperparameters on proof similarity, compiler-error diversity, and inverse attempt count.
- Training/test split is 42/43 problems from the 85-problem PutnamBench subset.
- v3 reports 28.9% average cost reduction at parity accuracy and 7.9% accuracy improvement at parity cost; the oracle gap remains large.

New negative evidence from primary-text inspection:
- The v3 paper contains no reported `calibration`, Brier score, ECE, reliability diagram, calibration slope/intercept, or selective-risk analysis.
- Thus the model is evaluated as a **decision/ranking component**, not as a validated probability estimator, even though its numerical probability enters the utility threshold directly.

Implication:
- For a binary action router, miscalibration can change decisions whenever `q_hat` is near `lambda*c_hat`; ranking quality alone is not enough.
- The 28.9% efficiency gain remains valid within the paper's tested simulation protocol, but it does not establish robustness under theorem-family shift, proof-depth shift, different prover models, or richer action spaces.
- High-value next experiment: fit the same router with raw logistic probabilities, temperature/Platt/isotonic calibration, and conformal/selective variants; report Brier/ECE/reliability/selective-risk together with pass@budget/cost.

Sources:
- https://arxiv.org/abs/2606.04883v3
- https://arxiv.org/html/2606.04883v3
- https://github.com/eth-sri/optimizing-lean-agents

## C35 — Cost-aware proof routing must be execution-substrate aware; token-only cost is not portable across Lean runtimes

Cross-primary synthesis (hypothesis bounded by each paper's tested setting):

1. The cost-quality router above explicitly treats Lean compilation cost as negligible and uses generated-token / SFLOP cost as the operative cost model.
2. `Keep the Proof State Live: Snapshotting for Efficient Tactic Search in Lean 4`, arXiv:2605.25556, measures a different common execution substrate where repeated import loading + theorem-body elaboration consume >99% of per-branch wall time; snapshot/forking gives 5.6–50x wall-time speedups (average 14x, median 9.7x across 45 hand-crafted prove-phase benchmarks).

Interpretation:
- There is no contradiction if the router's environment already amortizes/avoids Lean reconstruction. The conflict is **portability**: an action-cost model learned in one execution substrate can be badly wrong in another.
- A multi-action router that compares fresh branch, local repair, re-retrieval, decomposition restart, or model switch should condition cost on the concrete substrate: generation tokens/FLOPs, retrieval/reranking, Lean tactic/verifier work, state reconstruction, and wall-clock.
- Snapshotting also changes the relative price of exploration vs repair: cheap state forks can make semantic branch exploration much more attractive than under rebuild-per-branch execution.
- No surfaced paper directly combines snapshot/forking with the cost-quality router; this remains a compute-normalized systems frontier.

Sources:
- https://arxiv.org/html/2606.04883v3
- https://arxiv.org/abs/2605.25556

## C36 — Neighboring reasoning systems independently support triggered mid-course retrieval, but Lean-specific learned escalation remains untested

Neighboring primary sources:
- `Adaptive Retrieval for Reasoning-Intensive Retrieval` (REPAIR), arXiv:2601.04618: selective adaptive retrieval uses reasoning-plan feedback for mid-course correction and reports +5.6 percentage points over prior baselines on reasoning-intensive retrieval/complex QA.
- `When to Retrieve During Reasoning: Adaptive Retrieval for Large Reasoning Models`, arXiv:2604.26649: a step-level uncertainty detector and learned retrieval intervention policy report +10.1 absolute F1 over standard RAG while using 47% fewer retrieval calls than fixed-interval retrieval on multi-hop QA.

Scope:
- These are not Lean theorem-proving studies and cannot establish a Lean gain.
- They do independently strengthen the general controller hypothesis behind C29: retrieval should be an explicit, selectively triggered reasoning action rather than a fixed front-end.

## Updated synthesis

The controller frontier is now sharper:

1. **Separate predictive quality from trust in the prediction.** The current Lean router predicts success probability but does not report probability calibration; CovCal shows a practical pattern for coverage-aware abstention and finite-sample selective-risk control.
2. **Make observation coverage explicit.** Compiler feedback, typechecking, retrieval support, and trajectory diversity are partial observations; insufficient coverage should trigger abstention/escalation rather than confident routing.
3. **Make cost substrate-specific.** A token/SFLOP-only cost model may be reasonable in a cached Lean server but is not portable to rebuild-per-branch execution where elaboration dominates wall time.
4. **Treat retrieval as a controllable action.** LeanSearch v2 exposes a concrete one-shot-global-retrieval gap, while neighboring adaptive-retrieval systems show that learned mid-course retrieval can improve accuracy and reduce calls.
5. **Keep richer actions gated by calibrated utility.** Fresh branch, continue, local repair, whole-proof repair, graph expansion, global re-retrieval, decomposition restart, and model switching should be compared by calibrated outcome and substrate-aware cost estimates, with abstention when those estimates are not trustworthy.
