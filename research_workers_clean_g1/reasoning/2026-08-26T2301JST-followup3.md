The merged `generateRequest` result contains no context field. The original issue #72 had initially proposed a `result.request` object ready for `isAuthorized()` plus components, but the merged design exposes only `AuthorizationComponents` and external context construction.

Sources:

**Inference.** C374 is not only a theoretical reading of internal source comments: the public merged usage pattern explicitly reconstructs authorization context across the language boundary. ## C378 — MCP JSON-Schema -> Cedar lowering has already experienced semantic representation bugs; the lowering version is therefore grant-critical

**Observed.** Cedar-for-Agents issue #85, opened May 8 and completed May 11, 2026, documents that JSON Schema type arrays such as `{"type":["null","string"]}` were represented as tuples even though JSON Schema semantics make them equivalent to a union/`anyOf`. The issue explicitly calls the correction a potential breaking change for clients that had generated schemas or policies around the prior representation.

Source:
- https://github.com/cedar-policy/cedar-for-agents/issues/85

**Observed.** Issue #88, also completed May 11, documents that a JSON Schema fixed tuple could be lowered to `Set<...::Unknown>`, preventing meaningful type-specific policies; the intended representation was a positional record/tuple-like shape.

Source:
- https://github.com/cedar-policy/cedar-for-agents/issues/88

**Scope guard.** Both issues are closed/completed; this checkpoint does not claim those exact bugs remain in current main. Their importance is architectural: the tool-description/schema compiler has changed observable authorization semantics across versions and has previously produced coarse or wrong target types.

**Inference.** `tool_description_digest` alone is insufficient. Activation and execution witnesses must also bind the exact schema-generator/MCP-SDK lowering version and configuration. A proof or authorization result under schema version A must never silently carry across a lowering change to version B.

New hard regression:
`schema_lowering_version_change_invalidates_authorization_witness`.

## C379 — unsupported or coarsely representable tool-schema constructs should fail closed for grant-sensitive policies

**Observed.** The integration tests historically documented that a mixed-array construct could become `Set<Unknown>` and stated that meaningful policies could not be written against those types. The tuple issue similarly described `Set<Unknown>` as an inadequate representation.

Source:
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator/tests/integration.rs
- https://github.com/cedar-policy/cedar-for-agents/issues/88

**Inference.** A schema compiler should distinguish `fully represented`, `lossy but explicitly approved`, and `unsupported_for_authorization`. Coarsening an argument to `Unknown` must not cause a policy that would otherwise inspect it to become less restrictive by omission. For an effect whose grant depends on such a field, schema lowering should fail closed or require a separately approved conservative policy.

New fields for `PolicyActivationCertificateV0`/schema evidence:
- `schema_feature_coverage`;
- `lossy_lowering_flags`;
- `unsupported_grant_relevant_fields`;
- `lossy_lowering_approval_witness` when intentionally used.

New regressions:
- `unsupported_grant_relevant_field_cannot_disappear`;
- `lossy_lowering_cannot_widen_authority`.

## C380 — output-aware tool policies require a two-phase authorization model

**Observed.** The core request generator can optionally include tool output in Cedar context (`include_outputs=true`), and its API documentation says it can determine whether a principal is authorized to use a requested tool **or receive the output** of it. Output is only available after the tool has run.

Sources:
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator/src/generator/schema.rs
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator/src/generator/request.rs

**Inference.** For side-effectful tools, one output-aware authorization decision cannot retroactively authorize the tool effect: by the time output exists, the external side effect may already have happened. The runtime should distinguish:

1. `ToolDispatchAuthorizationWitness` — pre-effect, based on principal/resource/input/context and current policy;
2. `OutputReleaseAuthorizationWitness` — post-result, based on the exact returned output plus the prior dispatch/result identity, controlling disclosure or downstream use.

A denied output-release witness must suppress disclosure but cannot pretend the already executed side effect never occurred. Policies meant to prevent the side effect must be evaluable pre-dispatch.

New regressions:
- `post_output_allow_cannot_retroactively_authorize_dispatch`;
- `output_release_must_bind_exact_result_digest`;
- `denied_output_release_cannot_leak_result_to_planner`.
