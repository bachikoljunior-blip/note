## C283 — Decision/Outcome journaling alone is insufficient for crash-safe Stage A because provider generation precedes Decision
The real action-runtime order is:

```text
refresh cache
if empty:
  retrieval
  model routing
  proposal budget admission
  reserve_model_call()                 # volatile
  provider generation _generate(...)
  finalize/validate proposals
  record_proposal_request(...)         # still in memory
  cache.add(...)
select_admissible_action(...)
choice_set/action_selected             # current in memory
execute selected action
```

So there is a substantial upstream effect window before the first `ExecutionDecisionEventV0` can exist.

If the process crashes during provider generation, or after the provider has returned but before proposal/cost state is durably journaled, a restart can regenerate and silently pay a second provider cost. The structural action itself may be perfectly replayable and the Stage-A selector propensity perfectly logged later, yet run-level cost provenance is already broken.

## C284 — current provider physical-attempt records are also post-return and non-durable
`record_proposal_request()` is called after `_generate(...)` returns or raises. It can decompose provider metadata into physical request/usage/charge events, which is better than checker retry accounting, but these events are appended only to the in-memory `state.cost_ledger`. They are not committed before the provider request is dispatched and are not durably persisted mid-run.

Thus a provider `request_id` embedded in a successful response is useful provenance but does not solve a crash that occurs before the response/metadata reaches the process or before a journal commit.

## C285 — add a pre-decision generation causal layer
Before claiming crash-safe experimental trajectories, extend the journal with:

```text
ProposalGenerationAttemptV0:
  generation_operation_id
  branch/workspace snapshot identity
  model route/config/version
  exact input/context semantic hash
  admission/budget reservation
  started_before_dispatch=true

ProviderPhysicalReceiptV0:
  generation_operation_id
  physical provider request_id when returned
  retry index/status
  observed token/cost/wall facts
  response/proposal-batch semantic hash when available

ProposalBatchFinalizedV0:
  proposal_batch_id
  generation_operation_id
  workspace/config source tuple
  content-addressed finalized proposal-envelope refs
  validation/skipped-proposal diagnostics
  batch semantic hash
```

`ProposalGenerationAttemptV0` must be committed before a provider call. `ProposalBatchFinalizedV0` must be committed before action selection. If the provider substrate supports a real idempotency key, bind it to `generation_operation_id`; otherwise an Attempt without a Receipt remains in-doubt and recovery fails closed rather than silently regenerating.

## C286 — same-batch sibling continuity requires durable proposal envelopes, not only workspace snapshots
The C263 two-no-op path depends on the *unselected sibling proposal remaining cached* after consumer 1. A process crash after consumer-1 Outcome but before consumer 2 loses the in-memory `ProposalCache` today.

To continue without another provider call, recovery needs the unconsumed proposal envelopes. There are two clean options:

1. `ProposalBatchFinalizedV0` content-addresses every finalized proposal envelope, and replay reconstructs current cache by filtering durable unconsumed batch proposals against the recovered workspace; or
2. every Decision stores content-addressed refs for its full choice set, enough to reconstruct pending alternatives.

Prefer option 1 as source-of-truth plus Decision choice-set refs. It preserves proposals even if the process dies after generation but before the first Decision.

## C287 — proposal cache is a derived view; do not journal mutable cache internals as authority
A crash-safe design need not serialize every transient `ProposalCache` implementation field. Given:

- durable finalized proposal batches/envelopes;
- durable selected/consumed edges;
- recovered exact workspace snapshot/version;
- pinned frontier/config policy;

cache/frontier eligibility can be deterministically recomputed. This avoids coupling the durable schema to one in-memory cache layout.

The critical invariant is that recovery must never invoke provider generation merely to reconstruct proposals that were already paid for and durably finalized.

## C288 — crash-safe Stage A now has two independent effect boundaries
Even though randomized Stage-A *actions* remain reducer-only, the whole run contains:

1. upstream provider generation effect before selection; and
2. selected reducer transition after selection.

Therefore the minimal crash-safe experimental substrate needs both:

- generation Attempt/Receipt/Batch durability; and
- Decision/Consumption/WorkspaceSnapshot/Outcome durability.

Effectful checker action support is a third layer and may stay excluded initially.

This sharper decomposition prevents the phrase "pure structural Stage A" from being misread as "the whole Stage-A run has no external effects."
