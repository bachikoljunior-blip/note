## C209 — the current provider ledger is immutable by type but not by history semantics

Public CSSC source confirms that `CostLedgerEvent` and `CostLedger` are frozen/append-oriented objects, but `attribute_proposal_batch` reconstructs every matching historical provider event with `metadata.action_id = node_id` whenever a proposal from that batch is consumed. `execute_action_node` calls this before executing every selected action. Therefore a second consumer of the same `proposal_batch_id` can replace the first consumer's attribution in the final ledger even though no new provider charge occurred.

This is not merely a naming issue: the authoritative provider event says which physical request/usage/charge happened once, while action consumption is a separate many-to-many causal relation. Encoding both facts in one mutable metadata slot loses provenance.

## C211 — canonical migration: immutable physical events plus append-only consumption edges

Recommended authoritative representation:

1. Provider request/usage/charge/tool events are emitted once with stable `proposal_batch_id`; their metadata never changes after emission. `action_id` is absent or permanently null in the authoritative ledger.
2. Each consumption of a cached proposal appends a separate `ProposalBatchConsumptionEvent` with at least:
   - `consumption_event_id`
   - `run_id`
   - `decision_id`
   - `proposal_batch_id`
   - `node_id`
   - `branch_id`
   - `action_kind`
   - `consumer_index_for_batch`
   - `workspace_version_before`
   - `committed_before_effect = true`
3. Joining physical batch cost to an action is a query/projection, never a rewrite. Shared batch cost remains shared upstream generation cost `G`, not duplicated into per-action execution cost `E`.
4. If legacy presentation must remain temporarily, derive `metadata.action_id` only in a non-authoritative compatibility projection when a batch has exactly one consumer. For zero or multiple consumers report null plus explicit attribution status (`unconsumed` / `shared_multi_consumer`) rather than choosing the last consumer.
5. OPE/RL readers must ignore compatibility `action_id` and join by immutable batch-consumption events.

This preserves the existing single-consumer test's display intent without allowing the legacy projection to become causal evidence.

## C212 — decision journaling needs the exact admission inputs, not merely `allowed=true`

Current `select_admissible_action` constructs each choice row from node id, branch id, action kind, estimated execution cost and `BudgetAdmission`; the `UnifiedBudgetSnapshot` separately carries remaining/model/check/token/wall/API-cost dimensions, missingness statuses, obligation context and global reserves. `admit_estimate` can leave dimensions `not_compared`, and optional `reject_unknown` changes behavior.

Therefore `ExecutionDecisionEvent` v0 should commit before effect with:

- frozen controller/logging-policy versions and RNG draw/index;
- `decision_id`, run/task id, workspace version;
- canonical supported choice rows in D0 order, including action identity/kind/branch, estimated cost vector, admission object and support-membership flag;
- full canonical budget snapshot or content-addressed snapshot digest plus durable snapshot body;
- `remaining_budget_policy`, unknown-cost rejection mode, global reserves;
- chosen node and exact rational behavior propensity;
- unsupported-but-legal count and top-5-cap exclusions;
- proposal-batch identity/source for each supported node where applicable.

A replay/OPE reader must be able to recompute the legal-supported set and verify the chosen propensity from this event alone plus the frozen protocol, without consulting a mutable later trace.

## C213 — epsilon=0 equivalence should use two projections, not one over-broad byte comparison

A causal journal adds IDs, SQLite commit timing, WAL bytes and observability records that are intentionally different. Conversely, excluding too much can hide semantic drift. Use two frozen projections:

### A. Deterministic semantic projection (hard equivalence on fake/instrumented fixtures)

Compare exactly, in order:

- terminal `accepted`, normalized `stop_reason`, final workspace semantic state;
- selected action sequence as `(branch_id, action_kind, proposal content fingerprint / stable proposal identity)` rather than journal IDs;
- attempts: normalized edit/proof fingerprint, parent/branch/obligation semantic metadata, checker accepted/category/goal fingerprints, safety verdict;
- provider/model and checker invocation counts plus deterministic request/proposal fingerprints;
- budget counters for checks/model requests and all deterministic configured admissions;
- normalized proposal-cache choice/admission sequence already produced by baseline runtime;
- final proof/source fingerprint when accepted.

Exclude journal event IDs, SQLite row IDs, commit timestamps/latencies, WAL size, filesystem temp names and measured real wall-clock jitter. Cost measurements are compared exactly only on deterministic fake fixtures.

### B. Live observability invariants (provider pilot, not per-task byte equality)

With epsilon=0 and fixed protocol, require no systematic change in provider/checker request counts, action-policy inputs, success semantics or cost distribution beyond measured journal overhead. Provider outputs and wall time remain stochastic, so paired live runs are diagnostics rather than a hard same-output oracle.

This prevents a false failure from journal-only metadata while still detecting hidden extra model/checker calls.

## C214 — regression tests for the attribution migration are now concrete

Minimum tests before randomized collection:

1. **Single consumer:** physical provider events remain byte/field identical after one consumption; one immutable consumption edge exists; optional compatibility projection resolves to that node.
2. **Two consumers, same batch:** physical events remain unchanged; two ordered consumption edges exist; compatibility action id is null/ambiguous, never overwritten to consumer 2.
3. **Crash after decision+consumption commit, before executor effect:** reader returns committed decision with no outcome as censored; batch edge remains; no reselection on same run id.
4. **Crash after physical provider batch, before decision:** provider cost remains `G` and unconsumed; never attached to a future action by mutation.
5. **Replay same event:** identical id/payload is idempotent; same id/different payload is conflict.
6. **epsilon=0 baseline:** deterministic semantic projection is equal with journal null-vs-enabled; RNG stream used for prover/generator is unchanged by logging-policy RNG.
7. **Legacy trace reader:** absence of new consumption events is accepted as legacy/unavailable attribution, not synthesized as zero or one consumer.

## C215 — Stage-A/Stage-B cost boundary is reinforced by the actual call order

`action_runtime.py` performs retrieval, model routing, proposal-budget admission, provider proposal generation, proposal validation and cache insertion before `select_admissible_action`. Only after selection does it mark `event_start` and measure `action_cost_observed` through the execution boundary. This confirms the prior split:

- Stage A can directly control post-generation choice/execution and success effects of choosing among already-generated proposals.
- Stage A cannot directly recover retrieval/model-routing/proposal-generation cost already paid for that choice set.
- The deterministic pilot's `G/E/A` separation is therefore structural, not merely an accounting convention.

If `E/T` and multi-action opportunity are both too small under the frozen gate, moving upstream to Stage B is the correct architecture change rather than crediting shared generation cost to Stage-A actions.
