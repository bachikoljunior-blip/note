## C55 — OpenProver gives a matched-token free-form meta-action baseline and an explicit context-isolation mechanism

Primary/public sources:
- `OpenProver: Agentic and Interactive Theorem Proving with Lean 4`, arXiv:2607.09217 / CICM 2026.
- Public repository `Kripner/openprover`.

Controller structure:
- A Planner maintains a compact Whiteboard and a disk Repository of larger findings, then emits one or more heterogeneous actions each step: spawn focused parallel Workers, read/write stored items, re-read the theorem, update the Whiteboard, search literature, or submit informal/formal proof.
- Lean-capable Workers can independently invoke `lean_verify`, `lean_store` and `lean_search`.
- Verified Lean snippets may be persisted and reused; invalid snippets are rejected and their verifier errors are returned instead.
- The Planner chooses actions through ordinary LLM generation rather than a separately trained/calibrated action-value model.

Context-isolation design:
- Workers receive only a plaintext task describing their local purpose and **do not observe previous Workers' or the Planner's reasoning traces/outputs**.
- Verifiers also do not observe the Worker reasoning trace, reducing shared-line-of-thought bias.
- The Planner receives a compact Whiteboard at every step; larger detailed artifacts live in a Repository and only slugs/one-line summaries are always visible. Full items are pulled on demand.
- This is a concrete architectural defense against context pollution while preserving long-horizon memory: keep global coordination compact, keep large evidence externally addressable, and isolate parallel search trajectories until results are deliberately integrated.

Matched-token ProofNet evidence:
- Autonomous evaluation covers **185 formal ProofNet theorems** with a **100k-token per-problem budget**.
- Kimi-K2.5: linear rollout **36.8%** vs OpenProver **57.3%**.
- Leanstral: linear rollout **21.1%** vs OpenProver **28.1%**.
- The linear baseline receives the same token budget and unlimited Lean verifications, so this is stronger controller/scaffolding evidence than unmatched headline comparisons, although internal action overhead and parallel scheduling are not separately priced.

Additional control surface from the released implementation:
- Current public options expose `max-time`/`max-tokens`, maximum parallel Workers, planner/worker model split, LLM-verifier on/off, reasoning effort, planner-history budget, and a `conclude-after` fraction that triggers a conclusion phase.
- The search loop remains LLM-driven until proof is found or the budget is exhausted; these budget/parallelism/effort settings are fixed run parameters rather than a learned prospective controller.

Interpretation:
- OpenProver is the strongest direct Lean baseline found in this run for **free-form heterogeneous meta-action selection under a matched total token budget**.
- Together with AxProverBase, it strengthens the context-management conclusion: compact summaries plus external selective retrieval can outperform or avoid raw-history accumulation, while independent Workers protect branch diversity from irrelevant shared context.
- It also defines a cleaner learned-router experiment: keep OpenProver's exact action vocabulary, memory substrate and Worker isolation fixed, then compare the existing free-form Planner with a learned/calibrated typed policy over the same actions and budget.
- Because OpenProver shifts many behavior decisions from code into prompts, prompt/harness self-improvement is itself a candidate controller layer; however, the paper presents that as a future possibility rather than evaluated self-optimization.

Critical scope / caution:
- Same total output-token budget does not equal identical wall-clock, input-token, verifier, Worker-parallelism or model-call cost.
- Planner/Worker/Verifier scaffolding changes more than action selection, so 36.8→57.3 and 21.1→28.1 cannot be attributed to any one controller component.
- The Planner's free-form action choices are not calibrated and can still waste compute; this is a baseline, not the endpoint.
