## C466 — Vero exposes a repository-closure gap that local proof/spec success can hide

New public primary source: `Vero: Can AI Agents Build Formally Verified Software Repositories?`, arXiv:2608.13522, submitted 2026-08-13, plus the released `sunblaze-ucb/vero` benchmark repository.

Vero evaluates joint implementation/proof synthesis over 43 multi-module Lean 4 repositories. The strongest reported configuration, GPT-5.5 (xhigh), fully solves 27/43 in code-and-proof mode and 25/43 in proof-only mode. Yet the same configuration passes 87.3% of individual specifications in code-and-proof and 85.8% in proof-only. Ten repositories resist every evaluated configuration in both modes.

The paper’s analysis localizes the residual difficulty: hard repositories require cross-module invariants, shared abstractions and reusable lemma libraries. Agents often pursue local proofs instead; in code-and-proof mode they can also make implementation rewrites that break previously valid proofs or the repository build elsewhere.

This is useful evidence for the controller frontier because it separates two objectives that are easy to conflate:

1. **local obligation progress** — individual specs/checks become verified;
2. **repository closure** — all mutually dependent obligations remain simultaneously verified in one coherent buildable artifact.

High local pass rate is therefore not a sufficient proxy for the terminal objective at repository scale. This does not prove that any particular learned controller will solve Vero, and it is not an ablation of the current CSSC controller. It is an evaluation result showing that a controller trained/evaluated only on local success can miss the dominant repository-level failure mode.

A future matched controller experiment should therefore preserve at least two reward/evaluation layers rather than collapse them:

- kernel-verified local progress/reusable facts;
- global repository closure/build consistency, with full-repository solve as a separate terminal metric.

A particularly relevant comparison would fix the same prover/tool substrate and total compute budget, then compare a locally greedy allocation policy against one allowed to allocate effort toward shared lemmas/invariants and cross-module dependency bottlenecks. Report full-repository solves, per-spec coverage, reusable-lemma production, regressions of previously verified obligations, and real cost separately. This is a proposed experiment, not an observed causal result.
