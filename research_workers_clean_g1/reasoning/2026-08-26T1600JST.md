## C216 — the same-proposal-batch multi-consumer attribution bug has a concrete reachable runtime path

The prior attribution warning is not only a synthetic possibility. A valid `REFINE_ARGUMENT` proposal can pass the current cache/frontier checks yet execute as a semantic no-op:

- `SearchAction.validate` validates nonempty/unique `target_step_ids` but explicitly does not cross-check them against the live `ArgumentGraph`.
- `StructuredActionProposal.validate` validates the payload type and individual alignment syntax, but does not require `RefineArgumentPayload.steps` / alignment ids to hit an existing branch step.
- `node_invalid_reason` checks `action.target_step_ids` against the live branch, but it does not cross-check the payload's replacement step/alignment ids.
- `apply_argument` returns the original workspace when a `REFINE_ARGUMENT` payload hits neither an existing step nor an existing alignment.

Therefore construct a provider batch with two valid refine proposals on the same live branch. Give each `SearchAction.target_step_ids` a real existing step so the nodes remain frontier-valid, but give each payload only replacement ids absent from the branch. Both nodes can be cached with the same `proposal_batch_id`. The runtime consumes node 1 and calls `attribute_proposal_batch`, but the reducer leaves `workspace.version` unchanged. On the next loop, node 2 is still valid because its `cached_at_workspace_version` still equals the unchanged workspace version. Consuming node 2 calls `attribute_proposal_batch` again, rewriting the historical provider events' `metadata.action_id` from node 1 to node 2.

This gives C214's two-consumer regression an integration-level fixture using the real runtime semantics rather than a direct unit call to the attribution helper.

## C217 — normal successful mutations bound the bug; global workspace-version invalidation prevents ordinary second consumption

The vulnerability is narrower than “any multi-proposal batch may be consumed repeatedly.” Every successful structural mutation returns `workspace.successor(...)`, and `ProofWorkspace.successor` increments the global workspace version. On the next `refresh_action_cache`, every remaining node generated against the old workspace is dropped by `node_invalid_reason == workspace_version_changed`.

Thus same-batch repeated consumption is principally reachable through no-effect execution paths (or any other path that leaves the workspace version unchanged), not after ordinary successful structural mutations. This scope correction should be preserved in both risk claims and tests.

## C218 — current frontier membership is not the same thing as an effective-action legal mask

The current selection path treats `frontier.ranked()` plus `BudgetAdmission` as the choice set. But multiple structural actions can be syntactically/frontier valid while being deterministically unable to change the current workspace:

- `REFINE_ARGUMENT`: no payload step/alignment id intersects current state.
- `PROPOSE_ARGUMENT`: step/alignment coverage can fail inside the reducer even though individual alignment syntax passed proposal validation.
- `CHANGE_REPRESENTATION`: full argument/alignment coverage can fail in the reducer.
- `DECOMPOSE`: an empty child tuple is type-valid at proposal validation but reducer-no-op.

Therefore randomized collection needs two separately recorded notions:

1. `baseline_frontier_eligible`: exactly what current D0 can select today, for epsilon=0 semantic compatibility.
2. `effect_precondition_status`: pure live-state classification of whether the action is deterministically capable of its declared effect before execution.

Do not silently prune baseline no-op actions before the epsilon=0 oracle; that would conflate journaling with a controller bugfix. For epsilon>0, keep D0's exact behavior probability but restrict exploratory alternatives to actions passing the frozen safety/effect precondition. Record unsupported/frontier-only actions explicitly.

## C219 — add explicit effect observability to Decision/Outcome records

The causal journal should add, without changing the baseline executor initially:

- Decision row per candidate: `baseline_frontier_eligible`, `effect_precondition_status`, `effect_precondition_reason`, workspace/obligation versions, and exact support membership.
- Outcome row: `workspace_version_before`, `workspace_version_after`, `semantic_effect` (`mutated`, `checker_only`, `terminal`, `no_effect`), and whether a no-effect result was predicted by the precondition classifier.

This distinguishes a bad policy choice from an executor/reducer no-op and provides a direct metric for wasted proposal-generation spend.

A pure precondition helper can reuse existing reducer predicates without side effects. First coverage should target the structural Stage-A kinds; implementation/check actions can remain `unknown` until their effect contract is made equally pure.
