## C403 — OPA runtime/evaluator configuration is part of policy semantics

**Observed.** Current OPA documentation states that built-in runtime errors normally evaluate to `undefined` and policy evaluation continues, whereas the caller can enable `strict-builtin-errors` so the first built-in error becomes fatal. The current CLI/API/Go integration exposes this setting, while the current policy-language table explicitly says that strict built-in error mode is not available in the Wasm evaluation path. OPA also supports Rego v0 compatibility and v1 semantics through per-module/bundle/runtime configuration, with documented language and behavior changes across the v0/v1 boundary.

Primary/public sources:
- https://www.openpolicyagent.org/docs/policy-language
- https://www.openpolicyagent.org/docs/v0-compatibility
- https://www.openpolicyagent.org/docs/cli

**Inference.** A policy hash does not uniquely determine authorization behavior when evaluator/runtime mode is configurable. `PolicyActivationCertificateV1` and each dispatch witness must bind an exact evaluator-semantic tuple, including at least:
- Rego language/version mode;
- strict/error semantics;
- enabled/disabled or host-provided built-ins relevant to the policy;
- evaluation target/runtime kind;
- evaluator/compiler version and configuration digest.

New regressions:
- `strict_builtin_error_mode_change_invalidates_policy_runtime_identity`;
- `rego_language_mode_change_invalidates_activation_or_requires_revalidation`;
- `same_policy_source_different_evaluator_semantics_is_distinct_policy_identity`.

**Scope guard.** This establishes configuration-sensitive semantics in OPA. It does not claim that every setting changes every policy's result.

## C404 — compilation target can change available semantics and therefore belongs in the authorization witness

**Observed.** OPA's current Wasm documentation says Rego policies can be compiled into executable Wasm modules, but some built-ins are not natively supported and may require host implementations. Current integration documentation exposes several distinct execution paths: REST/Go evaluation, Wasm, SDKs, and low-level IR plans. The policy-language documentation also distinguishes strict built-in error handling availability across execution targets.

Primary sources:
- https://www.openpolicyagent.org/docs/wasm
- https://www.openpolicyagent.org/docs/integration
- https://www.openpolicyagent.org/docs/ir

**Inference.** Production correspondence cannot be represented only as `source policy -> evaluator version`. It must include **compile target and host runtime semantics**. For compiled policy artifacts, bind:
- source policy/bundle digest;
- compile target (`rego`, `wasm`, plan/IR, etc.);
- compiler version/config/entrypoint set;
- compiled artifact digest;
- host runtime/SDK identity;
- host-provided built-in implementation digest/capability set;
- runtime error/config semantics.

A source-level proof should not silently carry to a compiled target whose host built-ins or error behavior differ unless the correspondence is proved or separately validated for that exact target.

New regressions:
- `compiled_target_change_invalidates_dispatch_witness`;
- `host_builtin_implementation_change_invalidates_target_correspondence`;
- `unsupported_builtin_cannot_be_silently_reinterpreted_as_authorized_behavior`.

## C405 — policy identity should be semantic-configuration-complete, not text-complete

**Synthesis.** C394 (SELinux compiler flags) and C403–C404 (OPA language/error/target modes) independently show the same mechanism: **identical policy text can participate in different authorization semantics under different compiler/evaluator/runtime configurations**. Therefore the stable identity needed for authorization is not merely a policy-source digest; it is a digest over the policy source plus every grant-relevant semantic configuration and deployed artifact.

Candidate identity relation:

`semantic_policy_identity = H(source + source_language_version + compiler + compiler_flags + target + compiled_artifact + evaluator/runtime + error_mode + builtins + schema/data contract + policy epoch)`.

The exact field set should be minimized to grant-relevant facts for each engine, but any omitted field needs a proof that changing it cannot alter authorization semantics for the supported policy fragment.
