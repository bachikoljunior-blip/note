## C271 — current checker cost events are post-return summaries, not dispatch receipts
`StructuredControllerRuntimeMixin._check()` and `_check_source()` materialize a deterministic candidate, reserve the check budget, synchronously call `adapter.check(...)`, and only *after that call returns* invoke `_record_checker_cost(...)`. The resulting `CostLedgerEvent(kind=CHECKER)` has:

- positional `event_id=f"checker:{len(ledger.events)}"`;
- `status="completed"`;
- attempt index / checker kind / final category;
- final `check_result.elapsed_seconds` as wall time;
- no `call_id`, request ID, operation identity, durable started record, or pre-dispatch status.

Therefore current `CostLedger` cannot distinguish:
- checker never started,
- checker started and process died,
- checker finished but process died before `_record_checker_cost`,
when the final checker event is absent.

This directly confirms that effectful v0 recovery must remain fail-closed unless the new Attempt/Receipt layer is implemented.

## C272 — `CostLedgerEvent` has a `call_id` concept, but checker events do not require or populate it
The general cost-ledger schema requires `call_id` only for `TOOL_CALL`; `CHECKER` requires only `checker_kind`. This is an important distinction: an existing nullable field named `call_id` is not an existing checker idempotency contract.

Do not retroactively treat positional checker event IDs or candidate IDs as effect operation IDs. Add a separate stable `effect_operation_id` with explicit semantics/versioning.

## C273 — current Lean server retry logic can undercount checker wall cost even without crashes
`LeanAdapter.check()` may execute multiple physical checker attempts inside one logical check:

1. `_check_with_server()` measures one server attempt's elapsed time and returns a timeout result on `LeanServerTimeout`.
2. If a timeout result is received and `server_attempt < server_timeout_retries`, `check()` closes/restarts the server and repeats the unchanged candidate.
3. Only the final returned `CheckResult` survives to `StructuredController._record_checker_cost()`.

The elapsed time of an earlier timed-out server attempt is therefore discarded from the single final checker cost event. With the default `server_timeout_retries=1`, one logical action can consume at least two server attempt windows while the recorded checker wall time reflects only the final `CheckResult`.

A separate path also exists for `LeanServerError` / ambiguous completion: `_check_with_server()` closes the server and returns `None`, after which the adapter falls through to the subprocess checker. The elapsed server work before that fallback is likewise not included in the subprocess `CheckResult.elapsed_seconds` recorded by the controller.

This is a cost-accounting defect independent of the crash journal and independent of learned-policy randomization.

## C274 — physical checker attempts need the same treatment already used for provider retries
Provider generation already models physical retry attempts separately (`provider_requests` → one request/usage event pair per physical request), while a logical checker currently collapses internal physical retries/fallback into one post-hoc event.

For compute-normalized policy learning, add a physical checker attempt stream, e.g.:

```text
CheckerAttemptEventV0:
  effect_operation_id
  physical_attempt_index
  transport = lean_server | subprocess
  candidate_semantic_sha256
  command_or_server_version_fingerprint
  status = started | completed | timeout | error | ambiguous
  started/completed monotonic duration when available
  wall_time_ms
  cpu_time_ms nullable/unavailable
  fallback_parent_attempt_id nullable
```

The controller/action-level `EffectReceiptEventV0` may summarize the logical check, but authoritative checker cost must sum physical attempt receipts, not just the final `CheckResult`.

## C275 — retry/fallback accounting changes the Stage-A/Stage-B cost model boundary
The current planned Stage-A structural selector still has zero checker execution cost for its four reducer-only actions, so C273 does not invalidate the initial structural experiment. But any later comparison that includes `RUN_CAPABILITY_TEST`, `IMPLEMENT`, `REPAIR_IMPLEMENTATION`, final assembly checks, or policies that choose between structural progress and checker-bearing actions must correct physical checker-attempt accounting first.

Otherwise a policy that triggers more server timeouts/fallbacks can look artificially cheap and receive a distorted value-per-cost label.

## C276 — fault-injection matrix expands to physical checker attempts
Before checker-bearing actions enter randomized support, include at least:

1. crash after EffectAttempt commit but before checker dispatch;
2. crash after server subprocess/process begins but before return;
3. server timeout followed by restart/retry;
4. server ambiguous/error followed by subprocess fallback;
5. crash after a physical checker result but before its physical Receipt;
6. final logical checker result durable but action Outcome absent;
7. replay/reconciliation under a substrate that has no queryable checker receipt — must fail closed rather than rerun silently.

For cases 3–4, total observed checker wall time should equal the sum of physical attempt durations represented by receipts; the final logical result may be one summary record but must not replace physical cost facts.

- It does not establish CPU accounting; current checker CPU time is explicitly unavailable.
- It does not claim a process start record can survive a machine-level crash until an actual durable effect journal exists.
