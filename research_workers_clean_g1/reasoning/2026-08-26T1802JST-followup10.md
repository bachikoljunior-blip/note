## C314 — current action node identity hashes provider/cost telemetry, not only action semantics
`ProposalCache._make_node()` computes:

```text
fingerprint = json.dumps(proposal.to_dict(), sort_keys=True, ...)
node_id = sha256(branch | obligation_version | workspace_version | fingerprint)[:24]
```

`StructuredActionProposal.to_dict()` includes the whole `metadata` map. `ChatStructuredActionGenerator` copies into each proposal metadata:

- model;
- choice index / finish reason;
- merged token usage;
- `provider_requests` physical-attempt telemetry;
- tool-call telemetry;
- any model-supplied metadata.

`UrllibChatTransport` physical request labels contain fresh local UUID material. Therefore two semantically identical actions produced in otherwise identical states can receive different current `node_id`s solely because provider telemetry/request IDs differ.

## C315 — telemetry-sensitive node IDs can affect D0 action choice, not just observability
`ActionFrontier.ranked()` uses `node.node_id` as the final tie-break after check-cost, branch legacy key and action-kind value. Thus when two proposals are otherwise tied on those priority components and action kind, random/nonsemantic provider metadata can change their node IDs and therefore their D0 ordering.

This means the current baseline has a narrow but real path from transport telemetry → node hash → tie-break → selected action.

Do not describe current `node_id` as a semantic action identity.

## C317 — define execution envelope vs telemetry envelope explicitly
A robust content-addressed proposal store should not rely on "metadata minus a few known keys" without versioning. Freeze two hashes:

### `execution_envelope_sha256`
Includes every field needed to reproduce the selected executor/reducer behavior under the pinned substrate, e.g. action kind/target/mutation scope/target-step IDs/rationale, typed payload, and any explicitly execution-relevant compatibility metadata.

### `observation_envelope_sha256`
Includes the full frozen proposal object plus provider/model/tool/cost provenance exactly as received.

And a third learning identity can be narrower:

### `semantic_proposal_sha256`
Action/payload semantics after a frozen normalization contract, excluding request IDs, token/cost telemetry, timestamps and other observational metadata.

Never execute from the semantic hash alone; replay uses the full frozen execution envelope reference.
