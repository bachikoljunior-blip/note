## C234 — Current `proposal_cache_events` cannot reconstruct node→provider-batch causality
The action-runtime trace exposes the ingredients separately but not the necessary join:

- `cache_fill` records `proposal_batch_id`, source and aggregate `proposal_count`, but **not the node IDs** created from that batch.
- `choice_set` records `node_id`, branch, action kind, estimated execution cost and budget admission, but **not `proposal_batch_id`, proposal source/model tier, proposal fingerprint/payload, obligation version or cached workspace version**.
- `action_selected` records `node_id`, branch, kind and model-routing fields, but again not `proposal_batch_id`.
- `ActionFrontierNode.to_dict()` actually contains proposal + `proposal_batch_id`, but the final `ControllerResult` does not serialize the live/consumed cache itself.
- the current provider ledger temporarily supplies a reverse-looking join through mutable `metadata.action_id`, but after two consumers that field only retains the last node.

Therefore, in a production multi-consumer trace, node1→batch provenance can be **irrecoverably lost** even if all final JSON is retained. The one-batch regression can infer the relation only because the fixture controls the generator and knows there was exactly one batch.

Migration implication: `ExecutionDecisionEvent` and/or `ProposalBatchConsumptionEvent` must explicitly carry `proposal_batch_id` and stable proposal identity. Do not assume `proposal_cache_events` plus the physical cost ledger can reconstruct it later.

## C235 — Current `argument_records` report attempted structural edits as executions even when the reducer returns the identical workspace
`StructuredControllerActionMixin._run_argument()` always appends an `argument_records` entry after calling `apply_argument()`. It does not compare the workspace before/after and records no node ID, batch ID, action target-step pins, workspace versions or effect status. The same pattern exists conceptually for other structural action records.

For a ghost-ID REFINE no-op, the trace therefore contains an `argument_records` row and a log message saying the edit was executed even though the authoritative workspace did not change. Counting these records as progress would systematically mislabel deterministic no-ops.

This strengthens the Outcome contract: structural execution needs an explicit semantic effect record (`NO_EFFECT` vs `EFFECTFUL` vs error/terminal class) derived from authoritative before/after state, not from the mere existence of an executor record.

## C236 — Execution-cost observations also cannot distinguish a meaningful free structural mutation from a no-op
`action_cost_observed` starts its ledger window **after** selection/provider-generation attribution and projects only events emitted during selected execution. Structural actions have a static execution prior of zero checker calls. A pure structural mutation and a deterministic structural no-op can therefore both produce:
- zero model requests in the execution window,
- zero checks,
- zero token/API execution cost,
- and no ledger event IDs.

`actual_cost_from_events(())` intentionally reports zero controlled-action resource use. That is correct cost accounting, but it provides no semantic-progress signal. A learned value-per-cost policy must never infer “good cheap action” from zero execution cost alone; it needs a separate verified/structural outcome signal.

## C238 — Decision-event v0 needs proposal identity, not just opaque node ID
For OPE/replay, each supported choice row should minimally persist:
- `node_id`;
- `proposal_batch_id` / proposal source;
- canonical finalized proposal fingerprint (and either proposal body or content-addressed durable body);
- action kind, branch/obligation identity + versions, cached workspace version;
- baseline frontier rank and budget admission/cost estimate;
- structural preview status/reason;
- support-membership reason;
- chosen exact propensity for the selected row.

This lets a reader prove that the policy compared the same semantic alternatives and that a later outcome/batch edge refers to the same frozen proposal, rather than treating `node_id` as an unexplained label.
