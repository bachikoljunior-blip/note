## New findings

### C361 — Cedar closes much of the formal-policy -> analysis-IR gap, but only after a policy has already become a Cedar semantic object

**Observed.** Current Cedar security documentation describes an executable Lean formal model as semantic ground truth, a Rust production engine, property-based testing for properties including parser/formatter roundtrip, and differential testing between the formal model and production implementation. The current `cedar-spec` Lean README lists machine-checked properties including sound type checking, sound and complete symbolic compilation, and sound and complete verification based on the symbolic compiler. The symbolic compiler theorem states that the SMT encoding is sound and complete with respect to concrete Cedar semantics for well-typed Cedar expressions/policies.

Sources:
- https://docs.cedarpolicy.com/other/security.html
- https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/README.md
- https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/Cedar/Thm/SymbolicCompilation.lean
- https://arxiv.org/abs/2403.04651

**Inference.** For `SemanticLoweringCertificateV0`, a Cedar-like formally specified policy AST can be a substantially stronger authority root than arbitrary natural language. The downstream `formal policy -> symbolic analysis` link no longer needs to be treated as wholly open: Cedar provides a concrete, machine-checked precedent for that portion of the chain.

**Scope guard.** This does **not** establish that human intent -> Cedar source, Cedar text -> AST, or the production Rust implementation are all machine-proved end to end. Production correspondence uses testing/differential testing where the formal proof does not directly cover the implementation boundary.

### C362 — Cedar's text parser is a real trust boundary; downstream formal verification does not erase parser risk

**Observed.** Cedar's current security guide explicitly says parser/formatter roundtrip is checked with property-based testing rather than presented as a Lean theorem. Cedar's verification-guided development report records six parser-roundtrip bugs and two formatter-roundtrip bugs found by its testing regime; Amazon's engineering account also reports subtle Cedar policy-parser bugs found through differential/random testing.

Sources:
- https://docs.cedarpolicy.com/other/security.html
- https://assets.amazon.science/d3/86/99db1aa142ffb6981d86dc849e4c/how-we-built-cedar-a-verification-guided-approach.pdf
- https://www.amazon.science/blog/how-we-built-cedar-with-automated-reasoning-and-differential-testing

**Inference.** `source_semantics_class = machine_formal` is too coarse if it silently treats policy text bytes as identical to the formal AST. The certificate should split at least:

`source representation -> parser/constructor -> canonical policy AST -> type/schema validation -> symbolic compilation/verification -> activation`.

A proof about the AST/compiler cannot compensate for a wrong text-to-AST parse. For authority-increasing changes, activation should bind the canonical semantic object (or an unambiguous digest of it), plus the parser/constructor version/provenance if text was involved.

### C363 — Cedar 4.11+ provides a practical way to remove free-form policy-text parsing from the grant-critical authoring path

**Observed.** Cedar 4.11.0 introduced a public syntax tree (`pst`) API for programmatic construction, inspection, and manipulation of policies, with `from_pst()`, `to_pst()`, and `try_into_pst()`. The PST API validates identifiers during construction. Cedar 4.12.0 then fixed a `PolicySet::from_pst` defect where malformed map-key/policy-id disagreement could previously be silently accepted.

Sources:
- https://docs.rs/cedar-policy/latest/cedar_policy/pst/index.html
- https://docs.rs/cedar-policy/latest/cedar_policy/struct.Policy.html
- https://github.com/cedar-policy/cedar/blob/main/cedar-policy/CHANGELOG.md

**Inference.** A high-assurance authoring path should prefer direct construction/review of a typed policy AST/PST over string concatenation or reparsing generated Cedar text. Cedar's own security guide independently warns that dynamic string concatenation can cause Cedar-code injection and recommends structured templates. This removes an unnecessary text grammar boundary from the positive-authority path.

**Counter-scope.** PST construction is not itself demonstrated here as machine-verified against the Lean model. The 4.12 fix is evidence that structured construction still needs version binding, validation, and regression tests; it is not automatically a trusted compiler merely because it avoids text parsing.

### C364 — Verified parser technology exists, but parser correctness and source-language semantics are separate proof obligations

**Observed.** Vermillion is a Coq-verified LL(1) parser generator whose generated parsers are proved sound, complete, and terminating; its case study includes a linear-time verified JSON parser, reported as roughly 2–4x slower than an unverified parser for the same grammar. EverParse generates verified parsers/serializers and proves safety/correctness/non-malleability for its parsing layer, but its own paper explicitly keeps the higher-level QuackyDucky input-language compiler outside the trusted computing base because the input-language semantics are not formalized.

Sources:
- https://doi.org/10.4230/LIPIcs.ITP.2019.24
- https://www.usenix.org/conference/usenixsecurity19/presentation/delignat-lavaud
- https://www.microsoft.com/en-us/research/publication/everparse/

**Inference.** If a textual controlled policy language remains desirable, there is no need to accept an unverified parser by default; verified parser generators or validated parser tables are viable building blocks. But a verified parser alone does not prove that the parsed AST has the intended authorization semantics. `SemanticLoweringCertificateV0` must track parser correctness and semantic lowering as distinct edges.

### C365 — AutoCedar is a strong direct precedent for treating arbitrary NL as provisional until behavior-level intent is separately approved

**Observed.** AutoCedar (July 2026) turns NL requirements into schema/property atoms, requires both a mechanical pass and human intent acceptance before an atom enters the approved target, then synthesizes Cedar against that fixed target. The paper explicitly states that verifier success proves correctness only relative to the approved plan; whether that plan captures organizational intent remains a human-review assumption. On CedarBench it reports 221/221 convergence and 221/221 full property pass for AutoCedar; a direct GPT-5.5 baseline given the AutoCedar schema reaches 176/221 full property pass (79.6%), showing that merely producing valid-looking Cedar against the right vocabulary is not the same as satisfying the reviewed semantic boundary.

Sources:
- https://arxiv.org/abs/2607.03656
- https://github.com/neselab/cedar-synthesis-engine

**Inference.** This is close to the desired positive-authority discipline:

`arbitrary NL (untrusted) -> proposed intent atoms -> mechanical validity + trusted intent approval -> fixed formal target -> verifier-guided synthesis -> activation`.

The learned model may propose interpretations but does not get to turn agreement or fluency into authority by itself. This supports keeping `arbitrary_nl_untrusted` rather than promoting NL to a source of grant authority.

### C366 — Refine `SemanticLoweringCertificateV0` from a scalar trust class into a typed evidence chain

Proposed fields/invariants for the next implementation draft:

- `authoring_source_class`: `machine_ast | controlled_formal | arbitrary_nl_untrusted`.
- `source_digest` and `source_version`.
- `parser_or_constructor_id`, version/hash, and `parser_proof_status`: `not_applicable | verified_sound_complete | validated | differential_or_property_tested | unverified`.
- `canonical_policy_ast_digest` and `policy_language_semantics_version`.

- `semantic_lowerer_id`, version, proof/validation status.
- `symbolic_compiler_id`, version, proof/validation status.
- `intent_witness_type`: `machine_spec | trusted_human_atom_approval | trusted_translation_witness | none`.
- exact source-span / atom provenance for any NL-originated behavior.
- `authority_delta` and the exact `activation_witness` bound to the canonical AST/policy-set digest.

Hard rules:
1. `arbitrary_nl_untrusted` cannot create a positive authority delta without a separately trusted intent/translation witness.
2. Learned validators may attenuate/reject but may not upgrade an untrusted source edge to a verified one merely by agreement.
3. A machine-proved downstream compiler does not mask an unverified source parser/lowering edge.
4. Textual authoring should be avoided in the grant-critical path when direct typed AST construction is available.
5. All grant-critical transformations are version/digest bound; stale or mismatched parser/PST/compiler versions cannot commit.

New deterministic regressions to add before any effectful randomized support:
- `text_parse_mismatch_cannot_grant`.
- `canonical_ast_digest_is_activation_subject`.
- `pst_or_constructor_version_mismatch_cannot_commit`.
- `verified_downstream_cannot_mask_untrusted_source_lowering`.
- `nl_positive_delta_requires_trusted_intent_witness`.
- Preserve prior `authority_non_amplification`, `learned_omission_cannot_widen`, `stale_witness_cannot_commit`, `common_mode_lowering_error_cannot_grant`, and `arbitrary_nl_agreement_cannot_escalate_to_formal_authority`.

## Synthesis

The source-side frontier is narrower than before. The best current architecture is not "find a perfect NL translator". It is:

1. Keep unrestricted NL advisory/provisional.
2. Review behavior-level atoms or use an already machine-formal source as the authority root.
3. Materialize a canonical typed authorization AST/policy set and bind activation to its digest/version.
4. Treat any parser/constructor as a separately versioned/proven edge; prefer direct typed AST construction where possible.
5. Validate/typecheck against an explicit schema/type environment.
6. Use a machine-checked or at least proof-linked symbolic compiler/verifier for downstream semantic checks.
7. Recheck authorization/authority witnesses immediately before durable commit.

Cedar + AutoCedar jointly supply unusually close precedents for steps 2–6 while also exposing exactly where the remaining trust boundaries live: human intent capture, textual parsing/structured-construction implementation, production-vs-formal-model correspondence, and commit-time authority freshness.
