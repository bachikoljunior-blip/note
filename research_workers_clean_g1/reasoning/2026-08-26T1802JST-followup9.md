## C308 — current OpenAI-compatible transport retries are not an idempotency contract
`UrllibChatTransport.post_json()` generates a short local UUID-derived request label for telemetry and may retry transient network errors up to `max_retries` (default 2) with exponential backoff. That local request label is used in logs/telemetry as `request_id:attempt`, but it is not inserted into the HTTP headers or payload as a provider-recognized idempotency key.

Therefore a connection reset/timeout after the provider has accepted or completed a request but before the client receives the response can be retried as another physical generation. The client cannot infer from its local retry label whether the first physical request was billed or generated tokens.

## C309 — provider physical-attempt telemetry is better than checker telemetry but still post-hoc and process-local
The transport accumulates `_provider_request_events` in memory and exposes them after request processing. It records retry index, status, HTTP status, wall time and error, and adds token usage only to the final response-bearing event.

This preserves observed failed/retry transport attempts when the process survives, but:
- it is not durable before dispatch;
- a crash can lose the attempt list;
- an ambiguous network failure has no token/billing receipt;
- provider execution cannot be queried by the local telemetry ID.

Thus C285's durable generation Attempt layer remains necessary.

## C310 — current token reconciliation correctly becomes unknown under an ambiguous retry, but API-charge projection can still look falsely complete
For a retry event without provider usage, `record_proposal_request()` creates a `PROVIDER_USAGE` event whose token measurements are explicitly `unavailable`. The `CostLedger.reconcile()` token dimensions then become unavailable if any contributing provider-usage event is unavailable. This is fail-closed and good.

However `_record_charges()` creates a single batch-level CHARGE from the proposal metadata/provider-reported charge or a frozen-price estimate, normally based on the response-bearing aggregate usage. It does not create/mark a charge uncertainty for each earlier ambiguous physical retry.

Therefore a run can have:

```text
input/output/billed token total = unavailable because retry usage unknown
api_cost_usd = apparently observed/estimated from final response only
```

when an earlier network-failed attempt may also have been billed. That API-cost value is not a safe complete total.

## C311 — cross-dimension completeness must be explicit
Add a run/batch cost-completeness state. If any physical provider attempt has `execution_or_billing_ambiguous=true` and no queryable provider receipt, then:

- total provider token usage remains unavailable;
- total provider API charge must also be unavailable or explicitly lower-bounded, not a complete observed/estimated total;
- the response-bearing request's known charge may be retained as a component/lower bound with provenance;
- value-per-dollar training must not treat the lower bound as total cost.

Do not let one measured dimension silently imply another ambiguous dimension is complete.

## C312 — physical provider Attempt/Receipt should distinguish transport failure from execution certainty
A future durable provider physical-attempt event should carry separate fields such as:

```text
transport_status
provider_response_received
provider_request_id_from_server nullable
execution_or_billing_certainty = confirmed | not_executed | ambiguous
usage_receipt_status
charge_receipt_status
```

`URLError`, timeout or reset alone generally establish a client transport failure, not non-execution at the provider. Unless the provider contract supplies a stronger guarantee, classify that physical attempt's remote execution/billing as ambiguous.
