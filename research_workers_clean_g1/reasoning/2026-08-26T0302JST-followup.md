## C48 source update — HILBERT's public configuration confirms that escalation is controlled by fixed budgets/thresholds

Primary public artifact:
- `apple/ml-hilbert`, `configs/experiment/async_hilbert.yaml` on public main.

Exact surfaced controls in the released configuration:
- `max_depth: 4`.
- `complexity_proof_length_cutoff: 30`; the comment states that if the informal LLM is trying to write a proof longer than 30 lines, stop and recurse.
- `subgoal_decomp_attempts: 4`.
- `formal_proof_attempts: 4`.
- `main_theorem_error_corrections: 6`.
- `subgoal_error_corrections: 6`.
- `missing_tags_error_corrections: 3`.
- `parallel_subgoal_proof_attempts: 4`.
- `proof_sketch_corrections: 8`.
- `missing_subgoal_extraction_attempts: 3`.
- `proof_verification_timeout: 60` seconds.

Interpretation:
- This turns the earlier qualitative C48 observation into a concrete controller baseline: HILBERT exposes a useful heterogeneous hierarchy, but the public implementation purchases another proof attempt, correction, recursion/decomposition, or timeout exit through **fixed counts and thresholds**, not an estimated marginal value of the next action.
- A learned-controller experiment can therefore hold the available HILBERT actions/models/retriever/verifier fixed and replace only these thresholds with a state-dependent policy. That would isolate controller quality much more cleanly than comparing entirely different prover stacks.
- Because several limits operate at different semantic levels, a controller should predict both outcome and cost at the action's own scope rather than using one theorem-level scalar.

Scope:
- Configuration values establish released behavior, not that another threshold would improve or hurt performance.
- Public main may evolve; future replications should pin a commit before quoting exact values.

## C49 — LEAP is another strong direct Lean hierarchy, but explicitly leaves branch prioritization and compute allocation as future work

Primary source:
- `LEAP: Supercharging LLMs for Formal Mathematics with Agentic Frameworks`, arXiv:2606.03303 (2026-06).

Mechanism:
- LEAP first attempts a direct formal proof with compiler-feedback revision and LeanSearch retrieval.
- When direct proving fails, it switches to an informal blueprint and a compiler-checked Lean proof sketch, adding proposed lemmas as children of an AND-OR DAG.
- Verified lemmas are memoized globally in the DAG and reused across branches.
- An LLM reviewer rejects decompositions that are formally admissible but do not make semantic progress, thereby triggering backtracking and alternative strategies.
- The released/published search is a **simple DFS with backtracking**, not a learned policy over heterogeneous meta-actions.

Evidence:
- On Lean-IMO-Bench, the full DAG version improves over the otherwise matched naive-tree workflow from **73.3% to 83.3%** on the Basic split and **40.0% to 56.7%** on the Advanced split.
- On the difficult Putnam 2025 A5 case, removing the decomposition reviewer causes failure even after eight rollout attempts, whereas full LEAP solves the problem; this is a single-problem ablation and not an aggregate reviewer effect.
- The paper reports 100% solve rate on the twelve Putnam 2025 problems under its rollout setting and strong Lean-IMO-Bench performance, but these are pipeline-level results with substantial internal agentic compute.
- In an iterative compiler-feedback-only comparison on the Lean-IMO-Bench Basic set, Gemini-3.1-Pro improves from **20.0% one-shot Pass@128 to 36.6% iterative Pass@1**, whereas Goedel-Prover-V2-32B changes **10.0% to 6.6%**. This is strong negative evidence against assuming local feedback iteration helps every backbone.

Why it matters for the current frontier:
- LEAP independently validates `direct attempt -> retrieval/revision -> decomposition -> memoized subgoal search -> backtracking` as a useful Lean action hierarchy.
- More importantly, the authors explicitly identify **branch prioritization, decomposition strategy, and compute allocation across large proof searches** as central future challenges. Thus a very strong 2026 agentic Lean system still leaves the current learned heterogeneous-control frontier open.
- The reviewer result suggests that purely formal admissibility is insufficient for branch selection, but C18/FormalRewardBench warns against treating an LLM reviewer as a generally calibrated progress oracle. A future controller should compare reviewer scores with verifier/trajectory/progress signals and calibrate the decision.

Scope / caution:
- Full DAG vs naive tree is a useful same-workflow memory ablation, not a learned-controller ablation.
- A5 reviewer evidence is one hard case.
- Pipeline headline results are not comparable to one-shot/pass@K systems without accounting for internal calls and wall-clock.
- LEAP itself says the search is currently simple DFS with backtracking, so do not describe it as learned branch scheduling.

Source:
- https://arxiv.org/abs/2606.03303

## Frontier refinement

The direct Lean evidence is now unusually consistent:

1. High-performing systems already expose **heterogeneous actions**: direct proving, compiler repair, retrieval, decomposition, memoization/preservation, backtracking/replanning and model/reasoner escalation.
2. HILBERT, BFS-Prover-V2 and LEAP largely choose among those actions with **fixed budgets, event triggers, DFS/backtracking, or reviewer heuristics** rather than a calibrated learned action-value policy.
3. This means the highest-value missing experiment can be controller-only: preserve the same prover/retriever/verifier/action implementations and learn just the decision of **which action to buy next and when to stop/escalate**.
4. Backbone dependence is material. LEAP's iterative-feedback table improves Gemini but degrades Goedel, echoing earlier diversity/repair findings that an action's marginal value is policy/model dependent.
5. Global memory/memoization has direct value: LEAP's DAG vs naive-tree ablation is large, so action-value models must condition on which verified subgoals/context are already reusable, not only the current local proof state.
6. LLM semantic review can prevent pathological decompositions, but it should be treated as one noisy feature, not the sole controller oracle.

## Nonempty unresolved frontier

1. **Controller-only matched Lean experiment:** replace HILBERT/BFS/LEAP fixed thresholds/DFS triggers with a learned policy while holding action implementations, models, retrieval and verifier fixed.
2. **Calibrated action utility:** Brier/ECE/reliability/selective-risk for `attempt / repair / retrieve / decompose / replan / backtrack / escalate / stop` under theorem/backbone/policy shift.
3. **Action-specific sufficient state:** current proof state + compressed trajectory/progress/error history + reusable-DAG/cache state + retrieval coverage + remaining budget + execution substrate.
4. **Backbone-conditioned routing:** learn when feedback iteration, semantic branching or repair is beneficial vs harmful for the current prover family/training regime.
5. **Matched subgoal scheduling:** first-stuck focused vs hardest-branch vs independent parallelism vs total-work/tail-risk.
6. **Search purchase:** decide when a greedy learned scheduler suffices and when MCTS/beam/extra semantic branching pays for itself.
7. **Triggered global re-retrieval, online trajectory compression, snapshot+semantic-selection+repair**, and benchmark-audited compute normalization remain open.
