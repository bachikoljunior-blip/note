## C77 — The released Harness-RL artifact does not currently expose a tracked Behavior-Cloning or Forced-CHECK reproduction path

Primary paper: Yi & Song, *Learning to Control LLM Agent Harnesses with Offline Reinforcement Learning*, arXiv:2607.05458v1 (2026-07-05), https://arxiv.org/abs/2607.05458
Public artifact inspected at commit `5d577632ef4803f819125fc9ef9ef9dd257c077d`: https://github.com/Hik289/Agentic-RL-harness

The paper's Table 4 includes Base, Advantage Weighting (AW), Behavior Cloning (BC), and Forced CHECK (FC). Prior checkpoint C73 preserved the exact eight-domain lifts and their scope. This run resolved the remaining artifact-entry-point question negatively for the currently tracked release:

- README's paper-scale path says to run `examples/running_main_driver.py` plus `examples/main_table_analysis.py`, and describes each domain as `collect -> train -> evaluate`.
- `running_main_driver.py` is explicitly a **Base vs AW** experiment. It collects the epsilon-perturbed Base buffer, calls `train_aw`, then evaluates only `base` and `aw` policies.
- `main_table_analysis.py` reads only `results.json` and `eval_detail_{base,aw}.jsonl`; its output schema contains no BC or FC cells.
- `code/rl/offline_aw.py` implements advantage weighting only (`compute_advantages`, weighted dataset construction, `train_aw`) and exposes no BC trainer.
- `docs/ARTIFACT.md` explicitly states that no single reproduction runner is tracked and directs users to the README commands.
- The tracked `examples/` listing contains the AW anchor/main driver/analysis utilities but no clearly named BC/Forced-CHECK runner.

Therefore the published BC/FC ablation values are **not reproducible through the documented main-table entry point as released at this commit** without reconstructing additional baseline logic/protocol or obtaining an untracked command/script. This is a reproducibility gap, not evidence that the paper's Table 4 values are wrong.

Do not silently substitute an inferred implementation for the paper protocol. A plausible BC reconstruction would use the same featurizer/policy architecture with uniform per-step imitation weights, and a plausible FC reconstruction would force a legal CHECK before eligible submit, but the release does not define those as the authoritative Table-4 procedures. Exact action legality, fallback, budget interaction, seed handling, and evaluation parity would need to be specified before such a reconstruction could be called a reproduction.

## C78 — A 2026 Lean verification scaffold already exposes almost exactly the heterogeneous outer action classes needed for a learned controller, but its current progress controller is not learned

Primary source: Max Tan, *Automating Formal Verification with Reinforcement Learning and Recursive Inference*, arXiv:2605.30914v1 (2026-05-29), https://arxiv.org/abs/2605.30914

The thesis explicitly defines an agentic scaffold by five interfaces: maintained state, roles, tools, actions, and a controller. Its Lean progress-evaluation layer has:

1. deterministic hard gates for format, theorem-signature preservation, no-bypass constraints, Lean verification, recursion depth, and cost/call budgets;
2. task-level evaluation over the whole Lean artifact, diagnostics, unresolved obligations, and prior control decisions;
3. proof-level evaluation over a local obligation, Lean diagnostics/goal inspection/type information, branch history, and decomposition tree;
4. a discrete control action space with three broad classes:
   - local continuation / repair / tool-assisted search;
   - structural revision / proof-sketch revision / recursive decomposition;
   - escalation to the task-level scaffold or branch pruning;
5. budgeted termination, with additional attempts for branches judged to show progress.

This is a very close structural match to the proposed typed Lean harness MDP. Critically, however, the thesis states under future work that the **current scaffold relies on progress judgments** and proposes training a verifier-aware progress model from successful/failed scaffold traces; it likewise describes the proof reviser as still largely prompted and proposes trained value/reviser models that choose among repair, decomposition, retrieval, or abandonment. Thus this source does **not** close the learned outer-controller gap. It provides a strong hand/prompted-controller baseline and a ready action/state ontology.

The empirical ablations also show why action selection matters rather than mere tool/search volume. On the same 26-task Vericoding pilot with the same GPT-5.3 Codex base model:
- direct + repair: 12/26 (46.2%), 159 model calls, 109 verifier/tool calls;
- direct + repair + top-level tools: 6/26 (23.1%), showing tool exposure alone can hurt;
- E1 shallow decomposition: 7/26 (26.9%), 4,204 calls;
- E2 shallow decomposition + repair: 14/26 (53.8%), 4,945 calls;
- E3 recursive decomposition: 11/26 (42.3%), 5,962 calls, worse than E2 despite more calls;
- E4 recursive + larger budget: 15/26 (57.7%), 8,775 calls;
- E5 full scaffold balancing decomposition/repair/progress: 17/26 (65.4%), 5,104 calls, exceeding E4 with fewer calls;
- E5 recursive repair + subgoal tools: 17/26 (65.4%), 3,194 calls and the lowest reported cost among the 17-solve settings;
- full scaffold + proof reviser: 18/26 (69.2%), 3,231 calls, accuracy-oriented but higher reported cost.

The broader transfer result is an important counterweight: on a 30-task Dalek-Bench subset, recursive scaffold + tools + proof reviser solved only 2/30 (6.7%) versus direct + repair + tools 5/30 (16.7%), while spending much more search. So a learned controller must be calibrated under distribution shift and must retain a strong fallback; recursive/decomposition actions cannot be globally preferred.

Scope guard: these configurations differ in inference budget and mechanisms, so they are scaffold-design trends, not a clean matched causal estimate of one controller action. The thesis itself cautions that structured search gains spend additional inference budget and that dollar accounting is incomplete in some rows.

## C79 — BFS-Prover-V2's “multi-turn off-policy RL + planner” is a near miss, not an outer-controller RL result

Primary source: Xin et al., *Scaling up Multi-Turn Off-Policy RL and Multi-Agent Tree Search for LLM Step-Provers* (BFS-Prover-V2), NeurIPS 2025 MATH-AI workshop / public manuscript, https://bfs-prover.github.io/V2/

The title can misleadingly look like the sought learned meta-controller. The paper makes the separation clear:

- training-time off-policy RL/expert iteration trains the **step prover** as a Lean tactic policy over `(proof state, tactic)` trajectories, with adaptive tactic-level perplexity filtering and periodic retraining;
- inference-time hierarchical control is a separate **general reasoning LLM Planner** that proposes subgoals, re-plans when a subgoal exhausts its budget, and coordinates parallel prover agents over one subgoal at a time with a shared cache.

Therefore BFS-Prover-V2 provides strong evidence for tactic-level off-policy learning plus hand/free-form hierarchical inference, but it does not report an offline-RL policy over outer actions such as retrieve/repair/decompose/replan/escalate/submit, nor logged propensities for such meta-actions. It does not close C76's targeted gap.

It remains useful as a controller baseline/action primitive: the planner re-query is triggered only when a current subgoal fails within budget, successful subgoals are retained as context, and all parallel provers focus on one current subgoal to avoid spending compute on downstream subgoals invalidated by a later replan.

Source: https://openreview.net/pdf/ab2dc940dbfa0ff26a3a7d5b9e74f36418d4be56.pdf

## D1 — Stage-A/Stage-B action-eligibility matrix for an OpenProver-compatible Lean harness MDP

OpenProver's public planner directly chooses actions such as `spawn`, `literature_search`, `read_items`, `write_items`, `write_whiteboard`, `read_theorem`, and proof submission; Lean workers additionally expose `lean_verify`, `lean_store`, and `lean_search`. For propensity-identifiable data collection, do not randomize all of them uniformly.

### Direct OpenProver planner actions

| Action | Class | Stage A randomized? | Rationale / guard |
|---|---|---:|---|
| `read_theorem` | bounded read-only epistemic | yes | cheap/reversible; hard-mask when already fresh and redundant if desired |
| `read_items` | bounded read-only epistemic | yes | reversible; cap items/bytes |
| `literature_search` | bounded external epistemic | yes, only under explicit query/time/cost cap | may be expensive/noisy but does not mutate proof state |
| `write_whiteboard` | reversible scratch-state mutation | yes only with snapshot/restore and per-episode isolation | changes future context; exact state digest must be logged |
| `spawn` | expensive-but-reversible compute purchase | no in Stage A; separately gated Stage B | consumes model/worker slots and can dominate cost |
| `write_items` | persistent/shared proof-memory mutation | no in Stage A | even verified items alter future search; randomize only in isolated/versioned memory with exact rollback |
| `submit_proof` / `submit_lean_proof` | terminal | no in Stage A | premature random submit changes episode censoring/return |

### Worker/tool actions if promoted into the outer controller

- `lean_verify`: bounded verifier observation; Stage A eligible under call/time cap.
- `lean_search`: bounded retrieval; Stage A eligible under result/time cap.
- `lean_store`: persistent verified-memory mutation; Stage B only unless episode-isolated/versioned.

### Derived formal-proof control actions

Tan's scaffold motivates typed actions not directly named in OpenProver: `LOCAL_REPAIR`, `REVISE_SKETCH`, `DECOMPOSE`, `ESCALATE_TO_TASK`, `PRUNE/BACKTRACK`. These should be represented as explicit meta-actions only if their executor contract is fixed and replayable. Do not claim a one-to-one mapping to OpenProver's current planner tokens.

Stage A should provide support only over reversible/local/bounded choices. Expensive model/worker escalation, shared writes, and terminal submit remain deterministic-baseline-only until a separately preregistered Stage-B mixture defines eligibility, hard caps, and exact propensity.

## D2 — Replay-complete structural event schema for exact behavior propensities and later OPE

At every controller decision, log enough structural state to recompute hard masks, baseline action, randomization subset, and selected-action propensity without hidden chain-of-thought.

Pre-action event fields:

- identity/provenance: `episode_id`, `decision_id`, `step_idx`, theorem/task id, benchmark manifest/hash, Lean/toolchain/environment hash, executor/controller/baseline versions;
- proof structure: current proof-state/snapshot id, active subgoal ids, decomposition-tree digest, verified cache/DAG digest, whiteboard/repository-memory digest;
- verifier state: latest Lean status, normalized error class, unresolved-goal summary, signature/no-bypass gate results;
- compact learned/derived summaries: progress/value estimate, repairability estimate, estimated remaining proof cost, uncertainty/calibration fields, with model/version attached;
- retrieval state: current retrieved-context ids/digest, retrieval tier already tried, freshness/coverage summary;
- real budget vector: remaining input/output tokens, money/provider budget, Lean/tool time, state-reconstruction time, wall-clock, and occupied worker/model-slot time;
- routing state: model/worker tier, previous meta-action, bounded attempt counters, recursion depth;
- policy support: deterministic `baseline_action`, `baseline_policy_version`, full `legal_action_mask`, `randomized_action_mask`, `fallback_rule_version`, Stage-A epsilon and any gated Stage-B delta, full behavior probability vector, `chosen_action`, and `mu_chosen`;
- `controller_state_hash` over the exact replay inputs.

Post-action event fields:

- action executor/model/tool calls actually made and their versions;
- per-resource realized cost vector;
- Lean/verifier/tool result and normalized error class;
- proof/cache/retrieval/whiteboard state delta and resulting state hash;
- newly verified reusable progress, if any, kept separate from terminal success;
- terminal reason and terminal kernel-verified objective when terminal.

### Deterministic replay gate

Before using a trajectory for propensity-sensitive OPE, a separate replay must reconstruct from logged artifacts only:
1. the same legal mask;
2. the same deterministic baseline action and fallback;
3. the same randomized subset;
4. the same full behavior distribution;
5. the same `mu_chosen` and chosen action identity.

If any item differs, mark the decision non-replayable and exclude/abstain for estimators requiring exact behavior probabilities. Add the minimum structural feature needed to resolve state aliasing; do not add hidden reasoning traces simply to make replay pass.

## Updated synthesis

The outer-controller gap is now narrower and better specified:

- learned frozen-LLM outer harness control exists outside formal proof (C73-C76);
- Lean already has strong hand/free-form heterogeneous controllers with almost the exact desired action ontology (C78; OpenProver);
- tactic-level off-policy RL plus hierarchical planner inference exists (C79), but the learning is on the prover's tactic policy rather than the outer controller;
- public Harness-RL artifacts still lack a documented BC/Forced-CHECK reproduction path (C77), so baselines for a new Lean study should be fully implemented and published rather than inferred from prose;
- the clean experiment is therefore to hold the Lean executor/tool/memory substrate and real budget fixed, log an identifiable behavior policy over a bounded typed outer action space, and compare deterministic rule control, free-form planner control, BC, terminal-trajectory AW, and progressively stronger verifier-grounded sequential/value controllers.
