## C246 — the two-ghost-REFINE fixture survives proposal validation exactly as required
`StructuredActionProposal.validate()` delegates argument payload validation to `_argument_payload_errors()`. That validator checks each alignment spec's shape/relation/Lean-target consistency, but does **not** require REFINE payload step IDs to exist in the live branch, does not require step/alignment coverage, and does not compare payload IDs against `SearchAction.target_step_ids`.

Therefore a finalized REFINE proposal with one syntactically valid `ArgumentStepSpec(step_id="ghost_a", ...)` plus matching `AlignmentSpec(argument_step_id="ghost_a", relation="unaligned")` passes proposal validation. The reducer later sees no live step/alignment hit and returns the exact input workspace. Together with C229 (`_finalize_kind` erases target-step pins), this closes the last validation uncertainty in the one-call overwrite characterization fixture.

Recommended `workspace_transition_class` is mechanical:
- `mutated` — immediate returned workspace differs/version advanced;
- `no_effect` — exact input workspace returned;
- `checker_only` — read/check evidence changed search state only via checked-action reducer semantics, if later included in the typed controller;
- `terminal` — action directly produced terminal accepted/abort result;
- `error` — deterministic or runtime exception was captured before a successor was committed.

Do not treat `mutated` as reward. Reward/value features are derived separately from verified facts, obligation closure, terminal solve, or an explicitly versioned semantic-progress metric.

## C251 — transaction ordering needed for crash-safe causal interpretation
For one decision under journal protocol v0:

1. Freeze current finalized choice set, transition reports, budget snapshot, logging policy support and RNG ticket.
2. Select action and build DecisionEvent.
3. SQLite transaction: insert DecisionEvent; if model batch exists insert ConsumptionEvent in the **same transaction**; commit under WAL + `synchronous=FULL` and read back exact payload digest.
4. Only after successful readback: consume frontier node and invoke executor/reducer/tool/checker side effect.
5. Build OutcomeEvent from immediate before/after authoritative state and execution ledger window.
6. Commit OutcomeEvent, read it back, then advance to next decision.

Crash semantics:
- before step 3 commit: no durable decision; safe to recompute from unchanged substrate state;
- after step 3 and before effect: committed decision is censored; do not reselect under same run/decision identity;
- after effect but before outcome commit: decision remains censored and external/substrate effect may need recovery evidence; never invent a failed outcome;
- after outcome commit: replay is read-only/idempotent.

This is deliberately conservative: observational incompleteness is preserved rather than converted into a false reward label.

## C252 — semantic proposal fingerprint must exclude transport/cost metadata but include finalized action semantics
Canonical `proposal_semantic_sha256` v0 should hash a canonical JSON body containing exactly:
- finalized `SearchAction`: kind, finalized target branch, target-step IDs **as present in the frozen substrate after finalization**, allowed mutation values, rationale;
- typed payload `to_dict()`;
- score (including explicit null).

Exclude proposal metadata such as model, model tier, token usage, pricing, API cost, provider request IDs, routing diagnostics, proposal batch ID, journal IDs and timestamps. Those belong in the envelope/decision fields.

`proposal_envelope_sha256` may hash the full finalized `StructuredActionProposal.to_dict()` after canonical JSON normalization. This gives exact trace auditing without making provider usage part of semantic-action identity.

Because current substrate strips target-step IDs, the semantic hash records them as empty today. A future target-step-preserving substrate will naturally produce different semantic hashes and must carry a new `substrate_version`.
