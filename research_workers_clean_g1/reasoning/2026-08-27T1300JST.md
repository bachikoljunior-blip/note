## C475 — downstream successor compilation is a stronger semantic-admission test than kernel compilation alone, but it is not a direct reuse-utility metric

Primary source: Kim, Han, Hwang, `Benchmarking Testing in Automated Theorem Proving`, ACL 2026 Industry / arXiv:2604.23698. Public code/data: `ldilab/T2`.

T2 evaluates a generated Lean theorem by replacing the target declaration and then compiling its dependent successor theorems. The released benchmark covers 5 real-world Lean 4 repositories with 2,206 targets and about 41 successor theorems per target on average.

The semantic gap is large:
- Claude-Sonnet-4.5: full-set compile `80.3%`, Testing Accuracy (TA) `38.9%`; Hard compile `46.0%`, TA `4.5%`.
- GPT-5-nano: full-set compile `88.7%`, TA `36.6%`; Hard compile `75.6%`, TA `1.5%`.
- Goedel-Prover-v2-32B: full-set compile `74.6%`, TA `31.0%`; Hard compile `54.6%`, TA `3.2%`.

The public preprocessing code constructs a dependency graph from LeanDojo-traced declaration AST identifiers and uses repository successors as integration tests. This is broader than checking the target declaration in isolation.

Controller consequence: `ADMIT_REUSABLE_LEMMA` should include an optional **shadow downstream compatibility test** whenever a staged lemma is intended to replace/generalize an existing interface or alter a shared abstraction. A kernel-valid declaration can still be semantically misaligned with the contracts that downstream proofs expect.

Critical scope guard:
- T2 measures semantic compatibility of generated/replaced theorem statements, not future utility of adding a new coexisting lemma.
- Successor compilation therefore strengthens **admission safety/semantic compatibility**, but does not prove that the new lemma will ever be retrieved or used.
- The dependency extraction is an AST/reference graph, not a minimal causal proof-term dependency set; do not reinterpret TA as direct-reuse frequency.

## C476 — direct lemma-use instrumentation in Lean must combine proof-term dependencies with tactic-explicit rewrite/simplification references

Primary source: Zhu et al., `Premise Selection for a Lean Hammer`, ICLR 2026 / arXiv:2506.07477.

LeanPremise's training-label extraction distinguishes term-style and tactic-style proofs. For term-style proofs it uses the theorems that appear in the proof term. For tactic-style proofs it combines:
1. theorems appearing in the proof term constructed by the tactic sequence, capturing implicit premises;
2. theorems and definitions explicitly used by `rw` or `simp`.

The paper states that `rw`/`simp` can exploit definitional equalities that may not appear in the final proof term. Therefore a reuse metric based only on final proof-term names can undercount meaningful dependency use.

Controller consequence: future repository-scale memory experiments should record at least two direct-use channels for each admitted lemma:
- `proof_term_or_environment_dependency_use`;
- `tactic_explicit_rewrite_or_simplification_use`.

Keep advisory-context benefit separate from both. This directly sharpens the predecessor requirement to measure actual use rather than retrieval hits or library presence.

Primary sources:
- https://arxiv.org/abs/2506.07477
- https://openreview.net/forum?id=m04JJNeRK6

## C477 — staged-but-not-globally-admitted premises can be made queryable on demand without rebuilding the fixed library index

Primary implementation: `hanwenzhu/premise-selection`, the LeanPremise/LeanHammer premise selector.

The selector keeps a fixed server-side corpus for tagged Lean core/Batteries/Mathlib, while the client can send **new user-defined premises from the current file or imported files** with the current goal. These new premises are embedded dynamically and participate in top-k retrieval; server-side recent-new-premise embeddings are cached separately. The public implementation also imposes an upper bound on newly uploaded premises (example 8192) and truncates excess items with locality/recency priority.

Controller consequence: `STAGE_VERIFIED_LEMMA` does not need to imply permanent admission to the default global retrieval corpus. A practical alternative is a **query-time staged pool**:
- keep the stable/default index limited to admitted reusable lemmas;
- expose staged verified lemmas only to task-local/on-demand retrieval;
- track their retrieval cost and actual downstream use;
- promote only after cost-sensitive utility evidence.

This preserves optionality while reducing permanent index/context pollution.

Critical scope guard:
- LeanPremise demonstrates technical feasibility of dynamically incorporating local premises, not that a large staged pool is free or beneficial.
- The implementation has explicit size/latency limits; the staged pool itself still needs ranking, caps and cost accounting.
- Dynamic availability is not evidence of actual use.

Primary implementation/source:
- https://github.com/hanwenzhu/premise-selection

## C478 — Rtl2lean's 80.2% "reusable lemma ratio" remains availability evidence, not verified downstream-use frequency

## Updated synthesis — admission should optimize three different properties, not one "reuse" score

The new evidence separates three controller questions:

1. **Semantic compatibility / safety** — would admitting or replacing this abstraction preserve downstream contracts? Use T2-style successor/integration testing where applicable.
2. **Actual behavioural reuse** — did future proofs materially depend on the lemma? Instrument proof-term/environment dependencies plus tactic-explicit `rw`/`simp` use; do not infer from retrieval alone.
3. **Search guidance value** — did seeing prior verified material improve proof strategy even when no lemma entered the final dependency closure? Keep this advisory channel separate.

This suggests an updated staged-memory lifecycle:
- `STORE_GUIDANCE`: advisory only, never proof authority.
- `STAGE_VERIFIED_LEMMA`: Lean-kernel checked, provenance/version pinned, not in default cross-task corpus.
- optional `SHADOW_TEST_STAGED_LEMMA`: run successor/integration compatibility tests when the candidate changes/replaces shared semantics.
- `QUERY_STAGED_LEMMA`: task-local/dynamic retrieval from the staged pool with explicit cost and cap.
- `ADMIT_REUSABLE_LEMMA`: promote into default retrieval only after observed/predicted future utility net of retrieval/context/generalization cost.

A candidate can therefore be kernel-valid and semantically compatible yet still not deserve global admission if it has no demonstrated downstream value.
