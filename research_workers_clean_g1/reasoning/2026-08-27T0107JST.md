## C412 — SELinux CIL has unusually strong empirical compiler-correspondence evidence, but it is differential validation rather than compiler correctness

**Observed.** Ceragioli et al. give an executable formal semantics for SELinux CIL and report systematic validation against both the reference manual and the actual CIL compiler. They explicitly state that they tested complex configurations whose behavior depends on evaluation order, implemented an executable semantics, and validated it with hand-crafted and randomly generated configurations. This campaign exposed three compiler bugs; the developers fixed those bugs, while at least one global-environment/scoping inconsistency remained unaddressed in the 2024 paper.

Primary source:
- https://people.inf.ethz.ch/basin/pubs/acm2024.pdf

Public artifact:
- https://github.com/lceragioli/SELinuxCILSemantics

The artifact's random-test harness generates CIL configurations, invokes `secilc`, inspects the resulting policy using `sesearch --allow`, computes the executable semantics, and reports missing/unexpected allow edges. The generator inspected here covers a deliberately bounded fragment built from types, blocks, macros, allow rules, macro calls, and block inheritance.

**Inference.** This is meaningful `compiler_differential_conformance` evidence for a named fragment/projection. It is stronger than documentation or an ABI check, but it is not a theorem that `secilc` preserves all CIL semantics for all inputs.

**Scope guard.** The observed oracle projection is allow-edge behavior as exposed by `sesearch --allow`; the random generator is not the full CIL grammar. Passing this suite cannot certify omitted language constructs, all kernel-policy effects, or all compiler flags/targets.

## C417 — policy assurance should use a typed evidence lattice, not a single verified bit

**Synthesis from Cedar, OPA, and CIL.** Independent systems now expose at least four materially different evidence kinds:
1. `theorem_semantic_preservation` — e.g. Cedar CST->AST soundness/completeness on a precise branch/ref and supported fragment.
2. `shared_oracle_cross_backend_conformance` / `compiler_differential_conformance` — e.g. OPA topdown+Wasm common cases; CIL executable semantics vs `secilc`.
3. `serialization_or_schema_correspondence` — e.g. OPA IR JSON schema/drift tests.
4. `abi_or_interface_compatibility` / manual specification evidence.

These evidence kinds are complementary and must not implicitly satisfy one another. Every claim also needs `integration_state = feature_branch | merged_main | released | deployed`, exact source/target revisions, semantic configuration, supported fragment, test/proof artifact identity, known exclusions, and unresolved mismatches.

Candidate rule: evidence may strengthen a claim only within the intersection of its proven/tested fragment, exact artifact/runtime identity, and integration state. A lower evidence class never upgrades itself to theorem-level evidence through repeated passing tests.
