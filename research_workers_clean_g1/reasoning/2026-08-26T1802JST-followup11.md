## C321 — a selected structural action with zero checker cost can still be preceded by substantial Lean checking inside generation
At the action-runtime layer the four initial Stage-A structural actions have static selected-execution check cost zero. But `ChatStructuredActionGenerator` can enter the generic chat tool loop before emitting those proposals. `_should_allow_tools()` enables tools on the first generation attempt and also on retries after `UNKNOWN_IDENTIFIER` / `INVALID_REFERENCE` feedback.

If `check_lean_snippet` is registered, the model can therefore spend Lean-checker compute *before* a zero-check structural proposal is selected. The statement `selected structural action has zero checker cost` must not be widened to `the corresponding decision round has zero Lean-checker cost`.

## C322 — scratch Lean checks bypass the structured controller's coarse check reservation
`LeanProofToolProvider._check_snippet()` runs either a supplied `ProofSystemAdapter.check(...)` with its own `BudgetSlice(timeout_seconds=self.timeout_seconds)` or direct `lake env lean` / `lean` via `subprocess.run`. Its default timeout is 60 seconds.

This path does not call `StructuredController.budget.reserve_check()`. The chat tool loop tracks tool rounds independently (`max_tool_rounds`, default 5) and can execute multiple tool calls in one round.

Therefore `BudgetSnapshot.checks_used / remaining_checks` does not necessarily represent all Lean checker invocations consumed by proposal generation when tools are enabled.

## C323 — current generation admission priors do not bound actual scratch-check count
`ModelRouterConfig` gives the cheap proposal route a prior `model_requests=1`, and the strong route a prior `model_requests=1, checks=1`. These priors are used for proposal-generation budget admission before `_generate(...)`.

But actual chat generation can issue multiple model requests across tool rounds and can execute multiple scratch Lean checks before the final proposal response. Thus the route prior is a policy prior, not a hard upper bound on physical generation model/checker cost.

A run admitted under the static prior can consume materially more checker/model work than the admission vector suggests.

## C324 — generation tool telemetry is post-hoc and not a durable effect receipt
`run_tool_loop()` records a tool event only after `execute_tool(call)` returns or raises. The tool call ID comes from the model response, so it exists before local tool dispatch, but current code stores no durable pre-dispatch Attempt event. `seen_tool_calls` duplicate suppression is also process-local.

A crash after a scratch checker starts but before the post-hoc tool event is retained can therefore lose both the physical cost/result and the fact that this model-issued tool call may already have executed. Re-running the chat request or tool loop can duplicate the scratch check.

The model-supplied tool-call ID is useful causal input, but current code does not turn it into a crash-stable idempotency/reconciliation contract.

## C325 — add a distinct generation-tool-check cost/effect class
Do not merge scratch Lean checks into selected-action checker cost. Extend the physical effect schema/cost projection with an explicit scope such as:

```text
GENERATION_TOOL_CHECK
```

For every dispatched scratch check persist:
- parent `ProposalGenerationAttemptV0` / model request round;
- model tool-call ID + stable local `effect_operation_id`;
- code semantic hash and checker/substrate version;
- durable EffectAttempt before dispatch;
- physical checker Attempt/Receipt facts;
- measured wall/CPU where available;
- completion/censoring state.

Then compute generation cost as a derived sum over model-provider requests + generation tool checks + other configured retrieval/summarization effects, while keeping selected execution and assembly separate.

## C327 — complete cost vector needs at least four Lean/model execution compartments
For compute-normalized comparison keep separate:

1. upstream proposal-generation model/provider cost;
2. proposal-generation tool/retrieval/summarizer cost, including scratch Lean checks;
3. selected-action execution cost, including candidate/capability checks when later supported;
4. final assembly/verification cost.

A fifth derived total is allowed only when each contributing physical dimension has explicit completeness status. Do not infer complete dollars/tokens/checker time from an aggregate that contains ambiguous retry/effect components.

## C328 — in-memory duplicate tool suppression is not crash replay safety
Within one surviving `run_tool_loop`, duplicate calls are suppressed by an in-memory key `(tool name, canonicalized arguments)`. That is useful for one live conversation but disappears on process restart. A recovered generation pipeline cannot rely on it to prove that an identical scratch check did not already execute before the crash.

For recovery, use durable `effect_operation_id` / input semantic hash / physical receipt state. If no queryable/idempotent checker contract exists, an Attempt without Receipt remains in-doubt and must not be silently rerun.
