## C262 — the one-batch/two-no-op overwrite path is statically reachable through the real action-runtime loop
The remaining uncertainty was whether two same-batch no-op proposals can both survive the real cache/frontier lifecycle without a second generation call. The pinned source answers this affirmatively:

1. `ProposalCache.add()` accepts multiple distinct proposals from one `proposal_batch_id`, up to its per-branch/global limits. Node identity hashes the finalized proposal body, so two distinct ghost-refine payloads receive distinct node IDs.
2. Structural action priors have zero checker cost, and `ActionFrontier.ranked()` deterministically orders otherwise-equal nodes by action kind and node ID.
3. The selected node is removed from `ProposalCache` before execution; the other node remains cached.
4. A ghost `REFINE_ARGUMENT` with syntactically valid alignment but no live replacement hit returns the *same* workspace from `apply_argument()`, so `workspace.version` does not change.
5. On the next loop, `refresh_action_cache()` calls `node_invalid_reason()`. The remaining node still has the same cached workspace version, active branch and obligation version. Because current `_finalize_kind()` has already dropped generated `target_step_ids`, `target_step_missing` cannot invalidate it. The second node therefore remains executable.
6. `_fill_action_cache()` is called only when the refreshed frontier has no work. Because the second node remains, there is no second provider-generation call between consumer 1 and consumer 2.
7. `execute_action_node()` calls `attribute_proposal_batch()` before each reducer execution. The helper rewrites `metadata.action_id` on every physical provider event matching the shared batch. Thus the second consumer rewrites the first consumer's attribution.

This is a static path proof from the production runtime seam, not just a direct helper-level thought experiment.

## C264 — ghost refine validity is not accidental malformed-input behavior
`StructuredActionProposal.validate()` accepts `REFINE_ARGUMENT` when the payload type is correct and each alignment is shape-valid; `_argument_payload_errors()` does not cross-check payload step IDs against the live branch. `AlignmentSpec(relation="unaligned")` is valid exactly when it carries no Lean target. Live-hit detection happens later inside the reducer, where `hits_steps == hits_alignments == False` returns the input workspace unchanged.

Therefore the characterization should use *valid but semantically non-applicable* refine proposals, not malformed proposals. This matters because the learned-policy support boundary later needs to distinguish `frontier-valid` from `WOULD_NOOP` rather than treating no-op cases as validation failures.

## C265 — current frontier validity plus current target-step-loss explains why no-op alternatives survive
`node_invalid_reason()` already contains the desired live-step safety guard: any proposal `target_step_ids` missing from the branch causes `target_step_missing`. However, `_finalize_kind()` reconstructs `SearchAction` without preserving incoming `target_step_ids`, so normally generated proposals lose that evidence before caching. This joins two previously separate observations into one causal chain:

```text
generator target_step_ids
  -> _finalize_kind drops them
  -> cache node stores empty target_step_ids
  -> node_invalid_reason cannot reject target_step_missing
  -> valid ghost payload reaches reducer
  -> reducer returns deterministic no-op
  -> workspace version stays fixed
  -> same-batch sibling remains valid
  -> provider attribution can be overwritten by sibling consumer
```

The target-step fix remains a separate substrate version because silently correcting it inside logging instrumentation would remove the very current-code behavior needed by the epsilon=0 characterization.
