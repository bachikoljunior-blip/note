## C29 — LeanSearch v2's released prover code reveals a missing control action: global reasoning retrieval is one-shot and is *not* re-run after proof failure

Primary publication/code:
- `LeanSearch v2: Global Premise Retrieval for Lean 4 Theorem Proving`, arXiv:2605.13137v2.
- Public code at commit `94f4888cbaf9f4322535755f86cbac690ec18080`, `src/leansearchv2/prove/run.py`.

Implementation evidence:
- `retriever_mode="reasoning"` calls `run_reasoning(...)` **once before the initial proof attempt** using the theorem statement.
- During subsequent compiler-feedback reflection rounds, reasoning-mode retrieval explicitly reuses `initial_search_str`; the code comment says `reflect_search = initial_search  # keep the pre-retrieval`.
- In contrast, `retriever_mode="standard"` generates new retrieval queries from the **current failing proof + compiler error** on each reflection round.
- Therefore the released end-to-end prover demonstrates two useful but separated policies: (a) global proof-route reasoning before search, and (b) local/mid-proof retrieval after failure. It does **not** currently implement a learned action that re-runs global sketch/retrieve/reflect after a local failure or decomposition change.

Why this matters:
- The previous frontier asked whether context should be an explicit action. The code makes the gap concrete: global context selection is currently a frozen pre-search payload, so a hierarchical controller could gain a genuinely new action by escalating from local standard retrieval to a fresh global reasoning retrieval when local failures imply the current proof route is structurally unsupported.
- It also creates a clean compute ablation: `reasoning-once` vs `reasoning-rerun-on-trigger`, with trigger candidates such as repeated error class, premise/type mismatch, decomposition change, low predicted repairability, or repeated local retrieval failure.

Scope/limitation:
- This is an implementation fact, not evidence that dynamic global re-retrieval improves solve rate. The new action remains untested.

Sources:
- https://arxiv.org/html/2605.13137v2
- https://github.com/frenzymath/LeanSearch-v2/blob/94f4888cbaf9f4322535755f86cbac690ec18080/src/leansearchv2/prove/run.py

## C30 — Direct Lean proof-state uncertainty exists via conformal prediction, but it does not yet supply the calibration evidence needed for a modern router

Primary/publication evidence:
- Noor Rahim, Ali Abdul Rahim, `Probabilistic Proof State Compression: Optimizing LLM-Guided Formal Verification`, NeurIPS 2024 MATH-AI workshop, OpenReview id `x2yiUEH0f9`.

Mechanism:
- DeepSeek-Prover-V1.5-RL samples candidate Lean proof steps.
- The method estimates `P(success | state)` and constructs conformal prediction regions/intervals using state-similarity strata and binary success/failure nonconformity scores.
- The compression policy groups similar proof states and uses conformal uncertainty to retain/prune search regions.

Reported evidence:
- The paper reports **similar success rates with 75% fewer passes** and **23% lower average wall-clock time** on Lean miniF2F; it also states evaluation on ProofNet.
- It is therefore a genuine proof-search uncertainty/control result, not merely natural-language self-confidence.

Critical limitations:
- The paper is explicitly preliminary/workshop-scale.
- The surfaced primary text calls the probabilities `calibrated`, but does not report conventional calibration diagnostics such as **Brier score, ECE, reliability diagrams, calibration slope/intercept, or selective-risk curves** for proof-state success probabilities.
- The conformal interval construction depends on state strata intended to address dependence/exchangeability, but the evidence surfaced here is not enough to establish that the empirical strata satisfy the assumptions robustly across theorem distributions or evolving search trajectories.
- Thus this partially closes the frontier item “does calibrated Lean proof-state control exist?” but does **not** close “is there well-validated probability calibration good enough for a multi-action router?”

Design implication:
- A future router should compare ranking-only predictors, raw success probabilities, post-hoc calibrated probabilities, and conformal/selective rules under distribution shift, reporting both decision utility and calibration metrics.

Sources:
- https://openreview.net/forum?id=x2yiUEH0f9
- https://mlanthology.org/neuripsw/2024/rahim2024neuripsw-probabilistic/

## C31 — Repository graph/locality signals are not uniformly useful: CSLibPremiseBench gives strong negative evidence against “more structural locality is always better”

Primary source: `CSLibPremiseBench: Structure-Guided Premise Retrieval and Label Robustness for Lean 4 Computer-Science Theorems`, arXiv:2605.14549 (May 2026).

Pinned setup:
- CSLib v4.29.0 at commit `0d37cc7fcc985cfc53b155e7eef2453f846c6da2`, Lean 4.29.0.
- 801 strict-policy proxy-labelable tasks, 1875 candidate declarations.
- Labels are source-visible proof-reference proxies, explicitly **not** complete elaborated dependency traces.

Strict candidate-pool results:
- BM25+symbol: Recall@10 **0.5282**, MRR **0.5199**.
- CSG-Rerank (lexical + symbol + namespace/module + import graph + source order + module PPR): Recall@10 **0.5215**, MRR **0.5236**.
- CSG vs BM25+symbol paired-bootstrap: MRR +0.0037 with 95% CI `[-0.0103,+0.0173]`; Recall@10 -0.0067 with CI `[-0.0186,+0.0050]` — no established win.
- At context packet @10, CSG strongly increases same-module share (**0.8140** vs **0.7146**) but has lower proxy-gold coverage (**0.5215** vs **0.5282**) and lower gold/1k-token utility (**6.3979** vs **6.5119**); coverage/token-utility confidence intervals cross zero.

Where structure becomes useful:
- On a fixed 781-task subset, widening candidate scope from strict (~153 candidates) to all-earlier-CSLib (~1002 candidates) makes graph-aware hybrid information more useful relative to BM25: hybrid−BM25 MRR difference grows to **+0.0487 [0.0343,0.0639]**.

Interpretation:
- Typed/repository graph expansion should be **conditional on search-space width and uncertainty**, not blindly used to make context more local.
- “Locality” is not synonymous with “useful context”; graph priors can concentrate a packet without increasing top-k useful-premise coverage or token utility.
- This narrows the graph-first frontier into a gating problem: cheap lexical/symbol retrieval may suffice in small/strongly constrained candidate pools; structural expansion becomes more attractive as the candidate set broadens or lexical evidence weakens.

## C32 — Effect-grounded proof trajectories provide a quantitative state-transition prior, but end-to-end proof-search gains remain unproven

Primary institutional/ACL evidence:
- Elisaveta Samoylov, `Representing Lean Proofs: Tactics, Trajectories, Search`, Dartmouth CS thesis, awarded 2026-06-03.
- Related ACL 2026 SRW paper: `Representing Lean Proofs as Trajectories in Latent Space`.
- Builds on the 2025 ACL MathNLP `Modeling Tactics as Operators: Effect-Grounded Representations for Lean Theorem Proving`.

Mechanism/evidence:
- Delta Tokens encode the symbolic edit induced between successive Lean proof states rather than only tactic surface syntax.
- A Transformer embeds proof steps as state-change trajectories; solved-proof trajectories are aggregated into local direction fields and used as a candidate next-step reranking prior.
- On **76,855 held-out tactic transitions**, the trajectory field has mean cosine alignment **0.583** vs **0.165** for a surface baseline and recovers the correct next tactic family in **83.2%** of cases.
- The ACL paper studies 13.5k LeanWorkbook proofs and reports better held-out next-tactic retrieval than a matched surface-syntax control, with longer proofs becoming increasingly indirect in a bounded latent span.

Interpretation:
- This supplies a concrete, learnable `transition-effect / trajectory-direction` feature for the hierarchical router frontier. It is more semantically aligned than tactic-string similarity and could complement 3D-Prover-style transition prediction, compiler-error diversity, repairability, and future-cost estimates.

Critical limitation:
- The quantitative result is held-out tactic-transition retrieval/alignment, not end-to-end theorem solve rate or compute reduction. It is a promising routing representation, not proof that trajectory-field reranking improves pass@budget.

Sources:
- https://digitalcommons.dartmouth.edu/cs_senior_theses/65/
- https://aclanthology.org/2025.mathnlp-main.12/

## Updated synthesis

The hierarchy is becoming more concrete and more conditional:

1. **Use cheap retrieval when the candidate pool is already narrow and lexical/symbol evidence is strong**; graph/locality signals are not automatically useful (C31).
2. **Escalate structural/graph expansion as candidate ambiguity grows**, rather than making graph locality a fixed prior (C31).
3. **Treat global proof-route retrieval as a separate expensive action**, not a static front-end. LeanSearch v2's released code shows the global reasoning payload is currently frozen across local proof failures, which exposes a clean opportunity for triggered re-retrieval (C29).
4. **Represent local progress by proof-state transition effects**, not just tactic syntax; Delta/trajectory fields are a plausible low-dimensional feature substrate for branch selection (C32).
5. **Attach uncertainty to routing decisions**, but distinguish conformal coverage from probability calibration. The existing Lean conformal result is promising efficiency evidence yet does not satisfy the frontier's demand for ECE/Brier/reliability/selective-risk validation (C30).
6. **Choose among preserve/local repair/context re-retrieval/restart using calibrated decision utility**, not only ranking metrics.

A particularly clean experiment now emerges:
- fixed Lean prover + fixed total token/verifier/wall-clock budget;
- local state features = compiler-error class/diversity + Delta/trajectory effect + proof similarity + attempt count + predicted repairability/future cost;
- retrieval actions = none/reuse current packet, cheap lexical+symbol, graph expansion, full global reasoning retrieval;
- proof actions = fresh branch, preserve/continue, local edit, whole-proof repair, decomposition restart;
- compare uncalibrated scores, temperature/isotonic calibration, and conformal/selective policies;
- report Brier/ECE/reliability/selective-risk **and** end-to-end pass@budget/cost.
