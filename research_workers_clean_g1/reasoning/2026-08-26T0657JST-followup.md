## C80 — OpenProver's planner decision language is already machine-parseable, but the physical decision unit is an ordered action bundle rather than one categorical action

Public source:
- https://github.com/Kripner/openprover/blob/e200251b34349ab6c34548d30319abde86cb6bc6/openprover/prompts.py
- https://github.com/Kripner/openprover/blob/e200251b34349ab6c34548d30319abde86cb6bc6/openprover/prover.py

`prompts.py` declares a fixed planner vocabulary:
`submit_proof`, `submit_lean_proof`, `read_items`, `write_items`, `spawn`, `literature_search`, `read_theorem`, `write_whiteboard`.

Planner output is not parsed heuristically from prose. `parse_planner_toml` extracts tagged `<OPENPROVER_ACTION>...</OPENPROVER_ACTION>` TOML blocks, validates the action string against the fixed vocabulary, normalizes task/item lists, and permits multiple action blocks in one planner step with at most one `spawn` block.

The planner prompt explicitly encourages combining low-impact actions, e.g. `write_whiteboard + spawn`. `Prover._execute_plans` then executes the parsed plans **sequentially**. For multi-action steps, `plans.json` stores the full bundle, but `planner.toml` stores only the primary (last) plan and step-level metadata carries a single `action` field.

Implication for a learned/OPE controller: treating a physical OpenProver planner step as one categorical action loses information. There are two defensible representations:

1. **Macro-action bundle:** action = ordered tuple/list of all blocks. Faithful to current execution, but the combinatorial support space is very large and free-form planner propensities remain unavailable.
2. **Typed micro-decisions:** refactor the controller boundary so one policy decision selects one admissible meta-action at a time, with deterministic phase/order rules for optional scratch/read/write side actions. This creates a tractable propensity-bearing action space and is the preferred experimental design.

Do not infer behavior support from `meta.toml.action` alone. Multi-action steps require `plans.json` or an explicit new decision-event ledger.

## C81 — OpenProver does not currently expose a single centralized hard legal-action mask, and the planner's continuous budget state is not actually inserted into the planner prompt at this commit

The planner system prompt varies what it **documents** by mode and isolation: for example, `literature_search` is omitted under isolation, submission actions depend on proof/formalization mode, and Lean-specific descriptions depend on whether Lean is present. However:

- `parse_planner_toml` validates against the global `ACTIONS` list, not a mode-specific action mask;
- unavailable actions are sometimes rejected later by handlers (e.g. `_handle_literature_search` checks `self.isolation` and returns an unavailable message);
- therefore prompt-level availability, parser acceptance, and runtime executability are distinct layers rather than one explicit legal-action artifact.

This matters for exact propensity logging: the proposed learned behavior wrapper must compute and log a single authoritative `legal_action_mask(s)` *before* sampling, rather than trying to reconstruct legality later from prompt text and handler outcomes.

A second concrete source-level gap is budget exposure. `Prover._do_step` computes `budget_status=self.budget.summary_str()` and passes it to `format_planner_prompt`, but the inspected implementation of `format_planner_prompt` never inserts `budget_status` into the returned prompt. Instead, the planner receives only coarse budget pressure through `build_intervention`: >80% spent prompts wrapping up; >95% prompts urgent submission. Thus the free-form planner at this commit does **not** observe the full continuous remaining-budget vector even though the formatter signature suggests it might.

For a cost-aware learned controller, remaining budget must therefore become an explicit structural state feature rather than relying on the current planner prompt.

## C82 — OpenProver's durable traces are rich enough for a structural controller dataset, but current recent-history state includes raw planner output and current metadata is not replay-complete for OPE

`Prover.step_history` persists the latest planner `result` string plus action outputs and feeds up to the last three entries back into `format_planner_prompt`. The planner system prompt asks the model to think before emitting TOML, so the raw planner result can contain free-form reasoning text in addition to the decision block. A learned typed controller should **not** depend on this raw planner prose/hidden-deliberation channel. Its state should be rebuilt from structural artifacts only: whiteboard/repo digests, theorem/proof status, parsed previous action bundle, verified outputs/errors, cache/subgoal/decomposition state, and explicit budget/cost fields.

Current `meta.toml` already records useful observability:
- planner cost, duration, input/output/cache token counts, model, stop reason;
- per-worker cost, duration, input/output/cache token counts and errors;
- action outputs and worker tool-call logs elsewhere include tool/status/duration.

But it does not record the authoritative pre-action legal/randomization masks, baseline action, behavior probability vector or `mu_chosen`; nor does it expose an OPE-ready controller-state hash. Those fields still need the D2 event layer from the preceding checkpoint.

## D3 — Recommended controller boundary for OpenProver-compatible experiments

Use a **single typed meta-action per policy decision** even if the underlying executor can batch low-impact operations. Let the executor deterministically expand a chosen meta-action into a bounded internal operation sequence. Example controller actions:

- `READ_CONTEXT` — deterministic bounded theorem/repo reads;
- `RETRIEVE` — bounded Lean/library/literature retrieval tier chosen by a sub-parameter or separate small action;
- `UPDATE_SCRATCH` — bounded whiteboard update through the frozen executor;
- `SPAWN_BRANCH` — one bounded worker task/branch;
- `LOCAL_REPAIR` — verifier-guided repair of current proof state;
- `DECOMPOSE_OR_REPLAN` — structural revision/new subgoals;
- `STORE_VERIFIED` — persist only kernel-verified reusable item in episode-isolated/versioned memory;
- `BACKTRACK_OR_PRUNE` — restore/prune current branch;
- `ESCALATE_COMPUTE` — model/worker/search tier increase under hard caps;
- `SUBMIT` — terminal.

This list is a proposed normalized action layer, not a claim that OpenProver currently exposes all names directly. The mapping contract must specify exactly which frozen executor procedure implements each action.

### Stage-A support refinement

Because current OpenProver can emit bundles and lacks one central hard mask, Stage-A randomized collection should begin **outside** the free-form planner, at this typed wrapper boundary. Randomize only actions whose executor is bounded/reversible and whose legal predicate is deterministic from structural state. Keep `SPAWN_BRANCH`, `STORE_VERIFIED`, `ESCALATE_COMPUTE`, and `SUBMIT` baseline-only initially unless a separately isolated/capped experiment explicitly admits them.

### Replay requirement refinement

For every logged decision, the replay test must reconstruct not only `legal_action_mask` and propensity, but also the **executor expansion** of the chosen typed meta-action. If the same action label can expand into different hidden operation sequences under unlogged planner prose, it is not replay-complete and must be excluded until the executor contract is made structural.
