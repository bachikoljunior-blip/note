## C229 — Real StructuredController currently strips generator-supplied `target_step_ids` before validation/cache insertion
`StructuredControllerRuntimeMixin._finalize_kind()` reconstructs every proposal action as a new `SearchAction(kind, target_branch_id=current branch, allowed_mutations, rationale)` but does **not** copy `proposal.action.target_step_ids`. Because `SearchAction.target_step_ids` defaults to `()`, all generated target-step pins are erased before `_fill_action_cache()` calls `proposal.validate()` and before `node_invalid_reason()` can check them.

This matters because the action schema explicitly says `target_step_ids` pins the argument steps an action concerns, and the frontier has a `target_step_missing` invalidation rule. In the current real controller path that rule is effectively unreachable for ordinary generated actions unless some later path reintroduces target IDs (none was observed in the inspected runtime path).

Consequences:
1. The prior C216/C221 recipe does **not** need to arrange a live `s1` merely to satisfy frontier target-step validation; the controller erases that constraint.
2. A generator's malformed/stale target-step pins are also erased before the post-finalization `proposal.validate()` call, so current runtime action validity is weaker than the standalone `SearchAction` contract suggests.
3. Preserving `target_step_ids` in `_finalize_kind` would be a meaningful substrate bugfix, not logging-only instrumentation. It must not be silently bundled into epsilon=0 equivalence testing.
4. The reducer-owned effect preview becomes even more important for randomized support because the current real frontier cannot rely on target-step pins to reject stale/no-hit structural proposals.

## C230 — The minimal same-batch overwrite integration fixture collapses to one provider generation call
A smaller fixture than C221 is sufficient and better isolates the attribution defect:

- Use a deterministic structured generator with `_is_structured_generator=True` and `_uses_model=True`.
- On its **first and only** `generate()` call, emit exactly two distinct `REFINE_ARGUMENT` proposals against the root branch. Their payloads contain syntactically valid but nonexistent replacement IDs, e.g. `ghost_a` and `ghost_b`, each with a matching `AlignmentSpec(..., relation="unaligned")`. Generator-supplied `target_step_ids` can be empty (or even supplied and then observed to be stripped); the finalized actions have empty target-step tuples.
- Put provider-like metadata on the first proposal (and preferably identically on both for readability): e.g. `model="test-model"`, observed `token_usage`, and an observed `api_cost_usd`. `record_proposal_request()` uses the first finalized proposal's metadata, emits one physical provider request/usage/charge set, and assigns one `proposal_batch_id` equal to that request ID.
- Use `frontier_policy="action_cost_aware_v1"` with `BudgetConfig(max_checks=1, max_model_calls=1)`. No structural refine uses a checker. After the second no-op is consumed, the cache is empty and the exhausted model-call budget prevents another fill; the run ends deterministically with `budget:model_calls` rather than requiring a third empty generation.

Both refine nodes are valid against the same initial workspace, both reducers are deterministic no-ops, and the first no-op leaves the workspace version unchanged. Therefore the second same-batch node remains cached/valid and is selected next. This exercises the overwrite with one batch and no preparatory structural mutation.

## C231 — Exact pre-migration assertion surface is public result metadata
The existing runtime already exposes everything the regression needs:
- selected order: `result.metadata["proposal_cache_events"]` events where `event == "action_selected"`;
- batch identity: the `cache_fill` event with `proposal_count == 2` and its `proposal_batch_id`;
- final physical cost records: `result.metadata["cost_ledger"]["events"]` because `CostLedger.to_dict()` serializes the immutable event fields and current metadata, plus reconciliation.

Current-code oracle:
1. exactly two selected `refine_argument` node IDs `N1 != N2`;
2. exactly one model proposal batch B generated;
3. provider_request/provider_usage/charge events for B exist;
4. after both consumers, every matching B event's `metadata.action_id == N2` (the second selection), demonstrating N1 attribution was overwritten;
5. no checker event is caused by either refine and no workspace-version increase occurs across the two action executions.

The current test suite already has a single-consumer assertion in `test_action_runtime_routes_real_generation_to_strong_tier`: it selects the provider-request event and asserts `request["metadata"]["action_id"] == result.attempts[0].edit.metadata["action_node_id"]`. The new regression should sit near that test and explicitly document that the old one-consumer representation is not a valid authoritative schema for multi-consumer batches.

## C232 — `max_model_calls=1` is a clean deterministic stop for this test
The action runtime checks whether a model-like generator can be called before cache fill. Once the one model call has been reserved and its two cached refines have both been consumed, the next fill sees `can_call_model()==False`, adds no work, and the loop converts the default budget stop to the concrete exhausted reason. With `max_checks=1` unused, the exhaustion reason is `model_calls`, avoiding an accidental `checks` reason that would occur if `max_checks=0`.

This gives a test with:
- 1 provider generation batch,
- 2 selected structural actions,
- 0 candidate/assembly checker calls,
- 0 successful workspace-version transitions,
- and a deterministic terminal budget reason.

## C233 — Target-step preservation should be a separate regression/ablation from causal journaling
A focused public-source-compatible regression can independently characterize the current loss:
1. generator emits `REFINE_ARGUMENT` with `target_step_ids=("ghost",)`;
2. inspect the `choice_set`/cached node's finalized action serialization or node ID material if surfaced;
3. current controller has `target_step_ids=()` after finalization, so the frontier does not produce `target_step_missing`;
4. a future bugfix that preserves the tuple should make the same proposal stale/invalid when `ghost` is absent.

For the learned-controller experiment, keep the frozen current substrate unchanged at epsilon=0 and label target-step preservation as a separate substrate version. Otherwise any apparent policy gain could partly come from fixing stale-action filtering rather than learning.
