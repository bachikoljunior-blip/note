## New findings

### C60 — OpenProver already emits nearly all primitives needed for an offline meta-controller dataset; normalize them rather than inventing a second logging stack

Public implementation inspected at OpenProver commit `e200251b34349ab6c34548d30319abde86cb6bc6`.

Primary code:
- https://github.com/Kripner/openprover/blob/e200251b34349ab6c34548d30319abde86cb6bc6/openprover/prompts.py
- https://github.com/Kripner/openprover/blob/e200251b34349ab6c34548d30319abde86cb6bc6/openprover/prover.py
- https://github.com/Kripner/openprover/blob/e200251b34349ab6c34548d30319abde86cb6bc6/openprover/inspect.py

The planner action vocabulary is explicitly typed in `prompts.py`: `submit_proof`, `submit_lean_proof`, `read_items`, `write_items`, `spawn`, `literature_search`, `read_theorem`, `write_whiteboard`. The planner returns structured TOML blocks. `prover.py` parses the action batch, stores a primary `planner.toml` plus `plans.json` for multi-action steps, dispatches actions sequentially, and retains action outputs. Worker spawning stores task text, worker call archives, worker outputs, optional independent verifier outputs and tool-call TOML. Lean writes/submissions store source, verification result and command information. `inspect.py` parses the archived LLM-call frontmatter including model, elapsed time, input/output/cache tokens and cost. `meta.toml` adds timestamp, step status/action, planner cost/duration/tokens/cache/model/stop reason and worker cost/duration/tokens/cache/error.

This means a deterministic controller-learning dataset can be produced by a thin normalizer over existing run directories. Proposed canonical event sequence:

1. `run_start`: run id; theorem id/hash and Lean-statement hash; OpenProver commit; Lean/toolchain/mathlib identity; mode; planner/worker/verifier model identities; budget type/limit; `max_workers`; isolation/verifier/Lean-tool/history-budget settings.
2. `state_before`: step index; budget spent/remain; compact Whiteboard snapshot/hash; repo index digest plus item version/digest map; rolling-history digest; theorem/proof-present flags; `steps_since_productive`; intervention state. Store artifact references rather than duplicating hidden reasoning traces.
3. `planner_call`: call/retry/phase2 id; model; prompt/system artifact hashes; input/output/cache tokens; cost; elapsed; stop reason/error. **Also add behavior-policy meta-action probabilities if the logger can expose them; current archives do not provide them.**
4. `action_proposed`: deterministic `action_id = H(run_id, step, ordinal)`; typed action; canonicalized arguments; source planner-call id; parse/validation outcome; batch ordinal.
5. `action_result`: action id; success/failure class; result artifact refs; durable state deltas; elapsed and action-specific substrate cost. For `spawn`, include each worker task/call/result/verifier/tool-call as children; for `write_items`/`submit_lean_proof`, include Lean verification; for retrieval/read/write, include content-version/digest deltas.
6. `tool_result`: worker/action/step parent; tool name (`lean_verify`, `lean_store`, `lean_search`, etc.); canonical args hash; result class/artifact; duration.
7. `state_after`: new Whiteboard/repo/proof hashes; verified reusable-progress delta; budget delta; terminal flag.
8. `run_end`: kernel-verified solve/unsolved; proof artifact hash; total planner/worker/verifier tokens, monetary cost, wall-clock, Lean/tool time; explicit termination reason.

The learning target should remain vector-valued initially: terminal verified solve, new verified reusable progress, invalid/parse/repetition penalties, token/cost/wall-clock/Lean-time vectors, and terminal proof quality if independently defined. Premature scalarization would hide the exact tradeoff the controller is supposed to learn.

Scope: this is an implementation/data-contract finding. It does not show that an offline learned controller beats OpenProver's free-form planner.

### C61 — Current OpenProver logs are not sufficient for trustworthy IPS/DR counterfactual meta-action evaluation because the behavior action propensity is missing; data collection should deliberately log randomized meta-action support

OpenProver archives expose the selected structured action and detailed costs/results, but I found no behavior-policy probability over the typed planner actions in the inspected public code. A free-form LLM response parsed into TOML is not itself a logged propensity over the meta-action set.

This matters because importance-sampling and doubly-robust OPE depend on behavior-policy probabilities and support/overlap. Sequential doubly robust OPE extends the bandit estimator to RL, but its guarantees do not rescue actions that the behavior policy never takes in the relevant states. `DRUnknown`-style methods can estimate an unknown logging policy when it is not recorded, but this replaces a known-propensity assumption with a model-estimation assumption; it still does not manufacture support where none exists. Recent logging-policy design work makes the same point from the data-collection side: under weak-overlap requirements, deliberate randomization can be minimax-optimal when target/reward are unknown.

Primary/relevant sources:
- Jiang & Li, *Doubly Robust Off-policy Value Evaluation for Reinforcement Learning*, ICML 2016: https://proceedings.mlr.press/v48/jiang16.html
- Laroche et al., *Safe Policy Improvement with Baseline Bootstrapping*, ICML 2019: https://proceedings.mlr.press/v97/laroche19a.html
- Simão et al., *Safe Policy Improvement with an Estimated Baseline Policy*: https://arxiv.org/abs/1909.05236
- Sun et al., *When is Off-Policy Evaluation (Reward Modeling) Useful in Contextual Bandits? A Data-Centric Perspective* / DataCOPE: https://arxiv.org/abs/2311.14110
- *A Unifying View of Coverage in Linear Off-Policy Evaluation* (2026): https://arxiv.org/abs/2601.19030
- *Logging Policy Design for Off-Policy Evaluation* (2026): https://arxiv.org/abs/2605.15108

Design consequence for a future Lean controller benchmark: collect a new trajectory wave with **safe, low-amplitude randomized exploration at the meta-action level** and record the probability of every eligible action (or at least the full randomized decision rule and eligibility mask). Randomization should be limited to states/actions where exploration cannot corrupt theorem integrity, and deterministic Lean verification remains the outcome oracle. Candidate examples: when two safe retrieval modes are both admissible; one-vs-two worker spawn; repair-vs-fresh branch within bounded budgets; cheap-vs-strong model escalation in a capped slice. This turns controller evaluation from retrospective guesswork into estimable OPE.

For existing deterministic/near-deterministic traces, use them primarily for behavior cloning, representation learning, outcome/value modeling and hypothesis generation. Fitted-Q/value estimators can still be explored, but their extrapolation error must be diagnosed rather than presented as counterfactual ground truth. DataCOPE-like coverage diagnostics and explicit support statistics should gate whether any offline policy comparison is considered credible.

### C62 — Conservative policy improvement supplies a practical deployment rule for learned proof controllers: fall back to the free-form/rule baseline in uncertain state-action regions

SPIBB's core rule is directly suited to the controller frontier: when data support is weak, reproduce the behavior/baseline policy instead of taking an offline-learned action. The original algorithm provides safe-policy-improvement guarantees in its tabular assumptions, and the estimated-baseline extension shows the baseline can itself be learned from data while retaining guarantees under its assumptions.

For Lean this suggests a **baseline-bootstrap controller**, not unconstrained offline RL:
- baseline = current fixed/rule or free-form OpenProver controller;
- learned controller may override only where support/coverage and value margin pass a prespecified confidence gate;
- otherwise defer to baseline;
- separately allow deterministic verifier-based hard constraints that forbid integrity-violating actions.

This is stronger operationally than simply reporting an OPE point estimate. It also matches the broader frontier's calibrated-abstention requirement. However, SPIBB's formal guarantees do not automatically transfer to a partially observed, function-approximated Lean-agent environment. The transfer is a design principle until tested under the actual controller state/action representation.

### C63 — Mid-trajectory compute/model purchase has direct recent transfer evidence: escalation should be an action chosen from evolving state, not only a first-token budget class

New transfer evidence:
- *Learning to Seek Help: Dynamic Collaboration Between Small and Large Language Models* (2026): https://arxiv.org/abs/2604.17094 — trains a smaller model with online RL to decide during multi-step reasoning **when and how** to query a stronger LLM, and reports gains over static collaboration/standalone inference with transfer to unseen LLMs.
- *STEER: Step-wise Guidance for Efficient LLM Inference* (2025): https://arxiv.org/abs/2511.15394 — stepwise confidence-guided routing invokes a larger model only when needed; reports up to roughly +20% accuracy with 48% lower FLOPs than only-large-model on AIME in its tested setting.
- *Adaptive Parallel MCTS* (2026): https://arxiv.org/abs/2604.06921 — runtime-level negative early exit prunes unproductive reasoning trajectories and reallocates reclaimed compute to concurrent searches, improving throughput/tail latency while preserving reported accuracy in its tested workloads.

These are not Lean results. They do, however, strengthen `escalate_model`, `spawn_more_workers`, or `buy_search` as **mid-trajectory controller actions** conditioned on compact progress/verifier/cost state. The Lean-specific advantage is that compiler/verifier outcomes supply unusually strong state evidence, so escalation can be trained against objective downstream progress instead of self-reported confidence alone.

Important negative condition: confidence/uncertainty alone is not sufficient. Recent reasoning-instability work shows some early instability can recover while later instability is more destructive, so the controller should estimate recoverability/value-of-computation, not map `high uncertainty -> expensive model` mechanically.

## Concrete matched experiment now implied by the evidence

Use one OpenProver-compatible execution substrate and freeze theorem set, Lean/mathlib/toolchain, planner/worker/verifier backbones, repo/Whiteboard interface, worker isolation, verifier behavior, total real budget and artifact semantics. Compare:

1. **Fixed/rule controller**: deterministic policy over the typed action set, with explicit thresholds.
2. **Free-form LLM controller**: released OpenProver-style Planner -> TOML actions.
3. **Learned typed controller**: policy over eligible heterogeneous actions using compact state features; baseline-bootstrap/fallback in low-support regions.

For the data-collection phase, add randomized, logged exploration probabilities for a deliberately limited safe subset of meta-actions. Keep action eligibility masks explicit. Evaluate not only solve@budget but calibration/OPE diagnostics and real cost: output+input+cache tokens, planner/worker/verifier/model charges, Lean/tool execution, state reconstruction, concurrency-adjusted wall-clock, and durable verified-progress reuse. Stratify by theorem difficulty/backbone and separately report support/coverage for every learned-policy action region.

A deterministic first event normalizer can be implemented without changing OpenProver semantics. The one essential logging addition for rigorous policy comparison is the **behavior meta-action propensity / randomized decision record**; existing detailed trace files are otherwise unusually well suited.

## Negative evidence / scope guards

- No direct full Lean heterogeneous learned controller found in targeted searches != no such system exists.
