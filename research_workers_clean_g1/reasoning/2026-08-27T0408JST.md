## C436 — Regorus already performs a scoped interpreter-vs-compiled-RVM direct differential check on supported official OPA cases

`tests/opa.rs` does more than compare Regorus against static OPA expected results. For cases whose query can be reduced to a supported rule path, it:

1. evaluates the case with the ordinary Regorus interpreter;
2. compiles the same policy/rule through the Regorus RVM compiler;
3. round-trip serializes the resulting `Program` artifact;
4. loads it into `RegoVM`, sets the same data/input, and executes it;
5. directly compares the VM binding result against the interpreter result and fails with an explicit `RVM mismatch` if they differ.

## C437 — A 2×2 cross-implementation / cross-compilation matrix can localize generated semantic mismatches better than a single source-vs-target pair

The strongest practical generated harness now has four primary routes on their **shared supported fragment**:

- `OPA source`: OPA topdown evaluator;
- `OPA compiled`: OPA compile → exact emitted Wasm bytes → intended Wasm SDK/runtime;
- `Regorus source`: independent Regorus interpreter;
- `Regorus compiled`: Regorus compiler → exact RVM `Program` artifact → `RegoVM`.

Optional fifth evidence remains Swift-OPA over exact OPA-derived IR plans, scoped only to IR-execution triangulation.

**Why this is more informative.** A mismatch pattern can help localize fault classes without declaring any route a perfect oracle:
- OPA topdown differs only from OPA Wasm while both Regorus routes agree: evidence concentrates on OPA lowering/Wasm/host route.
- Regorus interpreter differs only from Regorus RVM while OPA routes agree: evidence concentrates on Regorus compiler/RVM.
- Both source interpreters agree and both compiled routes disagree in different ways: suspect compilation/runtime-specific semantics or unsupported target domains.
- OPA source and Regorus source disagree: source-semantics implementation/specification difference must be resolved before using either as oracle.

This is diagnosis evidence, not proof. Every generated case must persist route support status and exact semantic configuration. Do not force unsupported routes into an equality comparison.
