## C289 — current sample/proposal IDs are not crash-stable operation identities
`_StructuredRunState.sample_id` defaults to `new_sample_id()`, which is a fresh `uuid.uuid4().hex` whenever a new process constructs run state. Action-runtime proposal request IDs are then synthesized as `proposal:{sample_id}:{len(model_usage)}`.

These IDs are useful within one live run but are not a cross-crash idempotency/recovery contract: reconstructing `_StructuredRunState` after a crash creates a different sample ID and hence different local proposal request/batch IDs.

Introduce a durable `RunInstanceV0` committed before any effectful work. It should own a stable `run_instance_id` that recovery reuses rather than regenerates.

## C290 — `RunInstanceV0` is the correct place to freeze experiment identity and RNG provenance
Minimum fields before any randomized/provider activity:

```text
run_instance_id
schema_version
proof task semantic sha256
frozen controller/substrate/config versions
logging-policy version
behavior-policy version
policy RNG seed / stream identity
provider/retriever/summarizer/checker substrate identities
started-at diagnostics
```

The existing output `sample_id` may be retained for compatibility, but crash recovery should derive/reuse it from this durable run record rather than mint a new UUID.

A stable run identity is also needed to derive deterministic journal event IDs without relying on current ledger length or process-local list length.

## C291 — optional context summarization can be a hidden model effect inside one nominal proof-generator call
`StructuredController._generation_metadata()` calls `summarize_context(...)`. If a `ChatContextSummarizer` is supplied and the attempt is eligible, it invokes `ChatDriver.complete(...)` using its own chat configuration/transport before the proof action generator call.

The action-runtime `BudgetManager.reserve_model_call()` reserves one model-call slot around proposal generation, but the summarizer call has no corresponding reservation in this path. `ChatContextSummarizer.summarize()` returns only the parsed compact summary; provider token/charge metadata from the summarizer response is not propagated into `_StructuredRunState.model_usage` or the action-runtime `CostLedger`.

Therefore `model_calls_used`, proposal-generation token totals and value-per-cost labels can undercount real model work when an LLM context summarizer is configured.

This is independent of the learned selector and independent of crashes.

## C292 — generic retrieval is another pre-generation effect boundary with unspecified cost semantics
`maybe_retrieve()` directly calls `retriever.retrieve(...)` before generation whenever its trigger fires. The `Retriever` protocol does not, at this seam, classify whether retrieval is:

- pure/local index lookup;
- filesystem/database I/O;
- remote API/network search;
- model-augmented retrieval;
- billed or free.

The returned snippets are stored semantically, but action-runtime cost accounting does not automatically create a retrieval physical-attempt receipt here.

For a compute-normalized experiment, retriever identity/effect class must be frozen and logged. Remote/model/billed retrieval needs the same Attempt/Receipt treatment; deterministic local retrieval can be classified separately.

## C293 — initial matched controller experiments should freeze or instrument summarizer/retriever explicitly
For the first causal Stage-A comparison, choose one prespecified substrate contract rather than allowing hidden optional effects to vary between tasks/runs:

- simplest: `context_summarizer=None` and a deterministic local/disabled retriever for both D0 and learned/randomized policy arms; or
- if the production baseline requires them, instrument their physical calls, usage, latency and failures under durable effect IDs before collecting randomized policy data.

Never compare policies under a cost vector that omits one arm's hidden summarizer/retrieval work.

## C294 — generation effect accounting should be decomposed further
The previous `ProposalGenerationAttemptV0` is logically a generation *pipeline*, which can contain:

1. retrieval effect(s),
2. context summarization effect,
3. model-route decision (normally pure),
4. proof-generator provider request/retries,
5. proposal finalization/validation (pure),
6. finalized batch persistence.

Keep a parent generation operation for causal grouping, but physical receipts should preserve these components separately. A single aggregate "generation cost" can remain a derived projection only after every configured component is accounted.

## C295 — the first provider pilot needs a hidden-effect eligibility check
Before accepting any task into the frozen deterministic provider pilot, record whether retriever/context summarizer are enabled and whether their costs are fully observed under the experiment contract. Tasks/runs with uninstrumented remote/model summarization/retrieval should not be used to claim a complete cost share.

This can be simpler than building every adapter on day one: the pilot may fail closed on uninstrumented optional effects while preserving them as a future Stage-B frontier.
