## C50 — LeanFlow directly shows that deterministic queue/workflow control can dominate free-running Lean agent loops, but the benefit is model-dependent

Primary/public source:
- `LeanFlow: A Case Study in Workflow-Driven Lean Autoformalization`, arXiv:2607.20503 (2026).

Mechanism:
- A programmatic queue manager, rather than the LLM, owns which theorem/declaration is active, presents bounded theorem-local failed-attempt memory, and advances only after Lean accepts the current assignment.
- A cached declaration-level verifier (`LeanProbe`) checks repeated local edits against a prepared environment; final project acceptance remains standard Lean/Lake.
- The paper explicitly ablates queue management against free-running proof loops and full Lean tools against terminal-only interaction.

Document-level Table 3 evidence under a 2,000 prover-call cap:
- Pythagorean / Kimi-K2.6: Full queue+tools **success, 1,043 calls, 46.9M input tokens**; no-queue+tools **failure at 2,000 calls, 160.2M input tokens**; queue+CLI **success, 1,561 calls, 91.3M**; no-queue+CLI **failure at 2,000, 157.5M**.
- Cramer–Wold / Kimi-K2.6: Full **success, 1,278 calls, 66.0M input tokens**; no-queue+tools, queue+CLI, and no-queue+CLI all hit the 2,000-call cap without completion.
- Pythagorean / GPT-5.5: all variants succeed; Full uses **258 calls / 14.3M input tokens** vs no-queue+tools **568 / 45.0M**, queue+CLI **277 / 14.3M**, no-queue+CLI **984 / 89.9M**.
- Cramer–Wold / GPT-5.5: all variants succeed; Full uses **495 calls / 25.9M input tokens**; no-queue+tools completes in 448 calls but uses 32.8M input tokens, while queue+CLI uses 959 / 59.5M and no-queue+CLI 476 / 49.7M.
- On RLM25 statement autoformalization, LeanFlow GPT-5.5 reports **75.7% BEq+** vs **72.9%** for a terminal-only agent while using fewer calls/input/output tokens in the reported run.

Interpretation:
- This is unusually direct evidence that **externalized deterministic workflow state and bounded local memory can be more valuable than giving the model freer control**, especially for a weaker/less robust backbone.
- The effect is not universal in outcome space: GPT-5.5 completes both document projects even without the queue, whereas Kimi-K2.6 does not. The controller's marginal value therefore depends strongly on backbone capability, matching earlier evidence that repair/diversity actions can help one prover and hurt another.
- Queue ownership also reduces context pollution: theorem-local failures are retained while unrelated future targets are kept out of the active context. This is a concrete systems mechanism for compressed trajectory sufficiency, not merely a better prompt.
- LeanFlow still uses programmatic workflow rules rather than learning the optimal next meta-action, so it strengthens the baseline against which a learned controller should be compared.

Critical scope / caution:
- The central document-level comparison is one run per condition; the paper acknowledges missing variance estimates. A success/failure boundary at a 2,000-call cap can move under different seeds/budgets.
- This is document-to-project autoformalization, not isolated theorem proving.
- The two document skeletons are not generated symmetrically by each evaluated model, so model-specific queue claims have a confound.
- Do not generalize the exact Kimi call ratios as universal queue speedups.

## C51 — AlphaProof Nexus gives direct Lean evidence that richer asynchronous evolutionary control pays mainly on hard problems and can waste compute on easier ones

Primary source:
- `Advancing Mathematics Research with AI-Driven Formal Proof Search`, arXiv:2605.22763 (2026).

Controller structure:
- Basic agent A runs independent Gemini prover subagents with compiler feedback.
- B adds AlphaProof as a specialized subgoal tool.
- C adds evolutionary coordination.
- Full D uses an asynchronous controller over a population of valid partial Lean proof sketches, LLM rater subagents, Elo/Plackett-Luce ratings, Thompson-style matchmaking, and P-UCB parent selection.
- Parent selection first keeps the top 64 Elo-rated sketches, then adds an exploration bonus with `c=0.2`; two inspiration sketches are sampled alongside the root.
- Prover prompts can stochastically request decomposition, combination of prior ideas, or a new approach. Each episode is capped at 5 AlphaProof queries and 90 search/replace edits; individual novel subgoals receive a typical 400-simulation AlphaProof budget.
- Exact solved/disproved subgoal states are globally cached and reused across sketches.

Cost-quality evidence on the Erdős subset:
- The paper's post-hoc architecture comparison finds the **basic agent can solve all nine Erdős problems that the full agent solved**, but richer control is advantageous on the hardest cases.
- Full agent D is reported to save roughly **2x–5x inference cost** over A/B on hard problems such as Erdős #138 and #125, while being roughly **half as cost-efficient on the remaining easier problems** in that comparison.
- Full variants with 3 or 6 asynchronous generators are more efficient on easier tasks, but do not match the 10-generator configuration on the most challenging problems. Thus fixed high parallelism is not uniformly optimal.
- A full-system variant with only one generator but population sampling **underperforms the basic setup**, suggesting the population database only helps when asynchronous coordination is sufficient to exploit it.
- Standalone AlphaProof tree search, despite ~64 v6e TPU hours per problem in the reported test, solves none of the nine research problems; the integrated high-level agent matters.

Interpretation:
- This is direct Lean evidence for a **difficulty-dependent architecture selector**: simple compiler-feedback loops can be the cost-efficient choice on easier problems, whereas population/evolution/tool coordination can dominate on hard cases.
- It sharpens the `search purchase` frontier. The meta-controller should decide not only which proof action to take, but whether to activate expensive coordination itself (more generators, population sampling, specialized prover calls, rater capacity).
- P-UCB/Elo is a real learned/statistical allocation mechanism over *partial proof sketches*, but it is not a calibrated heterogeneous action-value policy. Tool calls, decomposition prompts, agent count and per-episode budgets remain largely fixed/manual.
- The result also supplies negative evidence for using an LLM critic as an unquestioned universal value oracle: it is useful inside the population system, but the full architecture can be less efficient than the basic loop on easier problems, and prior FormalRewardBench evidence shows proof-preference judging is weak in isolation.

Scope / caution:
- Agents C/D are expensive and have fewer independent trials, so variance is less well estimated than A/B.
- Cost figures omit AlphaProof inference in some plotted comparisons; the paper argues adding its estimated ~$60 does not change the qualitative hard-case conclusions, but exact monetary ratios should remain scoped to the reported accounting.
- Architecture comparisons are post-hoc on problems already solved by D, so they do not estimate unbiased performance over all 353 attempted Erdős problems.

Source:
- https://arxiv.org/abs/2605.22763

## Updated synthesis

A stronger pattern now spans theorem-level, document-level, and research-level Lean systems:

1. **External controller structure matters independently of the base model.** LeanFlow's queue, LEAP's DAG/reviewer, HILBERT's staged escalation, BFS-Prover-V2's ordered bottleneck replanning, and AlphaProof Nexus's population controller all alter efficiency/success without merely scaling pass@K.
2. **The optimal amount of controller complexity is state/model/difficulty dependent.** LeanFlow's queue is decisive for Kimi but not necessary for GPT-5.5 completion; AlphaProof Nexus's full evolutionary controller pays on hard Erdős problems but is less efficient on easier ones.
3. Therefore the missing controller should include a **meta-action to purchase additional control complexity itself**: stay in a cheap serial/queue loop, widen branches, launch more agents, activate retrieval, call a specialized prover, or enter population/evolutionary search.
4. Persistent verified memory is repeatedly valuable: LEAP DAG memoization, BFS subgoal cache, AlphaProof Nexus goal cache, and LeanFlow theorem-local failure state all reduce redundant work. The controller state should include reusable progress/memory coverage.
5. Fixed thresholds remain common even in top systems; richer statistical allocation exists mainly over candidate sketches, not over the full heterogeneous action vocabulary.

## Frontier refinement

1. **Hierarchical controller-of-controllers:** learn both local proof actions and whether to activate a more expensive search architecture (extra agents, population/evolution, specialized prover, global retrieval).
2. **Backbone/difficulty-conditioned compute purchase:** predict when simple compiler-feedback iteration is sufficient and when richer orchestration has positive marginal value.
3. **Calibrated candidate/action value:** compare sketch-level Elo/P-UCB, progress/value models, LLM reviewers and verifier-grounded features with calibration/selective-risk under shift.
4. **Memory-aware value:** condition on which exact Lean subgoals/lemmas/failures are cached or reusable so duplicated work is priced correctly.
5. **Replicated workflow ablations:** repeat LeanFlow-style queue/tool/controller conditions across seeds and theorem-level benchmarks, not only two document projects.
