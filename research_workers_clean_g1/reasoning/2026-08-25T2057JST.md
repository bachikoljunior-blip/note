## C21 — Proof-state snapshotting changes the wall-clock economics of tactic-semantic branching in Lean

Primary source: `Keep the Proof State Live: Snapshotting for Efficient Tactic Search in Lean 4`, arXiv:2605.25556 (2026-05).

Mechanism:
- Captures an already-elaborated Lean proof state once and reuses it across tactic branches through small Lean 4 LSP extensions.
- The immutable `Environment` is shared by reference; only the small local/metavariable proof state is copied per branch.
- This removes repeated Mathlib import loading and theorem-body re-elaboration from each branch.

Quantitative evidence:
- 48 miniF2F-v2 problems: 45 hand-crafted prove-phase cases plus 3 end-to-end DSP runs.
- Reported wall-clock speedup over the standard rebuild-per-branch fallback: **5.6–50×**, average **14×**, median **9.7×** on the 45 prove-phase cases.
- Tactic execution is typically only a few ms to 500 ms per branch, with 95th percentile **289 ms**; import + theorem-body elaboration account for **>99%** of fallback branch time.
- Import loading is about **60 s/branch** and theorem-body elaboration is estimated at **18–735 s/branch** depending on proof complexity.
- The snapshot path adds only about **4–13 s** total LSP/tactic overhead for an entire branch portfolio after one-time capture, and speedup increases with branch count.

Interpretation:
- This does not directly improve proof-search quality, but it materially changes the opportunity cost of CARTS/3D-Prover-style tactic-semantic diversity. A controller can afford many more local tactic branches before wall-clock overhead dominates.
- Therefore compute-normalized comparisons should distinguish **LLM generation cost**, **Lean tactic execution cost**, and **proof-state reconstruction/elaboration cost**. Treating every Lean call as equal can badly mismeasure the true cost of branching.
- Snapshotting is complementary to import-level caching and to intra-branch `SavedState` backtracking; it addresses branch-dispatch state reconstruction.

Limitations / negative evidence:
- Fixed static tactic portfolio; no learned semantic-diversity selector or repair router is evaluated.
- Small benchmark slice, single Apple M-series 8GB machine, no Linux/cluster characterization.
- The paper says the patched Lean binary/evaluation pipeline will be open-sourced; the advertised GitHub repository was not accessible through the connected GitHub API during this run, so artifact availability/reproducibility is not yet confirmed here.

Primary source:
- https://arxiv.org/abs/2605.25556

## C23 — Diffusion-style iterative proof refinement is viable but currently materially weaker than autoregressive Lean proving

Primary source: `Pythagoras-Prover: Advancing Efficient Formal Proving via Augmented Lean Formalisation`, arXiv:2606.12594 (2026-06), plus project/model cards.

Evidence:
- Pythagoras-Prover-Diffusion-4B uses block-diffusion decoding with tactic-aligned masking and iterative refinement at inference time.
- MiniF2F-Test pass@32: diffusion **63.25%**.
- A restricted autoregressive 4B comparison with training tokens capped at 4096 and evaluation at 8192 tokens reports **74.6%** pass@32; the full autoregressive Pythagoras-Prover-4B reports **86.1%** pass@32 under its normal setting.
- The diffusion checkpoint's published evaluation setting uses **8192 generated tokens, 8192 diffusion steps, block size 8**.

Interpretation:
- Iterative denoising/refinement can produce non-trivial formally verified Lean proofs, so it is a real alternative search geometry rather than a purely speculative mechanism.
- But current evidence is negative for treating diffusion refinement as a ready replacement for strong autoregressive generation/repair: it trails the restricted autoregressive comparison by about **11.3 points** at pass@32.
- It is not compiler-feedback-guided repair; its refinement signal is the generative diffusion process itself. Therefore it does not close the semantic-diversity + verifier-repair frontier.

Benchmark robustness side-result:
- The same project introduces MiniF2F-ALF, a structured mutation benchmark intended to reduce reliance on surface-form familiarity. Every evaluated prover degrades on it; at pass@32 Pythagoras-32B reports **85.04%**, Pythagoras-4B **83.19%**, Goedel-Prover-V2-32B **83.61%**, DeepSeek-Prover-V2-671B **79.71%**.
- This is useful as a robustness stress test, but ALF is a deliberate distribution shift derived from MiniF2F families; performance drops are not direct proof of contamination.

## C24 — Cross-ITP clue: history-sensitive tactic-transition priors improve Coq proof search without changing the base generators

Primary source: `Understanding and Improving Automated Proof Synthesis for Interactive Theorem Provers`, arXiv:2604.24354 (CoqGym, not Lean).

Mechanism:
- Mines frequent sequential tactic patterns from human-written proof corpora.
- At search time, reranks each prover's candidate tactics using whether they match a known transition from the parent tactic; unmatched tactics retain their original neural confidence order.
- Thus it injects a **history-sensitive transition prior** without replacing the underlying tactic generator.

Evidence across four CoqGym provers:
- ASTactic: **+5.64%** total proved theorems (90 additional).
- Tac: **+12.14%** (163 additional).
- Tok: **+9.24%** (130 additional).
- Passport: **+5.17%** (74 additional).
- Average gain: **8.05%**.
- Average unique added value: about **20% more previously unproven theorems** relative to baseline DFS.
- Guiding all tactics with mined patterns outperforms a restricted variant that guides only parameterized tactics.

Interpretation:
- This is not Lean and not semantic-diversity/repair evidence, so it should not be transferred as a direct performance claim.
- It does show that *transition history* can carry actionable search value beyond per-state tactic scores. A future Lean router should consider `previous tactic / transition class / failure sequence` alongside proof-state semantics, compiler error diversity, and repairability.
- This complements C22: error diversity is a useful failure-history signal; PGTS suggests tactic-transition history may be another low-cost feature family.

Primary source:
- https://arxiv.org/abs/2604.24354

## Updated synthesis

The strongest concrete design hypothesis is now more implementation-aware:

1. **Keep an elaborated proof state live and branch cheaply**; otherwise search-quality comparisons can be dominated by avoidable Lean reconstruction overhead (C21).
2. **Use semantic/transition diversity to choose branches**, not lexical prompt diversity (C15/C16), but augment semantic state with **history-sensitive transition features** where useful (C24).
3. **Use verifier-grounded failure features for routing**, especially compiler-error diversity; current v3 confirms this signal survives the updated router evaluation (C22).
4. **Exploit the large oracle gap** by learning calibrated success/repairability/future-cost estimators rather than relying on fixed attempt counts or uncalibrated LLM pairwise judges (C18/C22).
5. **Expose a hierarchical action set**: fresh semantic branch, preserved-state continuation, local repair, typed graph edit, blueprint/decomposition refinement, restart (C17/C19/C20).
6. **Do not equate iterative refinement with improvement**: diffusion refinement is formally viable but currently weaker than autoregressive proving in the available controlled comparison (C23).
7. Report cost on at least three axes when possible: **generated tokens / model FLOPs**, **Lean tactic/verifier work**, and **wall-clock including elaboration/state reconstruction**.
