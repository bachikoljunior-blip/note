## C421 — CIL's published random differential harness is not exactly replayable from repository state alone

**Observed.** The public `SELinuxCILSemantics` random test harness calls `Random.self_init()` and takes only four command-line bounds: maximum declarations, commands, names, and a configuration-count parameter. It does not persist or print the PRNG seed in the inspected source. Generated `.cil` and compiled `.out` artifacts under `GeneratedTestCases/` are ignored by the repository's `.gitignore`.

The loop is also inclusive (`for _ = 0 to configNum do`), so the implementation generates `configNum + 1` attempts for each combination of declaration/command/name bounds, not exactly `configNum` attempts as a casual reading of the parameter name might suggest.

Primary artifacts:
- https://github.com/lceragioli/SELinuxCILSemantics/blob/main/test/testCILSemRand.ml
- https://github.com/lceragioli/SELinuxCILSemantics/blob/main/test/Generate.ml
- https://github.com/lceragioli/SELinuxCILSemantics/blob/main/.gitignore

**Inference.** The published artifact is reproducible as a **procedure**, but an individual historical random campaign is not exactly replayable from committed repository state unless its generated cases or external seed/log were separately preserved. `PolicyEvidenceClaimV1` should distinguish `procedure_reproducible` from `campaign_exactly_replayable`.

New fields:
- `random_seed_status = recorded | externally_recorded | not_recorded`;
- `campaign_bounds`;
- `generator_loop_semantics`;
- `generated_case_artifact_digest_set` when preserved;
- `campaign_exactly_replayable`.

New regressions:
- `unrecorded_random_seed_cannot_claim_exact_campaign_replay`;
- `parameter_label_cannot_override_implemented_iteration_count`.

## C422 — CIL's formal semantics is explicitly a type-enforcement fragment, so compiler evidence must name the language fragment even when real policies are supported

**Observed.** The 2024 CIL semantics paper explicitly states that its formal semantics focuses on CIL's type-enforcement fragment. The authors note that this fragment covers the type-enforcement constructs used in the real-world configurations they analyze, but they also list extending coverage to all CIL features as future work.

Primary source:
- https://people.inf.ethz.ch/basin/pubs/acm2024.pdf

**Inference.** Empirical success on large real configurations does not erase the formal fragment boundary. Evidence should separately track:
- `formal_semantics_fragment`;
- `empirical_real_world_coverage`;
- `production_language_full_surface`.

A real-world corpus can show practical relevance of a fragment without proving that omitted language features preserve semantics.

New regression:
- `real_world_corpus_coverage_cannot_expand_formal_language_fragment`.

## C423 — current OPA evidence separates semantic E2E suites from fuzz robustness more cleanly than a single test-coverage label would suggest

**Observed.** OPA's current `make fuzz` target runs AST parser/compiler fuzzing (`FuzzParseStatementsAndCompileModules`), seeded by the v0/v1 test corpus. Separately, `wasm-rego-test` compiles dedicated YAML/JSON Wasm cases to actual Wasm bytes and executes them in Node, while the Go Wasm SDK E2E path compiles the shared v0/v1 semantic corpus and evaluates exact bytes in the Go Wasm SDK.

**Inference.** For policy-compiler assurance, three independent axes should be represented explicitly:
1. input/compiler robustness under fuzz mutation;
2. expected-result E2E conformance on fixed suites;
3. randomized cross-backend semantic equivalence, if such an oracle exists.

The inspected OPA paths clearly establish the first two, but this targeted search did not establish the third.

New regression:
- `robustness_fuzz_plus_fixed_e2e_cannot_be_relabelled_as_randomized_semantic_differential_testing`.
