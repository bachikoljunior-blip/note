## New findings

### C171 — the current source has a real causal logging gap between policy choice and action execution

For policy/OPE data, `proposal_cache_events` is not a durable decision journal. The critical current order is effectively:

`select -> append in-memory choice_set -> consume/remove -> append in-memory action_selected -> execute -> append in-memory action_cost_observed -> build result -> append result JSONL`.

Therefore a crash after selection but before final result persistence can erase the behavior action and its choice set. This is not only a generic durability concern: it makes interrupted trajectories preferentially disappear, which can bias outcome-conditioned learning and prevents exact behavior propensity reconstruction.

### C172 — minimal safe ordering is decision commit before consume/effect, outcome commit before the next randomized decision

Recommended instrumentation order for Stage-A randomized collection:

1. Build the frozen `ConstrainedSelection` and canonical choice rows without consuming the frontier.
2. Atomically commit one `execution_decision` event.
3. If the selected node came from a generated proposal batch, durably bind `decision_id -> proposal_batch_id -> node_id` without changing provider ledger events. This can be in the same transaction as step 2 because the batch id is already known at selection time.
4. Only after commit succeeds: consume/remove the selected node and execute it.
5. After execution, atomically commit one `execution_outcome` event.
6. Do not begin another randomized decision until step 5 commits. If outcome persistence fails after effects occurred, stop the run; the unmatched decision remains censored rather than silently continuing with an unknown transition.

A journal write failure before the decision commit is fail-closed: do not execute the action. A post-effect outcome-journal failure cannot roll back the action, so stopping the run is required to keep transition boundaries interpretable.

### C173 — exact first journal schema can be small and append-only

`execution_decision` should contain at minimum:

- stable `event_id`, `decision_id`, `run_id/sample_id`, `task_id`;
- controller/journal schema version, frozen code/source revision, policy id/version;
- workspace version and a canonical state/feature-manifest reference;
- canonical ordered choice rows or their content hash plus immutable recoverable body;
- effective legal/admitted mask, selected node/action kind, selected proposal batch id when any;
- epsilon/logging-policy parameters, exact `mu(a|s)` for every effective legal action and chosen propensity;
- frozen budget snapshot and cost-estimator/version reference;
- pre-decision cost-ledger boundary/id.

`proposal_batch_consumption` may be represented as fields in the committed decision or as its own append-only event, but must never mutate provider request/usage/charge records. It records only `batch_id`, `node_id`, `decision_id`, and immutable source/model-tier metadata needed for joins.

`execution_outcome` should contain at minimum:

- `decision_id` and stable outcome event id;
- workspace before/after version or canonical hashes;
- execution status and action-specific verified result/progress;
- exact new cost-ledger event ids/boundaries attributable after selection;
- terminal verified success state separately from local verified progress;
- stop/terminal reason and whether final assembly was executed separately.

The raw evidence layer still keeps terminal success, local verified progress, and the multidimensional real-cost vector separate; it does not store one baked scalar reward.

### C174 — executable fault-injection contract has eight useful boundaries

Use explicit hooks in a journal-enabled action-runtime fixture. Expected semantics:

| Hook | Injected failure point | Required durable state / behavior |
|---|---|---|
| F0 | before `execution_decision` INSERT | no decision; no consume; no action/effect |
| F1 | after INSERT, before decision COMMIT | transaction absent after reopen; no consume/effect |
| F2 | after decision COMMIT, before frontier consume | one unmatched decision; no outcome; action not executed; reader marks censored |
| F3 | after decision/batch binding COMMIT, before action dispatch | unmatched decision + immutable batch join; provider ledger unchanged; no execution cost |
| F4 | after in-memory consume/remove, before first action effect | unmatched decision; no verified outcome; replay must not treat missing outcome as zero reward |
| F5 | after first checker/tool/workspace effect, before outcome INSERT | unmatched decision; execution may have occurred; reader only sets `execution_may_have_occurred` when independent durable effect evidence proves it |
| F6 | after outcome INSERT, before outcome COMMIT | outcome absent after reopen; run stops; decision is censored |
| F7 | after outcome COMMIT, before next loop iteration | exactly one matched transition; safe to start next decision on recovery/new run |

Also test journal connection/SQL failure, exact duplicate replay, and conflicting replay. Same event id + byte/canonical-payload-equivalent data is idempotent; same id + different canonical payload fails closed.

### C175 — epsilon=0 instrumentation equivalence must compare semantics/resource counts, not wall clock identity

For every anchored fixture, run baseline and journal-enabled `epsilon=0` with identical controller/prover/cost-estimator inputs. Require exact equality for:

- selected node/action sequence and deterministic candidate ordering;
- workspace acceptance/status and semantic version transitions;
- proposal validation/cache outcomes and selected budget admissions;
- provider physical request count/ids, model tier/route, token/charge observations;
- checker/tool call counts, commands/verdict categories and final proof/stop reason;
- budget checks/model-call counts and cost-ledger canonical provider/check events;
- final assembly behavior and safety verdicts.

Do not require equal elapsed/wall-clock because durable journaling adds real I/O. Instead record instrumentation overhead separately. Journal implementation must not feed its elapsed time back into action ranking/budget admission in the equivalence arm; if elapsed-time budgets are active, freeze or disable that dimension for the semantic-equivalence test and measure it in a separate overhead test.

### C176 — shared proposal-batch attribution needs an immutability regression test before learning data are trusted

Construct one fake provider request returning two valid proposals under one `proposal_batch_id`, consume node N1, then later N2. Snapshot canonical provider request/usage/charge events immediately after proposal generation and assert they are byte/canonical-value identical after both consumptions. Assert instead that two distinct append-only batch-consumption joins exist, one for each decision/node, and that aggregate provider charge is counted once.

This specifically catches the current `attribute_proposal_batch` rewrite behavior. Learning code must never use the current mutable `action_id` metadata on provider events as a per-action generation-cost label.

### C177 — failed proposal generation is a useful negative control: no execution-decision event should exist

The existing provider-failure path can emit provider retry/failure usage/charge observations and stop before a choice set exists. Journal instrumentation must preserve that distinction: proposal-generation cost can exist with zero `execution_decision` events. This prevents forcing all run cost into a selected-action transition.
