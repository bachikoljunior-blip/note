## C254 — Stage-A structural actions have a materially stronger crash-recovery property than checker/tool actions
At the current action-runtime seam, proposal generation/retrieval/model routing occurs before action selection and caching. After a node is selected, `execute_action_node()` dispatches `DECOMPOSE`, `PROPOSE_ARGUMENT`, `REFINE_ARGUMENT`, and `CHANGE_REPRESENTATION` only through structured reducers. The inspected reducers construct immutable dataclass replacements and `ProofWorkspace.successor()` values; they do not invoke a provider, checker, shell/tool call, or persistent candidate-file write. Provider cost for a model proposal batch has already happened upstream of selection.

Therefore, after the mutable provider-attribution defect is migrated to immutable batch-consumption edges, these four action kinds can be classified as `pure_reducer_replayable`: a crash after a durable Decision/Consumption commit but before a durable Outcome need not cause re-selection or a second provider generation. Recovery can replay the *already selected* finalized proposal against the exact durable pre-decision workspace and append the missing Outcome.

This is narrower than "all proof actions are replayable." `RUN_CAPABILITY_TEST` writes a candidate and invokes a checker; `IMPLEMENT` / `REPAIR_IMPLEMENTATION` materialize a candidate and invoke checker/safety paths. Those are effectful for crash recovery even if the checker is local.

## C255 — current JSONL persistence is terminal-result persistence, not a mid-run recovery log
`_StructuredRunState.proposal_cache_events` is an in-memory list. The current action runtime appends `choice_set`, `action_selected`, and `action_cost_observed` there, but `JsonlTraceStore.append_result()` receives only a completed `ControllerResult`; `result_events()` then emits a run summary, a *final* workspace snapshot, a final cost-ledger snapshot, and attempts. If the process dies between selection and `ControllerResult` construction, the selected decision and intermediate workspace are not durably reconstructible from this trace path.

This means C248-C251 need an actual mid-run journal, not merely richer final trace serialization.

## C256 — exact workspace snapshotting is already technically straightforward
`ProofWorkspace` is frozen/immutable; every mutation returns a version-bumped successor with `parent_version`. It has a full deterministic `to_dict()` and a matching `workspace_from_dict()`. `initialize_from_task()` derives `workspace_id`, root obligation, graph, specification and initial state deterministically from the `ProofTask`.

Introduce a content-addressed `WorkspaceSnapshotV0` rather than trying to reconstruct full state from coarse Outcome deltas alone:

```text
schema_version = 0
record_type = workspace_snapshot
workspace_snapshot_sha256
workspace_id
workspace_version
canonical_workspace_body
```

Canonical JSON should be the normalized `ProofWorkspace.to_dict()` body. Insert-or-verify by SHA is idempotent; same SHA with different bytes is a hard conflict.

`ExecutionDecisionEventV0` should reference `pre_workspace_snapshot_sha256`. The Decision/BatchConsumption transaction should also insert-or-verify that snapshot before commit. `ExecutionOutcomeEventV0` should reference `post_workspace_snapshot_sha256`, inserted atomically with the Outcome. This makes a pure structural replay chain self-contained without requiring the terminal JSONL trace.

## C258 — refine C251 crash semantics with a recovery state machine
The journal protocol should distinguish `selection durability` from `effect recoverability`.

### Before Decision transaction commits
No durable decision exists. Recompute from the unchanged durable boundary.

### Decision + BatchConsumption + pre-workspace snapshot committed, executor not started
The decision is durable. Never reselect. For `pure_reducer_replayable`, execute/replay the selected reducer once from the referenced pre-workspace snapshot and commit Outcome + post snapshot. For effectful actions, normal execution may proceed if there is affirmative evidence it never started.

### Executor may have started, Outcome absent
- `pure_reducer_replayable`: because the reducer only changes in-memory immutable state, process death cannot leave a hidden external reducer effect. Reconstruct the pre-state and replay the same selected reducer; append the missing Outcome.
- effectful classes: mark `in_doubt_effectful` / censored and fail closed in v0. Do not automatically call the checker/provider/tool again merely because Outcome is absent.

### Outcome + post-workspace snapshot committed
Replay is read-only/idempotent. A duplicate Outcome insertion must either match the existing payload digest exactly or hard-conflict.

## C259 — SQLite durability does not create exactly-once semantics for external effects
SQLite documentation states that `synchronous=FULL` in WAL mode is ACID and performs an extra WAL sync after each transaction commit, supporting the journal's durable pre-effect decision boundary. But that database transaction cannot by itself make a separate checker/API/tool side effect atomic with the journal.

A useful public analogue is Stripe's official idempotency contract: a client can safely retry a mutating request when it supplies the same idempotency key; Stripe stores the first result and rejects parameter mismatches for key reuse. The relevant general lesson is not Stripe-specific: automatic retry of an effectful action needs a stable operation identity plus an execution substrate that actually honors idempotency or exposes a queryable durable receipt.

Public sources:
- SQLite PRAGMA synchronous: https://www.sqlite.org/pragma.html
- SQLite WAL: https://www.sqlite.org/wal.html
- Stripe idempotent requests: https://docs.stripe.com/api/idempotent_requests

Do not infer from this that CSSC's current checker path is idempotent; that has not been established.
