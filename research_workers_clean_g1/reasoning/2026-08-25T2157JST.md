## C25 — LeanSearch v2 shows that context retrieval should operate at proof-strategy scale, not only local proof-state scale

Primary source: `LeanSearch v2: Global Premise Retrieval for Lean 4 Theorem Proving`, arXiv:2605.13137v2 (2026-05-14).

Mechanism:
- Adds **global premise retrieval**: instead of asking only which lemma advances the current local proof state, generate a proof sketch, issue retrieval queries for multiple proof steps, filter candidates, judge whether the set jointly supports the sketch, and revise the sketch when support is missing.
- Standard retrieval is separated from reasoning mode as a black-box service; reasoning mode receives ranked declarations plus explicit absence-of-support signals rather than embedding internals.
- The reflection loop can revise a proof route when retrieval evidence indicates a missing premise, incompatible type/interface, or an alternative route.

Quantitative evidence:
- MathlibQR standard retrieval: reranked LeanSearch v2 reaches nDCG@10 **0.623** and Recall@10 **0.780** on the fair 810-query subset, versus the next-best system's nDCG@10 **0.533** and Recall@10 **0.698**.
- MathlibMPR global retrieval: the reasoning mode covers **30.4%** of full expert premise routings at top-10 under the main-or-alternative criterion, versus **24.6%** for DIVER and **2.9%** for the strongest proof-state premise-selection baseline; under the stricter original-PR-only routing it is **29.0%** vs **21.7%** and **2.9%** respectively.
- Fixed downstream prover loop on FATE-H: no retrieval solves **4/100**, standard mode **14/100**, reasoning mode **20/100** with Claude Sonnet 4.5. Replacing the prover backbone with Kimi K2 preserves the ordering: **1/100**, **8/100**, **12/100**.
- Reflection ablation with every other component fixed: initial sketch only solves **16/100**, up to three judge-driven sketch revisions solve **20/100**. Roughly one third of accepted queries require at least one revision; mean revision cost is about one extra revision call per accepted query.
- Reported reasoning-mode cost is about **$1.10/query** at the paper's hosted-model prices; standard retrieval service latency is about **0.2 s/query**.

Interpretation:
- Repository-scale Lean context should not be a one-shot static retrieval performed before proof search. The evidence supports a **two-timescale context policy**: retrieve a coherent global premise set for a proposed proof route, then re-retrieve when decomposition/route evidence changes.
- The +4-point reflection ablation is especially relevant to hierarchical routing: changing the *context/proof route* can be a productive action distinct from continuing or repairing a local proof.
- This directly strengthens the existing frontier item on non-oracle repository context retrieval: the unresolved question is now how to couple such retrieval with local semantic tactic selection and compiler-guided repair without paying the full sketch–filter–judge cost on every branch.

Limitations:
- The global-retrieval benchmark is only 69 theorems; downstream FATE-H is 100 problems.
- The reasoning loop uses hosted frontier LLMs and is not calibrated as a success-probability router.
- It does not integrate proof-state snapshotting, CARTS/3D-Prover semantic tactic diversity, or learned compiler repair.

Primary source:
- https://arxiv.org/html/2605.13137v2
- https://github.com/frenzymath/LeanSearch-v2

## C26 — TheoremGraph suggests typed dependency expansion can approach LM-reranked retrieval without a learned reranker

Primary source: `TheoremGraph: Bridging Formal and Informal Mathematics`, arXiv:2606.25363 (2026-06).

Mechanism/evidence:
- Releases LeanGraph, an elaborator-level dependency extractor spanning **388,105 Lean declarations** and **11.3M typed edges** across **25 Lean projects**.
- A name-and-signature representation plus graph expansion reaches formal concept retrieval Recall@10 **0.775**, within **0.5 percentage points** of LeanSearch v2's reranked **0.780**, without an LM reranker.
- The broader TheoremGraph also links 11.7M informal theorem-like environments and 18.3M candidate dependencies to formal statements, but those cross-formal/informal links use an LLM judge and should be treated separately from the typed LeanGraph evidence.

Interpretation:
- Dependency-graph expansion is a promising **low-latency context candidate generator** before expensive LLM reasoning/reranking.
- For a hierarchical prover, a useful architecture may be: typed dependency expansion for cheap high-recall neighborhood construction, then selective reasoning retrieval only when the local/global route remains unsupported.
- This is complementary to C25 rather than a replacement: C25 reasons about *which proof route should exist*; C26 provides a cheaper structural substrate for candidate expansion.

Limitations:
- Retrieval result is concept retrieval, not end-to-end proof success in this paper.
- Cross-domain theorem matching uses an LLM judge and is not a verifier-grounded proof router.
- No matched compute comparison against iterative proof-state retrieval is reported.

Primary source:
- https://arxiv.org/abs/2606.25363

## C27 — VeriSpecGen strengthens the case for traceable failure attribution before repair: localize the violated requirement, then edit only that clause

Primary source: `Intent-aligned Formal Specification Synthesis via Traceable Refinement`, arXiv:2604.10392 (2026-04).

Mechanism:
- Decomposes natural-language intent into atomic requirements.
- Generates requirement-targeted positive, negative-input, and negative-output tests plus an explicit traceability map from each test to the requirement(s) it checks.
- Lean proof automation validates each concrete specification test. Failed tests are lifted through the traceability map to implicated requirements.
- Repair prompts contain the current specification, only the implicated requirements, and representative failing tests; the model is instructed to preserve unaffected clauses instead of rewriting the entire specification.
- After ordinary tests pass, adversarial tests can add new failing cases and trigger another localized repair.

Quantitative evidence:
- VERINA SpecGen reaches **86.6%** with Claude Opus 4.5, improving over benchmark baselines by up to **31.8 points** across model families/scales.
- The trajectory corpus contains **343,827** supervised examples; fine-tuning reported models improves SpecGen by **15.6–18.2 points** (62–106% relative) and CodeGen by **18.2–21.5 points** (54–72% relative).
- The paper reports that ablations require all framework components and identifies requirement decomposition as the most critical component.

Interpretation:
- This is specification synthesis rather than theorem proving, but it provides strong same-ITP evidence for a more precise repair action: **first attribute failure to a semantic requirement/region, then perform the smallest scoped repair that preserves verified structure**.
- This strengthens the existing multi-action frontier. A prover/router should distinguish at least: local tactic edit, proof-fragment repair, premise/context re-retrieval, and decomposition/blueprint restart, with the action conditioned on where the verifier-grounded failure is attributed.
- It also reinforces the value of training on full failure→attribution→repair trajectories rather than only successful final artifacts.

Limitations:
- Validation is partly test-derived; when Lean automation is inconclusive the system may use an LLM judge for that concrete test, so not every refinement label is kernel-derived.
- Specification synthesis has a different search space from theorem proving; the 86.6% result must not be transferred to proof repair.
- The publicly surfaced text did not expose a compute-matched local-repair-vs-full-rewrite ablation, so the claim here is about the mechanism and overall ablation, not a quantified local-edit efficiency ratio.

Primary source:
- https://arxiv.org/html/2604.10392

## Updated synthesis

The strongest design hypothesis now has an additional **context-routing layer** above the previously identified proof-repair hierarchy:

1. **Cheap structural context expansion** from typed dependency graphs where possible (C26).
2. **Global proof-route retrieval/reflection** only when a coherent premise set is missing or the decomposition changes (C25).
3. **Snapshot/fork elaborated Lean state** before local branching so state reconstruction does not dominate wall-clock (C21).
4. **Select semantically distinct local tactic transitions**, not lexical prompt variants (C15/C16), optionally using transition history (C24).
5. **Attribute failures before choosing an action**: compiler-error class, implicated premise/requirement, proof-state transition, and repairability should determine repair granularity (C22/C27).
6. **Use the smallest justified action**: local edit → fragment/whole-proof repair → context re-retrieval → graph/blueprint refinement → decomposition restart.
7. **Train from failure trajectories** where verifier-grounded attribution is available, not only successful proofs/specifications (APRIL/C27).
8. Keep all routing evaluation **compute-normalized** across generated tokens/FLOPs, verifier/tactic work, state reconstruction, retrieval/reranking/model calls, and wall-clock.

A key architectural implication is that `retrieve context`, `branch`, `repair`, and `restart` should not be independent fixed pipelines. They are candidate **actions of one hierarchical controller**, each operating at a different semantic scope and cost scale.
