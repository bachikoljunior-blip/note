## C239 — successful DECOMPOSE advances workspace version by two, not one
The earlier optional preview field `predicted_workspace_version_delta` needs an action-specific contract. Current reducers behave as follows:
- successful PROPOSE_ARGUMENT / REFINE_ARGUMENT: one `workspace.successor(...)` → delta +1;
- successful CHANGE_REPRESENTATION: one `workspace.successor(...)` → delta +1;
- successful DECOMPOSE: `workspace.decompose(...)` itself calls `self.successor(obligation_graph=...)` → +1, then `apply_decompose()` calls another `workspace.successor(branches=...)` → final per-action delta +2.

Therefore preview/reducer parity tests must not assume every structural action mutates by exactly one version. Actual Outcome capture should measure the immediate before/after execution versions, not the later terminal `build_structured_result()` status-successor.

## C240 — rename the preview contract around reducer transitions, not “usefulness”
`EFFECTFUL` is too easy to misread as “made mathematical progress.” Current reducers can create a successor even when the user-visible argument payload is empty, and a hit REFINE can create a successor even if replacement values are materially identical. Conversely a ghost REFINE returns the exact input workspace.

Prefer a purely mechanical enum:
- `WOULD_MUTATE`: current reducer path is expected to return a successor/different workspace version;
- `WOULD_NOOP`: current reducer path deterministically returns the input workspace;
- `WOULD_ERROR`: current reducer path deterministically raises/violates a mutation precondition.

Then Outcome can separately record actual `workspace_transition_class` and later reward features can distinguish verified progress, reusable facts, semantic structural change, version-only/control-state change, and terminal success. This prevents the safe-support filter from pretending that “mutates” means “valuable.”

## C241 — canonical decision identity should separate semantic proposal content from transport/cost envelope
Current action-node ID hashes the full `proposal.to_dict()` plus branch/obligation/workspace context. That full dict includes proposal metadata such as model/token/routing data, so it is a good frozen runtime-node identity but not an ideal semantic-action identity. DecisionEvent v0 should persist:

1. `runtime_node_id` — current controller identity for exact replay within the substrate;
2. `finalized_proposal_body` or durable content-addressed body;
3. `proposal_semantic_sha256` over canonical `{finalized action, payload, score}` while excluding provider usage/cost/transport metadata;
4. optionally `proposal_envelope_sha256` over the full finalized proposal dict for exact byte-equivalent trace verification;
5. batch/source/model-tier/routing/cost metadata as separate fields.

This allows OPE to ask whether two policies chose the same semantic action without conflating that with how many tokens the provider happened to report, while still allowing exact runtime replay/audit.

## C243 — current physical-event filtering can use request identity directly
`record_proposal_request()` creates the fallback physical attempt with `request_id` equal to the logical proposal request ID B. `_append_provider_attempt` gives both provider-request and provider-usage that request ID; `_record_charges` gives the charge event the same request ID. The shared `common` metadata also carries `proposal_batch_id=B`.

Thus the characterization test can filter B events by:
`event["request_id"] == B or event["metadata"].get("proposal_batch_id") == B`
and then restrict kinds to `{provider_request, provider_usage, charge}`. In the one-batch fixture all three kinds should be present; no pricing/tool/checker events are necessary.

## C244 — reducer-owned transition preview should be extracted from the same builders/checks used by mutation
A safe API direction:

```python
class StructuralTransitionStatus(str, Enum):
    WOULD_MUTATE = "would_mutate"
    WOULD_NOOP = "would_noop"
    WOULD_ERROR = "would_error"

@dataclass(frozen=True)
class StructuralTransitionReport:
    status: StructuralTransitionStatus
    reason_code: str
    predicted_workspace_version_delta: int | None
```

Do not implement this as a second independent copy of reducer `if` statements. Refactor pure transition preparation so mutation and preview share it:
- argument reducer: one pure builder returns guard report + candidate branch if any;
- representation reducer: one pure builder returns guard report + child/retired-parent transition if any;
- decomposition: extract the existing duplicate/self-child/graph prechecks from `ProofWorkspace.decompose` into a pure validation helper used both by preview and the mutator.

Then parity tests invoke preview followed by the actual reducer on immutable input and assert:
- `WOULD_NOOP` → exact input workspace returned;
- `WOULD_MUTATE` → no exception and measured version delta matches the report;
- `WOULD_ERROR` → expected deterministic exception class/reason and no committed workspace mutation.
