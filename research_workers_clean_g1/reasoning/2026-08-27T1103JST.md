## C468 — controlled Lean evidence separates two kinds of reusable memory: verified lemmas increase reachability, guidance accelerates search

Primary source: `CircuitProver: Agentic Lean 4 Theorem Proving with Reusable Circuit Proof Library for Hardware Verification`, arXiv:2607.27259v1 (2026-07-29).

CircuitProver stores two distinct reusable memory channels after successful proofs:
1. a **Proof Guidance Library** containing distilled plans/repair strategies; and
2. a **Lean-Checked Theorem Library** containing generalized, module-independent formal theorems.

The paper reports a controlled 2x2 ablation on the same 63 Lean tasks. All four configurations use the same language model, generated Lean model, specification and theorem scaffold, with a 40-round budget where each round is one Lean compilation.

Observed contrasts:
- Holding guidance fixed, adding the theorem library raises within-budget coverage from 60 to 63 tasks.
- Without guidance, adding the theorem library raises coverage from 58 to 63.
- Holding the theorem library fixed, adding guidance raises round-10 coverage from 53 to 56 and reduces the rounds needed for full coverage from 29 to 18.
- Without the theorem library, guidance raises round-10 coverage from 43 to 50, but neither configuration reaches full coverage.

The matched vanilla agent in the main table solves 58/63, whereas the full system solves 63/63. On solved-task averages, the full system reports 50.0% fewer proof rounds, 23.2% lower verification time and 16.3% shorter proof LoC than the vanilla agent; token averages are not directly matched because the full system solves harder extra tasks.

Interpretation within tested scope: **machine-checked reusable facts and heuristic reusable guidance play measurably different roles**. The theorem library changes which tasks are reachable under the budget; guidance mainly shortens the search needed to exploit available knowledge. This is stronger causal evidence for proof accumulation than a single monolithic “memory on/off” comparison.

Important limits:
- Domain is parameterized hardware verification, not general mathematics or arbitrary software repositories.
- The system combines hardware-specific planning with library reuse; the 2x2 ablation isolates guidance vs theorem-library access within that substrate, not every possible abstraction mechanism.
- Natural-language guidance is not proof authority; final correctness still comes from Lean.

Primary source: https://arxiv.org/html/2607.27259

## C469 — Rtl2lean independently supports hierarchical kernel-checked lemma pools, but its reuse statistic is weaker causal evidence

Primary source: `Rtl2lean: Automated RTL-to-Lean Translation with Hierarchical Theorem Generation and Lemma Reuse`, arXiv:2607.16855 (2026-07-18).

Rtl2lean builds a four-layer theorem structure spanning combinational semantics, sequential updates, single-cycle behavior, and reachability/invariants. When a high-level property is not discharged by the current base, an LLM proposes intermediate lemmas from the proof context and Lean feedback; only Lean-accepted lemmas enter the reusable pool.

Reported evaluation across six SystemVerilog designs:
- 403 generated theorems, all checked by Lean;
- 358 foundational lemmas;
- 287 described as available for automatic reuse, a reusable-lemma ratio of 80.2%.

This independently supports the architectural claim that a verifier-grounded agent can grow a hierarchical theorem library rather than rediscover local facts repeatedly.

Scope guard: the 80.2% number is a **reusability/availability statistic**, not a matched measurement that 80.2% of later proof work was actually avoided. The accessible primary material does not provide a CircuitProver-style 2x2 causal ablation of reuse versus no reuse. Treat it as supporting architecture/evidence of feasible kernel-checked reuse, not as a quantified general efficiency gain.

Primary source: https://arxiv.org/abs/2607.16855

## New synthesis — make verified reuse an explicit controller action, separate from advisory memory

Vero's repository-level result from the predecessor checkpoint shows that high per-spec success can coexist with failure to close the whole repository. C468 now supplies a concrete mechanism with a controlled ablation: reusable **verified facts** can add within-budget reachability, while reusable **guidance** can reduce search rounds.

A sharper controller design therefore has two explicit durable actions rather than one generic `STORE_MEMORY` action:

- `STORE_VERIFIED_LEMMA`: admit only a Lean-kernel-checked fact, generalized away from incidental local names/assumptions, with exact dependency/version provenance. Its value can include expected future task coverage and repository-closure contribution.
- `STORE_GUIDANCE`: store an advisory decomposition/repair strategy. It can affect ranking/search but grants no proof authority and must remain discardable if it stops helping.

The controller objective should also separate at least three signals:
1. current-obligation verified progress;
2. expected future reuse value of newly verified abstractions;
3. repository-level closure/regression risk.

Proposed matched experiment after the substrate safety gates are trustworthy:
- same base model, Lean snapshot, repository tasks, task order and total real compute budget;
- 2x2 memory ablation: no durable memory / guidance only / verified lemma library only / both;
- fixed leakage guard: a stored lemma or guidance entry becomes visible only after the source task is completed and kernel-readback is recorded;
- report full-repository solves, per-spec coverage, proof rounds, tokens, Lean execution, wall-clock, number of reusable lemmas created, actual downstream lemma hit/use rate, regressions of previously verified obligations, and cost per full repository solve.

This directly tests whether the CircuitProver separation transfers from related hardware tasks to repository-scale formal development without assuming that it will.
