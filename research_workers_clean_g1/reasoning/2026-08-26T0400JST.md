## C56 — OpenProver already exposes a rich typed trajectory substrate for offline heterogeneous-controller learning, but its evaluated run traces are not released in the repository

Primary/public sources and pinned artifact:
- OpenProver paper: `OpenProver: Agentic and Interactive Theorem Proving with Lean 4`, arXiv:2607.09217 / CICM 2026.
- Public repository: `https://github.com/Kripner/openprover`.
- Repository `master` observed at commit `e200251b34349ab6c34548d30319abde86cb6bc6` (2026-07-13).

### Typed action surface

The released `openprover/prompts.py` defines the Planner action vocabulary directly:
- `submit_proof`
- `submit_lean_proof`
- `read_items`
- `write_items`
- `spawn`
- `literature_search`
- `read_theorem`
- `write_whiteboard`

Actions are emitted in a structured `<OPENPROVER_ACTION> ... </OPENPROVER_ACTION>` TOML block. `spawn` contains one or more typed worker tasks; repository reads/writes and Whiteboard replacement have explicit fields. This is substantially cleaner for learning a meta-policy than inferring actions from unconstrained chain-of-thought text.

### Per-step run logging is already suitable for constructing transitions

The released `openprover/inspect.py` parses each run as a sequence of `steps/step_NNN/` directories. Per step it can read:
- `planner_call.md` plus planner retries;
- `workers/worker_N_call.md` and optional search call;
- Lean proof/item attempts and corresponding verification result files.

Each LLM-call archive contains structured frontmatter fields including:
- model;
- call number;
- elapsed milliseconds;
- input/output tokens;
- cache read/write tokens;
- USD cost when available;
- exact system/user prompt;
- thinking/result/error sections.

Therefore a rerun can produce a practical offline dataset with, at minimum, `(compact planner context, typed planner action, worker/tool execution, Lean outcome, token/time/cost)` transitions. Exact verified-artifact reuse and Whiteboard/repository state can additionally be reconstructed from the run directory.

### What is missing from the public release

`scripts/run_proofnet.py` creates a distinct run directory for every theorem and supports token-budget execution, but its top-level OpenProver `results.json` records only theorem status/elapsed/error; it does **not** aggregate action frequency, worker-spawn count, repository/Whiteboard reads, Lean calls, or per-action cost. Moreover, the repository `.gitignore` explicitly excludes `runs/`, and no evaluated ProofNet run directories were found in the public repository during this pass.

Consequently:
- the published 185-ProofNet / 100k-output-token comparison remains a strong free-form-controller baseline;
- but public action-frequency and action-conditioned cost/outcome statistics cannot be recovered from the released repository alone;
- building the desired offline heterogeneous-controller dataset requires either rerunning the benchmark or locating a separately released run artifact that did not surface here.

This narrows a practical implementation gap: **data instrumentation is largely already present; missing public trajectories, not logging design, are the immediate obstacle.**

## C57 — Meta-Reasoner is a direct non-Lean proof-of-principle for compact progress state + contextual-bandit heterogeneous strategy selection

Primary source:
- `Meta-Reasoner: Dynamic Guidance for Optimized Inference-time Reasoning in Large Language Models`, Findings of ACL 2026, DOI 10.18653/v1/2026.findings-acl.649; arXiv:2502.19918.

Mechanism:
- The base model periodically condenses recent reasoning into a lightweight **progress report** rather than feeding the full raw chain as controller state.
- A contextual multi-armed bandit (e.g. LinUCB) selects a high-level strategy conditioned on that report.
- Strategy examples include continue/improve, restart, backtrack to an error point, change decomposition, and propose an alternative approach.
- Reward incorporates progress/correctness/adherence and computation cost; the bandit is updated online.
- The dynamic variant can add/refine strategy arms instead of keeping a fixed set.

Controlled ablation, GPT-4o-mini:
- Game-of-24: full 89%; no progress report/full CoT history 85%; direct LLM arm selection without MAB 82%; CoT without MAB 4%.
- TheoremQA: full 84.13%; no progress report 79.42%; direct arm selection 80.74%; CoT without MAB 39.46%.

Gemini-Exp-1206 shows the same direction:
- Game-of-24 94 / 91 / 87 / 11 for full / no progress report / direct arm selection / CoT.
- TheoremQA 86.32 / 81.78 / 82.14 / 43.12.

Dynamic-vs-fixed bandit on GPT-4o-mini:
- Game-of-24: fixed K=3 65%, fixed K=5 72%, dynamic 89%; dynamic used 14 unique strategies.
- TheoremQA: 72.34%, 79.17%, 84.13%; dynamic used 21 unique strategies.

Interpretation for the Lean frontier:
- This is strong transfer evidence that a **compact meta-state plus learned typed strategy selection** can outperform both raw-history accumulation and asking the LLM to choose the next strategy directly.
- It is especially relevant because OpenProver already exposes a comparable heterogeneous action surface and compact Whiteboard/repository state.
- A Lean version could replace noisy LLM-only progress reward with kernel/verifier-grounded outcomes, exact reusable-artifact success, and measured action cost.

Critical scope:
- Not Lean or formal proof search; no theorem-prover state/kernel feedback.
- Progress/reward evaluation uses LLM-mediated signals, so the reported gains do not establish calibrated action values under formal-verifier distribution shift.
- Actions are textual reasoning strategies rather than heterogeneous tool/substrate actions with exact Lean costs.

Sources:
- https://aclanthology.org/2026.findings-acl.649/
- https://arxiv.org/abs/2502.19918

## C58 — Learned compute purchase can be embedded as a discrete policy action, but current evidence chooses only once at trajectory start

Primary source:
- `Learning When to Think: Adaptive Reasoning for Test-Time Compute Allocation`, arXiv:2608.20256, submitted 2026-08-20.

Mechanism:
- A 1.5B distilled reasoning model emits one of three first-token modes: `NoThink`, `Short`, `Long`.
- The choice is learned end-to-end inside GRPO; there is no separate router.
- Shaped rewards and hard per-mode token caps keep the modes behaviorally distinct and prevent collapse.

Evidence:
- Held-out MATH500 accuracy stays near the base model: 0.782 vs 0.796.
- Mean response length falls from 4,796 to 2,811 tokens: **41% reduction**.
- The policy transfers without retraining; the abstract reports **76% token reduction on GSM8K** with accuracy competitive with similar-length baselines.

Interpretation:
- “Buy more thinking” can be trained as an explicit policy decision rather than a fixed deployment knob.
- For a formal-agent controller this should likely be a higher-level action available alongside `spawn`, `retrieve`, `repair`, `replan`, or stronger-model escalation.

Critical scope:
- The compute mode is selected **once as the first token**, not repeatedly as evidence arrives.
- No Lean state, verifier feedback, retrieval, worker spawning, reusable proof cache, or mid-trajectory escalation is involved.
- Therefore it supports a controller-of-controllers action vocabulary, not the stateful Lean policy itself.

Source: https://arxiv.org/abs/2608.20256

## C59 — Value-of-computation theory warns against routing expensive proof actions by uncertainty or information gain alone

Primary source:
- `Search as Computation Allocation`, arXiv:2607.27871, 2026-07-30.

Theory:
- Costly internal computations are modeled as observations that update beliefs but matter only through terminal decision loss.
- Bellman equations characterize optimal allocation under fixed budgets, priced computation, and exact certification.
- Mutual information equals myopic value of computation only under log loss.
- Under simple regret, value of computation is knowledge-gradient-like; information gain can rank computations arbitrarily poorly, even though a one-sided relationship exists.
- Bandit pulls, tree simulations, and node expansions fit the same computation-allocation abstraction.
- Under an explicit heuristic-error/frontier model, approximate VOC recovers weighted A*, with A* and greedy best-first as limiting cases.

Implication for Lean controller design:
- Do not buy `retrieve`, `verify`, `repair`, `spawn`, `decompose`, or `replan` merely because the action is uncertain or expected to reveal much information.
- The target should be **expected improvement in terminal proof decision/solve probability or reusable verified progress, net of action-specific real cost**.
- This makes prospective `repairability`, future proof cost, cache reuse, and terminal solve value more relevant than generic uncertainty scores alone.

Critical scope:
- Theory paper; no Lean empirical evaluation.
- Exact VOC is generally intractable, so practical controller learning still needs approximations and calibration/off-policy validation.

Source: https://arxiv.org/abs/2607.27871
