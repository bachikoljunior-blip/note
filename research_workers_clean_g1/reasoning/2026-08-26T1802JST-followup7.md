## C296 — initial exploration must not replace an effectful D0 action merely because pure alternatives exist
The first randomized support intentionally excludes checker/tool-bearing actions. That creates a subtle policy-support rule: if deterministic D0's selected action at a decision is effectful/outside the verified pure-reducer class, the behavior policy must execute D0 deterministically at that state rather than silently substitute a structural alternative.

Otherwise the "safe Stage-A logging policy" would cease to be an epsilon perturbation of D0 exactly where D0 chooses an unsupported action, and OPE could not honestly compare back to D0 on those states.

Freeze v0 eligibility:

```text
randomization_eligible(s) =
    D0_action(s) is in verified pure-reducer class
    AND at least one additional verified exploration alternative exists
```

If false:

```text
mu(D0_action | s) = 1
all others = 0
```

Log the full baseline frontier and the reason randomization was disabled.

## C297 — safe alternative support and baseline support are different sets
For an eligible state, construct:

- `baseline_action`: exact D0-selected node, always retained even if its mechanical workspace preview is `WOULD_NOOP` or a deterministic reducer error that current D0 would actually execute;
- `exploration_alternatives`: only prespecified action kinds with verified reducer/recovery contracts and allowed mechanical preconditions;
- `behavior_support = {baseline_action} ∪ exploration_alternatives`, deduplicated, capped at 5 by frozen D0 ranking.

This preserves epsilon=0/current baseline semantics while still allowing the exploration arm to be stricter than legacy frontier validity.

A learned target policy must fall back to D0 whenever it proposes an action outside logged behavior support or outside verified support diagnostics.

## C298 — workspace `WOULD_NOOP` is not a controller-state no-op
The ghost-refine sequence exposes an important modeling distinction. When a selected `REFINE_ARGUMENT` makes no `ProofWorkspace` change, the action runtime has already:

- committed/recorded the selection in the future design;
- consumed and removed that proposal node from frontier/cache;
- associated the consumed proposal batch edge;
- changed which sibling will be selected next.

Thus `WOULD_NOOP` means **no workspace mutation**, not "no causal transition." The controller state `(workspace, durable proposal set, consumed-set/history, budget)` changes even when `workspace.version` does not.

Rename/represent transition preview as separate dimensions, e.g.:

```text
workspace_transition = MUTATE | NO_MUTATION | ERROR
proposal_consumption = CONSUME_SELECTED
external_effect = NONE | CHECKER | PROVIDER | ...
```

Do not collapse these into one `no_effect` label.

## C299 — recovery state is `(workspace snapshot + durable proposal batches + consumption history)`, not workspace alone
`WorkspaceSnapshotV0` is necessary for reducer replay but insufficient to recover the scheduler after a no-workspace-mutation selection. The recovered cache/frontier must additionally know which durable proposal envelopes have already been consumed.

Therefore authoritative recovery inputs are:

1. content-addressed finalized proposal batches/envelopes;
2. append-only proposal-consumption edges / decisions;
3. exact workspace snapshot;
4. pinned frontier/config policy;
5. durable budget/effect state.

Cache/frontier are derived from this tuple. Replaying from workspace alone would resurrect consumed ghost proposals and change behavior.

## C300 — Stage-A coverage metrics should measure randomizable decisions, not only task-level multiplicity

## C301 — exact propensity contract under mixed deterministic/randomized states

