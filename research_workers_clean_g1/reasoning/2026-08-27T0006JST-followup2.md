## C394 — production policy compiler flags are part of authorization semantics, not mere build metadata

**Observed.** SELinux Common Intermediate Language (CIL) is a real production intermediate policy language compiled by `secilc` to a kernel binary policy. The current CIL documentation exposes compiler-enforced `neverallow` / `neverallowx` checks, but also documents a `-N` / `--disable-neverallow` option that disables those checks. The SELinux `checkpolicy`/`secilc` toolchain also exposes `handle_unknown` modes such as `allow`, `deny`, or `reject`, and policy-version / MLS-related compilation parameters.

Public sources:
- https://github.com/SELinuxProject/selinux/wiki/High-Level-Language-Infrastructure
- https://man7.org/linux/man-pages/man8/checkpolicy.8.html
- https://github.com/SELinuxProject/selinux/blob/main/secilc/docs/cil_access_vector_rules.md
- https://manpages.debian.org/unstable/secilc/secil2conf.8.en.html

**Inference.** Two builds of the same policy text under different compiler flags can have materially different safety/authorization meaning. Therefore a policy identity suitable for runtime authorization cannot be just `source_policy_hash` or `compiled_binary_hash`. The activation certificate must bind the exact **semantic build tuple**, including compiler version and all flags/configuration that can alter policy acceptance or unknown-action handling.

New hard bindings/regressions:
- `policy_activation.compiler_binary_digest/version`;
- `policy_activation.compiler_flag_digest`;
- `policy_activation.target_policy_version`;
- `policy_activation.handle_unknown_mode`;
- `policy_activation.mls_or_equivalent_semantic_mode`;
- `disable_neverallow_flag_change_invalidates_activation`;
- `handle_unknown_mode_change_invalidates_activation`;
- `same_source_hash_different_semantic_build_tuple_is_distinct_policy_identity`.

**Scope guard.** This is direct evidence that build configuration is security-semantic in SELinux; it does not imply every policy compiler has equivalent flags.

## C395 — verified source-policy analysis exists for XACML, but it is not a verified deployment compiler

**Observed.** St-Martin and Felty formally verified in Coq a sound-and-complete algorithm for detecting conflicts in a substantial subset of XACML access-control rules, including richer constructs such as ranges and Boolean combinations. The result is a verified **analysis**: it returns conflicting rule pairs. It does not establish that a production XACML policy-decision implementation, serializer/parser, or compiler is equivalent to a certified semantic core.

Primary sources:
- https://www.site.uottawa.ca/~afelty/dist/cpp16.pdf
- https://dl.acm.org/doi/10.1145/2854065.2854079

**Inference.** Certification must be typed by what is actually proved. A verified conflict analyzer can be an activation-time static check, but it must not be promoted into `evaluator_verified=true` or `deployment_compiler_verified=true`. The certificate should carry **claim-scoped evidence kinds** rather than a single assurance level.

Proposed `PolicyEvidenceClaimV0` fields:
- `claim_kind`: e.g. `parser_correctness`, `evaluation_semantics`, `conflict_detection_sound_complete`, `compiler_refinement`, `production_correspondence`, `runtime_complete_mediation`;
- `artifact_digest`;
- `proof/checker identity` or test evidence;
- `supported_language_fragment`;
- `assumptions`;
- `version/config tuple`;
- `scope_digest`.

New regression:
`verified_static_analysis_cannot_satisfy_unrelated_runtime_or_compiler_claim`.

## C396 — a certified semantic core plus an unverified production compiler still needs an explicit correspondence edge

**Observed synthesis.** ACCPL and TEpla provide machine-checked policy semantics/properties; Cedar provides a mechanized semantic model plus strong differential correspondence testing; SELinux CIL provides a real compiler pipeline whose flags alter semantic behavior; XACML has verified static analyses for selected policy properties. These are complementary components, but no source found in this targeted search collapses all four into a single end-to-end theorem from human-oriented policy source through production compiler into a live effect-authorizing runtime.

**Inference.** The deployment contract should be decomposed into explicit independently checked claims:

`source faithfulness -> certified semantic IR -> certified/validated source-to-IR translation -> production compiler correspondence -> exact build config -> runtime complete mediation -> per-effect authorization`.

This decomposition is valuable because a real system can legitimately have mixed evidence: theorem-level semantics, translation-validation for one compiler pass, differential testing for another boundary, and deterministic runtime interception. `PolicyActivationCertificateV1` should represent this honestly rather than flattening everything to “verified/not verified.”
