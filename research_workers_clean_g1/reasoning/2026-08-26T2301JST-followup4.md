## C381 — the latest EP authorization-receipt draft independently converges on exact-action, exact-policy, freshness, and consume-once binding

**Observed.** The latest version found in this invocation, `draft-schrock-ep-authorization-receipts-08` (published 21 July 2026), is explicitly an Internet-Draft rather than an IETF standard. Its Authorization Context binds an `action_hash`, `policy_id`, exact `policy_hash`, initiator, approver, a high-entropy nonce, issued/expiry times, and receipt-chain state. It requires a policy-hash match to the exact evaluated policy version and uses the nonce as the consumption/freshness key. It also requires an approval to be cryptographically bound to one exact action.

Source:

## C382 — one-time authorization is only as global as the shared atomic consumption domain

**Observed.** Version 08 narrows the one-time-consumption claim: an authorization reaches a terminal state at most once **within the executor's shared atomic consumption domain**. A second presentation inside that domain must be rejected, but an offline receipt alone cannot prove that an independent executor with separate state did not also consume it. The draft's formal invariant is therefore scoped to the shared consumption store rather than claiming universal global uniqueness.

Source:
- https://www.ietf.org/archive/id/draft-schrock-ep-authorization-receipts-08.html

**Inference.** A bare nonce is insufficient for `ExecutionAuthorizationWitnessV0`. The witness and journal need a named/versioned `consumption_domain_id` and atomic state transition whose durable record joins the exact authorization witness to the exact effect execution. Cross-runtime deployments need either a shared consumption authority/store or a higher-level coordination protocol; local `consumed=true` cannot truthfully claim global one-time execution.

New regressions:
- `same_nonce_second_consume_in_domain_is_rejected`;
- `independent_consumption_domain_cannot_be_claimed_globally_unique`;
- `effect_commit_and_witness_consumption_are_atomic_or_recoverably_linked`.

## C383 — canonical JSON/action-receipt hashes are useful audit joins but do not replace the semantic authorization-request digest

**Observed.** `draft-farley-acta-signed-receipts-02` was announced 28 June 2026 as an Internet-Draft for signed machine-to-machine decision receipts. Its current published family defines JCS-canonicalized signed decision payloads, an optional `payload_digest` for associated tool input/output, and an `action_ref` computed from a canonical action representation for cross-engine correlation. The receipt format is aimed at auditability/offline verification of decisions and tool activity.

Sources:
- https://mailarchive.ietf.org/arch/msg/i-d-announce/Zt4Hmw7ZCV2eKQGwwaa7TTHFswI/
- https://datatracker.ietf.org/doc/draft-farley-acta-signed-receipts/
- https://www.ietf.org/archive/id/draft-farley-acta-signed-receipts-02.html

**Inference.** Keep two linked identities rather than collapsing them:
1. a transport/audit action identity derived from the exact dispatched tool-call representation or canonical receipt preimage;
2. the semantic authorization-request digest after trusted typed normalization/lowering (for example the canonical Cedar request + entities/context/schema epoch).

The former is valuable for correlating systems and proving what bytes/action representation were logged. The latter is needed to prove what authorization semantics were actually evaluated. JSON canonicalization does not repair an incorrect schema lowering, omitted typed context, or request-to-dispatch mismatch.

**Scope guard.** The Farley document is also an Internet-Draft, not a standard. Its `action_ref` preimage is not assumed here to bind every grant-relevant argument in every runtime; exact effect binding remains a local hard requirement.

## C384 — separate pre-execution authority evidence from post-execution audit evidence

**Observed.** The latest EP draft explicitly distinguishes its pre-execution authorization role from post-hoc receiver-attested logging: a complete deployment can benefit from both, but the latter records what the receiver observed after execution and does not itself create prior authorization.

Source:
- https://www.ietf.org/archive/id/draft-schrock-ep-authorization-receipts-08.html

**Inference.** Refine the causal chain to:

`delegation/identity facts -> PolicyActivationCertificate -> pre-dispatch ExecutionAuthorizationWitness -> atomic consumption/effect commit -> EffectReceipt -> optional OutputReleaseAuthorizationWitness -> output-release receipt`.

A signed `EffectReceipt` can prove or strengthen audit evidence about what happened; it must never be accepted as retrospective authority for an effect that lacked a valid pre-dispatch witness.
