## C65 — A direct learned heterogeneous LLM-harness controller now exists; the remaining gap is Lean-specific rather than general-agent-specific

Primary paper: Haiwen Yi, Xinyuan Song, *Learning to Control LLM Agent Harnesses with Offline Reinforcement Learning*, arXiv:2607.05458, 2026-07-05: https://arxiv.org/abs/2607.05458

Primary public code, pinned main observed at `5d577632ef4803f819125fc9ef9ef9dd257c077d`: https://github.com/Hik289/Agentic-RL-harness

This paper is unusually close to the open Lean-controller frontier. It freezes the LLM executor and learns the **outer execution harness** as a finite-horizon MDP. A lightweight controller selects structural actions from state metadata rather than changing the LLM itself. It is trained offline with advantage-weighted regression from terminal task-rubric rewards. The abstract reports consistent improvements in verification behavior and selective final-quality gains across six controlled domains plus adapted tau-bench retail and AgentBench DB-Bench; public paper summaries report roughly `+18.2 pp` on adapted tau-bench retail and `+13.2 pp` on adapted DB-Bench. Ablations against behavior cloning and Forced CHECK indicate the effect is not simply imitation or always-verifying.

The code confirms the controller is genuinely structural rather than token-level:
- `code/rl/state_features.py` uses an 18-dimensional coding state: normalized step, draft presence/length, rubric coverage/missing criteria, error count, cost used, remaining steps, last-test pass/failure information, and one-hot previous action.
- coding action space: `read_problem`, `inspect_code`, `write_code`, `run_tests`, `debug_error`, `revise_code`, `check_rubric`, `submit`.
- `code/rl/generic_harness.py` uses domain-specific structural actions such as search/open/extract/compare/draft/cite/check/submit, multi-tool calls, memory retrieval/comparison, planning/verification/revision, all behind explicit action masks.
- `code/rl/policy.py` is a 1-hidden-layer 64-unit MLP producing masked categorical action probabilities; invalid actions are zeroed and renormalized.
- `code/rl/offline_aw.py` trains with advantage-weighted cross entropy plus entropy regularization. All steps in a trajectory inherit the same clipped terminal-advantage weight.
- `examples/running_main_driver.py` collects training data using an epsilon-perturbed baseline (`eps=0.25` by default), then trains/evaluates the AW controller. The code reports a standard collect → train → evaluate protocol and paired bootstrap comparison.

This materially changes the research map: **planner/harness-level heterogeneous action learning is demonstrated for frozen LLM agents.** The unresolved question is now whether deterministic formal verification, proof-state structure, persistent verified lemma caches, compiler feedback, and proof-specific real costs make the same idea stronger or require a different controller in Lean.

Scope guard: this is an arXiv/workshop-era general-agent result, not a Lean theorem-proving evaluation. Public benchmark adapters are adapted settings, not necessarily official leaderboard protocols. Do not transfer the reported percentage-point gains to formal proving.

## C66 — The Agentic-RL-harness epsilon behavior policy is a directly reusable data-collection template because its action propensities are reconstructable, unlike free-form OpenProver planning

The public generic harness defines

- base structural policy sequence per domain;
- legal-action mask from current logged state;
- epsilon perturbation: with probability `eps`, sample uniformly from currently legal actions; otherwise take the deterministic base action;
- default main-driver `eps=0.25`.

Therefore, for a state with `L` legal actions and legal deterministic base action `b`, the exact behavior propensity is reconstructable as

- `mu(b|s) = (1-eps) + eps/L`,
- `mu(a|s) = eps/L` for each other legal action `a`.

If the deterministic base action is unavailable, the code's fallback rule is also deterministic from the logged action mask and step, so the propensity remains reconstructable. This is much better suited to IPS/DR diagnostics than a free-form LLM Planner whose parsed TOML action does not come with a probability over the meta-action vocabulary.

Lean experiment consequence: **do not randomize the LLM text directly.** Put a typed policy layer outside the executor, enumerate a safe eligible action set, use a known epsilon/mixed behavior policy over that set, and log the mask + chosen action + exact probability. The executor then realizes the selected action. This preserves OPE identifiability and makes exact exploration cost controllable.

However, uniform epsilon exploration can waste proof budget when the legal action set contains actions with very unequal cost/risk. The next step should compare uniform epsilon with logging-policy designs that allocate exploration by target/OPE value or constrained Neyman-like principles, while maintaining minimum support.

## C67 — The harness paper exposes a useful credit-assignment weakness that Lean can improve: every step inherits one terminal trajectory advantage

`offline_aw.py` computes `A_i = G_i - mean_task_return`, then assigns the same `exp(A_i/beta)` weight to **every state-action step** in trajectory `i`. This is simple, stable and sufficient to move process behavior in the paper's tested domains, but it cannot tell which individual structural action caused the terminal success/failure.

Lean has unusually strong intermediate supervision that can improve this without an LLM judge:
- new kernel-verified lemma/item appeared;
- compiler error class changed or proof state progressed;
- a previously failing subgoal became closed;
- reusable proof DAG/cache grew;
- a complete proof passed the theorem-integrity guard and kernel verifier.

Therefore a Lean controller should compare at least three credit schemes under the same logged trajectories:
1. paper-style **trajectory AW** using terminal verified solve/score only;
2. **potential/progress-shaped AW/value targets** using strictly verifier-grounded reusable progress, with shaping defined so it does not reward superficial action patterns;
3. sequential value learning/FQE/DR where coverage permits.

Important negative lesson from the harness paper itself: process diagnostics such as Harness Maturity Score are kept post-hoc rather than directly optimized. For Lean, `verify often`, `spawn often`, or `repair often` must likewise remain diagnostics unless shown to improve terminal verified outcomes; otherwise the controller can learn ritualized checking rather than proof progress.

## C68 — Partial observability turns compact-state design into an OPE-identifiability requirement, not just a context-efficiency choice

Recent OPE theory strengthens the need to separate the controller state from raw hidden LLM reasoning.

Sources:
- Yuheng Zhang, Nan Jiang, *Statistical Tractability of Off-Policy Evaluation of History-Dependent Policies in POMDPs*, ICLR 2025 (OpenReview id `Qja5s0K3VX`). The paper establishes hardness for general history-dependent target policies under partial observability and studies coverage conditions needed for tractable cases.
- Hongyi Zhou et al., *Demystifying the Paradox of Importance Sampling with an Estimated History-Dependent Behavior Policy in Off-Policy Evaluation*, ICML 2025: https://proceedings.mlr.press/v267/zhou25f.html. Estimating behavior policy with longer history decreases asymptotic variance but increases finite-sample bias; the result extends beyond ordinary IS to sequential IS, doubly robust and marginalized IS.
- Tennenholtz et al., *Off-Policy Evaluation in Partially Observable Environments*, AAAI 2020: https://ojs.aaai.org/index.php/AAAI/article/view/6590 — general partial observability can introduce arbitrarily large OPE errors without additional structure.

Design consequence: define the learned Lean controller as explicitly **observation-Markov over a logged compact structural state** (proof/subgoal progress, verifier outcomes, verified cache/DAG summary, retrieval state, cost/budget, previous action, model/tool status). The LLM executor may reason internally, but hidden chain-of-thought must not silently become an unlogged control-state variable. If meta-action selection itself depends on hidden free-form reasoning that is not represented in the logged state/probability, counterfactual evaluation becomes much harder.

This also gives a new reason not to feed the entire raw proof history into the controller. More history can change the bias/variance properties of estimated behavior models, and arbitrary history-dependent policies in POMDPs can be statistically difficult. Prefer a deliberately defined compact state whose sufficiency can be ablated and whose action propensities are exactly recorded.

## C69 — The general learned-harness result gives a strong Lean implementation starting point, but its state/action design should be enriched only where deterministic formal feedback justifies it

A minimal Lean adaptation can stay close to the successful general harness rather than jumping immediately to a large neural controller:

**Compact state v0**
- normalized step / remaining verifier-call and token budget;
- active goals/subgoals count and depth summary;
- verified reusable item/cache count and recent delta;
- most recent Lean result class (success / syntax / elaboration / type / timeout / unresolved goal) and repeated-error count;
- progress estimate / remaining-step value if available;
- retrieval coverage/last-retrieval result;
- current model/tier and worker count;
- last structural action one-hot;
- cumulative planner/worker/verifier tokens, Lean time and wall-clock.

**Typed action v0**
- `continue_local` / generate next proof attempt;
- `repair_current`;
- `retrieve_local`;
- `retrieve_global` or route-level re-retrieval;
- `decompose/replan`;
- `spawn_branch` (bounded worker count);
- `escalate_model_or_search_budget`;
- `backtrack/restart`;
- `submit/stop`.

**Hard action masks**
- no `submit` unless theorem-integrity + Lean verification can be executed;
- no repair without a current failed artifact/error;
- no escalation past budget/cap;
- no duplicate branch when a semantically identical verified/current state is already cached;
- no retrieval repetition when the exact query/source state is unchanged unless an explicit reretrieval trigger fires.

Start with a small MLP or calibrated tree/linear policy and compare against the exact free-form Planner and rules. Only increase controller capacity after an ablation demonstrates state aliasing or nonlinear benefit. This mirrors the general harness evidence: a lightweight controller can change execution quality without changing the executor.

## Updated frontier

1. **Lean Harness-MDP adaptation:** map OpenProver's actual planner actions and Lean worker tools into a typed outer policy while keeping the executor frozen; preserve the free-form Planner as a matched baseline.
2. **Behavior logging:** use reconstructable epsilon/mixed exploration over safe eligible Lean meta-actions; log mask and exact propensity. Compare uniform epsilon with OPE-aware logging-policy design.
3. **Compact-state sufficiency:** build v0 structural state without hidden CoT; ablate added features (error class, progress/value, retrieval, cost, cache/DAG, model tier) and test state aliasing/OPE coverage.
4. **Credit assignment:** terminal-only AW versus verifier-grounded potential/progress targets versus sequential value/OPE estimators; never optimize ritual process metrics directly.
5. **Conservative deployment:** learned action only where coverage/value confidence is adequate; otherwise baseline bootstrap. Report abstention/baseline-use frequency.
6. **Sequential OPE under partial observability:** use exact propensities where possible; compare DR/TDR/FQE/coverage diagnostics, and refuse numeric policy ranking where support is inadequate.
7. **Mid-trajectory compute purchase:** integrate `escalate_model/search/workers` as typed actions and learn their marginal value under real cost.
8. Continue prior proof-specific branches: subgoal scheduling, semantic branching+repair, triggered re-retrieval, snapshot reuse, calibration under shift and benchmark/harness robustness.

The broad 'learnable harness exists?' gap is now closed by C65 for general LLM agents. The important open question is the **Lean-specific matched, verifier-grounded, OPE-identifiable controller**.
