## C178 — use WAL + synchronous=FULL for the first causal journal, while keeping the durability claim scoped

Current SQLite documentation states that in WAL mode `synchronous=FULL` adds a WAL sync after each transaction commit and provides ACID durability across application/OS crash or power loss under SQLite's VFS/storage assumptions. `synchronous=NORMAL` keeps consistency but may lose a just-committed transaction after power loss. Official docs also warn that SQLite must trust the filesystem/hardware implementation of sync.

Therefore Stage-A v0 should freeze:

- `PRAGMA journal_mode=WAL;`
- `PRAGMA synchronous=FULL;`
- `PRAGMA foreign_keys=ON;`
- a fixed SQLite library/runtime version in each journal header/receipt;
- one controller writer per journal file for the initial experiment;
- integrity check in crash-recovery tests.

This strengthens the prior local `os._exit` smoke test but does not turn it into a universal hardware power-loss proof.

Sources: https://sqlite.org/pragma.html and https://www.sqlite.org/wal.html (retrieved 2026-08-26).

## C179 — canonical append-only schema can stay small

A minimal SQLite schema sufficient for Stage-A collection:

```sql
CREATE TABLE journal_event (
  event_id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,
  decision_id TEXT,
  run_seq INTEGER NOT NULL,
  event_type TEXT NOT NULL CHECK (
    event_type IN ('execution_decision','proposal_batch_consumption','execution_outcome')
  ),
  schema_version INTEGER NOT NULL,
  payload_json BLOB NOT NULL,
  payload_sha256 BLOB NOT NULL,
  created_monotonic_ns INTEGER,
  UNIQUE (run_id, run_seq),
  UNIQUE (decision_id, event_type)
) STRICT;

CREATE TRIGGER journal_event_no_update
BEFORE UPDATE ON journal_event BEGIN SELECT RAISE(ABORT,'append_only'); END;
CREATE TRIGGER journal_event_no_delete
BEFORE DELETE ON journal_event BEGIN SELECT RAISE(ABORT,'append_only'); END;
```

`created_monotonic_ns` is diagnostic only and never establishes cross-process chronology or policy state. Logical chronology comes from `run_seq` plus transaction boundaries. A generated-proposal selection inserts `execution_decision` and its optional `proposal_batch_consumption` in the same transaction with consecutive sequence numbers. The outcome is a later transaction. The writer reads back inserted row ids/hashes before allowing the corresponding effect boundary.

A separate immutable `journal_meta` row/file header should pin schema version, controller source revision, feature-manifest digest, journal mode, synchronous mode and SQLite runtime version. It must not contain learned outcomes or mutable policy semantics.

## C180 — canonical event payloads should avoid floating-point ambiguity; log propensities exactly

Canonical JSON bytes for hashing/replay:

- UTF-8, sorted object keys, no insignificant whitespace;
- arrays retain semantic order (especially the D0-ranked choice set);
- booleans/null/integers only for exact protocol fields when possible;
- digests are lowercase hex strings;
- no NaN/Infinity;
- probabilities and epsilon are stored as reduced rational integer pairs `{num, den}`, not binary floats;
- measured real-valued costs remain source observations, but canonicalize their decimal representation once at ingestion and retain measurement-status/source metadata.

For the logging policy below, exact behavior probabilities are rational by construction and therefore reconstructable without float tolerance.

## C181 — recovery reader is deliberately conservative

For each `run_id`, parse `run_seq` strictly increasing and enforce:

1. A decision must have exactly one selected node included in its frozen choice set and exact behavior propensity >0.
2. `proposal_batch_consumption`, if present, must immediately belong to the preceding decision and match that decision's selected node/batch id.
3. An outcome must reference an earlier unmatched decision in the same run and may occur only once.
4. A new decision after an unmatched prior decision is invalid for Stage-A randomized data; collection runtime should stop before creating this state.
5. Exact duplicate `event_id` + canonical payload is idempotent; same id with a different payload/hash is a hard conflict and invalidates the affected run from policy/value estimation.
6. A committed decision with no committed outcome is `censored`. Never synthesize reward=0, cost=0 or failure.
7. If no separate durable effect receipt exists, the reader does not guess whether an unmatched action executed. It reports effect status `unknown`.
8. Provider-generation ledger events can exist without any execution decision; they remain run-level/upstream cost evidence rather than a fabricated action transition.

The event reader should materialize two datasets rather than one overloaded table: (a) behavior-decision rows, including censored rows for BC/support diagnostics; (b) matched transition rows for reward/value/OPE estimators that require outcomes. Any estimator that can correctly use censoring must opt in explicitly rather than receiving zero-imputed rows.

## C182 — freeze a first safe-epsilon protocol before randomized outcomes: epsilon=1/4, at most 5 randomized candidates

Stage-A logging-policy v0 design choice:

- Start from the deterministic D0 ordering after the hard legal/budget mask.
- Let `L = min(number of effective legal candidates, 5)`.
- The randomized pool is the first `L` D0-ranked candidates. Actions outside this pool are **not in the support of v0** and cannot later be selected by an offline target policy evaluated from this dataset.
- If `L=1`, choose it with probability 1.
- If `L>=2`, epsilon-greedy with exact `epsilon=1/4`:
  - D0 top action: `mu = 3/4 + (1/4)/L = (3L+1)/(4L)`;
  - each other pooled action: `mu = 1/(4L)`.
- Therefore the minimum behavior propensity is `1/20=0.05` and the maximum importance ratio of any deterministic target action that stays inside observed pool support is at most 20.
- Store the full pool, excluded-but-legal count, exact rational `mu` vector, RNG algorithm/version and sampled index in `execution_decision`; never infer propensity later from current code.

This is an **experimental protocol choice**, not a claim that epsilon=0.25 or K=5 is universally optimal. Its point is to make support/auditability explicit before rewards are seen. If the deterministic provider pilot later shows that many meaningful Stage-A choices occur below D0 rank 5, do not quietly enlarge the pool in-place; create a new logging-policy version and analyze it separately.

## C183 — deficient support is handled by target-policy restriction and deterministic fallback, not reward extrapolation

Contextual-bandit OPE requires overlap for ordinary importance-weighted/DR estimators; support-deficient logging can fail badly. Published work explicitly treats restricting the action/policy space as one principled response to deficient support. Therefore Stage-A v0 should use the simplest auditable rule:

- OPE target policies must put zero probability on actions outside the logged v0 pool for that state/protocol version.
- Outside that support at deployment time, fall back to D0 rather than extrapolating a learned controller's value.
- Always report behavior-propensity histogram, maximum importance weight, normalized effective sample size `ESS=(sum w)^2/sum(w^2)`, support-violation count and target-policy fallback rate.
- Prefer DR/self-normalized/shrinkage estimates as sensitivity analyses, but no estimator is allowed to convert zero support into observed evidence.
- For policy selection/deployment, pair point estimates with confidence bounds; offline policy selection is blocked when support violations occur in the evaluated target path.

Method sources: Sachdeva, Su & Joachims, *Off-policy Bandits with Deficient Support* (2020); Wang, Agarwal & Dudik, *Optimal and Adaptive Off-policy Evaluation in Contextual Bandits* (ICML 2017); Su et al., *Doubly Robust Off-policy Evaluation with Shrinkage* (ICML 2020); Karampatziakis, Mineiro & Ramdas, *Off-Policy Confidence Sequences* (ICML 2021).

## C184 — Stage-A evaluation should be Pareto/constrained first, scalar reward only as a training implementation detail

Prespecified raw outcomes per theorem/task:

- terminal kernel-verified success;
- reusable local verified progress events;
- input/output/reasoning/billed tokens;
- API charge;
- checker CPU/wall time if measured;
- total wall time;
- provider proposal-generation cost, selected execution cost and final assembly cost as distinct scopes.

Primary comparisons should use success under matched fixed resource budgets and the resulting success-vs-cost curves, plus cost per solved theorem. Report Pareto dominance across the separate cost dimensions. A learned policy is not declared better merely because one arbitrary scalarization improves.

Training implementations may use prespecified scalar utilities or Q targets, but evaluation always returns to the raw layers above. Where two policies trade success against different costs, report the tradeoff rather than force a universal winner. Hypervolume or area-under-budget-curve may be secondary summaries only after the component curves are shown.
