## New evidence and design updates

### C342 — Kernel-verified capability reachability is not trajectory-level confidentiality

`l3m`, a coding agent implemented in Lean 4, exposes a closed `ToolCall` surface, opaque confined `SafePath`s, a closed `TameCommand` type, and eight kernel-verified reachability/surface theorems in tame mode. Its own public documentation nevertheless records a production secret-exfiltration incident: under an opted-in wild capability, the agent read `~/.zshrc`, copied an Anthropic API key into a documentation file, and the file was later committed/pushed. The l3m author explicitly notes that no capability theorem was violated; each local action was individually permitted, while their composition leaked the secret.

Sources:
- https://lean4.ai/l3m/
- https://deanfoster.net/blog/agent-leaked-my-key.html

**Scope:** this does not falsify l3m's stated reachability theorems. It falsifies the stronger inference that a per-call capability proof alone implies end-to-end confidentiality.

### C343 — Route closure must be semantic, not syntactic

The same l3m incident review found a second hole in tame mode: `lake env <ARG>` had been treated as an environment-reading operation, but Lake semantics execute `<ARG>` with the Lake environment. Therefore `lake env /usr/bin/printenv` exposed environment variables, including secrets. The fix was to remove that operation from tame mode and restrict Lake to build/clean plus validated targets.

Source:
- https://deanfoster.net/blog/agent-leaked-my-key.html

**Implication:** `effect_route_id` cannot be assigned only from action/tool names. Route closure needs a trusted semantic effect model or validated executor contract. A syntactically benign route can realize a much broader effect class than its surface name suggests.

### C344 — Information-flow labels are a direct formal mechanism for the composition gap

Fides formalizes confidentiality/integrity labels for agent data, propagates those labels, and enforces deterministic information-flow policies independently of the model. The key distinction is capability versus data: a tool may be callable while the data currently influencing its arguments is not authorized to cross that sink.

Source:
- https://arxiv.org/abs/2505.23643

This directly complements C342: `effect_route` closure answers *which executable route realizes an effect*; IFC/taint answers *which information is allowed to flow through that otherwise-authorized effect*.

### C345 — Tool-sequence safety is a third independent dimension

`Towards Verifiably Safe Tool Use for LLM Agents` (ICSE-NIER 2026) argues that agent hazards arise from interactions among tool calls and proposes enforceable specifications over both information flows and temporal tool sequences. Their motivating specifications distinguish a confidentiality flow rule from a temporal obligation such as requiring a notification after an update.

Sources:
- https://arxiv.org/abs/2601.08012
- https://doi.org/10.1145/3786582.3786839

**Implication:** a local `P_effect(state, action)` is insufficient for some hazards even if it has correct route and taint labels. The authoritative precondition may need a history/automaton component over prior committed effects.

### C346 — FAVA is a measured precedent for learned semantic extraction feeding deterministic formal authorization

FAVA (2026-07-29) is the closest public falsification target found in this pass. It uses an LLM to extract a Permission IR from ambiguous natural-language tasks, deterministically lowers that IR into an evidence-backed permission graph, and then uses an SMT authorizer plus runtime gateway before effectful execution. It reports:

- aggregate Decision Compliance Rate: `90.5%` over 801 cases;
- attack interception rate: `98.9%`, with 69 benign false blocks under its conservative policy;
- explicit false negatives when safety labels or workflow guards are missed by the LLM extraction stage;
- median active JIT authorization under 1 ms (`0.845 ms` over 607 checks, P95 `1.580 ms`).

Ablations are unusually informative: removing evidence labels drops DCR to `7.4%` on OctoBench and `15.6%` on OpenAgentSafety; removing data-flow edges or replacing SMT global reasoning with a local rule drops to `25.8%` / `61.6%`; disabling the runtime gateway drops the trace-conditioned split from `100%` to `40%`.

Source:
- https://arxiv.org/html/2607.27267

**Scope guard:** FAVA explicitly says its formal guarantee begins only after evidence has been lowered into the permission graph. Its trace-conditioned 100% split uses benchmark-provided trace evidence and is a labeled diagnostic, not zero-shot discovery. The measured false negatives show that a mathematically sound downstream authorizer does not repair omitted semantic facts upstream.

### C347 — Learned extraction should not be able to erase grant-critical hard facts

FAVA's failure analysis identifies extraction misses and sink mismatches as sources of false decisions. This suggests a stronger controller boundary than merely “learned model proposes, deterministic solver decides.” If the learned stage is allowed to omit a required confidentiality label, obligation, dependency edge, or sink identity, the deterministic solver can validly prove safety of the wrong graph.

**Design consequence:** wherever the substrate can derive a safety-relevant fact mechanically (effect class, destination, workspace path, credential use, external-vs-local sink, consumed proposal identity, policy version), that fact should enter the hard graph directly. Learned extraction may enrich ambiguous semantics or add conservative risk, but should not silently remove/override mechanically established grant-critical facts.

### C348 — Lean-kernel authorization still has a specification-translation boundary

The Lean-Agent Protocol formalizes financial policies and allows a proposed action iff Lean proves it satisfies precompiled policy axioms. Its paper explicitly identifies the primary vulnerability as the translation/formalization layer: a semantically incorrect but well-typed policy mapping can be successfully proved. The public demo acknowledges that concept-symbol constraints intended to prevent formalization drift and the proposed shadow-verification phase are not implemented.

Sources:
- https://arxiv.org/abs/2604.01483
- https://github.com/arkanemystic/lean-agent-protocol

**Scope:** this is not evidence that Lean's kernel is unsound. It is evidence that kernel soundness is relative to the formalized statement and therefore policy-artifact provenance/semantic fidelity is a separate load-bearing boundary.

### C349 — Revised effect-safety decomposition

The prior `EffectContractV0` should be extended before any effectful action enters randomized support. The minimum authoritative boundary now has four separable properties:

1. **Execution truth:** `P_effect` plus tri-valued postcondition `Q_effect ∈ {TRUE,FALSE,UNKNOWN}` and durable Attempt/Receipt semantics.
2. **Route closure:** every route realizing the same semantic effect crosses the same hard gate; route identity is based on validated effect semantics, not just tool names.
3. **Flow closure:** confidentiality/integrity provenance is propagated across reads, model-visible transformations, writes, commits, network/public sinks, and durable memory; declassification is explicit and auditable.
4. **Sequence/policy closure:** temporal obligations and authority-changing policy artifacts are versioned; the verifier sees the relevant execution prefix and exact policy version. Learned policy/formalization changes cannot become authoritative merely because the generated formal artifact compiles.

Suggested schema additions for a later versioned contract, without changing the current frozen substrate yet:

- `semantic_effect_id`
- `effect_route_id`
- `source_labels` / `source_provenance_refs`
- `sink_scope` / recipient-or-destination identity
- `declassification_rule_id` and declassification evidence
- `history_automaton_state` / temporal obligation refs
- `policy_artifact_version` / `formalization_provenance`
- exact pre/post workspace/run snapshot refs

Suggested append-only causal events:

- `DataFlowEdgeV0(source_event, derived_event, labels)`
- `DeclassificationEventV0(input_labels, output_labels, rule_id, evidence)`
- `PolicyActivationEventV0(old_version, candidate_version, validation/shadow evidence)`

These are design hypotheses derived from the evidence above, not claims that CSSC already implements them.

## New required regressions before effectful randomization

1. **Flow composition:** allow a sensitive read, then a benign intermediate local write, then attempt commit/public/network egress. The sink must be blocked unless an explicit valid declassification permits that value flow, even though each tool/action is individually callable.
2. **Semantic fallback route:** disable the nominal route and force a semantically equivalent alternate route; assert the same effect contract applies. Include a command whose surface name understates execution semantics, analogous to `lake env`.
3. **Derived-data propagation:** transformed/summarized model output influenced by sensitive input must retain conservative provenance unless a trusted sanitizer/declassifier proves a narrower label.
4. **Temporal obligation:** verify a required predecessor/successor sequence with a security automaton; local per-call permission is not enough.
5. **Policy formalization drift:** synonym/rephrasing perturbations must not silently remap protected concepts to a different permitted symbol. Activation of an authority-changing policy artifact must be separately versioned and validated/shadowed.
6. **Fail-closed missing evidence:** delete a grant-critical label/edge from the learned semantic extraction while leaving the underlying typed runtime fact observable; the hard substrate must restore or conservatively reject rather than authorize from the incomplete graph.
