## New findings

### C107 — current CSSC traces preserve ordered scheduling metadata only at *run completion*; they are not event-sourced decision trajectories

`_StructuredRunState` accumulates `proposal_cache_events` in memory. `build_structured_result(...)` places the complete tuple into `ControllerResult.metadata`. `JsonlTraceStore.append_result(...)` is then called on a completed result and emits a `run_summary`, optional final `workspace_snapshot`, optional final `cost_ledger_snapshot`, and attempt rows. `_summary_metadata(...)` removes only `workspace` and `cost_ledger`, so the ordered `proposal_cache_events` survive inside the run-summary metadata.

This is better than a summary-only trace: under normal completion, the ordering of `model_routed`, proposal-budget, cache-fill, cost-estimated, `choice_set`, selected-action and observed-action-cost records is preserved. However it is **not a durable per-decision event stream**. The workspace and cost ledger are serialized only as final snapshots, and the JSONL write occurs only after the controller has produced a complete `ControllerResult`.

Consequence: an interrupted/crashed expensive collection can lose the entire in-memory decision history for that run, including future randomized behavior propensities if those were stored only in `proposal_cache_events`. For OPE-ready data collection, the decision/outcome logger should be append-durable at each decision, or at least checkpointed incrementally with stable decision ids.

Scope: this is source-level trace architecture evidence for the pinned public CSSC revision. It does not claim actual crash-loss frequency.

### C108 — old completed traces can partially reconstruct ExecutionSelection, but not a lossless `ExecutionDecisionEvent`

Immediately before consumption, action runtime already appends `choice_set` with `workspace_version`, every ranked row, selected node id and the unified budget snapshot. After selection it appends `action_selected`; after execution it appends `action_cost_observed` with the exact `ledger_event_ids` in the selected execution slice. The final cost-ledger snapshot preserves event order and event ids.

Therefore a completed trace can recover:
- the post-generation choice-set ordering;
- per-row `node_id`, `branch_id`, `action_kind`, estimated execution cost and budget admission;
- selected node and budget snapshot;
- exact final ledger events attributed to the selected execution window.

But it cannot losslessly recover the proposed causal decision record because the current `choice_set` omits at least:
- explicit `decision_index` / stable decision id;
- experiment policy id/version;
- full behavior distribution `mu(a|s)` and exact chosen propensity;
- pre-execution ledger boundary count/hash;
- `obligation_id` and obligation version;
- proposal source, `proposal_batch_id`, proposal model tier and cached-at workspace version;
- experiment effect class / legal-mask gate reason;
- an immutable per-decision workspace/state snapshot or compact state fingerprint.

The deterministic current baseline can often be inferred as the first budget-admitted ranked row, but future randomized propensities must be recorded at action time rather than reconstructed afterward.

### C109 — `action_cost_observed.ledger_event_ids` is an excellent post-action join key, but it is not a substitute for the pre-action ledger boundary

`event_start = len(state.cost_ledger.events)` is captured immediately before `execute_action_node(...)`; `execution_end` is captured before final assembly; and `action_cost_observed` stores all event ids in `[event_start:execution_end]`. This correctly keeps terminal assembly as a separate fixed tax and lets completed traces recover exactly which ledger events occurred during selected execution.

However `event_start` itself is not persisted. A pure-local structural action can legitimately produce no new ledger event ids, and a future execution mechanism could mutate non-cost state without emitting ledger events. Therefore the minimal decision record should persist `ledger_event_count_before` plus, defensively, the previous tail event id or ledger fingerprint. The outcome should retain the already-existing exact `ledger_event_ids`.

### C110 — shared proposal-batch `action_id` attribution is mutable and latest-consumer-wins; use an append-only consumption relation instead

`record_proposal_request(...)` creates provider request/usage/charge/tool events with common metadata containing `action_id=None` and `proposal_batch_id=request_id`. One provider request can yield multiple cached proposals carrying the same batch id.

At the start of every `execute_action_node(...)`, `attribute_proposal_batch(...)` rewrites *all* ledger events matching that batch and sets metadata `action_id=node_id`. The rewrite is applied again whenever another node carrying the same batch id is consumed. Therefore if two proposals from one model batch are executed sequentially, the second consumption necessarily overwrites the prior event metadata so the final ledger says the shared generation batch belongs to the latest consumer.

This strengthens C103: provider generation spend is not merely conceptually batch-scoped; the current action attribution field is non-monotonic provenance and cannot safely be used as an action-cost label.

Recommended invariant:
1. provider-generation ledger events remain immutable with `action_id=None` and stable `proposal_batch_id`;
2. each consumption writes a separate append-only relation/event `(proposal_batch_id, node_id, decision_id, workspace_version)`;
3. generation cost is evaluated at batch/run level, never duplicated across consumer actions;
4. selected execution cost remains the independent execution-window ledger slice.

A regression test should construct one model batch with at least two nonterminal consumable proposals, consume both, then assert the provider events remain unchanged and two distinct consumption joins exist. The current inspected tests do not explicitly mention `proposal_batch_id`, so this invariant is not presently regression-protected in the bounded test pass.

### C111 — the current public CSSC source tree does not contain committed run JSONL traces suitable for measuring Stage-A cost headroom

The pinned recursive repository tree contains trace-store code, benchmark scripts, fixtures and a report, but no obvious committed per-run JSONL trajectory corpus from which to partition real provider spend into pre-selection proposal generation versus selected execution/checking versus terminal assembly.

Therefore the prior headroom question cannot be answered quantitatively from the currently inspected public tree. The correct next step is a small pinned rerun/collection with provider usage enabled, not an estimate from static cost priors. This is a bounded repository-content observation, not a claim that no external/private trace dataset exists.

### C112 — the smallest robust instrumentation patch is now more precise and should separate durability from schema

For Stage A, the source-local semantic patch remains small:

- add monotone `decision_index` to `_StructuredRunState`;
- immediately before `frontier.consume`, emit `ExecutionDecisionEvent` containing the version-pinned candidate universe, complete candidate provenance, legal/effect mask, deterministic baseline, full randomized behavior distribution, chosen propensity, frozen budget, cost-estimator/policy fingerprints and `ledger_event_count_before`;
- after `execute_action_node`, emit `ExecutionOutcomeEvent` with resulting workspace version/status, terminal/reusable verified progress labels, actual execution-cost vector and exact ledger event ids;
- replace mutable proposal-batch `action_id` rewriting with append-only batch-consumption joins.

But schema alone is insufficient: if these events remain only in `state.proposal_cache_events` and are flushed through `append_result` after completion, a crash still destroys OPE data. The collection path therefore needs an append-durable decision-event sink (or frequent atomic run checkpoints) with stable run/decision ids. Final `ControllerResult` serialization can remain as a convenient summary projection.

## Updated synthesis

The Stage-A experiment is closer to executable than before, but the first implementation target should be **instrumentation integrity**, not policy training. Current normal-completion traces already provide enough structure to validate the new event schema against the deterministic baseline, yet they lack propensity logging, complete candidate provenance and crash durability. Fixing those gaps creates a reusable causal dataset interface without changing low-level proving behavior.

The cost attribution correction is equally important: proposal-generation cost should be joined to decisions through an immutable many-to-many provenance relation, not rewritten into a single latest `action_id`. This prevents a learned scheduler from receiving false per-action costs when one generation batch supplies several candidate actions.
