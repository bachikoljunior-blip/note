## C368 — proof-carrying authorization gives a direct architecture for using an untrusted learned agent as a prover rather than as the authority

**Observed.** Classic proof-carrying authorization (PCA) systems formalize authorization policy as logic and require access to a protected resource to be accompanied by a proof. The 2002 USENIX web access-control system implemented a browser that mechanically constructs proofs by fetching policy components and a server that checks the proof before granting access. A separate 2010 dependently typed implementation embeds an authorization logic in Agda, implements proof search, and exposes proof-carrying primitive operations whose types require a valid authorization proof.

Sources:
- https://www.usenix.org/conference/11th-usenix-security-symposium/general-and-flexible-access-control-system-web
- https://static.usenix.org/publications/library/proceedings/sec02/full_papers/bauer/bauer_html/pcaproto.html
- https://www.cs.cmu.edu/afs/cs.cmu.edu/Web/People/drl/pubs.html
- https://www.researchgate.net/publication/221241207_Security-Typed_Programming_within_Dependently_Typed_Programming
- https://www.cs.cmu.edu/afs/cs.cmu.edu/Web/People/drl/pubs/thesis/thesis.pdf

**Inference.** For an agentic runtime, a learned model does not need to be trusted to decide authorization. It can be an untrusted proof-search/proposal component. The authority boundary can remain a small deterministic proof checker/typechecker that accepts only a proof for the exact effect under the exact active policy/context. Search failure then fails closed rather than silently widening authority.

**Scope guard.** PCA does not solve intent capture, policy activation, stale context, or effect-to-authorization-request mapping by itself. It assumes that the checked proposition/policy is the proposition that actually governs the effect. The proof checker can be correct while a wrong action/resource/context was encoded.

## C369 — separate policy activation evidence from per-effect execution authorization evidence

The previous `SemanticLoweringCertificateV0` was becoming overloaded. C361–C368 suggest two distinct artifacts with different proof obligations:

### `PolicyActivationCertificateV0`

Answers: *Why is this authorization policy trusted as the active policy?*

It should bind:
- trusted intent source / reviewed behavior atoms / machine specification;
- canonical policy AST/policy-set digest and semantics version;
- parser/constructor and semantic-lowering provenance;
- schema/type environment;
- symbolic compiler / verifier evidence;
- authority delta from the previously active policy;
- activation witness and policy activation epoch/version.

### `ExecutionAuthorizationWitnessV0`

Answers: *Why may this exact effect execute now?*

It should bind:
- canonical effect/action identity and effect-route ID;
- exact principal / delegation chain / authenticated originating subject;
- exact resource and relevant entity-set digest;
- exact action arguments / context digest;
- active policy AST/policy-set digest + activation epoch;
- proof/authorization result and checker/authorizer version;
- freshness or temporal facts used by the proof;
- execution/commit binding so that post-authorization argument, route, principal or policy changes invalidate the witness.

Hard invariant: a valid policy-activation certificate is not an execution permission, and a valid execution proof under a stale/different policy or request is not reusable.

## C370 — current Cedar-for-Agents code provides a concrete typed request-mapping substrate, but the mapping itself remains a grant-critical boundary

**Observed.** The public `cedar-policy/cedar-for-agents` repository includes an MCP SDK plus a Cedar MCP schema/request generator. Its Rust `RequestGenerator::generate_request`:

1. validates the actual MCP `Input` against the server/tool description;
2. obtains the tool matching the validated input name;
3. converts typed tool arguments into Cedar restricted expressions/entities;
4. maps the tool name to the Cedar `Action` entity;
5. includes the typed input (and optionally output) in request context;
6. constructs a Cedar `Request` while supplying the generated validator schema, forcing request/schema validation.

Source:
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator/src/generator/request.rs
- https://github.com/cedar-policy/cedar-for-agents
- https://docs.cedarpolicy.com/auth/authorization.html

**Inference.** This is a useful engineering substrate for `ExecutionAuthorizationWitnessV0`: tool identity and typed input can be included in the Cedar request rather than authorized only by an opaque tool name. The request can therefore bind fine-grained argument predicates.

**Critical boundary.** The authorizer only proves/decides the request it was given. The runtime must still prove mechanically that the subsequently executed MCP tool call is the same effect as the authorized request. Any mutation between request generation and dispatch, any alternate effect route, or any incorrect schema/tool-description mapping can otherwise invalidate the security argument.

New deterministic regression:

`authorized_request_must_equal_dispatched_effect` — after authorization, mutate tool name, principal, resource, or any grant-relevant input argument before dispatch; execution must fail before the effect occurs. The dispatch record must bind to the same canonical request/effect digest used by authorization.

## C371 — current agent authorization integrations independently reinforce per-effect fail-closed checking

**Observed.** Cedar's current authorization guide states that applications should invoke the authorizer for each protected action. Current Bedrock AgentCore authorization flow maps the concrete MCP tool call, including input arguments, into a Cedar authorization request. The Cedar-for-Agents project specifically provides schema and authorization-request generation for MCP tools.

Sources:
- https://docs.cedarpolicy.com/auth/authorization.html
- https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html
- https://github.com/cedar-policy/cedar-for-agents

**Inference.** The strongest runtime pattern now has independent support from both formal authorization literature and current agent infrastructure:

`untrusted planner/prover -> canonical effect request -> deterministic authorization/proof check -> sealed execution witness -> exact effect dispatch`.

This does not replace route-closure, data-flow, temporal, crash-recovery or commit-time freshness checks; it gives them a cleaner authorization object to bind to.

## C372 — a learned controller can safely optimize authorization *search* without controlling authorization *truth*

Combining the proof-search work from the reasoning frontier with PCA yields a useful separation:

- learned controller may decide which policy facts to retrieve, which proof branch to try, whether to backtrack, which subgoal to prove first, or when to spend more compute;
- deterministic checker decides whether the produced proof/witness actually establishes authorization;
- runtime only dispatches an effect whose canonical request digest is sealed into a valid witness under the current active policy epoch.

This is a particularly attractive place for cost-aware learning because failed proof search costs latency/tokens but need not create unsafe authority. The safety loss becomes fail-closed denial/unavailability rather than unauthorized execution, provided no fallback route bypasses the checker.
