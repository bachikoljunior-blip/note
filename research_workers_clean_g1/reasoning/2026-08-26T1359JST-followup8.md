## New findings

### C171 — a support-floor contract gives a concrete reason to cap the initial randomized pool

For the proposed uniform epsilon mixture over a safe pool of `L` actions,

- baseline probability is `(1-epsilon) + epsilon/L`;
- each alternate probability is `epsilon/L`;
- a deterministic target policy that chooses an alternate can have importance weight as large as `L/epsilon`.

For the current candidate `epsilon=0.25`, alternate propensity is:

- `L=2`: 0.125, maximum deterministic-target weight 8;
- `L=3`: 0.0833, max weight 12;
- `L=5`: 0.05, max weight 20;
- `L=10`: 0.025, max weight 40.

Thus blindly randomizing across every safe node can make OPE variance increase with candidate-set width even though propensities are technically nonzero.

A conservative **initial collection contract** is therefore:

- design support floor `p_min = 0.05`;
- corresponding importance-weight design cap `W_max = 20` for a deterministic target action;
- with `epsilon=0.25`, randomized pool size `L <= 5`;
- pool consists of the deterministic baseline plus up to four highest-ranked experiment-safe alternatives under the frozen production ordering;
- effectively legal candidates outside that pool have zero experimental support in v0 and any learned/deployed v0 policy must fall back to the deterministic baseline instead of assigning them target mass.

`p_min=0.05` / `W_max=20` are conservative experiment-design choices, not universal statistical optima. They should be frozen before randomized outcomes are observed. A later protocol may change them after an explicit safety/coverage study.

### C172 — if deterministic pilot shows wide safe pools, expand coverage by protocol version rather than silently lowering propensities

The deterministic provider pilot can inspect candidate-set widths and action/effect composition **without using treatment outcomes**. If many decisions have more than four plausible safe alternatives, there are three transparent options for a later protocol:

1. increase epsilon while retaining the support floor, accepting greater behavioral perturbation;
2. rotate/stratify which safe alternatives enter a capped pool under a fully logged selection distribution, which preserves marginal support but requires more complex propensity accounting;
3. keep the cap and explicitly restrict target policy support.

For v0, option 3 is simplest and most identifiable. Do not quietly enlarge `L` under fixed epsilon after seeing learned-policy results, because that changes both safety exposure and OPE variance.

### C173 — success and cost should be estimated as separate value heads/axes before any scalar utility is chosen

Raw labels already preserve terminal verified success, local verified progress and multidimensional cost. The learned controller should initially mirror that separation:

- `Q_success(s,a)`: probability/expected indicator of eventual verified run success under a specified continuation policy;
- optional `Q_progress(s,a)`: expected downstream verifier-grounded reusable progress;
- `Q_cost_d(s,a)` for each additive cost dimension `d` (checks, model/tokens, checker time, API cost, wall time as estimable).

This permits evaluation of a policy's verified success and cost vector separately. A deployment scalarization or constraint can then be selected **only on training/validation**, while the test report shows the full success-cost tradeoff.

The controller should not learn that, for example, one second equals a fixed number of tokens or dollars merely because a convenient scalar reward was chosen during logging.

### C174 — primary causal endpoint should be verified success under identical hard budgets; cost is a co-primary efficiency surface

A clean matched comparison keeps hard budget configuration, prover, generator, retrieval, cost estimator and action space fixed. Primary effectiveness endpoint:

- theorem/task-level verified solve rate under the exact same hard budget envelope.

Efficiency endpoints:

- total model requests/input/output/billed tokens;
- checker count and checker CPU/wall time;
- API cost where measured/estimable with frozen price table;
- end-to-end wall-clock;
- proposal-generation vs selected-execution vs assembly shares.

Report a Pareto-style success-versus-cost surface or validation-selected operating point plus the unscalarized axes. A policy that saves cost but materially lowers verified solve rate is not automatically better; a policy that raises solve rate at substantially higher cost also needs explicit tradeoff reporting.

### C175 — initial return construction can be simple Monte Carlo with no discount, while preserving auxiliary progress and cost targets

For a normally completed finite run with decisions `t=0..T-1`:

- terminal success return for every decision can be `G_success_t = final_verified_success` (gamma=1) as the simplest baseline;
- future additive cost return for dimension `d` is `G_cost_t,d = sum_{k=t}^{T-1} action_cost_{k,d} + terminal/assembly cost if the objective includes it`;
- local verified progress remains an auxiliary per-step label rather than a substitute terminal reward.

This is high-variance credit assignment but transparent. More sophisticated TD/sequence models should be later ablations, not prerequisites for the first compact-controller test.

For a censored trajectory with no reliable terminal result, do not construct `G_success=0`. Cost returns can be used only through the last causally observed outcome, and terminal-return training excludes or explicitly models the censored suffix.

### C176 — define logical terminal failure separately from infrastructure censoring

A normally completed run can legitimately end unsolved because of budget exhaustion, no actions, verified rejection, or another controller stop condition. If the final `ControllerResult` is durably recorded, terminal verified success=0 is an observed theorem-run outcome.

By contrast, an unmatched decision caused by crash/journal failure before a trustworthy final result is infrastructure censoring. Treating both as failure would teach the policy that logging/runtime instability is evidence an action is mathematically bad.

Dataset builder therefore needs a run-level `terminal_observation_status` such as:

- `observed_terminal_result`;
- `censored_before_terminal_result`.

Proof success is defined only when terminal observation is present.

### C177 — v0 deployment fallback can make the estimand identical to the deployable policy

Define the target policy itself as:

- if state/candidate support diagnostics satisfy the frozen v0 support contract, use learned masked policy over the supported randomized pool;
- otherwise choose the deterministic production baseline.

Then OPE estimates the same fallback policy that would actually be deployed, rather than evaluating an unconstrained learned policy and adding an unmodeled safety fallback afterward. This removes an important estimand/deployment mismatch.

### C178 — support diagnostics should be computed at theorem-group and decision levels

Decision-level ESS/propensity summaries can overstate information when many correlated decisions come from the same theorem. In addition to standard decision-level weights/ESS, report:

- number of distinct theorem/task groups contributing support for each action/effect class;
- support concentration (fraction of weighted mass from top-N theorem groups);
- clustered/bootstrap uncertainty resampling theorem groups rather than individual decisions where possible.

This aligns uncertainty with the actual split/independence unit and reduces false confidence from long trajectories on a few hard theorems.

## Updated synthesis

The first randomized protocol can now be conservative by construction: epsilon=0.25, at most five supported actions per decision, exact fallback outside support, and a maximum deterministic-target single-decision importance weight of 20 by design. This is not claimed optimal; it is auditable and keeps the first OPE problem from becoming unnecessarily ill-conditioned.

Separating success/progress/cost heads also makes the experiment more faithful to the real objective: solve more verified theorems under a fixed budget, while showing rather than hiding the cost tradeoff.
