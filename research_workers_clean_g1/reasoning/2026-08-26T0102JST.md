## C39 — Direct proof-progress prediction improves Lean search; trajectory history is a large part of the signal

Primary/public sources:
- `LeanProgress: Guiding Search for Neural Theorem Proving via Proof Progress Prediction`, arXiv:2502.17925, TMLR 2025.
- Official LeanDojo project page: https://leandojo.org/leanprogress.html

Mechanism:
- Learn the number of remaining proof steps from the current Lean proof state, optionally including proof history.
- Combine the predicted remaining distance with tactic log-probability inside best-first search rather than ranking branches by tactic likelihood alone.
- The released project also exposes the progress estimate interactively through LeanCopilot.

Evidence from the current official project page:
- DeepSeek-Coder-1.3B progress predictor with proof history: **75.8% exact-step accuracy, MAE 3.15**.
- Without proof history: **61.8% accuracy, MAE 5.22**.
- ReProver Mathlib4 proof-search pass rate: **41.4% -> 45.2%** (+3.8 percentage points) when progress prediction is integrated.
- Training data is about **80k proof trajectories**; balancing changes the average retained proof length from 2.47 to 10.1 steps so the predictor is not dominated by trivial short proofs.

Interpretation:
- This gives direct Lean evidence that a low-dimensional **future-cost/progress feature** can improve end-to-end search, and that history materially improves that feature.
- It complements compiler-error diversity and proof similarity: the controller should not infer progress only from local syntax/error observations when trajectory history carries substantial additional signal.
- A useful future router could predict multiple targets from the same trajectory representation: remaining steps, next-attempt success, repairability, and expected future compute.

Scope / caution:
- Remaining-step accuracy/MAE is not probability calibration. The surfaced primary/public material does not establish Brier/ECE/reliability/selective-risk robustness across theorem families, prover changes, or policy shift.
- The current official page reports 41.4% baseline and 75.8% predictor accuracy, while the original arXiv abstract reports 41.2% and 75.1%; preserve source/version rather than silently mixing values.
- The predictor is trained from search-generated trajectories, so transfer to states reached by a materially different future controller remains an OOD question.

Sources:
- https://arxiv.org/abs/2502.17925
- https://leandojo.org/leanprogress.html

## C40 — AlphaProof demonstrates learned progress value, state reuse, progressive widening, and hardest-subgoal routing at scale

Primary source:
- `Olympiad-level formal mathematical reasoning with reinforcement learning` (AlphaProof), Nature 651, 607–613; published 2025-11-12, version of record 2026-03-13, DOI 10.1038/s41586-025-09833-y.

Mechanism relevant to the current controller frontier:
- A 3B proof network emits both a tactic policy and a value function over Lean tactic states.
- Per tactic reward is -1. The learned value therefore estimates remaining proof cost rather than only a binary success label.
- For states split into independent subgoals, return is the **minimum return / longest proof branch**, and AND-node search prioritizes the currently hardest unproven subgoal. This deliberately encourages decompositions with balanced subgoal difficulty.
- Search stores/restores Lean tactic states, explores them concurrently, merges tactics reaching the same Lean state, and retains the lower-cost edge using a string-length + execution-time cost.
- **Progressive sampling** adds more tactic samples only at sufficiently visited nodes, broadening strategy support along promising search regions instead of applying a fixed branching factor everywhere.

Quantitative evidence:
- Main RL spans about **80,000 TPU days**; auto-formalization about **100,000 TPU days**. This is a major scale/cost caveat, not a deployable low-cost baseline.
- During main RL, the final agent reaches roughly **30%** solve rate on historical IMO problems with about **300 simulations**, a level earlier checkpoints could not reach even with much larger search, showing training can convert huge offline compute into stronger search guidance.
- Scaling tree search from roughly **2 TPU minutes to 12 TPU hours per problem** raises solve rate by **more than 10 absolute percentage points** on formal-imo and PutnamBench-test.
- For still-unsolved targets, test-time RL adds roughly **15 absolute points** over the 12-TPU-hour search on both formal-imo and PutnamBench-test, but at **hundreds of TPU-days per target** rather than hours.

Interpretation:
- This is strong evidence that a proof controller can use a **structured progress/cost value**, dynamic widening, and AND-goal difficulty routing rather than only a binary `continue/restart` score.
- It also suggests a distinct high-cost meta-action: when ordinary search saturates, problem-specific learning can be useful. However, its cost is so large that a practical controller should expose it only behind a strict value-of-information / budget gate.
- AlphaProof's single-search design globally reallocates compute among retained proof paths without committing to one intermediate trajectory, which is complementary to the preserve/fork/restart hierarchy in smaller systems.

Scope / caution:
- The Nature paper does not establish conventional probability calibration of the value head; its value semantics are expected remaining return/steps, not a calibrated success probability.
- Scale, proprietary proof network, custom environment and corrected/internal benchmark components limit direct reproducibility and small-model transfer.
- TTRL's +15pp should never be described as a cheap inference optimization: its x-axis is hundreds of TPU days, whereas ordinary tree-search scaling is measured in TPU hours.

Source:
- https://www.nature.com/articles/s41586-025-09833-y

## C41 — LeanTree factorizes multi-goal states into independently searchable branches, but its current solve-rate evidence is preliminary rather than a causal factorization ablation

Primary sources:
- `LeanTree: Accelerating White-Box Proof Search with Factorized States in Lean 4`, arXiv:2507.14722 / AI4Math@ICML 2025.

Mechanism:
- Factorizes a Lean proof state with multiple goals into simpler independently searchable sub-states, while separately addressing metavariable coupling.
- Supports restarting from intermediate states, tree search/backtracking, parallel execution through a dynamic environment pool, state reuse, and smaller context per branch.
- This is a representation/execution primitive that can reduce the controller's state-action complexity before learning which branch/action receives compute.

Preliminary MiniF2F evidence with Llemma-7B:
- Whole-proof generation: **9.59% +/- 0.71**.
- Black-box linear rollout: **5.32% +/- 0.37**.
- White-box rollout with internal proof states: **18.36% +/- 0.60**.
- A previously reported best-first-search reference is **26.23%**.
- The rollout experiment uses 10 independent rollouts, each up to 25 steps, and averages five runs.

Interpretation:
- Exposing intermediate/factorized states is clearly useful in this particular protocol relative to black-box rollout.
- More importantly for the current frontier, factorization makes **subgoal-level routing, reuse, and parallelism** explicit instead of forcing the controller to treat a multi-goal state as one opaque branch.
- Combined with AlphaProof's hardest-subgoal value semantics, this suggests future routers should estimate branch-specific remaining cost and allocate compute across independent subgoals rather than merely score the aggregate state.

Scope / caution:
- The experiment does **not** isolate factorization alone: black-box vs white-box conditions differ in state visibility/interaction, and the 26.23% best-first number is a literature reference rather than a same-run LeanTree ablation.
- The authors call the results preliminary; some tactic proofs cannot yet be converted.
- Do not infer that factorization by itself doubles solve rate.

Sources:
- https://arxiv.org/abs/2507.14722
- https://openreview.net/pdf?id=pROVJwTb6w

## C42 — MPS-Prover shows that a learned critic plus deliberately different search perspectives beats a single search criterion under approximately matched expansion compute

Primary sources:
- `MPS-Prover: Advancing Stepwise Theorem Proving by Multi-Perspective Search and Data Curation`, arXiv:2505.10962 / ICLR 2026 submission.

Mechanism:
- At each selected state, MPS expands four perspectives: one critic-selected node plus three heuristic-selected nodes intended to diversify search (tactic efficiency, minimum cases, shortest state).
- Standard BFS expands one best node. For approximate compute matching, the paper compares MPS pass@k with BFS pass@4k because MPS expands four nodes per pass.

Evidence:
- At the lowest matched budget, MPS pass@1 solves **165/244 = 67.62%** miniF2F versus BFS pass@4 **162/244 = 66.39%**.
- At a fixed budget equivalent to the full MPS pass@64 condition, full MPS solves **177/244**.
- Replace critic guidance with random node choice: **164/244**.
- Remove/replace each diversity perspective with random choice: tactic-efficiency **174/244**, minimum-cases **173/244**, shortest-state **172/244**.
- Removing the data-curation strategy changes 177 -> **176/244** while the strategy itself removes about **40%** of redundant/low-value post-training data, indicating large training-data savings with almost no final solve loss in this tested setup.

Interpretation:
- A single learned critic is not sufficient in this experiment; complementary search criteria add solved problems even under an approximately matched node-expansion budget.
- This supports keeping multiple **orthogonal low-cost perspectives** available to a future router rather than collapsing everything into one scalar learned value.
- However MPS hard-wires one slot per perspective. The higher-value next step is a learned/calibrated gate that decides *how many* critic/diversity/progress/retrieval/repair actions to allocate per state, especially when some perspectives become redundant.

Scope / caution:
- Compute matching is based on node-expansion accounting, not equal generated tokens, Lean execution time, critic/heuristic overhead, or wall-clock; it therefore does not close the substrate-aware cost frontier.
- The heuristics are hand-designed and their gains are modest individually; the result does not establish a universal fixed four-way mixture.

Sources:
- https://arxiv.org/abs/2505.10962
- https://openreview.net/pdf?id=Ox3U97Svtl

## Updated synthesis

The controller frontier now has a clearer separation between **state representation, progress estimation, and action allocation**:

1. **Represent independent obligations separately.** LeanTree and AlphaProof both expose multi-goal decomposition so branch-level compute can be allocated rather than treating an AND state as opaque.
2. **Predict structured future cost/progress, not only success.** LeanProgress shows remaining-step prediction improves search and benefits strongly from trajectory history; AlphaProof uses a learned remaining-return value and hardest-subgoal semantics.
3. **Retain multiple perspectives.** MPS-Prover shows that critic-only navigation leaves measurable coverage on the table and that orthogonal heuristic perspectives recover some of it.
4. **Dynamically widen promising regions.** AlphaProof's progressive sampling is a large-scale precedent for variable branching factor; this matches the earlier 3D-Prover/CARTS evidence that diversity is most valuable when candidate redundancy is high.
5. **Do not confuse good ranking/progress regression with calibrated decision probability.** LeanProgress/AlphaProof/MPS add useful value features, but none of the surfaced evidence closes Brier/ECE/selective-risk robustness under distribution shift.
6. **Make the action-cost target explicit.** Binary solve probability, expected remaining tactics, longest subgoal branch, generated-token cost, Lean execution/reconstruction cost and wall-clock are distinct objectives. A practical router should predict or constrain the dimensions actually relevant to its execution substrate.

A promising controller design is now:
- factorize independent goals;
- maintain a trajectory-aware progress vector per branch (`remaining_steps`, compiler-error trajectory, semantic transition, retrieval support, uncertainty/coverage);
- allocate a variable number of actions from multiple perspectives (critic, semantic diversity, local repair, retrieval escalation, branch/restart) rather than a fixed K;
- use calibrated/selective rules to abstain/escalate when progress estimates are OOD or under-covered;
- optimize expected longest-branch completion cost plus real substrate cost, not only tactic count.

## Rejected / narrowed leads this run

- **A scalar current-state score is sufficient for progress:** weakened by LeanProgress's large history ablation and by MPS's gain from multiple perspectives.
- **The relevant value target must be binary success:** weakened by LeanProgress and AlphaProof, which successfully use remaining-step/return signals to guide search.
- **Always expand a fixed number of diverse branches:** not established. MPS hard-codes four perspectives and AlphaProof dynamically widens promising nodes; learned budget allocation remains open.
- **Factorized proof-state tooling itself is proven to cause the full LeanTree solve-rate gap:** rejected; current experiment changes state access/interaction together with factorization.
- **AlphaProof TTRL is a practical low-cost fallback:** rejected by the published compute scale; it is evidence for a meta-action at extreme budget, not an ordinary repair step.

## Nonempty unresolved frontier

1. **Calibrated progress/value under search-policy shift:** compare LeanProgress/AlphaProof-style remaining-step or return prediction with binary success/repairability predictors using Brier/ECE/reliability/selective-risk and OOD theorem/policy splits.
2. **Variable-perspective allocator:** replace MPS's fixed four expansions with a learned gate deciding critic vs semantic-diversity vs progress vs repair/retrieval branches under equal token/Lean/wall-clock budget.
3. **AND-goal cost routing:** test branch-specific remaining-cost prediction and hardest-subgoal allocation on LeanTree/factorized states; compare longest-branch, sum-of-branches, and risk-sensitive objectives.
4. **Coverage-aware routing:** bring CovCal-style finite-sample/selective-risk abstention into proof-search decisions when progress/error/retrieval evidence is sparse.
5. **Triggered global re-retrieval:** learned escalation from local failure-conditioned retrieval to a fresh LeanSearch-v2 global route/retrieve/reflect cycle.
6. **Trajectory-effect integration:** test Delta/trajectory representations end-to-end alongside LeanProgress-style history features; determine incremental value after compiler-error diversity and remaining-step prediction.
7. **Execution-substrate-aware compute:** snapshot/persistent server vs rebuild-per-branch; report generation, retrieval, Lean tactic/verifier, reconstruction, and wall-clock separately.
8. **Exact Lean composite:** snapshot/fork + learned tactic/transition-semantic diversity + compiler-guided repair + calibrated multi-action routing under equal compute.
9. **Benchmark-audited robustness:** pinned Lean/mathlib/repository/harness versions and candidate-access sensitivity.
