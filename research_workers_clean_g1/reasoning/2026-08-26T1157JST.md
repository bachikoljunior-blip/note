## New findings

### C99 — the cleanest existing CSSC intervention point is narrower than the desired meta-controller: current action selection happens *after* retrieval, model routing, provider spend and proposal generation

The action runtime calls `refresh_action_cache`; if no work exists it calls `_fill_action_cache`. `_fill_action_cache` performs `maybe_retrieve(...)`, chooses a proposal-generation model tier via `_route_proposal_generation(...)`, performs proposal-budget admission, reserves/calls the provider, validates generated proposals, inserts them into the version-pinned cache, and estimates their execution costs. Only after those steps does `_run_action_runtime` call `select_admissible_action(...)` over the cached frontier.

Therefore replacing `select_admissible_action` with a learned selector gives a strong **scheduler-ablation** over already-generated typed proposals, but it does **not** learn whether to retrieve, whether to pay for proposal generation, which model tier to use, or whether to generate a new proposal batch at all. Those costs and decisions are upstream and partly sunk before the selector acts.

Implication: use two explicit policy boundaries rather than pretending one controller already covers the full ontology:

1. **ExecutionSelection** — choose among already-generated, version-pinned action nodes.
2. **GenerationControl** — later decide retrieval, model tier/escalation, whether/where to generate a proposal batch, and possibly cache refill.

The first is immediately testable with the existing runtime. The second requires moving the intervention boundary earlier or representing retrieval/escalation/generation as explicit typed frontier actions.

Scope guard: this is source-level control-flow evidence about the current public CSSC runtime, not evidence that either learned policy will improve proving outcomes.

### C100 — for the *existing* selector boundary, the canonical legal mask is simpler than previously assumed because stale/invalid proposals have already been removed before the choice set exists

`ProposalCache.add(...)` validates proposals and rejects invalid/stale targets, duplicates and capacity overflow. `refresh_action_cache(...)` calls `cache.valid_nodes(workspace)`, whose `node_invalid_reason(...)` checks exact workspace version, active branch, obligation/version match, proposal target, target-step existence and branch readiness. The frontier presented to `select_admissible_action(...)` therefore contains only currently valid cached nodes.

Within this exact post-generation decision boundary, a minimal authoritative legal mask does **not** need to reconstruct every distributed validator post hoc. It can be defined over the version-pinned current frontier as:

`legal_i = current_frontier_member_i AND budget_admission_i.allowed AND experiment_effect_gate(action_kind_i)`.

The decision event should still preserve the exclusion semantics (frontier/cache version and source proposal batch) so an absent node is not confused with an illegal present node. A richer `allowed_action_kinds` mask remains necessary for **upstream action-space/generation ablations**, because currently ungenerated action kinds are outside the post-generation candidate universe entirely.

This refines the previous mask gap: the immediate OPE blocker for scheduler replacement is mainly **explicit candidate-universe/version identity + experiment-safe mask + exact behavior propensities**, while the broader action-generation experiment still needs `allowed_action_kinds` or equivalent.

### C101 — a minimal causal `ExecutionDecisionEvent` can be added without changing executor semantics, and the exact insertion point is immediately after `select_admissible_action` inputs are frozen and before `frontier.consume`

The current loop already freezes enough information for a decision event before execution. The smallest useful schema is:

- `sample_id`, monotonically increasing `decision_index`, task/theorem identity;
- `workspace_version`, frontier-policy/version, cost-estimator snapshot/fingerprint;
- frozen budget snapshot;
- complete current candidate list, each with `node_id`, `branch_id`, `obligation_id`, `obligation_version`, `action_kind`, `proposal_source`, `proposal_batch_id`, `proposal_model_tier`, `cached_at_workspace_version`, estimated execution-cost vector and baseline rank/priority explanation;
- `legal_mask` plus machine-readable gate reason (`budget`, `effect_class`, future explicit action-kind mask);
- deterministic baseline action;
- experiment policy id/version and full `mu(a|s)` over legal candidates;
- chosen node id and exact chosen propensity;
- **ledger boundary before execution**, so no post-action cost/outcome leaks into state.

Then log a separate `ExecutionOutcomeEvent` after `execute_action_node(...)` containing resulting workspace version/status, checker/safety/verified-progress outcome, actual execution-cost vector, terminal status and ledger event ids. Keeping decision and outcome separate prevents accidental future leakage during dataset construction.

The insertion point is source-local and causally clean: replace/wrap the call that currently returns `ConstrainedSelection`, log the frozen decision, then call the unchanged `frontier.consume(node_id)` and unchanged executor.

### C102 — Stage-A safe randomization can start with structural workspace actions; checker/file actions should remain gated initially

Source-level executor classification at the *post-generation execution* boundary:

- **P0 / deterministic local workspace transform:** `DECOMPOSE`, `PROPOSE_ARGUMENT`, `REFINE_ARGUMENT`, `CHANGE_REPRESENTATION`. Their execution methods validate the already-generated proposal and mutate the structured workspace/records without a provider call or Lean checker invocation.
- **E1 bounded tool/check plus local materialization:** `RUN_CAPABILITY_TEST` writes a candidate/probe and runs the Lean checker (forced subprocess in the current implementation).
- **E1 + local persistent-artifact surface (conservatively gate as effectful until cleanup/idempotency is explicit):** `IMPLEMENT`, `REPAIR_IMPLEMENTATION` expand a candidate branch, render/write a candidate, run checker and safety review, then reduce the verified/failed result into workspace state.

Important separation: **proposal generation for all of these actions is already an upstream provider/retrieval effect before ExecutionSelection**. A P0 execution action is only P0 relative to the frozen generated proposal; the proposal itself may have cost model/tool calls.

Recommended first randomized safe subset: only currently valid P0 execution nodes. Add checker-backed nodes only after exact replay/idempotency and candidate-file lifecycle are explicitly frozen.

### C103 — proposal-generation cost attribution is batch-scoped, not intrinsically action-scoped; learning per-action value-per-cost must not treat the current late attribution as causal action cost

`record_proposal_request(...)` records provider requests/usage/charges with scope `PROPOSAL_GENERATION`, `proposal_batch_id=request_id`, and initially `action_id=None`. One model request can return multiple proposals, all cached with the same `proposal_batch_id`.

When a specific cached node is later consumed, `attribute_proposal_batch(...)` rewrites every matching batch event's metadata to set `action_id=node_id`. If another node from the same proposal batch is consumed later, the same batch events satisfy the matching condition again and can be re-attributed to the later node. Thus the provider spend is fundamentally **shared batch cost** and should not be treated as a unique causal execution cost of whichever node most recently consumed the batch.

Separately, `actual_cost_from_events(state.cost_ledger.events[event_start:execution_end])` starts its window immediately before `execute_action_node`, so the current `action_cost_observed` event intentionally measures execution cost and excludes earlier proposal-generation spend.

Implications for learning/evaluation:

- preserve `proposal_batch_id` as a first-class cost unit;
- never duplicate or assign all batch generation cost to every proposal/action;
- report **run-level total cost**, **generation/batch cost**, and **post-selection execution cost** separately;
- if action-level cost sharing is needed, choose and pre-register an allocation rule, but do not confuse it with observed causal spend;
- before expecting large scheduler savings, measure the fraction of total cost already sunk before ExecutionSelection. If generation dominates, a post-generation learned selector has limited direct cost headroom and the next target should be GenerationControl.

This is a stronger reason to freeze the cost estimator but distinguish its **execution estimate** from provider-generation expenditure.

## Updated synthesis

The experimental plan should now be explicitly **two-stage** rather than one monolithic controller replacement:

### Stage A — post-generation execution scheduler

Freeze task split, Lean/Mathlib, retrieval, proposal-generation model/router, proposal generator, workspace/action semantics, checker/SafeVerify and cost estimator. Instrument `ExecutionDecisionEvent` exactly before `frontier.consume`. Randomize only valid P0 structural nodes with known propensities around the deterministic baseline. Learn value/advantage for scheduling already-generated proposals. Evaluate terminal verified solve and reusable verified progress against **total run cost**, with generation and execution cost broken out.

This stage answers: *does learning which already-generated typed proposal to execute next improve outcome/cost beyond deterministic cost-aware ranking?*

### Stage B — generation-control policy

Only after Stage A is understood, expose upstream choices now hidden in `_fill_action_cache`: whether to retrieve, which branch to refill, cheap/strong model route, whether to generate another batch, and later semantic repair/retrieval escalation. Give each such choice explicit legal masks, effect semantics, behavior propensities and batch-cost accounting.

This stage answers: *can the controller reduce the dominant pre-selection spend and decide when to buy information/proposals?*

A crucial diagnostic before training: partition current trace cost into `pre_selection_generation`, `selected_execution`, checker/tool, and terminal assembly. If most spend is pre-selection, Stage A is primarily a quality/scheduling experiment rather than a large direct cost-saving opportunity.
