# Reasoning Systems — clean_g1 follow-up 5 — deterministic provider pilot and Stage-A headroom gate

Same frozen semantic tuple and clean boundary as the preceding 14:27 JST checkpoints. This checkpoint does not consume randomized policy outcomes; it prespecifies the pilot before such data exist.

## C202 — pilot sampling unit/order must be task-level and deterministic

Provider cost-share pilot v0:

- population: the fixed held-out target benchmark/corpus chosen for the eventual Stage-A controller experiment, restricted only by protocol-level infrastructure eligibility defined before running outcomes;
- one task is the bootstrap/split unit; all decisions, retries and proposal-batch siblings from that task remain grouped;
- deterministic task order: sort by `sha256(protocol_id || task_id)` so no cost/outcome-dependent cherry-picking occurs;
- run fixed D0 selection with causal journal enabled and `epsilon=0`; use the same prover/generator/model route/cost estimator/feature manifest intended for the Stage-A comparison;
- no task is dropped because it is expensive, fails to prove, has no multi-action choice, or incurs provider errors; infrastructure-invalid tasks are reported separately under prespecified eligibility reasons;
- collection cap v0: first 200 eligible tasks in the deterministic order, or the entire eligible corpus if smaller;
- no automatic extension beyond the cap if precision is inadequate; report `INSUFFICIENT_PRECISION` and revise protocol/version explicitly if a larger pilot is later justified.

The 200-task cap is an experimental cost-control choice, not an empirical optimum.

## C203 — define cost scopes before calculating shares

For each task and each measured cost dimension `d`, preserve three non-overlapping scopes:

1. `G_d` — pre-decision generation/upstream cost: retrieval/model routing/provider proposal generation and retries that occur before the corresponding execution choices; provider batches counted once.
2. `E_d` — post-decision selected execution cost: checker/tool/other measured events that occur after a committed decision and before its committed outcome, summed across matched decisions.
3. `A_d` — final assembly/fixed terminal cost.

`T_d = G_d + E_d + A_d + other_unallocated_d`, with unallocated/unknown measurements reported rather than silently treated as zero.

Major dimensions for the pilot, where observation status supports them:

- API charge USD;
- billed tokens;
- input tokens;
- output tokens;
- checker wall time;
- total run wall time (scoped using explicit timing spans, not inferred from provider/checker sums).

For each dimension report both:

- **ratio-of-totals execution share:** `H_d = sum_i E_{i,d} / sum_i T_{i,d}`;
- unweighted distribution of per-task shares for tasks with positive observed denominator.

The ratio-of-totals is the primary headroom statistic because it upper-bounds the fraction of aggregate measured cost that a pure post-generation selector could eliminate even under an unrealistic perfect zero-cost execution replacement.

## C204 — bootstrap precision rule is now executable

At the fixed final pilot sample (no precision-based early stopping):

- perform 10,000 bootstrap resamples of **tasks** with replacement using a fixed documented bootstrap RNG seed/version;
- recompute each ratio-of-totals `H_d` in each resample;
- use the 2.5th/97.5th percentile interval as pilot uncertainty summary;
- report CI half-width and retain the already frozen target `<=0.05` (5 percentage points) for every dimension designated `major_observed`;
- a dimension is not `major_observed` if required measurements are unavailable for a material part of the denominator; report its observed/missing mass explicitly rather than zero-fill;
- if any required primary share misses the precision target at the collection cap, mark the cost-share conclusion `INSUFFICIENT_PRECISION` instead of choosing a more favorable estimator after seeing data.

Also report task-level bootstrap CIs for the opportunity metrics in C205.

## C205 — cost share alone is insufficient; measure whether Stage A actually has choices to make

Prespecified opportunity diagnostics:

- `M_task`: fraction of tasks with at least one committed decision whose supported pool size `L>=2`;
- `M_decision`: fraction of decisions with `L>=2`;
- supported pool-size histogram L=1..5;
- number/fraction of effective legal candidates excluded only by the top-5 support cap;
- decisions per task;
- fraction of tasks with zero execution decisions because generation/provider/budget failed upstream;
- D0 top-vs-second estimated score/cost margin distribution as a **diagnostic only**, not verified counterfactual advantage.

This prevents a misleading conclusion such as “execution cost is cheap, therefore Stage A is useless” when action selection may still materially affect success, or the opposite conclusion when almost every decision has only one legal action.

## C206 — freeze a conservative v0 Stage-A vs Stage-B gate before the pilot

Because the purpose of the pilot is to decide whether randomized Stage-A collection is worth its cost, use two independent headroom conditions. These thresholds are protocol choices, not universal scientific constants.

Proceed to a small randomized Stage-A collection only if **either** condition is supported at the pilot's 95% task-bootstrap level:

1. **cost headroom:** for at least one primary economically/compute-relevant observed dimension, the lower CI bound of `H_d` is >=0.10;
2. **choice headroom:** the lower CI bound of `M_task` is >=0.25.

If neither condition holds, do not randomize Stage A first; move the learning boundary upstream to Stage B (generation/retrieval/model-routing control), while retaining the Stage-A journal as observability infrastructure.

If precision is insufficient, do not force either decision; report insufficient evidence and keep the architecture choice open.

Rationale/scope:

- `H_d>=0.10` says at least ~10% of a measured aggregate cost dimension is demonstrably downstream of the selector, so there is nontrivial cost leverage.
- `M_task>=0.25` says multi-action selection is a recurring task-level phenomenon even if the execution itself is cheap, leaving plausible success-quality leverage.
- Neither threshold proves a learned selector will improve success/cost. They only justify paying for randomized evidence.

## C207 — pilot cannot use censored outcomes as zero-cost/failure tasks

Censored decisions remain in behavior/support diagnostics but not as completed transition cost/outcome labels. For run-level cost accounting, real provider/checker costs observed before the censoring boundary still count. The pilot must report:

- completed matched-decision tasks;
- tasks containing censored decisions;
- run-level observed cost including pre-censor cost;
- opportunity metrics based on committed decision choice sets;
- transition-level `E_d` only for matched outcomes unless a durable effect receipt permits a correctly scoped partial execution cost.

A high censoring rate is itself a journal/runtime reliability blocker for randomized collection.

## C208 — deterministic provider pilot should test instrumentation overhead simultaneously but not mix it into semantic equivalence

After epsilon=0 semantic equivalence passes on deterministic fake fixtures, provider pilot can run paired or interleaved no-journal vs journal-enabled tasks only if doing so is operationally affordable and provider conditions are stable. Report journal overhead separately:

- commit latency per decision/outcome;
- journal bytes/WAL growth per task;
- total wall-time delta;
- any change in provider/checker request counts (which should be zero if semantic equivalence holds).

Do not subtract journal overhead from the learned policy's later cost. If journaling is required for safe deployment, its real cost belongs in end-to-end evaluation; the separate overhead report only explains where it comes from.
