## SQLite decision-journal contract

Following the local benchmark in the predecessor, a minimal SQLite schema was prototyped and smoke-tested locally. The schema is intentionally a causal journal, not a replacement for CSSC's monetary/resource `CostLedger`:

```sql
CREATE TABLE decision_events (
    event_id TEXT PRIMARY KEY,
    run_id TEXT NOT NULL,
    decision_index INTEGER NOT NULL CHECK(decision_index >= 0),
    event_type TEXT NOT NULL CHECK(
      event_type IN (
        'execution_decision',
        'proposal_batch_consumption',
        'execution_outcome'
      )
    ),
    node_id TEXT,
    proposal_batch_id TEXT,
    payload_sha256 TEXT NOT NULL,
    canonical_json TEXT NOT NULL,
    created_seq INTEGER NOT NULL UNIQUE
);

CREATE UNIQUE INDEX one_decision_per_index
ON decision_events(run_id, decision_index, event_type)
WHERE event_type IN ('execution_decision','execution_outcome');

CREATE INDEX events_by_run_decision
ON decision_events(run_id, decision_index, created_seq);

CREATE INDEX events_by_batch
ON decision_events(proposal_batch_id)
WHERE proposal_batch_id IS NOT NULL;
```

The prototype inserted a decision plus batch-consumption event, correctly returned that decision from an unmatched-decision query, then inserted the outcome and returned zero unmatched decisions. This is only a schema/query smoke test, not a production durability test.

## New findings

### C150 — causal journal schema should enforce one decision and at most one outcome per `(run_id, decision_index)`, while allowing multiple batch-consumption joins

`execution_decision` and `execution_outcome` are one-to-zero/one per decision index. `proposal_batch_consumption` is one-to-many because a future controller architecture may consume/reference more than one batch or represent multi-source provenance.

The partial unique index above captures the first invariant without incorrectly making the whole `(run_id, decision_index, event_type)` triple globally unique for batch joins.

Reader invariants should additionally require:

- no outcome without a matching decision;
- no batch-consumption event without a matching decision;
- decision indexes strictly monotone/unique per run;
- `created_seq` strictly orders committed events within the journal;
- selected node in outcome equals selected node in its decision;
- every unmatched decision is explicitly classified `censored_no_outcome` by the reader, never silently dropped.

### C151 — idempotence must be enforced before relying on SQL uniqueness exceptions

For `append_event(event)`:

1. canonicalize payload and compute SHA-256;
2. query by `event_id`;
3. if absent, insert inside one transaction;
4. if present with identical hash and canonical bytes, return `identical` without inserting;
5. if present but bytes/hash differ, raise a `duplicate_conflict` and fail closed.

A bare `INSERT OR IGNORE` is unsafe because it cannot distinguish benign replay from a semantic conflict. Event identity is a causal assertion, so conflicting replay must be visible.

### C152 — transaction boundaries follow causal irreversibility, not storage convenience

For each randomized decision:

- **T1:** persist and commit `execution_decision` before `frontier.consume` or any action execution;
- **T2a:** if needed, persist/commit `proposal_batch_consumption` before execution because it binds the selected generated proposal to shared provider provenance;
- execute action;
- **T2b:** persist/commit `execution_outcome` before another randomized decision.

Do not combine the pre-action decision and post-action outcome in one transaction; that would erase the very crash/censoring evidence the journal is intended to preserve. For deterministic non-randomized pilot runs the same event ordering should still be used so instrumentation is matched.

### C153 — final JSONL export should be a derived artifact, not the authoritative online journal

After a run or collection shard is closed, export rows ordered by `(run_id, decision_index, created_seq)` as canonical JSON lines. Verify each stored `payload_sha256` during export. The online SQLite journal remains authoritative for crash recovery/idempotence until export verification succeeds.

The existing completed-run `JsonlTraceStore` can continue to write run summaries/workspace/cost snapshots; a downstream merger can join decision JSONL and final run summary by `run_id`. This avoids forcing a schema migration into existing trace consumers before the experiment proves useful.

### C154 — deterministic epsilon-mixture sampler passed a large synthetic frequency check

A simple safe-pool epsilon mixture with `epsilon=0.25` was simulated for 200,000 decisions per pool size using independent seeded draws.

Expected versus observed frequencies:

- `L=2`: baseline 0.875 expected / 0.87487 observed; alternate 0.125 / 0.12513.
- `L=3`: baseline 0.83333 / 0.832845; alternatives expected 0.08333 each and observed 0.08324 / 0.083915.
- `L=5`: baseline 0.800 / 0.800625; four alternatives expected 0.050 each and observed 0.050555 / 0.050210 / 0.048875 / 0.049735.

The largest absolute deviation in these checks was about 0.00113. This is a sanity check of the probability formula/sampler, not evidence about theorem-solving policy quality.

### C155 — sampler implementation should avoid depending on candidate input order

The canonical randomized pool must be ordered by a stable key (prefer stable `node_id`) before constructing the probability vector and applying a pseudorandom draw. Otherwise two semantically identical candidate sets presented in a different Python iteration order could map the same random draw to different actions despite having the same set hash.

Decision provenance should therefore contain:

- ordered randomized-pool node IDs;
- exact probability vector in the same order;
- realized uniform value or sampled index;
- sampler implementation/version and seed/shard identifier;
- chosen node and chosen propensity.

This makes the sampler fully replayable from the event itself.

### C156 — v0 feature schema needs a separate manifest hash, not just event-schema version

A dataset can remain syntactically compatible while feature semantics drift. Freeze a manifest containing:

- ordered numeric feature names;
- ordered missing/presence mask names;
- categorical fields and vocabularies including explicit `OTHER/UNKNOWN` values;
- transformation rules (`log1p`, ratios, clipping if any);
- which provenance fields are excluded from learning;
- training-split normalization parameters once fitted;
- source code/substrate commit identifiers.

Hash the canonical manifest to `feature_manifest_sha256` and attach it to every transformed dataset shard/model artifact. Raw causal journal events should **not** depend on this manifest; they remain lossless and can be re-featurized later.

### C157 — training normalization must be split-safe and missingness-preserving

Recommended v0 preprocessing:

- positive costs/counts: `log1p(value)` where known;
- bounded ratios: leave on `[0,1]`, plus presence/status features;
- rank: normalized by current candidate-set size;
- counts/streaks/depth: either `log1p` or robust standardization fitted only on training split;
- categorical fields: fixed vocabulary with `UNKNOWN/OTHER`, never inferred from validation/test frequencies;
- optional clipping thresholds learned/frozen from training split only.

Store normalization parameters with the model/manifest. Recomputing normalization from evaluation data would leak target distribution information and make offline comparisons non-reproducible.

### C158 — event journal and learned-policy dataset should be intentionally decoupled

The journal's responsibility is complete causal provenance. The dataset builder's responsibility is to derive one row per decision/candidate under a particular `feature_manifest_sha256`, attach observed sequential/terminal labels, and enforce support/censoring rules.

This separation enables:

- correcting feature bugs without recollecting provider traces;
- comparing text-free vs text/embedding feature ablations from the same decisions;
- excluding censored transitions from objectives that require outcomes while retaining them for censoring/failure analysis;
- rerunning OPE under improved support diagnostics without altering raw evidence.
