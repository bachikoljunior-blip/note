## C373 — request encoding configuration is part of authorization semantics, not mere serialization metadata

**Observed.** Cedar-for-Agents `SchemaGeneratorConfig` includes options that alter the generated authorization vocabulary and request representation: output inclusion, record-vs-entity encoding, namespace flattening, numeric representation, and entity-type deduplication. The source explicitly warns that `numbers_as_decimal=true` rounds numbers to four decimal places and can make an authorization policy unsound; it gives an example where distinct values become equal after conversion. It also warns that namespace flattening can create conflicting names. Deduplication can move equivalent types into a lowest-common-ancestor namespace.

Source:
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator/src/generator/schema.rs

**Inference.** `ExecutionAuthorizationWitnessV0` cannot bind only the high-level MCP input. It must bind the exact request-encoding configuration and schema/tool-description version/digest. Otherwise the same external tool call can map to materially different Cedar semantics across deployments/configurations.

New hard regression:
`request_encoding_config_mismatch_cannot_reuse_witness` — change any grant-relevant generator setting after authorization; the old witness cannot authorize execution.

## C374 — current WASM/Python request-generation surface drops the typed input context from its returned authorization components

**Observed.** The core Rust `generate_request()` validates MCP input, converts typed arguments to Cedar expressions/entities, and constructs the request with an `input` field in Cedar context. But the convenience `AuthorizationComponents` returned by `generate_request_components()` contains only `principal`, `action`, `resource`, and `entities_json`; its own comment says the caller is responsible for constructing context from the MCP tool input. The current WASM `generateRequest()` and Python `generate_request()` public return shapes likewise expose only principal/action/resource/entities, not the generated Cedar context.

- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator-wasm/src/lib.rs
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator-wasm/README.md
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator-python/cedar_mcp_schema_generator/__init__.py

**Inference.** For policies that depend on tool arguments, crossing the current convenience FFI surface introduces a second independently implemented request-context construction step. The Rust generator may have correctly validated/typed the input, while a JS/Python caller can omit, alter, differently round, or differently serialize the context actually submitted to the authorizer. The policy decision would then be about a different request.

**Scope guard.** This does not prove that every consumer is vulnerable; a careful caller can reconstruct context correctly. The finding is that the public convenience API does not itself carry the grant-relevant context through the boundary, so end-to-end equality is not guaranteed by this interface.

New hard regressions:
- `ffi_request_context_roundtrip_must_preserve_semantics`.
- `argument_sensitive_policy_requires_bound_context`.
- `missing_context_cannot_fall_back_to_less_restrictive_request`.

Preferred design: return one canonical serialized authorization request or a typed request object/digest from the trusted generator, not independently reconstructed PARC pieces.

## C375 — request generation validates against a regenerated local schema, not necessarily the exact schema deployed with the authorizer

**Observed.** The WASM `generateRequest()` path accepts `schema_stub`, `tools_json`, and `config_json`, constructs a fresh `SchemaGenerator`, adds tool descriptions, creates a fresh `RequestGenerator`, and validates the request against that generated schema. Its output carries no schema digest/version. Schema generation for the authorizer is a separate call with the same inputs.

Source:
- https://github.com/cedar-policy/cedar-for-agents/blob/ebaa70a8c1139f87bb394f636fe8e4f52e627fe2/rust/cedar-policy-mcp-schema-generator-wasm/src/lib.rs

**Inference.** Validation only establishes that the request matches the schema regenerated in that call. It does not establish that the exact same schema/tool-description/config tuple is the one installed with the policies/authorizer. A stale tool description or config drift can therefore create two individually valid but semantically different worlds.

New invariant:
`authorization_schema_digest == request_generator_schema_digest == active_policy_schema_digest` before execution. Also bind tool-description digest and generator config digest.

New regressions:
- `schema_digest_mismatch_cannot_execute`.
- `tool_description_version_mismatch_cannot_execute`.
- `request_generator_config_drift_cannot_execute`.

## C376 — canonical request identity should be computed after trusted semantic normalization, not from raw JSON text

**Observed.** The request generator parses MCP input into typed values, validates it against the matching tool description, and then lowers those typed values to Cedar restricted expressions/entities. Raw JSON surface syntax therefore is not the final authorization semantics. For example numeric encoding can change depending on configuration; objects can become records or entities; deduplication can change type placement.

**Inference.** The execution witness should carry at least two linked digests:

1. `raw_effect_input_digest` — exact bytes/structured RPC input that will be dispatched, for TOCTOU/equality checks;
2. `canonical_authorization_request_digest` — digest of the normalized typed Cedar request + relevant entities/context/schema epoch.

The trusted mapping step proves or validates the relation between them. Comparing only raw JSON hashes misses semantic-normalization bugs; comparing only Cedar request hashes misses dispatch mutation.
