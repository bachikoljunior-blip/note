## C329 — effect truth and response truth should be modeled separately
Public source: *Verified Tool Calls Improve LLM Agent Reliability Under Non-Atomic Failures*, arXiv:2608.02645 (2026-07-31).

The paper explicitly separates the **effect channel** (what state transition actually occurred) from the **response channel** (what acknowledgement the agent observed), and tests timeout-after-dispatch, delayed visibility, partial success, and stale-conflict faults. A retry policy that treats missing/ambiguous response as proof of no effect is therefore structurally unsound.

For the CSSC causal journal, `EffectAttempt/EffectReceipt` should not collapse into one binary success field. A physical response is evidence about the attempt, not authoritative evidence that the intended postcondition is false or true.

Source: https://arxiv.org/abs/2608.02645

## C330 — use a tri-valued postcondition verifier for ambiguous effects
The same paper defines a read-only postcondition verifier returning `TRUE / FALSE / UNKNOWN` and uses verify-before-retry. `TRUE` means the intended effect is already present, `FALSE` means it is confirmed absent, and `UNKNOWN` covers inconclusive state such as eventual-consistency windows.

This maps cleanly onto recovery semantics:
- `TRUE` => reconcile the in-doubt Attempt as effect-complete without redispatch;
- `FALSE` => retry only if the logical operation is still authorized and retry-safe;
- `UNKNOWN` => keep the operation in-doubt/censored, poll or defer, and do **not** silently classify it as failure.

For provider/checker/tool paths without a queryable postcondition, `UNKNOWN` is the honest state. This strengthens the existing rule that an Attempt without Receipt must remain conservatively reserved after restart.

Source: https://arxiv.org/html/2608.02645v1

## C331 — idempotency and verification are complementary, but blind retries can be harmful
The paper's main experiment uses 300 runs over two workflow tasks and three fault levels with the model/tools held fixed. On `activate_customer`, baseline success falls from 92% at low fault to 64% at high fault while the wrapped agent remains at 100%; duplicate side effects at high fault fall from 72% to 20%. On `record_invoice`, high-fault duplicates fall from 76% to 20%.

More important for controller recovery, its separate medium-fault ablation reports approximately:
- retry-only baseline: 58% task success, 42% duplicates;
- verify-only: 80% success, 20% duplicates;
- verify-before-retry: 72% success, 28% duplicates.

The authors caution that this ablation uses a separate run configuration, so those absolute rates must not be compared to the main figures. Within the ablation, however, the direction is useful: retrying is not automatically beneficial even after verification.

Implication for the CSSC substrate: if an external effect lacks a provider-supported idempotency/query contract, recovery should prefer deterministic verification or conservative `UNKNOWN` over automatic redispatch. Idempotency keys strengthen the guarantee when the underlying service actually honors them; they are not created merely by hashing a request locally.

Source: https://arxiv.org/html/2608.02645v1

## C332 — Hoare-style pre/post contracts can unify legal gating and commit verification
Public source: *ToolGate: Contract-Grounded and Verified Tool Execution for LLMs*, Findings of ACL 2026 / arXiv:2601.04688.

ToolGate represents trusted world state explicitly and gives each tool a Hoare-style precondition and postcondition. The precondition gates invocation; the postcondition gates whether the observed result is committed into trusted symbolic state.

For CSSC this suggests a simpler canonical effect contract per action/tool/checker/provider edge:

```text
P_effect(state, action) -> invocation/admission allowed?
Q_effect(pre_state, attempt, observed_state) -> TRUE | FALSE | UNKNOWN
```

The existing `baseline_frontier_eligible`, mechanical reducer preview, budget admission, effect Attempt/Receipt, and recovery class can be projected onto this contract boundary rather than maintained as unrelated booleans. Crucially, only verified postconditions may advance the trusted recovery state for effectful operations.

Sources:
- https://arxiv.org/abs/2601.04688
- https://aclanthology.org/2026.findings-acl.470/

## C333 — learned contracts are useful for ranking, not sufficient as the hard safety mask
Public source: *Contract2Tool: Learning Preconditions and Effects for Reliable Tool-Augmented LLM Agents*, arXiv:2606.07904.

Contract2Tool learns preconditions/effects/risk/cost from metadata, schemas, documentation, and traces. In its controlled benchmark, learned-contract causal filtering achieves 0.980 downstream success versus 0.990 for gold contracts, while reducing visible tools from 100 to 1 and average token usage from 26,172 to 2,528 relative to all-tools exposure.

That is strong evidence that learned contracts can be valuable for **soft ranking or proposal support construction**. It is also direct evidence that they are not exact. For randomized CSSC data collection, the authoritative `legal_action_mask` / irreversible-effect guard must therefore remain deterministic and mechanically validated. A learned precondition/effect model may rank among already-safe actions, predict likely `WOULD_NOOP`, or propose a contract for review, but should not grant capability.

Source: https://arxiv.org/abs/2606.07904

## C334 — contract integrity itself is a load-bearing assumption
Public source: *The Gate Is Only as Honest as Its Contracts: ContractGuard for the Contract Layer of Risk-Aware Causal Gating*, arXiv:2606.18550.

The paper shows that causal gating moves trust into the contract layer rather than eliminating it. In its threat model, forged **effects** are more dangerous than naive risk-label tampering because causal-path membership depends on effects. ContractGuard adds signed provenance, typed attestation, and runtime effect verification; on the paper's controlled benchmark it reports zero injection success for all modeled attacks, including an adaptive white-box attacker, without rejecting honest contracts.

For CSSC, the implication is not to import this security stack wholesale. The useful constraint is narrower: effect summaries used to expose/randomize actions must be tied to versioned substrate code or typed mechanically checked predicates, not free-form model text or telemetry that the model can influence. Learned/derived effect contracts need provenance and runtime parity checks before they can influence a hard mask.

Source: https://arxiv.org/abs/2606.18550

## C336 — deterministic invariants should precede learned failure monitors
Public source: *Real-Time Detection and Repair of LLM Agent Failures*, arXiv:2608.02464 (2026-08-03).

Across 2,823 agent episodes the learned telemetry monitor reports AUROC 0.872 and detects 0.71 of failures at a 5% false-alarm budget, but a deployment shift requires recalibration. The paper's deterministic verification layer recomputes required task facts from actual tool results; it catches 60% of failures, 96% with a coverage check, with 0/63 false positives in the reported head-to-head. Targeted rollback/re-run recovers 45% of flagged failures versus 16% for resampling control and raises task success from 52% to 73% for roughly one additional model call per run.

This is not theorem-proving evidence and should not be generalized to Lean solve rates. It does support an engineering ordering: first enforce cheap deterministic completeness/coverage invariants over the causal journal; only then add learned anomaly or value models. Recovery actions should be targeted from verified failure state, not triggered by a generic monitor alone.

Source: https://arxiv.org/abs/2608.02464

## Synthesis / design update

The causal journal can be simplified around one verified-effect abstraction without weakening prior contracts:

1. **Hard precondition** `P_effect`: mechanical legality, version, authorization, effect precondition, and budget admissibility.
2. **Durable dispatch identity**: stable logical operation ID + physical Attempt(s), with provider/tool idempotency capability recorded explicitly rather than assumed.
3. **Tri-valued postcondition** `Q_effect`: `TRUE/FALSE/UNKNOWN`, independent of the response channel.
4. **Commit rule**: trusted controller/recovery state advances only from verified postconditions or exact local reducer transitions.
5. **Retry rule**: retry only from `FALSE` plus still-valid authority and a retry-safe/idempotent contract; `UNKNOWN` remains in-doubt.
6. **Learning boundary**: learned contracts/value models may rank or reduce exploratory alternatives **inside** the deterministic safe set, never widen it.

This does not replace the existing `RunInstanceV0`, generation Attempt/Receipt, `ProposalBatchFinalizedV0`, `BehaviorSelectionV0`, Decision/Consumption/Outcome, workspace snapshots, or cost compartments. It gives those records one consistent effect/recovery semantics and adds a falsifiable invariant: no effectful redispatch from `UNKNOWN` unless a substrate-specific idempotent/queryable contract proves it safe.
