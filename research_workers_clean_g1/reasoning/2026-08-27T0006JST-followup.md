## C391 — certified access-control policy languages already exist; the frontier is the source-to-language and deployment correspondence

**Observed.** TEpla is a certified Type Enforcement access-control policy language with explicit formal semantics encoded in Coq. The 2023 paper reports approximately 4,700 lines of Coq, no axioms for the stated predicate conditions, and machine-checked proofs of language properties. TEpla has an explicit BNF grammar and a three-valued authorization decision semantics. The paper states that program extraction from the Coq algorithms used to express TEpla semantics is **future work**, alongside certified policy-analysis tooling.

Primary sources:
- https://www.eecs.uottawa.ca/~afelty/dist/isse23.pdf
- https://www.site.uottawa.ca/~afelty/isse22/

**Observed.** ACCPL is an earlier Certified Core Policy Language for access control, also encoded in Coq. Its semantics are a translation from policy statement + access request + environment to access decisions. The paper ties the translation function directly to the correctness theorem and reports machine-checked correctness results. It explicitly presents Coq program extraction as a path to executable decision programs and proposes ACCPL as a target/intermediate language for other policy languages, while certification of those source languages with respect to ACCPL remains future work.

Primary sources:
- https://www.site.uottawa.ca/~afelty/dist/pst17.pdf
- https://www.site.uottawa.ca/~afelty/accpl/

**Correction/refinement to the prior frontier.** The missing object is **not** “a formally verified authorization language.” That exists. Nor is it merely “a formally verified policy evaluator.” ACCPL/TEpla substantially cover formal semantics and evaluator properties. The high-value missing chain is:

`human/controlled source -> faithful source semantics -> certified policy language/IR -> executable/deployed decision engine -> exact runtime effect authorization`.

Specifically, this invocation still did not establish an end-to-end machine-checked compiler from a human-oriented controlled policy language into TEpla/ACCPL/Cedar/Datalog plus a proved production-runtime correspondence.

**Scope guard.** TEpla and ACCPL proofs concern the semantics/properties of their formal languages. They do not prove that an arbitrary natural-language or controlled-English policy was translated faithfully into them, nor that a separate production runtime executes an extracted/compiled policy with theorem-level correspondence.

## C392 — use a certified policy language as the semantic anchor; translation validation should target that anchor rather than arbitrary runtime syntax

**Inference from C385–C391.** A stronger architecture is now available than inventing a fresh `AuthAST` semantics from scratch. A compact certified authorization language such as ACCPL/TEpla, or a comparably mechanized Cedar/Datalog core, can serve as the **semantic anchor IR**. The untrusted source compiler can then be validated against a fixed, machine-checked decision semantics.

Candidate pipeline:

`controlled-formal source -> verified parse/source denotation -> untrusted lowering -> CertifiedPolicyIR -> translation-validation theorem/certificate -> executable evaluator/production engine correspondence -> PolicyActivationCertificate`.

The translation certificate should prove at least one of:
- semantic equivalence for all requests/environment states in the supported source fragment; or
- a conservative refinement in which the target's permitted set is a subset of the source-authorized set, while explicit obligations/denials remain preserved.

For positive authority, a weaker “same parse tree shape”, “same generated rule count”, “LLM agreement”, or benchmark-level translation accuracy is insufficient.

## C393 — Cedar's production strategy shows an explicit proof-vs-production correspondence boundary, not an end-to-end deployment proof

**Observed.** Cedar's verification-guided development uses Lean models and mechanized proofs for key authorization properties, including default deny, forbid-overrides-permit, explicit allow, slicing soundness, validation soundness, and termination. Production code is Rust. Rather than formally proving the Rust implementation equivalent to the Lean model, Cedar uses differential random testing over millions of generated policies/requests/entities plus property-based testing. The published 2024 account reports four bugs found while developing proofs and 21 additional bugs found by differential/property testing. It also states that the production parser is not modeled in Lean; parser roundtrip/safety are tested instead.

Primary source:
- https://arxiv.org/abs/2407.01688

**Inference.** `PolicyActivationCertificate` and deployment witnesses should distinguish evidence levels:
- `semantics_machine_checked`;
- `compiler_translation_validated`;
- `production_correspondence_formally_proved`;
- `production_correspondence_differentially_tested`;
- `parser_roundtrip_tested_only`.

A verified semantic model plus very strong differential testing is materially stronger than an unverified runtime, but it must not be mislabeled as a theorem that the deployed implementation is equivalent to the model. For effect authorization, the exact production version/digest remains grant-critical.

## Updated synthesis

The strongest currently supported semantic architecture is:

1. Make the grant-authoritative policy source machine-formal or a controlled language with fixed formal semantics; otherwise require trusted confirmation.
2. Parse it through verified/validated parser infrastructure into a canonical source AST.
3. Lower to a **certified authorization semantic core** (ACCPL/TEpla-like or an equivalently mechanized target).
4. Check a translation certificate proving equivalence or authority non-amplification and source-clause coverage.
5. Separately establish how the certified semantic core corresponds to the deployed decision engine; do not conflate model proof with differential-testing evidence.
6. Activate only after exact version/digest joins are fixed, then issue per-effect request-bound authorization witnesses.

This turns the frontier from an open-ended “verify NL policy compilation” question into three independently falsifiable edges: **source faithfulness**, **certified IR lowering**, and **production correspondence**.
