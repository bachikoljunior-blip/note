## New findings

### C89 — Seed-Prover 1.5 gives direct evidence that terminal RL can implicitly learn tool-allocation efficiency, but not that a separate controller is causally responsible

Primary source: Seed-Prover 1.5, arXiv:2512.17260, https://arxiv.org/abs/2512.17260 .

The paper's agentic RL policy interleaves Lean verification, Mathlib semantic search and Python calls, with no fixed ordering and multiple tool calls per turn. Training uses a terminal Lean-verification reward (`+1` verified, `-1` otherwise) through VAPO/PPO-style agentic RL. During training, average function calls fall roughly from 15 to 10 and average sequence length from about 28k to 17k while theorem-proving performance rises. Search usage also adapts by problem distribution: FATE-H trajectories use roughly 10 Mathlib searches on average, while Putnam uses roughly 1–2; later checkpoints tend to use fewer searches while improving performance.

Interpretation: terminal verifier reward can induce a large autoregressive prover to become more selective about expensive interactions rather than merely learning stronger tactic text. This strengthens the evidence that resource allocation is learnable from terminal proof success.

Scope guard: Seed-Prover is a full-model/free-form agent policy, not a factored compact meta-controller. Its binary reward has no explicit token/$/Lean-time term; legal-action masks, exact behavior propensities and controller-only ablations are not exposed. The observed efficiency change therefore cannot isolate a causal routing module from general model improvement.

### C90 — A current public Lean project independently converges on almost exactly the compact cost-sensitive action space, but its controller is deliberately heuristic

Public artifact: `anetigone/cssc`, https://github.com/anetigone/cssc .

The project explicitly studies fixed-budget Lean proof search and exposes meta-actions closely aligned with the current frontier: cheap tactic expansion, cheap local repair, retrieval, strong-model detailed proof, strong-model decomposition, backtrack, prune and stop. It proposes controller-facing state containing goals/local context, recent error class, branch depth/history and remaining budget, and evaluation metrics including solved tasks under fixed budget, token cost, verifier calls, strong-model calls, pruning accuracy and timeout/repetition rates.

Crucially, the README says the first controller is intentionally small and heuristic: fixed action costs, fixed error-category rules, best-first progress-per-cost, budget phases and fixed escalation thresholds, with **no learned value model in the first version**.

Interpretation: this is independent engineering convergence on the same research question and a useful concrete heuristic baseline/action ontology for a matched study. It does **not** close the learned compact-controller gap and is not evidence that a learned controller improves proof success.

### C91 — Leanstral 1.5 has an unusually open reproducible execution surface, but official OPE-identifiable trajectories are still missing

Official sources: Mistral Leanstral 1.5 model/docs (June 30/July 2026), https://docs.mistral.ai/models/leanstral-1-5 ; Mistral `LeanstralSafeVerify`, https://github.com/mistralai/LeanstralSafeVerify .

Leanstral 1.5 is open-weight under Apache-2.0, exposes function calling, and is intended for Lean 4 agent use with filesystem/shell/Lean-LSP style tooling. Mistral's reported training uses CISPO RL in both a multiturn theorem-refinement environment and a code-agent environment; SafeVerify replays/checks generated Lean environments to prevent unsound acceptance. This makes Leanstral a plausible fixed low-level model/executor substrate for a controller experiment because the model and final verifier surface are publicly runnable.

A third-party preserved-evaluation dataset, `yidannwang/Leanstral-1-5-results` on Hugging Face, reports per-attempt metadata, generated Lean files/trajectory streams, compiler and SafeVerify logs, token budgets, timeout/exit/verification fields and fixed-budget plus rescue attempts. This can be valuable for descriptive state/error/cost modeling.

Scope guard: the third-party dataset is **not an official Mistral training-trajectory release**. Evaluation trajectories do not provide a known randomized behavior policy, exact action propensity or authoritative legal-action mask. Rescue phases are adaptively selected and use heterogeneous budgets. Therefore these traces should not be used for unbiased OPE/policy-value claims unless the logging policy and support can be reconstructed and verified; use them first for supervised representation/error taxonomy/cost modeling.

## Updated synthesis

The strongest current experiment is no longer motivated by the claim that formal-proof outer behavior cannot be learned; Seed-Prover/Leanstral refute that broad claim. The sharper question is whether a **small typed controller** can capture the useful resource-allocation behavior while keeping the low-level prover/executors fixed, making cost, legal actions, propensities, replay and safety observable.

A practical matched substrate is emerging: use an open low-level Lean model/executor (Leanstral or a smaller open prover), a SafeVerify/kernel-backed checker, and CSSC-like atomic meta-actions. Compare: deterministic/rule controller; free-form LLM planner; BC on logged actions; terminal trajectory advantage weighting; sequential verifier-grounded value/advantage; cost-aware constrained typed policy; and, where feasible, a full-model agentic-RL reference. Freeze theorem set, Lean/Mathlib, low-level model, retrieval corpus, tool implementations, cache/memory, and real budget.

Historical/evaluation trajectories without propensities remain useful for feature engineering but not causal OPE. A new OPE-ready collection must log exact structural state, hard legal mask, randomized safe subset, deterministic baseline/fallback, full behavior distribution, chosen action/`mu_chosen`, deterministic executor version, effect identity/result obligations and the full remaining budget vector. Stage-A randomization should stay with pure-local P0 and bounded deterministic E1 read/compute actions; persistent E2 and terminal/resource-commitment E3 actions remain baseline/gated until idempotency/authorization/exact-once semantics are explicit.
