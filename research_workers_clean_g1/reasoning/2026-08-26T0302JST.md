## C46 — BFS-Prover-V2's released implementation makes replanning a separate fixed-trigger phase rather than a learned replan decision

Primary/public artifact:
- `ByteDance-Seed/BFS-Prover-V2`, inspected at commit `ada0f976e95b09e0b9efa8f171fdf4b09e161ba0`.
- Relevant files: `README.md`, `src/plan/main.py`.

Implementation evidence:
- The public CLI has two explicit planner modes, `initial` and `replan`; `dynamic_replanning(...)` is a separate call path that sets `is_replan=True`.
- The README instructs users to generate an initial plan, then optionally invoke `run_local_replan.sh` **when proof search gets stuck**. It does not expose a learned state-value or calibrated marginal-value trigger deciding when to replan.
- The paper's operational description similarly triggers dynamic replanning when the current subgoal exhausts its search budget; successful earlier subgoals are preserved in the shared cache/context.
- The planning code explicitly notes that replanning updates plans while proof-search progress is preserved.

Interpretation:
- C44 established that planner-guided focused parallelism + replanning is a strong system design. The released code now sharpens the remaining gap: **replanning itself is still a fixed/event-driven meta-action**, not a learned decision over `keep searching / repair / decompose / replan` with calibrated expected value and cost.
- This produces a concrete matched experiment: keep the planner/prover/cache fixed and compare fixed budget-exhaustion replanning against a learned trigger using trajectory progress, compiler-error diversity, proof-state value, attempt history and remaining budget.
- The public implementation also supports preserve-and-replan rather than destructive global restart: the plan changes while already-established progress remains available.

Scope / caution:
- Absence of a learned trigger from the surfaced public implementation does not prove that no private or later experimental scheduler exists.
- `initial` vs `replan` CLI separation is implementation evidence, not a performance ablation.
- The planner headline gain remains non-compute-matched and cannot be attributed solely to the replan trigger.

## C47 — AlgoSkill gives a program-synthesis precedent for a learned typed multi-action scheduler with verifier-derived repair credit

Primary source:
- `AlgoSkill: Learning to Design Algorithms by Scheduling Human-Like Skills`, arXiv:2606.29999v1, submitted 2026-06-29; currently under review.

Mechanism:
- Models algorithm design as sequential control over a library of 20 **typed skills** rather than free-form code edits. Skills include abstraction, constraint analysis, brute-force oracle construction, state design, data-structure selection, decomposition, proof/invariant checking, counterexample construction and complexity refinement.
- Each skill has an applicability precondition, transition, expected postcondition, complexity effect, verification rule and known failure modes. Invalid actions are masked before policy selection.
- The learned policy conditions on problem type, constraints, current plan/code, current complexity estimate, recent failed tests/verifier messages and skill history.
- MCTS searches skill sequences using the learned policy prior and verifier-backed value; compilation, unit/stress testing and complexity analysis feed reward back to state-skill choices.
- The reward includes an explicit repair term for `failed -> passing`, and local credit uses the reward delta after each skill. Entropy regularization discourages early collapse to a small action subset.

Evidence:
- On the paper's audited CP-275 table **after filtering to positive-gain backbones**, correctness is Haiku Direct **78.2% (215/275)** vs AlgoSkill **80.7% (222/275)**; Gemini Direct **11.6% (32/275)** vs AlgoSkill **18.2% (50/275)**.
- Version-1 leave-one-skill-out sensitivity over 60 runs reports full greedy library **57/60 = 95.0% pass@1**; removing problem abstraction drops to **44/60 = 73.3%**; removing brute-force oracle or state design gives **53/60 = 88.3%**; removing counterexample or complexity refinement gives **52/60 = 86.7%**.
- Search is not uniformly beneficial in every reported slice. On one hard 20-problem sample, greedy policy and beam search both achieve **90.0% pass@1**; greedy is slightly better at pass@5 (**19/20 vs 18/20**). On HB-15, AlgoSkill-MCTS and Reflexion both solve **7/15**, while greedy AlgoSkill solves **4/15**.

Interpretation for formal reasoning:
- This is useful cross-domain evidence that a controller can learn over an explicit heterogeneous action vocabulary with **typed applicability**, failure-history conditioning, verifier reward and action-level credit instead of merely learning a scalar proof-state ranking.
- The closest Lean transfer would expose actions such as `continue tactic search`, `semantic diversify`, `local compiler repair`, `retrieve`, `decompose`, `replan`, `preserve/backtrack`, and perhaps `model escalate`, with preconditions and verifier-grounded transition features.
- The negative evidence matters: the result does **not** support always adding tree search. Typed action structure and learned state-dependent scheduling may carry value even when a greedy controller is competitive.

Scope / caution:
- Competitive-programming/program-synthesis evaluation, not Lean proof search; functional tests and complexity judges are weaker correctness signals than a proof kernel.
- The paper is under review and mixes audited version-2 tables with version-1 sensitivity experiments; preserve version labels.
- The main CP-275 table is explicitly filtered to positive-gain backbones, so it is not evidence of universal backbone-level improvement.
- Some optimality labels use an LLM judge; do not transfer those as verifier-grounded proof claims.

Source:
- https://arxiv.org/html/2606.29999v1

## C48 — HILBERT supplies a strong Lean hierarchy of cheap-first proof attempts, retrieval, verifier-guided repair and recursive decomposition, but its escalation thresholds are fixed

Primary/public sources:
- `Hilbert: Recursively Building Formal Proofs with Informal Reasoning`, ICLR 2026 / arXiv:2509.22819.
- Public code: `apple/ml-hilbert`.

Mechanism relevant to routing:
- For each generated subgoal, first try the specialized Lean prover directly with a small fixed candidate budget.
- If that fails, ask the more expensive informal reasoner whether the subgoal is mathematically/formally well-posed.
- If the subgoal is sound but still hard, use a shallow-solve stage with Mathlib retrieval and verifier-guided proof correction; the published algorithm uses fixed retry/correction budgets and a proof-length threshold to decide when shallow repair has become too expensive.
- If shallow solving still fails, recursively decompose the subgoal; if the plan itself is incorrect, revise the proof sketch; if the overall decomposition fails, restart the theorem-level decomposition.

Evidence:
- ICLR 2026 reports **99.2% MiniF2F** and **462/660 = 70.0% PutnamBench** for the strongest configuration.
- Retrieval is both an accuracy and compute intervention in the reported MiniF2F ablation. With DeepSeek-Prover-V2, retrieval changes **97.1% -> 98.4%**; with Goedel-Prover-V2, **97.9% -> 99.2%**.
- For the Goedel configuration, retrieval reduces average reasoner calls **862 -> 548** and reasoner tokens about **4.0M -> 2.3M** while improving the solve rate. The DeepSeek configuration also reduces average prover calls and reasoner tokens.

Interpretation:
- HILBERT strongly validates the **heterogeneous action hierarchy** itself: cheap formal attempt first; only escalate to expensive semantic checking/retrieval/repair/decomposition when cheaper proof search fails.
- It also provides direct Lean evidence that retrieval can reduce total reasoning compute rather than merely add cost, because surfaced premises simplify downstream repairs and avoid theorem-name failures.
- But the switch policy remains largely rule/threshold driven. This complements C46: modern high-performing hierarchical Lean systems expose useful meta-actions, while the decision of *when* to invoke each action is still an open learned-control problem.

Scope / caution:
- Headline results include substantial recursive internal compute and multiple heterogeneous models; they are not one-model/pass@1 comparisons.
- The routing steps use fixed attempt counts, recursion depth and proof-length thresholds rather than calibrated expected-utility estimates.
- Strong result does not establish that the exact action order is optimal under a matched real-compute budget.

## Updated synthesis

The latest evidence changes the frontier from `do heterogeneous meta-actions help?` to **how should a controller schedule already-useful heterogeneous meta-actions under real cost and uncertainty?**

1. Strong Lean systems already expose a meaningful action hierarchy: cheap prover attempts, retrieval, local verifier repair, subgoal decomposition and replanning (C44/C46/C48).
2. Public BFS-Prover-V2 and HILBERT use mostly **fixed failure/budget thresholds** to switch levels. The high-value next step is a calibrated marginal-value trigger, not inventing another static hierarchy.
3. Program synthesis now supplies an explicit learned typed-action precedent (C47): mask inapplicable actions, condition on failure history/state, learn context-dependent action value, preserve action diversity, and credit successful repairs locally.
4. Search itself should remain optional. C47's reported slices show greedy scheduling can match or beat a search variant; the controller should buy tree search only when its expected information/coverage gain exceeds overhead.
5. Retrieval should be priced by downstream savings, not only retrieval latency. HILBERT's retrieval ablation shows higher accuracy with materially fewer expensive reasoner tokens/calls in the tested configuration.
6. The target Lean experiment is therefore a **typed, calibrated, substrate-aware meta-controller** over `continue`, `diversify`, `repair`, `retrieve`, `decompose`, `replan`, `preserve/backtrack`, and `escalate`, trained/evaluated on actual verifier transitions and real cost.

## Rejected / narrowed leads this run

- **BFS-Prover-V2 already learns when to replan:** not supported by the released control surface; replanning is exposed as a separate phase and the paper triggers it after current-subgoal budget exhaustion.
- **A fixed high-performing hierarchy closes the routing problem:** rejected. HILBERT is strong, but its fixed retry/length/depth thresholds leave action timing and resource allocation unoptimized.
- **Tree search is inherently better than a learned greedy action scheduler:** weakened by AlgoSkill's own hard-sample ablation; typed state-dependent actions can be valuable without universal MCTS dominance.
- **AlgoSkill proves the same controller will improve Lean:** rejected; it is a program-synthesis transfer lead, not theorem-proving evidence.
- **Retrieval necessarily increases inference cost:** false in HILBERT's tested configuration; it reduces expensive downstream reasoner/prover work while improving solve rate.

## Nonempty unresolved frontier

1. **Matched Lean meta-action scheduler:** compare fixed HILBERT/BFS-style thresholds against a learned policy over keep-searching, repair, retrieval, decomposition/replan, preserve/backtrack and model escalation with identical available tools and real compute.
2. **Calibrated replan/action utility:** Brier/ECE/reliability/selective-risk for the marginal value of one more local attempt versus replan/decompose/retrieve/restart under theorem-family, proof-depth and policy shift.
3. **Typed action preconditions in Lean:** determine whether error class, proof progress, retrieval support, context coverage, attempt history and budget can safely mask impossible/low-value actions before expensive policy scoring.
4. **Matched subgoal scheduler comparison:** ordered first-stuck focused parallelism vs AlphaProof hardest-branch vs independent parallelism vs total-work/tail-risk allocation.
5. **Compressed online trajectory sufficiency:** combine LeanProgress/DT-Solver history value with Delta/error/retrieval summaries without raw trajectory growth.
6. **Variable branching/search purchase:** learn when greedy action scheduling suffices and when MCTS/beam/semantic branch expansion has positive marginal value.
7. **Triggered global re-retrieval:** learned escalation from failure-conditioned local retrieval to a fresh global proof-route retrieval cycle.
8. **Execution-substrate-aware cost:** model generation, retrieval, verifier/tactic work, snapshot/reconstruction and wall-clock separately; include downstream compute savings from retrieval.
9. **Exact Lean composite:** snapshot/fork + semantic tactic diversity + compiler repair + typed/calibrated hierarchical meta-action routing under equal real compute.
10. **Benchmark-audited robustness:** pin Lean/mathlib/repository/harness and prevent candidate/retrieval leakage.
