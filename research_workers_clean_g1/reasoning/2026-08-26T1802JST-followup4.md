## C277 — current Lean server checks have no stable per-check JSON-RPC request identity
`LeanServerClient.check_file()` does not issue a JSON-RPC request for the proof check. It:

- chooses `uri = path.as_uri()`;
- increments an in-memory per-URI `document_version`;
- sends `textDocument/didOpen` as a JSON-RPC **notification** (no request id);
- waits for in-memory diagnostics / `$/lean/fileProgress` state for that URI;
- sends `textDocument/didClose`, also as a notification.

The `_next_id` request counter is used by ordinary `_request(...)` calls such as server initialize/shutdown, not by the document check itself.

Therefore there is no current per-proof-check protocol request ID that can serve as a durable `effect_operation_id` or be queried after controller/server restart.

## C278 — Lean server completion state is process-local and non-reconcilable after restart
Completion bookkeeping (`_diagnostics`, `_completed_documents`, `_processing_documents`, diagnostic publication count/deadline, per-URI document version) lives only in the `LeanServerClient` process memory. Restarting/closing the server discards it. A crash after `didOpen` but before the controller records the result cannot later ask the restarted Lean server, by operation identity, whether that exact check completed and what resources it consumed.

This independently confirms `effectful_checker_fail_closed` for v0 recovery.

## C279 — subprocess checks likewise expose no durable application-level operation receipt
`ProcessGroupRunner.run()` creates a process, waits, kills the process group on timeout, and returns/raises in memory. The process PID/process-group identity is not written to a durable causal journal before dispatch and is not an application-level idempotency key or post-crash result store.

A machine/process crash can therefore leave the application without a durable fact distinguishing a check that never launched from one that consumed most of its timeout budget before dying.

## C280 — current check/model budget reservations are volatile counters
`BudgetManager.reserve_check()` and `reserve_model_call()` increment process-local counters. They are intentionally simple runtime accounting, not durable reservations. Thus after process restart, coarse counts alone cannot reconstruct whether an in-doubt effect already consumed a check/model slot.

For a crash-safe experimental harness, the durable journal must be authoritative for budget reconciliation:

- a committed effect dispatch/Attempt counts as consuming the reserved check/model-operation budget unless a stronger substrate-specific reconciliation contract proves otherwise;
- an in-doubt effect remains counted conservatively, even when no result/cost receipt exists;
- replay of a `pure_reducer_replayable` action consumes no new check/model reservation;
- recovery must rebuild remaining budget from durable decisions/effect attempts/physical receipts rather than reset to a fresh in-memory `BudgetManager`.

This is a safety/admission accounting rule, not a claim about true resource cost; in-doubt actual cost may remain unknown/censored.

## C281 — separate three quantities that are easy to conflate after crashes
For each effectful action maintain separately:

1. **admission reservation** — whether the controller committed budget permission for dispatch;
2. **physical cost receipt** — what resource use was actually measured for physical attempts;
3. **policy outcome/reward** — terminal/verified consequence of the selected action.

An in-doubt action may have reservation=consumed, physical cost=unknown/censored, outcome=unknown/censored. Filling either unknown field with zero is invalid.

This separation also prevents recovery from accidentally granting extra checker/model attempts merely because a prior process died before recording its final result.

## C282 — effectful action support remains blocked by observed substrate facts, not by generic conservatism
At the pinned CSSC version all three checked effect substrates lack the needed reconciliation guarantee:

- Lean LSP check: notification/URI/process-local completion state, no stable check request/receipt;
- Lean subprocess: process-local PID/result only;
- action-level checker cost: post-return final event only.

Therefore excluding checker-bearing actions from the first randomized support is now grounded in concrete implementation evidence. A future substrate version may relax this if it introduces durable operation IDs and queryable/idempotent receipts.
