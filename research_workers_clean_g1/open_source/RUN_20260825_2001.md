## Branch 1 — ReasoningBank SWE-Bench memory path is active, online, and forced top-1

Public repository: `google-research/reasoning-bank` at current main observed in this run.

### Execution path

`SWE-Bench/run.sh` invokes the vendored mini-SWE-agent command directly:

- `mini-extra swebench`
- model `gemini-2.5-flash`
- subset `verified`
- split `test`
- one worker

There is no separate CLI flag enabling memory; the vendored SWE runner itself contains the memory mechanism.

In `third_party/src/minisweagent/run/extra/swebench.py`, every instance:

1. Loads `./memory/{model_name}.jsonl` or creates an empty file.
2. Calls `select_memory(1, ...)` using the current problem statement and a model-specific embedding cache.
3. Flattens the retrieved prior task's `memory_items` and passes them to `agent.run(task, selected_memory=...)`.
4. After execution, reads the trajectory, asks an LLM judge whether the task was successful, then induces up to three generalized memory items under either the successful-trajectory or failed-trajectory instruction.
5. Appends `{task_id, query, memory_items, status}` to the model-specific memory bank for later instances.

This means the released SWE-Bench path is **online sequential self-evolution over the test stream** rather than evaluation against one immutable prebuilt memory bank. Earlier test instances may affect later instances. That is compatible with a continual/self-evolution framing, but it matters when comparing the result to static-memory or memory-free baselines.

### Retrieval semantics

`memory/memory_management.py` loads the existing embedding cache, embeds the current query, appends the new query embedding to disk, but computes similarity against the pre-append cached tensor. Therefore the current task does not self-retrieve in that same call.

When prior memories exist, `select_memory(1)` takes the single highest-ranked prior task. There is no absolute similarity threshold or confidence abstention. Empty cache/bank yields no memory; otherwise retrieval is forced top-1.

### Memory representation and utilization

`memory/instruction.py` asks the inducer to extract at most three non-overlapping, generalizable memory items. Successful trajectories yield reusable success insights; failed trajectories yield failure explanations / avoidance strategies. The instruction explicitly forbids retaining specific sites, queries, or literal strings as the lesson.

`agents/default.py` injects the selected items into the **system message** and tells the acting model that they *may* be helpful, that it can use them when relevant, and that at each step it should explicitly consider whether to use each item before acting.

Thus ReasoningBank's released SWE path combines:

`forced top-1 prior task retrieval → <=3 generalized success/failure lessons → system-level injection → explicit model-level utilization discretion`.

### Important evaluation caveat

The online memory label used for induction is produced by `llm_judge_status(task, trajectory, model_name)` from the problem statement and trajectory. In the released runner, this induction-time status is not the official SWE-Bench patch evaluator result. Official benchmark scoring is a separate downstream evaluation step. This creates a concrete unresolved question: how often does the online LLM memory label disagree with the official task-native outcome, and what does that do to subsequent memory quality?

This does **not** invalidate the published ReasoningBank result; it identifies an implementation-level mechanism whose noise should be measured before treating the memory bank as outcome-verified experience.

## Branch 2 — Memento differs mainly in retrieval unit, volume, prompt authority, and placement

Public repository: `Memento-Teams/Memento`.

`client/parametric_memory_cbr.py` shows the parametric CBR path:

- `MEMORY_TOP_K` defaults to **8**.
- The retriever ranks the memory pool and returns the top eight; there is no absolute score threshold in the caller and no no-memory fallback when a healthy nonempty retriever/pool is available.
- Retrieved entries are split by `case_label` into positive and negative cases.
- Positive entries are rendered as concrete prior `Question` + `Plan`; negative entries are also rendered as concrete `Question` + `Plan`.
- The generated memory prompt says to provide a plan for the current task **based on the examples**, focus on positive examples, and avoid patterns in negative examples.
- `process_query` first adds the current query to shared history and then appends this memory prompt as a **second user message** before the meta-planner is called.

This gives a sharper public-code contrast with ReasoningBank:

| Component | ReasoningBank SWE path | Memento parametric CBR path |
|---|---|---|
| retrieval count | top-1 prior task | top-8 cases by default |
| abstention | no threshold when bank nonempty | no threshold when retriever/pool healthy |
| retrieval unit | prior task whose output is <=3 generalized lessons | concrete prior case + plan |
| failure representation | generalized avoidance lessons | concrete negative case + plan |
| prompt placement | system message | extra user message to meta-planner |
| utilization contract | explicitly decide whether each item is relevant before acting | plan based on examples; focus positive / avoid negative |

### Candidate `clean-os-g1-003` refinement

The earlier idea that a retrieval-admission threshold explains the observed Memento-vs-ReasoningBank divergence is not supported: **both public implementations retrieve without an absolute similarity threshold** when usable memory exists.

A better testable hypothesis is that negative transfer depends on a combination of:

1. **representation abstraction** — concrete case/plan anchoring vs generalized procedural/avoidance lessons;
2. **retrieval volume** — eight examples vs one prior task / a few distilled items;
3. **prompt authority and placement** — a directive user-message to the planner vs optional relevance-conditioned system guidance;
4. **outcome-label quality** — whether memories reflect task-native success or a noisier proxy;
5. **context interaction** — model × scaffold × domain.

The public EvoAgentBench cell where Memento collapses cannot yet be causally attributed to any one of these components because its third-party adapter/config/per-run artifacts are not public in the benchmark release. The correct next experiment is a matched factorial ablation, not a post-hoc causal story.

## Branch 3 — Argus supplies a separate verification-gated durable-evolution pattern

A separate repo-first frontier action inspected `microsoft/ArgusAgent` and its public technical-report sources.

### Candidate `clean-os-g1-005` — reviewer/verifier-gated admission into durable state

**Mechanism.** Separate production from admission: executor-produced artifacts, memories, skills, routes, procedures, or other reusable state should not become durable truth merely because the producing agent says they succeeded. A separate Reviewer checks current artifacts against explicit stage criteria and, when a task-native verifier exists, uses that external/official evidence. Accepted reusable state can be committed; failed routes remain negative evidence; contradictions may trigger replan/rollback rather than silent continuation.

**Implementation evidence.** The repository exposes stage checklists that the Reviewer certifies. Examples include:

- benchmark authenticity checks that require real outputs and official scorers/metrics rather than success-shaped stubs;
- explicit prohibition on candidate/baseline paths reading gold or scorer-derived fields;
- comparison against published baseline numbers before trusting a harness;
- generation-limit/truncation accounting;
- evidence paths per stage rather than free-form completion claims.

The Reviewer prompt also says that previous acceptance is not itself evidence of truth, that a prior verdict must not be rubber-stamped, and that a suspicious or externally unconfirmed headline number can be reopened. It provides a `reconsider` channel for challenging the plan itself rather than endlessly repairing local symptoms.

**Quantitative operational evidence.** The public technical report records about 78% on 731 SWE-Bench Pro tasks versus about 59% for Direct Copilot, at 1.41x aggregate token use. The report also describes external/task-native gated route changes in MLE-Bench; for example, one initial transparent-conductor approach was rejected at 0.208 RMSLE, then replaced and externally graded at 0.06402 against a 0.06582 bronze threshold.

The associated public paper reports verifier recoveries, review-loop rescues, and lower mature-wave token/time cost, but these are architecture-level operational results rather than a clean ablation of the admission gate itself.

**Scope.** Do **not** infer that the gate alone causes the full benchmark gain. Argus bundles roles, durable state, routing, review, verification, and campaign machinery. Longitudinal mature-vs-early efficiency can also be confounded by task order and accumulated state. The evidence is strong that verifier/reviewer gating is an implemented and operationally useful control pattern; causal effect size of that individual component remains unresolved.
