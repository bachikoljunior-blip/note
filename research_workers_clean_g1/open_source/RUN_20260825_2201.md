## Frontier action 1 — Memento parametric retriever validation audit

### New finding: released checkpoint validation is row-level, while labels are query-level

The released Memento parametric retriever is a pair classifier over `(query, case+plan)` and ranks cases by the class-1 softmax probability. However, its training-data generation assigns the current query's final `is_correct` outcome as `truth_label` to **every retrieved case** for that query. Thus the supervised target is query-level outcome broadcast onto every query-case pair, not an observed marginal utility label for the individual case.

The released `train_memory_retriever.py` then creates its default validation split by shuffling **individual row indices within positive/negative labels**. It does not group by query, case, episode, or task. The README's recommended command uses this internal split with `--val_ratio 0.1 --save_best`. Validation reports accuracy/F1/AUC, and `best.pt` is selected by validation AUC (falling back to F1 only when AUC is NaN).

This creates two coupled validation risks:

1. **Query overlap leakage.** Multiple rows for one query can be divided between train and validation, so the exact query text can appear on both sides. Because every row from that query has the same broadcast `truth_label`, a classifier can benefit from query/outcome memorization without learning which retrieved case is useful.
2. **Exact-row duplicate leakage.** The checked-in raw blob begins with two identical rows for the same `(query, case, plan, truth_label)`. Since splitting is by row index, exact duplicate examples are eligible to land on opposite sides of the split.

The raw artifact immediately shows eight rows for `What is the capital of Columbia County?` with four positive-labelled and four negative-labelled memory cases but the same `truth_label=false`; the next query similarly has positive- and negative-labelled cases all carrying `truth_label=true`. This confirms that `case_label` and supervised `truth_label` are distinct and that the retriever training target does not identify per-case causal contribution.

### Why this matters

A validation AUC selected under row-level splitting is not evidence that the score is calibrated to **held-out-query memory benefit**. It may partly measure whether the model predicts the final success class of queries already represented in training. Therefore a stronger transferable contract for a learned memory router is:

- split validation by query/task/episode group, never by generated pair rows;
- evaluate ranking against pair-specific or counterfactual utility labels where possible;
- separately report unseen-query downstream task delta versus no-memory/non-parametric controls;
- do not use classifier AUC alone as an admission signal for durable memory injection.

### Scope / uncertainty

This finding applies to the **released 2025-10-05 parametric retriever training/data path currently present in the public repository**. It does not establish that the original paper's private/earlier experiment protocol used the same row-level split or that published benchmark gains are invalid. No matched rerun was executed here. The claim is narrower: the public retriever's default validation protocol is not group-held-out by query and cannot by itself establish case-level utility calibration.

## Frontier action 2 — Argus stage-certificate enforcement trace

### Scope correction to `clean-os-g1-005`

`stage-certificates.json` is **not a fail-closed stage-admission ledger** in the released ArgusAgent path.

In `_mission_execution_settlement.py`, the Manager stage decision/transition has already been processed before `record_stage_review(...)` is attempted. The certificate write is inside a broad exception handler explicitly described as an `observability/control aid`; failure is logged and execution continues. Subsequent `stage_continues` handling can keep the mission moving based on the stage transition itself.

The main downstream consumer found in `_planning_cycle_enqueue.py` uses `latest_stage_review(...)` to prevent repeated stage-closing certification churn. If the certificate is missing/unreadable, that function deliberately falls back to completed/reviewed backlog rows for the current stage. Tests verify both the host-certificate path and the backlog fallback behavior.

Therefore the mechanically grounded part of `clean-os-g1-005` should be stated as:

- Reviewer/Manager outcomes affect backlog status, replanning, rollback, learned-candidate promotion, and stage transition through multiple host-owned mechanisms;
- stage certificates add durable fingerprinted evidence and improve re-proposal/churn control;
- **certificate persistence itself is not required before stage advancement and is not the root fail-closed gate**.

This is a useful design distinction: an audit receipt should not be described as an admission lock unless every state transition actually requires it. If a receipt is meant to be authoritative, mutation ordering should be `validate -> persist receipt atomically -> apply transition`, or recovery must reconstruct the receipt before treating the transition as certified.
