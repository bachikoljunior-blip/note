## 1. Memento parametric-retriever protocol: released row-level validation is post-paper code, not demonstrated paper protocol

### New chronology evidence

The arXiv record for **Memento: Fine-tuning LLM Agents without Fine-tuning LLMs** says v1 was submitted **2025-08-22 07:25:30 UTC** and v2 on **2025-08-25 13:32:12 UTC**.

The official README separately records:

- 2025-08-27: authors said CBR code would be released next week and **Parametric Memory code next month**;
- 2025-08-30: non-parametric CBR inference code released;
- 2025-10-05: parametric Case-Based Reasoning inference code released.

Git history for `memory/train_memory_retriever.py` is especially constraining: the path history contains one introduction commit, `92ce185a2ceb93688cb0d9ebe2fad7a87af653da` (`Add files via upload`, authored 2025-10-05T13:55:06Z). Fetching the same path at its parent `f3441042959dfca6ce7b1c7894232240bdc5a0fd` returns 404. The same history appears in the public `gaixen/AgentFly` mirror.

Therefore the exact released training script whose default split we audited earlier did **not exist in public repository history at the paper's v1/v2 dates**. This sharply narrows the previous warning: the row-level split/leakage risk is established for the released Oct-2025 implementation, but public history does not establish that this script or split generated the paper's Aug-2025 results.

### Paper itself does not specify the held-out retriever validation protocol

The v2 paper describes the parametric memory as a single-step learned Q-function / binary classifier: it reduces to supervised learning on `(s,c,r)` and replaces MSE with binary cross-entropy because reward is binary. Retrieval uses TopK by learned Q-value. The paper reports continual-learning curves and ~3k training data saturation, but a search of the paper finds **no AUC discussion and no train/validation split for the retriever**. The word “validation” is used for benchmark splits such as GAIA, not for held-out Q-function model selection.

Thus there is currently no primary public paper text that can answer whether the published neural retriever used query-group-held-out validation, row-level validation, a separate validation file, or no validation-model-selection loop at all.

### Released implementation remains leakage-prone when `--valid` is not supplied

`memory/train_memory_retriever.py` loads each JSONL row as one `(query, case/plan, truth_label)` sample. With no explicit `--valid`, `stratified_split_indices` splits row indices independently within positive/negative labels using a seeded shuffle. It does not group by query/task/episode. The README's documented training command supplies `--train training_data.jsonl --val_ratio 0.1 --save_best` but no `--valid`, so the documented released path selects `best.pt` from a row-level held-out set.

This combines poorly with the previously observed data semantics: many rows share a query, some exact pairs repeat, and all retrieved cases for one query inherit that query's final `truth_label`. A row-level AUC/F1 can therefore benefit from query identity and duplicate-pair overlap and does not by itself measure unseen-query memory utility.

### Corrected claim scope

**Supported:** the documented Oct-2025 public retriever training path has a validation-design flaw for estimating unseen-query case utility, because its default validation split is row-level while labels and repeated rows are query-correlated.

**Not supported:** that the Aug-2025 published Memento results used that exact validation split; that the paper's benchmark gains are invalid; or that a grouped split necessarily changes downstream task accuracy by any particular amount.

## 2. ArgusAgent: actual stage-admission gate identified

Previous run narrowed `stage-certificates.json` to an observability/re-proposal artifact rather than the root fail-closed stage gate. This run traced the actual primitive.

At public commit `455da6cb2fe10e9fbaeab5126f2f3b363237cf57`:

1. Manager `_apply_stage_decision_to_disk` delegates an `advance` decision to `skills.stage_machine.advance_stage(...)` and catches `StageCompletionError`, converting failure into a `hold` transition rather than mutating stage.
2. `advance_stage` validates that target stage is later, then calls `_ensure_stage_completion(project_root, current_stage, evidence_root=...)` **before** `_set_stage` writes `PIPELINE_STATE.json`.
3. `_ensure_stage_completion` invokes the active vertical's deterministic `vertical_stage_completion_issues(...)`. If the validator itself errors/unavailable, it wraps that as `StageCompletionError("completion validator unavailable: ...")` — explicit fail-closed behavior. If issues are returned, it raises `StageCompletionError` as well.
4. Only after the deterministic completion check passes does `_set_stage` mark the previous stage `done`, set the new current stage, append history, and atomically write pipeline state.

The source comments are unusually explicit about the threat model: `advanced_by` is free text and caller identity is **not authenticated** at this primitive; the real protection is that every transition runs the deterministic completion validator against evidence on disk. So the transferable mechanism is not “trust the reviewer/manager role” but **put an evidence-backed deterministic validator immediately before the durable state transition primitive and fail closed if the validator cannot run**.

Scope caveat: this is a gate on the intended `advance_stage` primitive, not filesystem-level tamper-proofing. Arbitrary code with write access could in principle bypass the API and edit state directly; the artifact supports a robust internal transition contract, not a security boundary against a malicious writer.
