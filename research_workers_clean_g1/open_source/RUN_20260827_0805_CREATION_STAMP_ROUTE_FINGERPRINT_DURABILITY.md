## 1. Minimal immutable creation stamp can be smaller than a row hash

The continuous Manager path already has two stable provenance values before side effects: `root_task_id` is reserved before handoff persistence, and `PreparedManagerHandoff.intent_id` is created before the Manager decision and survives through the handoff. The same path constructs one operator-priority item from the Manager-clean `execution_task`, merged context refs, a fixed review/stage-transition contract, and the committed route decision.

A recovery identity should therefore be a versioned creation contract, not a hash of the mutable `BacklogItem` row.

Recommended canonical stamp payload (`manager_operator_priority_v1`):

- `item_id`: the pre-reserved `root_task_id`;
- `manager_intent_id`: `PreparedManagerHandoff.intent_id`;
- `execution_task_sha256`: SHA-256 of the exact stripped Manager-clean execution task frozen by the handoff;
- `context_refs_sha256`: SHA-256 of the canonical JSON for the already-merged context-ref list (sorted object keys, list order preserved);
- `protected_route_fingerprint_v4`: canonical Manager route identity described below;
- `dispatch_contract_id`: a fixed version token such as `manager_operator_priority_reviewed_v1`, representing the path's fixed `manager/operator/operator_priority/scope:bounded/review:required/stage_transition:skip`, `iterate=False`, one-cycle contract.

Do **not** include:

- `ts`: it is first-insert receipt metadata, generated by `BacklogItem.new()` and should remain the original successful insert timestamp on retry;
- `priority`: it is scheduler metadata whose exact value must be allocated under the backlog lock at first insert and then preserved from the stored row;
- `title`: it is derived presentation text and has legitimate post-create rewrite paths;
- raw `manager_decision`: it is a mutable partial projection and omits route axes needed for resume identity;
- `original_objective`: in this continuous operator-priority path it is set to the same Manager-clean execution body, so carrying it in addition to `execution_task_sha256` is redundant.

This gives an exact recovery identity without making ordinary later lifecycle/reroute/iteration mutations look like a different creation.

## 2. Narrowest exact-insert API belongs inside `Backlog`, but should remain path-scoped

`Backlog.add()` owns the cross-process `portalocker` transaction and currently appends without checking existing IDs. `add_many()` and plan revision already reject duplicate IDs. The operator-priority path also currently computes queue priority before taking the add lock.

The narrowest safe shape is a path-specific method on `Backlog`, e.g. `ensure_operator_priority_item_exact(...)`, rather than a public general-purpose duplicate-bypass helper. It must own the same `_locked()` section as persistence because both priority allocation and exact-ID comparison must observe one queue snapshot.

Inside one lock:

1. load rows once and collect all rows matching `item.id`;
2. if more than one row matches, fail closed as ambiguous legacy corruption;
3. if one row matches, require a nonempty equal immutable `creation_stamp`; return that current row unchanged, preserving all legitimate post-create mutations and its original priority/timestamp;
4. if one row matches but the stamp is missing or different, fail closed — do not backfill provenance that cannot be proved;
5. if no row matches, validate this is the operator-priority contract, derive `priority=min(current pending priority - 1, -1)` from the locked rows, persist the chosen priority plus immutable stamp exactly once, validate the dependency DAG, and save.

Separately, ordinary `Backlog.add()` should reject every duplicate ID immediately so new ambiguity cannot be introduced. Existing unstamped rows remain valid ordinary backlog rows; they are simply ineligible to satisfy an exact handoff recovery. No automatic legacy stamp migration is justified from current evidence.

## 3. `protected_route_fingerprint_v4` can reuse existing semantic normalizers

The restart identity should bind the six Manager-owned route axes already identified, but canonicalize them exactly as current Argus semantics do:

- `vertical`: current vertical normalization (`strip/lower`, trailing `-needed` removal, legacy `direct -> software`, then known-vertical/data-domain validation);
- `domain`: current domain normalization (`strip/lower`, `-` -> `_`), or empty when absent;
- `workflow_mode`: the **effective** `direct|staged` value; a missing persisted value resolves to `staged` and should fingerprint as `staged`, not empty;
- `research_target_level`: current enum normalization (`exploratory|publishable|doctoral`) or empty;
- `research_direction_mode`: current enum normalization (`broad|locked`) or empty;
- `target_venue`: the research venue semantic key normalizer (uppercase, remove separators, strip trailing 2/4-digit year), consistent with current built-in/dynamic profile matching.

`current_stage` remains excluded because legitimate progress changes it without changing the route contract.

Current `manager-handoff.json` version 3 binds objective hash, vertical, domain, generation and intent id but not the other four route axes. Versions 1–3 should therefore not be upgraded by merely reading the current route and stamping it as trusted: the missing axes may already have drifted. A fail-closed one-time Manager reconcile/reclassification, followed by writing v4 from the resulting protected route, is the safer migration.

## 4. Process restart should consume current state, never replay copied objectives

Current source still has three distinct semantics mixed behind `resume_continuous`:

- Web `start_project_daemon` may re-enable any disabled state whose `done_reason` merely starts with `operator `, and it performs that write before daemon admission/spawn;
- daemon boot has the narrower correct allowlist `RESUMABLE_STOP_REASONS`, but `_rearm_operator_drain_for_resume()` re-enables from an earlier read using non-CAS `write_continuous_config`;
- immediate and scheduled upgrade paths capture `continuous.enabled/objective` before drain and later write that copied objective back.

A single `reconcile_or_rearm` boundary should instead read the **current** continuous record under the continuous-state lock and apply exactly one rule:

- current state enabled -> no semantic mutation; start executor against it;
- current state disabled + exact `RESUMABLE_STOP_REASONS` + nonempty objective -> exact CAS that same record to enabled with the same objective;
- current state is a Manager handoff fence -> enter handoff recovery/reconcile, never process-only rearm;
- every semantic stop/hold/completion/unknown reason -> remain disabled.

Process start/upgrade/replacement should pass only a restart/resume intent; they should not carry an old objective as authority. A scheduled upgrade request may retain process identity/audit metadata, but current continuous state at completion time must decide whether anything is rearmed.

## 5. New durability gap: backlog atomic visibility is weaker than continuous-state durability

The proposed two-CAS handoff fence depends on one ordering invariant: the operator mission must be durably present before the final CAS makes the new continuous objective enabled.

Current `Backlog._save()` uses `_atomic_rewrite_jsonl()`: write a temp file, close it, `os.replace()` it into place. It does **not** explicitly `fsync` the temp file or parent directory. By contrast, `continuous.json` writes flush+`fsync` the temp file before replace and `fsync` the parent directory afterward.

Therefore `Backlog.add()` is atomic for visibility/concurrent readers, but it is not proven to have the same power-loss durability as the final continuous CAS. A machine/storage crash after backlog `_save()` returns but after the final continuous state becomes durably enabled can, in principle, leave an enabled objective whose first mission row was not durably committed.

For the strong handoff invariant, the exact operator-priority insertion path needs a durable rewrite boundary (temp flush+file `fsync` -> replace -> parent-directory `fsync`) before the final continuous enable CAS. This can be implemented by hardening `_atomic_rewrite_jsonl()` globally if cost is acceptable, or by using a durable variant for authoritative exact inserts. This is a durability design observation, not a reproduced power-loss failure.

## 6. Regression matrix additions

Retain the prior duplicate/stamp/mutation tests and add:

1. exact operator insert allocates priority under one backlog lock; retry returns the stored row and never recomputes priority or timestamp;
2. existing same ID with no stamp, different stamp, or multiple matching rows -> fail closed with no rewrite;
3. v1-v3 Manager handoff identity + same vertical/domain but changed workflow/research/venue axis -> must reconcile once, then emit v4;
4. process rearm CAS race: read disabled drain state, concurrently issue semantic stop/new objective, then attempt rearm -> CAS loses and current semantic command wins;
5. scheduled upgrade created while A is active, then user stops/replaces A before completion -> upgrade restarts executor but never resurrects captured A;
6. handoff failure after exact mission insert but before final continuous CAS; recover twice -> exactly one row, same immutable stamp, same insertion timestamp/priority;
7. durable-write call-order test for the authoritative exact insert: file flush/fsync occurs before replace and parent-directory fsync occurs after replace, before final continuous enable is allowed.
