## 1. ArgusAgent: Reviewer verdicts are mechanically connected to durable state, but independent review is conditional

Public repository inspected: `microsoft/ArgusAgent`, commit/path references around `455da6cb2fe10e9fbaeab5126f2f3b363237cf57`.

### Code-enforced transition semantics

The released runtime defines Reviewer statuses including `done`, `continue`, `blocked`, and `replan_requested`. `done` maps to a completed loop; `blocked` / infra failure map to terminal block classes; `replan_requested` maps to a replacement-plan outcome. A separate planner signal `reconsider` is also promoted into `replan_requested` unless the challenged decision is operator-authority-bearing, in which case the runtime blocks for the operator.

The settlement layer does more than log those words:

- successful missions are durably `mark_done` in the backlog;
- a blocked mission carrying an operator question is atomically persisted as `paused_operator` together with the question/decision card;
- `replan_requested` with evidence of forward progress is closed as failed work that now needs a replacement plan;
- `replan_requested` without forward progress is reset to `pending` with durable `consecutive_replans` incremented so the planner can replace/re-dispatch it;
- repeated no-progress replans cross a bounded convergence threshold and become a terminal no-progress failure instead of being re-dispatched forever;
- journal entries distinguish `mission_complete`, `mission_replan_requested`, `mission_aborted`, and `mission_failed`, and prior replan streaks can be reconstructed from the journal until the last completion marker.

A dynamic-plan stage guard also checks for unfinished sibling/dependent nodes. If the Manager has prematurely advanced the pipeline stage, the supervisor can call host code to roll the stage back, emit the rollback, and expose a local `hold` transition rather than accepting the premature advance.

### Independent-review evidence admission

The round packet is sealed as independent Reviewer evidence only when `review_source == "reviewer"`; the code comment explicitly rejects sealing an Engineer self-review as independent stage evidence. For learned vertical candidates, durable promotion is even stricter: promotion occurs only if the mission succeeded, the final review status is `done`, and `final_review_source == "reviewer"`. A rejected restricted validator-repair capability overrides the model-reported success and forces a permanent error.

For stage-closing attempts, the host can write a stage certificate containing the task id, Manager action, completion-checklist fingerprint, and evidence fingerprint. The certificate is atomically written via temporary-file + `os.replace`, and its `certified` bit is true only for Manager actions `advance` or `complete`.

Important scope correction: Argus does **not** globally require independent review for every mission. The effective requirement is conditional on the explicit call, environment, or active vertical/project contract. Direct/legacy work can still use Engineer self-review where policy permits it. Also, stage-certificate write failures are caught fail-soft in the surrounding supervisor, so the certificate itself should not be described as a universal mandatory gate without tracing every downstream consumer.

### Operational reviewer statistics

The repository ships `technical_report/evidence/swebench_pro/reviewer_mechanism_stats.json` for 731 SWE-Bench Pro tasks:

- external Reviewer path: 466 / 731 = 63.75%;
- Engineer self-review path: 265 / 731 = 36.25%;
- among the 466 external-review trajectories: first review accepted 388, first review blocked 35, revision requested 43;
- among those 43 revision-requested trajectories, 34 were eventually officially resolved by the task-native verifier, 22 eventually ended Reviewer-accepted, and 21 did not end Reviewer-accepted;
- mean solve input tokens were about 3.05M for external-review tasks vs 1.11M for self-review tasks; mean active time about 591 s vs 329 s.

The artifact itself warns that Reviewer routing is task-dependent rather than randomized. Therefore these are operational/descriptive statistics, **not** a causal estimate that Reviewer revision caused the 34 resolutions or the full-system benchmark gain.

### Candidate refinement: `clean-os-g1-005`

Retain reviewer/verifier-gated durable self-evolution as a plausible mechanism, now with stronger implementation grounding: a Reviewer verdict can change the durable backlog state, force replanning, bound repeated replans, prevent some premature stage advances, and gate learned-candidate promotion. Scope the claim carefully: independent review is policy/vertical-dependent, and the full Argus performance result bundles many mechanisms.

## 3. Independent ReasoningBank reproduction: structured retry recovers naive-retry harm, persistent cross-task memory shows no positive transfer signal

A separate public repository, `ramankrishna/reasoning-bank`, contains a detailed independent experiment dated 2026-05-31 using Claude Haiku 4.5 at temperature 0.0 on a 30-instance SWE-bench Lite subset, 3 seeds, and the official `swebench.harness.run_evaluation` scorer.

Headline clean-cell results reported by the experiment:

| Arm | Mechanism | Clean cells | Pass rate |
| --- | --- | ---: | ---: |
| arm1 | one attempt, no retry | 90/90 | 45/90 = **50.0%** |
| arm2 | up to 3 naive retries with raw failure feedback | 90/90 | 38/90 = **42.2%** |
| arm3a | up to 3 retries, fresh per-instance ReasoningBank | 86/90 | 45/86 = **52.3%** |
| arm3b | same bank persistent across 30 instances within seed | 45/90 | 21/45 = **46.7%** |

Reported contrasts are therefore:

- naive retry vs one-shot: **−7.8 pp**;
- fresh per-instance bank vs naive retry: **+10.1 pp**;
- fresh per-instance bank vs one-shot: **+2.3 pp** (within overlapping intervals; no demonstrated net lift);
- persistent bank vs one-shot: **−3.3 pp**;
- persistent vs fresh bank: **−5.6 pp**.

The persistent-bank cross-task transfer check is also wrong-sign rather than progressively improving. On the clean arm3b cells, pooled early instances had attempt-1 success 10/22 = 45.5% versus arm1 13/22 = 59.1% on the exact same instances (−13.6 pp). Late instances had 8/23 = 34.8% versus arm1 13/23 = 56.5% (−21.7 pp). The reported raw late-minus-early position effect is −1.8 pp; after difficulty subtraction, the deficit widens by 8.1 pp.

### Major validity limits

This is useful negative/matched evidence, but it is not decisive:

- arm3b retained only 45 of 90 intended clean cells because of API-credit exhaustion and other infrastructure incidents;
- the 30-instance pool is highly bimodal (13 always solved by arm1, 13 never solved, only four instances offer much inter-arm differentiation);
- confidence intervals overlap heavily and the report says sub-~10 pp effects are unresolved;
- raw per-cell data referenced by the report were not committed, so the public artifact is a detailed result report + source code rather than a fully auditable raw result bundle.

An earlier 12-puzzle experiment in the same repository hit a complete ceiling: control 100%, bank-on 100%, and one logged bank condition 91.7%; the bank still distilled 34 memories. This reinforces the methodological point that a memory benchmark must provide real headroom and informative failures.

### New candidate `clean-os-g1-006` — distinguish within-task failure repair from cross-task durable memory admission

**Mechanism.** Treat retry/repair assistance and durable cross-task memory as different interventions. First establish a no-retry/no-memory baseline. A structured failure-reasoning mechanism may be valuable if it repairs the well-known harm of naive retries; but cross-task memory should be admitted only after held-out positive-transfer evidence, with a vanilla/no-memory fallback when that evidence is absent.

**Evidence.** In this independent SWE-bench Lite reproduction, naive retry loses 7.8 pp, a fresh per-instance bank recovers 10.1 pp against that damaged retry baseline but only +2.3 pp against one-shot control, while the persistent cross-task bank is −3.3 pp vs control and does not improve later in the stream.

**Scope.** This does **not** refute the original ReasoningBank result. The official ReasoningBank report uses different models/scaffolds/tasks and reports positive gains, including +4.6 pp on SWE-Bench Verified with Gemini-2.5-Flash. The independent experiment supports a narrower operational rule: persistent memory needs its own matched transfer test and should not inherit credit from within-task retry recovery.

## 4. Memento parametric CBR: outcome-label broadcast and persistent planner history are concrete confounds

Public implementation inspected: `Memento-Teams/Memento/client/parametric_memory_cbr.py` and `memory/train_memory_retriever.py`.

### Case-label provenance

For each query, the client obtains a predicted answer and calls an LLM judge (`gpt-4o-mini`) with the question, ground-truth answer list, and predicted answer. `is_correct` is the judge's `correct` / `incorrect` result. The newly stored memory case is then labeled `positive` if `is_correct`, otherwise `negative`; judge failure is treated as incorrect.

So in this DeepResearcher path, memory labels are not produced by a task-native executable verifier; they are produced by a second model judging against a known answer list.

### Retriever credit assignment

More importantly, `save_training_data` writes one training sample for **every retrieved case** with:

- current `query`;
- the retrieved case and its existing positive/negative `case_label`;
- the retrieved plan;
- `truth_label = is_correct` for the **current query's final outcome**.

`memory/train_memory_retriever.py` then trains the pair classifier directly on this `truth_label`. Consequently, every memory item retrieved on a solved query receives the same positive pairwise utility target, and every item retrieved on a failed query receives the same negative target, even if an individual memory item was ignored, irrelevant, harmful, or uniquely helpful. This is coarse outcome credit, not marginal utility estimation.

### Cross-query history confound

`HierarchicalClient` owns one `shared_history` list. `process_query` appends the current query, optional retrieved-memory user message, planner responses, and executor task/results to this list. The main path constructs one `HierarchicalClient` before iterating over queries; no per-query history reset was found in the inspected file.

Therefore this public parametric-CBR script changes at least two things over a query stream: the retrieved memory pool **and** the accumulated planner conversation history. Any stream-level degradation or improvement cannot be cleanly attributed to retrieval alone from this implementation.

### Refinement to `clean-os-g1-003`

These code paths make the earlier negative-transfer hypothesis more concrete. Memento's public CBR path combines:

- concrete `Question + Plan` memories;
- up to 8 retrieved examples;
- strong user-message instruction to follow positive / avoid negative examples;
- LLM-judged outcome labels;
- query-level outcome credit broadcast to every retrieved pair during retriever training;
- persistent planner history across queries.

Any of these could contribute to negative transfer, and several can interact. None has yet been causally identified as the reason for EvoAgentBench's 45.8 → 9.5 Nanobot/Qwen3.5-27B SWE-Bench collapse. Preserve that distinction.

Potential mechanism lead (not yet promoted to high-evidence candidate): train memory admission/retrieval on per-memory marginal utility or a leave-one-out/causal proxy rather than broadcasting whole-query outcome to every retrieved memory. A matched quantitative ablation is still required before promoting this beyond a testable hypothesis.
