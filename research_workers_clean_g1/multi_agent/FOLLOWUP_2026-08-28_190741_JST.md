## New exact mechanism result: safe repair is a portfolio, not one scalarized policy
The previous checkpoint separated currentness from mutation quiescence. This run asks what a controller should *do* when a fresh snapshot says an irreversible branch is absent but an old writer to that branch may still complete.

There are 11 current-state/in-flight cases and 32 retry/compensation capability vectors, for **352 worlds per action budget**. An action budget counts additional `wait/retry/compensate` actions after one fresh snapshot; the final proof read is mandatory and common to all terminal claims, so it is not charged in the comparative budget. These counts are synthetic mechanism counts, not production frequencies.

At incremental action budget **2**:
- `current_min` minimizes mutations from the current snapshot while ignoring the unresolved writer. It terminalizes **264/352 = 75.0%** of worlds, but **52/264 = 19.70% of its terminal claims are unsafe**. Every unsafe case is the same mechanism: the policy chooses rollback, then the old writer later creates irreversible `C`.
- `quiescence_gate` blocks whenever a writer is unresolved. It terminalizes **120/352 = 34.09%**, with **0 unsafe terminal**. Expected incremental actions are `0.1818/world`; irreversible-C retries are `0.0568/world`.
- `forward_guard` never rolls back under writer ambiguity and instead forward-completes when certified capabilities allow it. It terminalizes **168/352 = 47.73%**, with **0 unsafe terminal**. Expected incremental actions are `0.3636/world`, but irreversible-C retry exposure is relatively high at `0.1932/world`.
- `wait_then_min` spends one action to settle the old writer, then re-plans from the resolved state. It terminalizes **232/352 = 65.91%**, with **0 unsafe terminal**. Expected incremental actions are `0.6364/world`, while irreversible-C retry exposure is `0.1023/world`, substantially below `forward_guard` despite higher safe coverage.

At budget 3, `wait_then_min` reaches **248/352 = 70.45%** safe terminal coverage, versus **176/352 = 50.0%** for `forward_guard` and the same **120/352 = 34.09%** for pure quiescence blocking. All tested `quiescence_gate`, `wait_then_min`, `forward_guard`, and `always_forward` variants have zero unsafe terminal in this deliberately bounded model; this is not a general safety proof outside the tested state/action semantics.

The policy genome also makes the QD-like structure explicit. Behavior is indexed by terminal coverage, expected action cost, and irreversible-C retry exposure. At budget 2 there are multiple non-dominated safe genomes: low-action/blocking niches, higher-coverage wait-and-replan niches, rollback-biased low-irreversibility niches, and forward-biased low-latency niches. A single weighted scalar can select one point, but no one safe genome dominates all three axes.

### Controller implication
For an unresolved writer to an irreversible branch, the controller should not collapse to a universal `rollback`, `forward`, or `wait` rule. Keep a *certified repair-policy archive* whose behavior descriptors include at least:

`{terminal coverage, additional action/latency cost, irreversible-effect issuance, rollback availability, proof requirements}`

All archive entries still pass the same non-substitutable safety certificates. Selection among safe entries can then respect the operator/objective preference:
1. low latency -> certified forward completion may be admissible;
2. low irreversible exposure -> wait/settle then re-plan can dominate;
3. low action budget -> block/quiescence gate may be the only admissible option.

The critical invariant is unchanged: **a fresh current snapshot is not rollback authority while an older writer can still cross a point of no return**.

Its Payments v2 refund flow creates a refund identified separately from the original capture and exposes a separate refund-status GET. The June 4, 2026 refund guide also recommends refund-specific idempotency and states that processed refunds cannot be cancelled.
  - https://developer.paypal.com/reference/guidelines/idempotency/
  - https://developer.paypal.com/checkout/refund-payment
- Adyen's refund endpoint returns a unique `pspReference` for the refund request; the refund is asynchronous. A successful `REFUND` validation webhook can later be followed by `REFUND_FAILED` or `REFUNDED_REVERSED`. Thus a compensation attempt has its own identity, in-flight state, and late adverse transitions.
  - https://docs.adyen.com/online-payments/refund/
- Stripe v1 and v2 idempotency contracts differ materially in time window and replay semantics. v1 stores the first endpoint result only after endpoint execution begins and does not save an idempotent result for a request that conflicts with another request executing concurrently; v2 defines replay scope by same API plus same account/sandbox within 30 days. The controller must therefore keep operation/API/scope/time evidence rather than treat `has_key=true` as a generic fence.
  - https://docs.stripe.com/api/idempotent_requests
  - https://docs.stripe.com/api-v2-overview

These provider facts are used only to establish the existence of separate request/resource/lifecycle semantics within the documented scopes; the synthetic lattice does not estimate provider-specific failure rates.
