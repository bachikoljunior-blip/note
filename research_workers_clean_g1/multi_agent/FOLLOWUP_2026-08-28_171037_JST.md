## New mechanism result: idempotency is not finality
The prior boolean effect state was replaced by a typed state lattice: `NONE / PENDING / PARTIAL / COMPLETE`, plus reconciliation-read modes `CURRENT / STALE_NONE / STALE_COMPLETE / UNKNOWN`.

The important controller separation is now:
1. **request identity / multiplicity proof** — whether an exact logical operation can be retried without creating an unintended duplicate;
2. **physical effect state** — what amount/resource state actually exists now;
3. **freshness / source proof** — whether an observation is current enough and authoritative for the decision being made;
4. **settlement/finality proof** — whether the effect is actually complete rather than accepted, pending, or partial.

Current provider documentation supports this separation:
- Stripe PaymentIntents can be `processing` for asynchronous methods for days, and `requires_capture` can represent uncaptured or partial-capture state. Stripe says the API/Workbench Inspector provides authoritative state and that webhook delivery order is not guaranteed; webhook endpoints can also receive duplicate events. Snapshot webhook payloads can be followed by a fresh API resource retrieval for the latest object.
  - https://docs.stripe.com/payments/payment-intents/verifying-status
  - https://docs.stripe.com/webhooks
  - https://docs.stripe.com/payments/partial-authorization
- Adyen capture requests return a request reference while the outcome is asynchronous in a `CAPTURE` webhook; partial capture is supported. Adyen also instructs webhook consumers to use timestamps/sequence information for chronological processing and to handle duplicate events by using the latest event details.
  - https://docs.adyen.com/api-explorer/Checkout/72/post/payments/_paymentPspReference_/captures
  - https://docs.adyen.com/development-resources/webhooks/handle-webhook-events
- PayPal explicitly distinguishes `PAYMENT.CAPTURE.PENDING` from `PAYMENT.CAPTURE.COMPLETED` and says not to fulfill while completion is pending. Its invoicing webhook guidance also warns that events can arrive out of order and recommends fetching current resource status when needed.
  - https://developer.paypal.com/payment-methods/webhooks/
  - https://developer.paypal.com/api/invoicing/webhooks/

Therefore an idempotency contract can certify **same logical request**, but it must not be promoted to `effect COMPLETE` or `rollback COMPLETE` without independent current-state/finality evidence.

## Exact synthetic mechanism lattice
A deliberately balanced exact study was executed. It is a mechanism counterexample, not a provider incident-rate estimate.

### Forward retry
Six exact same-intent retry worlds were enumerated. If no prior effect existed, a certified retry may leave the logical operation `PENDING`, `PARTIAL`, or `COMPLETE`; if an operation already exists, the retry preserves its current effect state.

- Treating `certified retry` itself as completion terminalized all 6 worlds and was wrong in **4/6 = 66.67%** of this balanced toy lattice.
- Requiring authoritative post-action current proof terminalized only the 2 genuinely `COMPLETE` worlds and had **0 unsafe terminal**.
- Adding an observation layer (24 worlds) shows why freshness is a separate certificate: accepting any observed `COMPLETE` without qualifying freshness produced **4 unsafe / 8 terminal = 50%** in the toy lattice, while freshness-qualified current proof produced 0 unsafe terminals.

These proportions are intentionally balanced mechanism counts, not empirical frequencies.

### Destructive compensation authority
Across 16 actual-state × read-mode worlds, granting destructive authority whenever the observed state was `NONE` admitted 5 cases, of which **3/5 = 60%** were stale-absence false authority in the toy lattice. Requiring a freshness-qualified current `NONE` admitted only the actually absent case and produced 0 unsafe destructive-authority admissions.

The key design implication is that **stale absence is not proof of no live effect**. A controller must not infer compensation safety from an unqualified read simply because the payload says absent/not-found.

### Compensation symmetry
Compensation was given the same semantics as forward execution: a certified compensation request can be accepted while physical undo is still pending/partial.

Across 9 pre-effect × compensation-residual worlds:
- treating compensation idempotency as completed rollback produced **6 unsafe / 9 terminal = 66.67%** in the balanced toy lattice;
- authoritative post-compensation current proof admitted only the 3 actually absent residual states and had 0 unsafe terminal;
- with stale/unknown reads added (36 worlds), unqualified observed absence produced **6 unsafe / 12 terminal = 50%**, while freshness-qualified absence produced 0 unsafe terminal.

Thus compensation requires its **own** provider-scoped same-intent contract *and* its own post-action physical-effect proof. A compensation key is not a rollback-complete certificate.

### Branching point of no return
A toy `A -> {B,C}` slice conditions on branch `C` already being `COMPLETE` and irreversible. In all 8 balanced `B state × B retry-certification` worlds, clean rollback is structurally impossible. Yet **5/8 = 62.5%** retain a safe forward reconciliation route because B is either already complete or has a certified retry route; the remaining 3/8 must remain blocked/nonterminal.

This is a structural demonstration only: after an irreversible branch crosses a point of no return, `failure -> rollback` is not generally admissible. Forward reconciliation can be the only safe terminal path.

## Controller revision
The candidate controller now carries these non-substitutable evidence objects:

`request_contract = {provider, API/version/call-type, account/sandbox/company/merchant scope, region where applicable, operation identity, idempotency key/request ID, request fingerprint, first-use time, provider retention evidence, first-result identity}`

`effect_observation = {provider/resource identity, intended amount/resource fingerprint, typed state, actual/settled amount when exposed, observation source, resource/event version or sequence where exposed, event/effective time, observed-at time, freshness/consistency qualification}`

`compensation_contract = {compensation operation identity, scope, idempotency key/request ID, compensation fingerprint, first-use time, retention evidence, first-result identity}`

Terminal forward requires proven intended effect finality; terminal rollback requires proven absence/fully compensated state. Request acceptance, event delivery, recorded success, or an idempotency key cannot substitute for those predicates.

For webhook-driven flows, event evidence should preserve at least `{event_id, resource_id, event_type/state, provider event timestamp, sequence/version if exposed, delivery-observed-at}`. Because duplicate/out-of-order delivery exists in public provider contracts, the controller must reconcile event ordering and, for high-risk terminal/destructive decisions, fetch/verify current resource state when the provider offers a suitable authoritative endpoint.
