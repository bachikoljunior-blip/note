### Crucial scope correction: there are no same-prompt repeats
This corpus does **not** supply repeated stochastic calls of the same judge/prompt in the way LAJ-Gherkin does. The second call is a different prompt intervention. Therefore it cannot honestly replicate `same-judge repeat vs heterogeneous escalation` directly.

The valid independent experiment is narrower:
1. one v1 judge as base,
2. one extra **same-model v2 prompt-intervention** call on a routed subset,
3. one extra **heterogeneous v1 judge** call on the same routed subset,
4. equal extra-call count, with the base/heterogeneous judge/routing rule chosen on training data only and evaluated on untouched deterministic test items.

A predeclared executable protocol is now durable at:
`research_workers_clean_g1/multi_agent/SECOND_CORPUS_ROUTING_PROTOCOL_2026-08-26_2100.py`.
It pins the public commit, hashes item IDs before labels/outcomes to form a deterministic 100/rest split, selects only a small train-only rule family, caps extra calls at 30%, compares binary accuracy/kappa, and emits a paired bootstrap interval. It explicitly labels the same-model arm as a prompt intervention rather than a repeat. ## B. Negative evidence already visible in the pinned corpus
### Same model + richer prompt is not uniformly beneficial
The public `E1_prompt_intervention.csv` shows that v2 can materially help or hurt the **same** judge. Examples on all 147 common items:
- gemma4_31b: kappa `0.279 -> 0.489` while flag rate `0.184 -> 0.694`;
- nemotron_550: `0.281 -> 0.416`, flag `0.299 -> 0.743`;
- llama33_70b: `0.534 -> 0.069`, flag `0.626 -> 0.959`;
- gptoss_120b: `0.515 -> 0.401`, flag `0.551 -> 0.755`.
This is evidence that “spend an extra call on the same model with a stronger rubric” is a qualitatively different intervention from repeat sampling and can systematically change decision boundaries.

### Naive multi-judge aggregation can be worse than the best individual
The public `T7_ensembles.csv` reports, on the same 147 items:
- six-judge majority vote kappa: `0.401`;
- unanimity: `0.272`;
- any-flag: `0.278`.
The majority vote is below the best individual v1 judge (`0.534`) and the second-best (`0.515`). This directly strengthens the prior controller conclusion: more judges/agents are not an objective; conditional residual value and error structure matter. It does **not** show that all trained/weighted ensembles fail.

## C. Breadth repair outside evaluator-noise/routing
A fresh primary-source scan found **AgentConductor** (arXiv:2602.17100, submitted 2026-02-19), a dynamic multi-agent topology system for code generation. Its orchestrator chooses roles and a task-difficulty-aware layered DAG, then regenerates topology after execution feedback. Across three competition-level and two foundational code datasets, the paper reports up to `+14.6%` pass@1 over the strongest baseline, `13%` topology-density reduction, and `68%` token-cost reduction. The method explicitly uses difficulty-dependent node bounds and multi-turn execution feedback rather than a fixed team graph.

Scope: this is code-generation evidence with an RL-trained orchestrator and a predefined role pool. It supports *difficulty-conditioned topology/agent allocation* and feedback-driven restructuring, but it is not evidence that the same controller transfers to open-ended research or that arbitrary additional agents help.

## Updated controller hypotheses
1. **Independent judge count is not a target variable.** Even six-family majority voting can underperform a strong individual on a fixed corpus.
2. **Prompt interventions and stochastic repeats must be kept separate.** The same model under a richer rubric can shift threshold/flag behavior strongly enough that treating it as another iid vote is invalid.
3. **Conditional escalation remains the right comparison.** The next independent test should ask whether a routed heterogeneous v1 call beats a routed same-model v2 call at identical extra-call count, not whether heterogeneous always wins globally.
4. **Broader MAS allocation should be difficulty/state-conditioned.** AgentConductor adds contemporary support for topology density and role choice that scale with task difficulty and execution feedback.
