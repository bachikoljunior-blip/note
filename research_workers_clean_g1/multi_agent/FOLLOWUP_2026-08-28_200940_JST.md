## New exact mechanism result: compensation writers need the same quiescence/finality gates as forward writers
The previous checkpoint showed that an unresolved forward writer can invalidate a rollback chosen from a fresh snapshot. This run applies the same temporal model to *compensation itself* and makes compensation a separate request/resource lifecycle.

A balanced exact lattice contains **260 synthetic worlds**. Every world has capture target 100 and varies:
- current physically observed refund amount `0/50/100`;
- whether that current refund is merely provisional and will later fail/reverse;
- an older ambiguous compensation writer for `0/50/100`;
- whether that writer eventually has no effect or applies;
- whether retrying the old compensation is covered by a certified same-operation idempotency contract;
- if not certified, whether the retry becomes an independent duplicate compensation;
- whether a webhook/wait channel is authoritative for terminal resolution;
- whether issuing a new compensation for the remaining amount is itself contract-certified.

The safety objective is eventual durable refunded amount exactly 100 after all unresolved transitions settle. The proportions below are therefore mechanism counts on a deliberately balanced lattice, **not provider incident rates**.

This is the compensation-side analogue of the prior currentness-vs-quiescence counterexample.

## Public provider evidence: compensation really is a separate lifecycle
Fresh official documentation remains consistent with the mechanism model, within each provider's documented scope:

- PayPal's June 4, 2026 refund guide uses Payments v2 `POST /v2/payments/captures/{capture_id}/refund` and a separate `GET /v2/payments/refunds/{refund_id}` status resource, and supports partial refunds. This establishes that compensation has its own resource identity/status rather than being a Boolean inverse of capture.
  - https://developer.paypal.com/checkout/refund-payment
- Adyen documents that a refund can later emit `REFUND_FAILED` even after a prior successful `REFUND` validation webhook, and can also emit `REFUNDED_REVERSED`. Thus compensation success can be provisional relative to a stronger durable-finality predicate.
  - https://docs.adyen.com/online-payments/refund
- Stripe's Refund object has typed states including `pending`, `requires_action`, `succeeded`, `failed`, and `canceled`; Stripe also documents refund failures that can occur after submission. Separately, Stripe API v1 and v2 idempotency scopes differ, so retry eligibility cannot be represented safely as a provider-independent Boolean key bit.
  - https://docs.stripe.com/refunds
  - https://docs.stripe.com/api/refunds
  - https://docs.stripe.com/api/idempotent_requests
  - https://docs.stripe.com/api-v2-overview

These sources establish the existence of distinct request/resource/finality semantics; they do not supply the synthetic lattice's probabilities or costs.

## Controller implication
Compensation should be modeled as another effect graph with non-substitutable certificates:

`compensation_request_contract + compensation_resource_identity + compensation_writer_quiescence + compensation_currentness + compensation_finality + amount conservation`

Forward-operation idempotency/finality evidence must not be reused automatically as compensation evidence. A current refund amount of 100 is not rollback completion if an older refund writer can still add money or if that refund is still in a lifecycle state that can later fail/reverse.

The policy controller should therefore keep multiple *safe* compensation strategies—block, certified retry/status, authoritative webhook wait, settle/wait, and issue-new-compensation—inside one certified behavior archive instead of forcing one universal weighted scalar policy.
