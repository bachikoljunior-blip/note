## Main update: direct empirical support for dependency-guided selective rollback, with a sharper provenance caveat

A new primary-source paper directly targets the current frontier rather than only adjacent provenance/recovery mechanisms:

**Yu et al., “From Faulty Memories to Corrected Actions: Dependency-Guided Rollback Repair for Memory-Augmented Agents,” arXiv:2608.10502, 11 Aug 2026.**
- Primary source: https://arxiv.org/abs/2608.10502
- PDF: https://arxiv.org/pdf/2608.10502

The method assumes an upstream detector has already diagnosed faulty memories and then constructs a typed memory-to-action dependency graph from runtime-emitted provenance. It traces explicit propagation edges, checks for independent trusted support, deterministically plans memory/trace rollback, and selectively replays only answer-relevant affected computation. The paper explicitly states that missing provenance is **not** inferred from natural-language logs: incomplete provenance can under-trace contamination, while spurious edges cause unnecessary invalidation. That assumption is highly aligned with the prior synthetic result that false-negative dependency capture is a safety error and false positives are mainly a cost/blast-radius error.

### Controlled benchmark: selective dependency-guided repair beats both broad replay and trace-only repair

On the 150-case controlled benchmark:

| method | recovery | recurrence | faulty removal | benign preservation | claim-invalidation F1 | replay ratio | LLM calls |
|---|---:|---:|---:|---:|---:|---:|---:|
| LLM-judge repair | 0.773 | 0.121 | 1.000 | 1.000 | 0.946 | 0.217 | 9.80 |
| AgentTrace-style | 0.607 | 0.341 | 0.000 | 0.997 | 0.853 | 0.091 | 4.69 |
| Dependency-guided rollback (full) | **0.853** | 0.266 | **1.000** | **1.000** | 0.566 | **0.123** | **5.70** |

The full method improves immediate recovery by +8.0 points over LLM-judge repair while using 43.3% less replay and 41.8% fewer LLM calls. AgentTrace-style is cheaper but loses 24.6 recovery points and does not clean persistent faulty memory. This is direct evidence that the target is not “minimum replay” or “maximum invalidation precision” alone: answer recovery, persistent cleanup, benign preservation, and recomputation cost must be optimized jointly.

### Ablation: rollback planning drives correctness; support checking and selective replay drive preservation/cost

The component ablation is especially useful for controller design:

| variant | recovery | recurrence | benign preservation | replay ratio | LLM calls |
|---|---:|---:|---:|---:|---:|
| full | 0.853 | 0.266 | 1.000 | 0.123 | 5.70 |
| w/o support checking | **0.880** | 0.265 | 0.986 | 0.154 | 6.51 |
| w/o rollback planner | 0.713 | 0.430 | 0.996 | 0.152 | 9.19 |
| w/o selective replay | 0.840 | **0.071** | 1.000 | **0.755** | **24.01** |

Interpretation:
- The deterministic rollback planner is the main correctness component: removing it drops recovery by 14.0 points and increases calls by ~61%.
- Independent-support checking is not a raw-accuracy maximizer. Removing it slightly raises recovery but causes benign over-invalidation and +25.2% replay / +14.2% calls. Its job is selective preservation.
- Broad replay can reduce recurrence, but at a huge compute cost: removing selective replay raises replay ratio from 12.3% to 75.5% and calls from 5.70 to 24.01, while recovery is slightly lower. This directly supports the current local-closure vs whole-redraw framing.

The repair-cost table reports 12,697.55 total tokens for the full method versus 28,175.28 for LLM-judge repair and 55,018.01 without selective replay. So the selective dependency policy is not merely shifting cost from replay count into hidden prompt tokens in this benchmark.

## Important mechanism detail: the provenance contract is explicit, deterministic, and still a single point of failure

The dependency graph edges are instantiated deterministically from runtime fields (`used_ids`, generated-memory IDs, invalidation/update/consolidation lineage, etc.), not inferred by an LLM. Pure temporal chain edges are excluded from contamination propagation. This is stronger than a “later step probably depended on earlier step” heuristic.

But the paper is equally explicit that it presupposes an instrumented runtime and does **not** solve missing provenance. Therefore the paper validates the value of selective rollback **conditional on a usable provenance contract**; it does not answer the current proof-state question of when local replay is safe under known capture gaps or unknown blind spots.

This narrows the next controller target: rather than asking whether selective replay is useful in principle, ask how to gate it when provenance coverage is heterogeneous or incomplete.

## Public LangGraph coverage cross-check: concrete proof-state classes already exist in an implementation

The current public `auditable` LangGraph adapter provides a concrete implementation-level taxonomy that can seed the next coverage suite:
- keyed `state["x"]` / `state.get("x")` reads are captured as precise channel reads;
- whole-state iteration/copy records every channel and marks them `overcaptured`;
- same-superstep parallel writes are not fabricated as dependencies, and reducer channels fan in from committed writers;
- Runnable nodes pass through **uncaptured** and the graph is warned incomplete;

## Updated controller hypothesis

The combined external evidence and prior role-local synthetic results now support a more specific architecture:

1. **Diagnose source correction separately from dependency coverage.** A correct source repair does not imply a complete rollback closure.
2. **Use typed runtime lineage to build the affected candidate closure.** Do not treat execution order as dependency.
3. **Preserve independently supported state.** Independent support is a selectivity/cost mechanism, not necessarily an immediate-recovery maximizer.
4. **Use selective replay only when provenance coverage is sufficiently proved.** If provenance is `known_uncaptured` or `unknown`, expand conservatively or whole-redraw rather than silently trusting a partial graph.
5. **Treat overcapture as a cost problem and undercapture as a safety problem.** They require different thresholds and metrics.
6. **Keep recurrence separate from immediate recovery.** Broad replay can lower recurrence while being much more expensive; a controller needs an explicit cost/risk trade-off rather than optimizing one scalar endpoint.

## Scope guards / negative evidence

- DGRR assumes diagnosed faults; it does not evaluate fault-detection accuracy or false diagnosis cost.
- Its graph depends on explicit runtime provenance. Missing or wrong dependency metadata can under-trace or over-invalidate, and the paper does not provide a provenance-recall/noise sweep.
- Rollback cannot itself undo irreversible external side effects; those require resettable interfaces or domain-specific compensation.
- Controlled-benchmark numbers are paper-reported; no public code repository was identified in this run, so no independent reproduction was performed.
- The adapted LongMemEval-V2 result is a 50-case converted subset and must not be treated as full-benchmark performance.
- The `auditable` LangGraph notes describe implementation scope, not measured production dependency recall.
