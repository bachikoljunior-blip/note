## New mechanism result: currentness is not quiescence
The previous typed-effect controller separated idempotency from physical finality. This run adds another non-substitutable distinction: a resource snapshot can be fresh at time `t` while an earlier unresolved mutation is still able to change the resource after `t`.

A balanced exact four-world TOCTOU study held the initial read fixed at fresh `NONE` while varying whether a prior forward attempt was still in flight and its eventual outcome (`NONE/PARTIAL/COMPLETE`).

- `fresh_only`: 4 terminal claims, **2 unsafe**.
- `quiescence_gated`: 1 terminal claim, **0 unsafe**.
- `settle_then_read`: 2 terminal claims, **0 unsafe**.

This is a mechanism counterexample, not an incident-rate estimate. It shows that freshness and quiescence answer different questions. For a destructive rollback or a terminal claim of absence, the controller needs both a sufficiently current state observation and evidence that no earlier unresolved writer can subsequently invalidate it. When a writer is unresolved, an explicit `wait/settle -> re-read` action can safely recover more terminal coverage than blocking on quiescence alone in this toy lattice.

Public provider behavior supports the existence of this race class within documented scopes:
- Stripe documents that simultaneous mutations of the same object can cause lock timeouts and recommends serializing them; its idempotency contract also distinguishes requests that conflict while another request is executing. Stripe webhook delivery order is not guaranteed, so an event snapshot is not a stable-state certificate.
  - https://docs.stripe.com/rate-limits
  - https://docs.stripe.com/api/idempotent_requests
  - https://docs.stripe.com/webhooks
- Adyen documents same-key requests that are already processed or in progress and asynchronous capture processing. HTTP 202 / capture request acceptance is not itself completion.
  - https://docs.adyen.com/development-resources/api-idempotency/
  - https://docs.adyen.com/api-explorer/Checkout/72/post/payments/_paymentPspReference_/captures
- PayPal documents that simultaneous requests carrying the same `PayPal-Request-Id` are not equivalent to a settled singleton operation: the first is processed and the second might fail; request-ID support/retention is API-specific.
  - https://developer.paypal.com/reference/guidelines/idempotency/

Therefore `CURRENT` is no longer a sufficient destructive-authority predicate by itself. High-risk terminal/destructive actions need a separate in-flight/generation certificate or must reconcile before acting.

## New mechanism result: observation multiplicity is not amount multiplicity
The effect model was expanded from a scalar state to amount/resource identity.

A balanced six-world capture study fixed intended amount at 100 and included duplicate deliveries of the same physical capture object.
- summing observations terminalized 5 worlds and was **unsafe in 3/5 terminal claims**;
- deduplicating by unique physical capture resource identity terminalized the 2 truly complete worlds and had **0 unsafe terminal**.

The symmetric refund study produced the same counts:
- observation-sum: 5 terminal, **3 unsafe**;
- resource-identity dedupe: 2 terminal, **0 unsafe**.

Examples include one physical 50-unit capture delivered twice, which looks like 100 if deliveries are summed, and a physical 90-unit total with one 30-unit observation duplicated, which looks like 120. These proportions are exact counts on deliberately balanced synthetic worlds, not empirical frequencies.

Controller implication: event IDs, delivery attempts, and API observations are evidence about a physical operation; they are not themselves separate amount-bearing operations. Conservation checks must aggregate unique physical capture/refund/reversal resource identities, with amount and status tied to those identities.

## Lifecycle finality is target-dependent
A fresh/current `COMPLETE`-like state can still be weaker than durable finality if the documented provider lifecycle permits a later adverse transition. Adyen explicitly documents the rare possibility of a `CAPTURE_FAILED` webhook after a successful `CAPTURE` webhook, including cases days later. Therefore the terminal predicate must name its objective: e.g. operational capture success is different from durable settlement/finality.

This run used a two-world structural counterexample (`STAYS_COMPLETE`, `LATE_FAILURE`). Treating current completion as durable finality terminalized both and was unsafe in one balanced toy world. The 1/2 proportion is not a provider failure-rate estimate; it exists only to prove that the predicates are logically distinct.

## Controller revision
The controller now carries the prior request/effect/compensation evidence plus four additional non-substitutable certificates:

`observation_currentness = {source endpoint/event, observed_at, provider timestamp/version/sequence if exposed, freshness qualification, documented consistency/lag guarantee or explicit unknown}`

`mutation_quiescence = {resource_id, write generation/attempt identities, unresolved-inflight count or explicit unknown, serialized mutation/lock discipline evidence, latest completed attempt identity}`

`effect_vector = {resource_id, currency, intended amount, authorized amount, unique capture IDs with amount/status, captured_total_dedup, settled_total if exposed, unique refund/reversal IDs with amount/status, refunded_total_dedup, residual amount, duplicate observation IDs}`

`terminal_predicate = {objective, required lifecycle state, allowed late-failure/reversal horizon, proof source}`

Key invariants:
1. currentness does not imply quiescence;
2. request idempotency does not imply effect completion;
3. delivered-observation count does not imply physical-operation count;
4. current completion does not imply durable finality unless the lifecycle contract supports that promotion;
5. destructive rollback requires both current eligibility/absence proof and quiescence or explicit reconciliation of unresolved writers.

## Provider-specific currentness matrix, tested scope only
- **Stripe:** resource retrieval is the best documented route used here for a current resource snapshot; webhook events are snapshots and delivery order is not guaranteed. No source used in this run establishes universal linearizability or stable-absence semantics, so the controller must leave that guarantee unknown rather than promote a GET to a generation fence.

- **Adyen:** capture is explicitly asynchronous; a successful `CAPTURE` webhook can still be followed by a later `CAPTURE_FAILED` in documented rare cases. Thus CAPTURE success is not automatically durable-finality proof for objectives that require final settlement certainty.
