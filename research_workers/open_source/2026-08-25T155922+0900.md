### os-agencybench-scaffold-coupling-2026 — strong, scoped

**Mechanism:** co-optimize model + agent scaffold/tooling rather than treating model capability as scaffold-invariant.

Primary repo: https://github.com/GAIR-NLP/AgencyBench  
Paper: https://aclanthology.org/2026.acl-long.337/

Repository/paper evidence:
- AgencyBench-V2 exposes 138 tasks across 32 real-world long-horizon scenarios and six capability categories, with scenario-level evaluation scripts and Docker-based automated functional/visual evaluation.
- The paper reports average closed-source vs open-source benchmark performance of 48.4% vs 32.1%.
- A 10-scenario scaffold ablation shows large model-specific shifts:
  - GPT-5.2: custom 57.4; Claude-Agent-SDK 53.5 (-3.9); OpenAI-Agents-SDK 58.7 (+1.3).
  - Claude-4.5-Opus: 50.8; 71.3 (+20.5); 47.1 (-3.7).
  - Gemini-3-Pro: 46.3; 45.9 (-0.4); 46.9 (+0.6).
  - Kimi-K2-Thinking: 50.5; 44.6 (-5.9); 37.7 (-12.8).
  - Minimax-M2: 45.8; 54.4 (+8.6); 43.0 (-2.8).
  - GLM-4.6: 33.6; 44.2 (+10.6); 36.0 (+2.4).
- Resource profiles also differ strongly (tokens, duration, turns), reinforcing that execution architecture is a first-class experimental variable.

**Inference:** framework/model coupling can move benchmark score by roughly -12.8 to +20.5 points in this ablation. Any optimization/evaluation pipeline should compare model-scaffold pairs, not just models.

**Scope limits:** scaffold ablation is on 10 representative scenarios; no repeated-seed uncertainty estimate was surfaced in this pass. Need per-scenario configs/results before assuming the mean shifts generalize.

### os-sia-self-conditioning-anchor-202607 — medium, controlled but narrow

Primary repo: https://github.com/vermayuvraj/self-improving-agent  
Key artifact: `EXPERIMENTS.md`; EXP-004 cell registry at `experiments/EXP-004/cells.json`.  
Relevant commits: `b4056ce7dcb3d925099e45b1f45fcbd669fac062` (EXP-010 close), `93321914849a48dadb2e6c8e2e4039abcede5e0f` (arXiv package).

**Mechanism:** conditioning a coding model on its own failed attempt can anchor retries; matched-budget blind resampling is a necessary baseline for self-repair claims.

Evidence on MBPP+ (n=378, k<=8, seed 7):
- Qwen2.5-Coder 1.5B / 3B / 7B: execution-feedback self-repair minus blind resampling = -6.1 / -4.2 / -1.1 percentage points; feedback used about twice the tokens; feedback minus placebo was ~0.
- EXP-005 reports own-output retry similarity +0.30 to +0.38 relative to blind resampling; 33–68% of retries were near-identical with own code in context vs 2–14% blind.
- Cross-task solved-example context (EXP-006) produced a clean null across nine Holm-corrected contrasts, bounded to about +/-3.5 pp, arguing against a generic "any extra context hurts" explanation.
- Full-precision replication EXP-009: Qwen1.5B FP16 feedback-resample -6.3 pp, p=0.0008, versus -6.1 pp at Q4; anchoring similarity changed <=0.003.
- Independent-family EXP-010: DeepSeek-Coder 1.3B feedback-resample -11.4 pp (p<0.0001); DeepSeek 6.7B -2.9 pp (p=0.14). Pooled six configs/two families/two precisions: reported descriptive r=+0.96 between baseline quality and placebo anchoring penalty (six uneven points; no error bars).

**Inference:** for these code-model/benchmark conditions, self-repair gains cannot be assumed to come from feedback content; diversity-preserving resampling can be stronger and cheaper.

**Scope limits / audit gap:** one benchmark and one seed dominate; raw run outputs were not located in this pass, only the experiment narrative and cell-ID registry. Do not extrapolate to frontier models or repository-level SWE without replication.

### os-gepa-parallel-proposals-202607 — promising but PROVISIONAL after validity audit

Primary repo: https://github.com/gepa-ai/gepa  
Parallel-proposals blog artifact: `docs/docs/blog/posts/2026-07-30-parallel-proposals/index.md`.  
Release v0.1.4: https://github.com/gepa-ai/gepa/releases/tag/v0.1.4  
Critical issue: https://github.com/gepa-ai/gepa/issues/424  
Fix commit: `ef525a44626a725b6987a35b4a75e36fbfaf0e25` (2026-08-17).

**Proposed mechanism:** batch multiple reflective proposals per adaptation step, evaluate concurrently, and update a Pareto frontier less frequently. This can reduce wall time and may reduce validation-set over-adaptation.

Reported held-out experiments at equal metric-call budget:
- LiveBench-Math: 100 train / 100 val / 168 test, 5,000 metric calls, gpt-4.1-mini task LM, gpt-5-mini proposer. Sequential held-out 68.9%; best batched 72.1% (2x2). Representative 2x4 = 71.9% (+3.0 pp). Sequential 7.7 h; broad settings reduced wall time toward ~2–4 h.
- HoVer: 200 train / 150 val / 200 test, 3,000 rollout-level metric calls. Sequential 49.0% all-three-gold-pages retrieval; best batched 60.0% (8x1), +11 pp. Representative 2x4 +6 pp; wall time roughly 47 min -> ~14–15 min in wide settings.
- Blog reports comparable total LLM spend (~$12–16) and smaller validation-to-test gap for one 2x4 comparison.

**Validity problem found by repo-first audit:** issue #424 documents that released v0.1.4 and then-main could conflate train and separate-validation example IDs in `EvaluationCache`, silently serving train minibatch rollouts as validation scores. The issue's real-run example had 11/108 val slots substituted; reused scores averaged .895 vs .659 for genuine val evaluations; one candidate's reported val average was inflated .592 -> .697. These contaminated per-instance scores also affected Pareto parent selection. The fix namespaces cache entries by split and drops legacy unnamespaced caches.

**Current judgment:** held-out test measurements are still valuable observations, but the optimization path and candidate selection in the July parallel-proposal experiments require verification/rerun on or after `ef525a...` unless their exact configs prove cache was disabled or IDs were disjoint. Do not promote the headline gains as clean causal evidence yet.

**Important scope separation:** this bug finding concerns the recent `optimize_anything`/v0.1.4 separate-train/val path. It does NOT by itself invalidate the older ICLR GEPA paper/artifact; that needs an independent code-path audit.

### os-gepa-gskill-repo-skills-202602 — medium/provisional, high-value transfer mechanism

**Mechanism:** generate verifiable repository-specific SWE tasks, evolve a compact textual skill file from agent successes/failures, then reuse the learned skill with other models/agent harnesses.

- Transfer to Claude Code, Jinja figure: Haiku 4.5 93.9% (177s) -> 100% (148s); Sonnet 4.5 100% (254s) -> 98.5% (225s).

**Audit notes:** prose around the figures contains inconsistent percentages (it swaps/mixes some figure values), so raw result files should be treated as authoritative if located. Current repository contains the gskill training/evaluation implementation, but this pass did not locate the original raw run bundle. The current script explicitly makes separate train/val/test splits; applicability of the later cache-collision bug to the February runs remains unresolved and must not be assumed either way.

**Inference if replicated:** cheap-model experience can be distilled into portable repository-specific text skills that improve stronger agents and reduce task time; this is a potentially high-leverage form of offline agent learning.

**Scope:** only two repositories and SWE-smith-style generated tasks; authors note these tasks are simpler than broad real-world SWE.
