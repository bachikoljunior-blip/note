# 改善ループ

分類: AI補助方針。ユーザー恒久指示ではない。恒久指示の正本は `OPERATIONS/CORE_DIRECTIVE.md`。

作成 2026-08-08。**このファイル自身もループの対象**（最後の節を読むこと）。

## なぜ作るか

2026-08-08 の実測。**8か月ぶんの作業があって、売上は0円。**
止まっていたわけではなく、毎日何かは動いていた。動いていたのに、
**「効いたか」を測る仕組みが無かった。**

同じ日に、報告の側でも同じ形の失敗を6回した。1つの観測で断定する。
書いた結果を読み直さない。**121分前の残量を「実測」と言う。**

どちらも原因は同じ。**測る手続きが、作業の外にあった。**
だから測らなくても作業は進み、進んだことと効いたことの区別がつかなくなる。

## ループの定義

すべての仕事は、次の5つを1周とする。**1周に満たないものは仕事ではなく作業。**

1. **測る** — 数値と、その数値を取った時刻。時刻の無い数値は使わない
2. **判定する** — 目標に対して近づいたか。近づいていないなら、そう書く
3. **1つだけ変える** — 同時に2つ変えると、どちらが効いたか永久に分からない
4. **確かめる** — 変えた後にもう一度測る。`tools/verified.py` を使う
5. **記録する** — 変えた理由・前後の数値・外れた予想を残す。やったことの列挙は要らない

### 測定には必ず時刻を付ける

`state/loops.json` の各ループは `measured_at` と `max_age_hours` を持つ。
古い測定は測定ではない。**2026-08-08、121分前の残量を「実測」として報告した。**
`scripts/check_loops.py` はこれを失敗として落とす。

### 変えて効かなかったときの決まり

同じループで **3回続けて指標が動かなかったら、パラメータではなく手法を変える。**
値段を下げる → 文面を変える → 送り先を変える、は全部同じ層の手。
3回外したら層を上げる。それでも動かないなら、そのループを閉じて資源を移す。

**「まだできることがある」は継続の理由にならない。** 数字が動いていないことが答え。

## ループの一覧

`state/loops.json` が正本。各ループは次を持つ。

| 欄 | 意味 |
| --- | --- |
| `id` | 一意の名前 |
| `metric` | 何を数えるか。**1つだけ**。複数あるものはループを分ける |
| `how_to_measure` | 再現できる手順。コマンドかAPI |
| `current` / `measured_at` | 最後に測った値と時刻 |
| `max_age_hours` | これを超えたら測り直す |
| `target` | 到達したら閉じてよい値 |
| `last_change` / `changed_at` | 直近で変えたこと |
| `consecutive_no_move` | 指標が動かなかった連続回数。3で手法を変える |
| `owner_actions_required` | このループを回すのに必要な本人操作の件数。**0を目指す** |

## ループ自身のループ（メタ）

この仕組みが効いているかも、同じ5手順で測る。

- **指標**: `state/loops.json` のうち、直近7日で **指標が実際に動いたループの数**
- **判定**: 動いたループが0なら、この仕組みは効いていない。**文書を足すのではなく、
  仕組みを変えるか捨てる**
- **変える対象**: ループの粒度、測定間隔、手法を変える閾値（いまは3回）、この文書の書き方
- **記録**: `state/loops.json` の `meta` へ

`scripts/check_loops.py` は次を落とす。

1. 測定が `max_age_hours` より古い
2. `consecutive_no_move >= 3` なのに `last_change` が同じ層のまま
3. `owner_actions_required > 0` のループが、代替の0件経路を検討した記録を持たない
4. **メタループ自身が7日以上測られていない**

## この文書の変え方

より速い道が見つかったら書き換えてよい。ただし**書き換えた理由と、
その前後で何の数字が動いたか**を `state/loops.json` の `meta.revisions` に残すこと。
理由の無い書き換えは、次の周で元に戻される。
